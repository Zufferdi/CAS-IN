📊 SIEM — Le système nerveux de la cybersécurité
Un SIEM (Security Information and Event Management) centralise les logs de l'ensemble de l'infrastructure — endpoints, serveurs, firewalls, IDS/IPS, applications, cloud — dans un seul moteur de recherche capable de corréler des événements en temps réel. Sans SIEM, un attaquant qui se déplace latéralement dans 50 machines en 10 minutes laisse 50 traces isolées que personne ne voit. Avec SIEM, ces 50 traces deviennent une seule alerte corrélée. Lors d'un incident, le SIEM est souvent la première source consultée — et parfois la seule si les logs locaux ont été effacés par l'attaquant. Marché : Splunk (référence historique, payant cher), Elastic/ELK (open source dominant), QRadar (IBM, banques), Microsoft Sentinel (cloud-native). Sigma est le « langage universel » pour écrire des règles de détection portables entre tous ces SIEM.

🟢 Splunk — Investigation forensique (SPL)
Search Processing Language · langage le plus utilisé en entreprise.
-- Échecs d'authentification sur 24h (Event ID 4625)
index=windows EventCode=4625
| stats count by src_ip, user
| sort -count

-- Timeline d'une IP suspecte
index=* src_ip="10.0.0.42"
| timechart span=1h count by EventCode

-- Connexions hors horaires de bureau (07h-20h)
index=windows EventCode=4624 LogonType=2
| eval hour=strftime(_time,"%H")
| where hour<7 OR hour>20
| table _time, user, src_ip, host

-- Détection brute force RDP
index=windows EventCode=4625 LogonType=10
| stats count dc(user) as users by src_ip
| where count>20 AND users>5

🔍 KQL — Kibana Query Language
  • winlog.event_id:4624 AND NOT user.name:SYSTEM
  • event.code:4688 AND process.name:powershell.exe
  • network.direction:outbound AND destination.port:443
  • source.ip:192.168.0.0/16 AND event.action:failed*
  • process.parent.name:winword.exe AND process.name:cmd.exe
  • Wildcards *, ranges field:[1 TO 100], regex .*malware.*

🎯 Use Cases SIEM — Détections critiques
🚨 Authentification
  • Brute force (4625 répétés sur 1 IP)
  • Password spraying (1 password × N comptes)
  • Logon hors horaires (LogonType 2/10/3)
  • Logon depuis pays inhabituel (geo-IP)
  • Compte privilégié utilisé à distance (4672)
🦠 Exécution suspecte
  • PowerShell encodé (-EncodedCommand)
  • cmd.exe enfant de Word/Excel (macro)
  • Process inconnu dans C:\Windows\Temp\
  • Sysmon EID 1 sans signature valide
  • Téléchargement + exécution chaîne
📡 Mouvement latéral
  • SMB lateral (4624 type 3 multi-hôtes)
  • WMI/PSExec depuis 1 source vers N cibles
  • Pass-the-Hash / Kerberoasting
  • RDP depuis poste de travail (anormal)
  • Token impersonation (4672 + 4624 type 9)
📤 Exfiltration
  • Volume sortant anormal (Packetbeat)
  • Connexions DNS vers TLD rares (.tk, .xyz)
  • Beaconing périodique vers IP externe
  • Upload vers cloud non corporate
  • Compression+chiffrement avant transfert
🧠 Testez-vous
Vous voyez 200 EventCode 4625 depuis l'IP 10.0.0.42 en 5 minutes. C'est forcément une attaque ?Faux positifs · Niveau : facile
Pas forcément. Les faux positifs courants incluent : (1) un service avec mot de passe expiré qui retente automatiquement, (2) un proxy/load balancer qui agrège les requêtes (toutes les IPs apparaissent comme cette IP), (3) un test de pentester interne, (4) un script de backup mal configuré. Procédure : (a) corréler avec EID 4624 (le succès final est-il survenu ?), (b) vérifier le LogonType (3=réseau, 10=RDP — différentes implications), (c) regarder si la même IP attaque plusieurs comptes (= password spraying) ou 1 seul compte (= brute force ciblé), (d) consulter l'inventaire pour identifier la machine. Vraie attaque = pattern + diversité des comptes + persistance dans le temps.
Quelle est la différence entre Sigma et YARA ?Détection · Niveau : moyen
YARA = règles pour détecter des fichiers malveillants par contenu (strings, magic bytes, patterns binaires). Utilisé sur des fichiers ou en mémoire. Ex: détecter Mimikatz dans un dump RAM. Sigma = règles pour détecter des événements suspects dans des logs. Utilisé dans un SIEM. Ex: détecter un EID 10 Sysmon avec accès à lsass.exe (= tentative Mimikatz). Les deux sont complémentaires : YARA détecte le malware sur le disque, Sigma détecte son comportement dans les logs. Tous deux sont des standards portables écrits en YAML/text — Sigma se traduit en SPL/KQL/etc., YARA se traduit en règles AV/EDR. Hayabusa est intéressant : il applique des règles Sigma directement sur des fichiers EVTX hors-ligne, sans SIEM.
Un attaquant a effacé les Event Logs Windows avec EID 1102. Tout est-il perdu ?Anti-forensique · Niveau : difficile
Pas du tout — c'est même un signal très fort. Plusieurs sources permettent de récupérer une partie : (1) SIEM centralisé — les logs ont été forwardés en temps réel avant l'effacement local (raison principale d'avoir un SIEM), (2) EID 1102 lui-même = preuve d'effacement intentionnel (avec timestamp + utilisateur — souvent oublié), (3) EVTX carving dans l'unallocated space avec EvtxECmd ou Plaso (les fichiers .evtx ont une structure découpable), (4) Sysmon a un canal séparé (Microsoft-Windows-Sysmon/Operational) souvent oublié par les attaquants, (5) logs réseau (DNS, firewall, IDS) sont hors de la machine compromise, (6) logs cloud (Azure AD, M365, AWS CloudTrail) idem, (7) USN Journal + Prefetch + Amcache — artefacts NTFS qui survivent à l'effacement EVTX. L'effacement EVTX prouve l'intention et oriente l'enquête vers une attaque ciblée et expérimentée.
