🎯 C2 Frameworks — l'arme post-exploitation universelle
Un C2 framework (Command & Control) fournit à l'attaquant l'infrastructure complète pour piloter un agent (beacon, implant) installé sur la machine victime : exécution de commandes, exfiltration, pivot, persistence, élévation. Originellement des outils légitimes de red team, ils sont devenus l'arme principale des groupes ransomware (Akira, Play, LockBit, Black Basta) et des APT. Cobalt Strike (Fortra) reste dominant via les versions crackées qui circulent en undergound. Depuis 2022-2023, on observe une migration vers les alternatives open-source ou commerciales : Sliver, Brute Ratel, Mythic, Havoc — plus modernes, moins détectées, modulaires.
Les 5 frameworks dominants (2025-2026)
🔴 Cobalt Strike (Fortra, commercial cracké)

Beacon · langage : C/asm · transports : HTTP/HTTPS, DNS, SMB pipes, TCP · Aggressor Scripts · profiles Malleable C2. Encore #1 en intrusions réelles malgré 10 ans de signatures défensives. Utilisé par 30+ groupes APT trackés (Cobalt Group, FIN7, APT29, …). Selon Red Canary Threat Detection Report 2023+, Cobalt Strike est le framework C2 le plus fréquemment observé dans les environnements clients.

⚪ Sliver (BishopFox, open-source)

Go · transports : mTLS, HTTP/S, DNS, WireGuard · cross-platform (Win/Lin/Mac). Devenu standard pour APT modernes (APT29 observé en utilisation simulée). Open-source = forks rapides, signatures évoluent vite. Repo : BishopFox/sliver.

🟡 Brute Ratel C4 (commercial)

Implant Badger, écrit par Chetan Nayak. Anti-EDR by design (sleep obfuscation, indirect syscalls, ETW patching). Licences vendues officiellement aux red teams, mais versions crackées diffusées par Conti leaks en 2022 → adopté par Qakbot et plusieurs groupes ransomware. Lateral movement via SMB, WinRM, WMI.

🟣 Mythic (open-source)

Framework modulaire par @its_a_feature_ · architecture multi-agents (Apollo pour Windows, Apfell pour macOS, Poseidon, etc.). Interface web. Adopté progressivement par les acteurs malicieux (mentionné par Team Cymru à partir de 2023+). Repo : its-a-feature/Mythic.

⚫ Havoc (open-source, @C5pider)

Implant Demon. Focus extrême sur l'évasion EDR moderne : reflective loading, indirect syscalls, sleep obfuscation. Très utilisé par les pen-testeurs et les attaquants. Repo : HavocFramework/Havoc.

📊 Tendance opérationnelle

Les opérateurs ransomware mixent souvent : Cobalt Strike pour intrusion initiale + lateral movement, puis Sliver/Havoc pour la persistance long-terme (moins détectés). Convergence APT ↔ cybercrime : les mêmes outils circulent dans les deux écosystèmes (cf. rapports Red Canary 2025, Mandiant M-Trends 2025).

📡 Le cycle d'un beacon — sleep, callback, tasking
Un beacon ne maintient pas une connexion permanente avec son C2 (trop visible). Il dort pendant un intervalle configurable (sleep), avec une variation aléatoire (jitter) pour éviter une régularité détectable. À chaque réveil, il appelle le team server (check-in), récupère les tâches éventuelles, les exécute, renvoie les résultats, puis re-dort. C'est ce pattern périodique qui trahit le beacon en analyse réseau, même chiffré.
Paramètres clés d'un beacon
⏰ Sleep / Jitter

Sleep = intervalle moyen entre check-ins (ex. 60s, 5min, 1h…). Jitter = variation ±N % (ex. jitter 30 % sur sleep 60s → callbacks entre 42s et 78s). Cobalt Strike par défaut : 60s/0% (très détectable). Opérateurs avancés : sleep 1h jitter 50% → quasi-invisible en analyse fréquentielle.

🌐 Transports

HTTPS le plus courant (caché dans le trafic légitime). DNS (TXT records) pour sortie restrictive. SMB pipes (\\.\pipe\msagent_*) pour beacon-to-beacon en lateral movement. TCP direct pour réseaux internes.

🎭 Malleable C2 Profile

Fichier de configuration qui définit l'apparence du trafic : URI, headers HTTP (User-Agent, Host, Cookie), structure de la requête, TLS cert (subject, issuer, validity). Permet de mimer un trafic connu (Office 365, Slack, Akamai…) pour échapper aux signatures naïves.

🔐 Watermark

Identifiant numérique unique à la licence Cobalt Strike (watermark) intégré au beacon. Les watermarks crackés/leakés sont catalogués publiquement (rapports Stairwell, NCC Group). Permet de tracker quel groupe utilise quelle version crackée.

📦 Named pipes

Cobalt Strike utilise des pipes nommés pour la communication beacon-to-beacon en lateral movement, configurables. Patterns par défaut : \pipe\msagent_*, \pipe\status_*, \pipe\postex_*. Détection : monitorer les pipes inhabituels créés (Sysmon EventID 17/18).

🔄 Process injection

Beacon est généralement injecté dans un processus légitime (rundll32.exe, explorer.exe, svchost.exe). Techniques : VirtualAllocEx + WriteProcessMemory + CreateRemoteThread, APC injection, process hollowing, module stomping. MITRE T1055.

Indicateurs d'infrastructure typiques (Cobalt Strike)

📡 Port 50050/TCP exposé publiquement — port par défaut du Team Server. Beaucoup d'opérateurs négligents le laissent ouvert → Shodan scan trivial.

📛 Certificat TLS par défaut : CN=Major Cobalt Strike, O=cobaltstrike.com (jamais changé chez les amateurs).

🔢 DNS Beacon : un serveur Cobalt Strike répond 0.0.0.0 aux requêtes DNS quand il est busy — pattern unique.

🎯 JA3 Beacon : a0e9f5d64349fb13191bc781f81f42e1 (signature client Windows socket TLS classique de Cobalt Strike).

🌐 TLS fingerprinting — JA3, JA3S, JA4, JARM
Le contenu d'un beacon HTTPS est chiffré, mais le handshake TLS reste en clair et révèle énormément. Les fingerprints TLS calculent un hash unique à partir des paramètres du ClientHello (versions TLS, suites de chiffrement, extensions, courbes elliptiques) côté client, et du ServerHello côté serveur. Deux beacons Cobalt Strike générés depuis la même version de Windows produisent le même JA3 — IOC robuste et reproductible. JA3 a été développé par Salesforce ; JA4 est l'évolution moderne (2023+) qui ajoute TLS 1.3 et un format human-readable.
Les quatre signatures TLS à connaître
🔍 JA3 (client)

Hash MD5 sur les champs du ClientHello : SSLVersion,Ciphers,Extensions,EllipticCurves,EllipticCurvePointFormats. Format : 32 caractères hex.

JA3 connu Cobalt Strike : a0e9f5d64349fb13191bc781f81f42e1 (sur ~10 ans, très stable car lié à la stack Windows).

🔍 JA3S (server)

Hash MD5 sur le ServerHello : SSLVersion,Cipher,Extensions. Couple JA3 + JA3S = signature plus fiable.

Limitation : les redirectors (HAProxy, socat) modifient le JA3S.

🔍 JA4 (moderne, 2023+)

Successeur JA3 par FoxIO. Format multi-parts human-readable. Supporte TLS 1.3, QUIC, SSH. Plus difficile à spoofer car ne se base pas que sur des paramètres facilement contrôlables.

Format exemple : t13d1516h2_8daaf6152771_b186095e22b6

🎯 JARM (active)

Fingerprint actif par Salesforce — envoie 10 ClientHello orchestrés au serveur cible et hashe les ServerHello reçus. Permet de scanner Internet à la recherche de team servers connus.

Différence clé : JA3/JA4 = passif (observation trafic), JARM = actif (scan).

Outils réseau

Calcule JA3/JA3S/JA4 nativement en sortie standard. Logs ssl.log + conn.log + x509.log. Standard NSM (Network Security Monitoring).

🚀 Suricata

IDS avec règles signature + extraction JA3/JA4 + détection malleable C2 patterns. Couplable Splunk/Elastic.

📈 RITA

Real Intelligence Threat Analytics (Black Hills Information Security). Analyse statistique des callbacks beacon (régularité, jitter analysis, long connections). Open-source.

🧠 Memory forensics — extraire le beacon de la RAM
Quand un C2 framework est utilisé proprement, le beacon est injecté en mémoire et ne touche pas le disque. La seule façon de l'extraire et de l'analyser est de dumper la RAM de la machine compromise pendant qu'elle est encore allumée (jamais shutdown !), puis d'analyser le dump avec Volatility 3 + outils spécialisés. La config du beacon contient les informations cruciales : URL C2, port, watermark, sleep, jitter, certificats, profile Malleable.
Workflow forensique standard (Volatility 3)
# 1. Identifier les processus suspects injectés
vol -f memory.raw windows.malfind

# Sortie typique : rundll32.exe pid=4892, page RWX inattendue
# Tag MZ détecté en zone RWX = beacon injecté très probable

# 2. Dumper le processus suspect
vol -f memory.raw windows.memmap --pid 4892 --dump
# → produit pid.4892.dmp

# 3. YARA-scanner avec règles Cobalt Strike publiques
yara -s elastic_rules/cobalt_strike.yar pid.4892.dmp
# Repo de référence : elastic/protections-artifacts (Elastic Security)

# 4. Extraction de la config beacon avec 1768.py (Didier Stevens)
python3 1768.py pid.4892.dmp
# Sortie : URL C2, port, sleep, jitter, watermark, public key
# Repo : DidierStevens/Beta (script 1768.py)

# 5. Alternative : CobaltStrikeParser (Sentinel One / Gal Kristal)
python3 parse_beacon_config.py beacon_dumped.bin
# Affiche la config décodée + Malleable C2 profile

# 6. Si conf packée encore en mémoire : CSCE (Stroz Friedberg)
python3 -m csce.parser pid.4892.dmp
# Repo : strozfriedberg/cobaltstrike-config-extractor
Difficultés rencontrées en pratique
🔒 Config unpacked

Cobalt Strike charge sa config, la dépacke en heap mémoire, puis écrase la version packée avec des zéros. Beaucoup d'outils cherchent la version packée → échouent. Solutions : scanner spécifiquement la unpacked config (CSCE, scripts custom comme celui de cyber.wtf).

🔐 Masking XOR

Les beacons modernes masquent les strings sensibles (URL, keys) avec XOR 0x2E ou autre. 1768.py et CSCE déchiffrent automatiquement. Manuellement : CyberChef avec recette XOR Brute Force.

📦 Stagers vs full beacons

Stager (taille ~250 octets) ne contient qu'une URL et déclenche le download du beacon complet. Pas de config exploitable. Full beacon (taille ~250 KB) contient toute la config Malleable C2. Stairwell propose un stager decoder open-source (2026).

🧬 64-bit vs 32-bit

Certains outils anciens (CobaltStrikeParser v1) ne gèrent que 32-bit. Vérifier que la version supporte le 64-bit (la plupart des beacons modernes le sont). 1768.py et CSCE modernes supportent les deux.

Plugins Volatility spécialisés

🇨🇭 Le paysage suisse 2024-2026 — Akira, Play, Cobalt Strike
Le NCSC / OFCS (Office fédéral de la cybersécurité) publie semestriellement un rapport de situation. Les éditions 2024-S2 et 2025-S1 confirment que Cobalt Strike est l'outil C2 le plus observé dans les incidents suisses, généralement déployé après une intrusion initiale via phishing, exploits RDP exposés, ou compromission VPN/firewall (SonicWall CVE-2024-40766, Fortigate CVE-2024-21762, etc.). Le MPC (Ministère public de la Confédération) conduit depuis avril 2024 une procédure pénale contre inconnus dans le contexte du groupe Akira, qui utilise massivement Cobalt Strike pour ses opérations en Suisse (~200 victimes confirmées).
Implications juridiques et opérationnelles
⚖️ Qualifications pénales

L'opération d'un C2 framework malveillant relève de :

• Art. 143 CP — Soustraction de données
• Art. 143bis CP — Accès indu à un système informatique
• Art. 144bis CP — Détérioration de données
• Art. 147 CP — Utilisation frauduleuse d'un ordinateur
• Art. 156 CP — Extorsion (couplage ransomware)

📞 Obligation LSI 24h

Depuis le 1er avril 2025, les autorités et organisations assujetties (art. 74b LSI : infrastructures critiques — banques, assurances, énergie, transports, cantons, hôpitaux, prestataires cloud, etc.) doivent signaler les cyberattaques à l'OFCS dans les 24 heures (art. 74e LSI) via report.ncsc.admin.ch. Amendes administratives jusqu'à 100'000 CHF en cas de manquement (art. 74g LSI, entrée en vigueur 1er octobre 2025).

Réponse incident : checklist DFIR

1. Ne pas éteindre la machine compromise → préserver la RAM (et le beacon en mémoire).

2. Isoler réseau mais maintenir alimentation. Si pivot OT/ICS suspecté, segmenter physiquement.

3. Dumper la RAM via WinPmem, Magnet RAM Capture, Belkasoft RAM Capturer.

4. Préserver SIEM logs + EDR alerts + flow netflow avant rotation.

5. Notifier OFCS dans les 24h (art. 74e LSI).

6. Coordonner MPC si jonction série Akira/Play/LockBit envisageable.

7. Si paiement envisagé → consultation préalable juriste + OFCS + MROS (LBA).

8. Analyse forensique : extraction config beacon, IOCs partagés via MISP (Cyber Security Hub CH), attribution si possible (watermark, infra patterns).

Ne pas confondre Cobalt Strike (outil) et l'opérateur Cobalt Group (FIN7-like) — homonymie historique

Vous analysez un dump mémoire Windows compromis. Volatility malfind révèle une zone RWX dans rundll32.exe avec un header MZ. Vous extrayez la région mais 1768.py renvoie une erreur de parsing. Que faites-vous, et pourquoi ?
C2 Frameworks · Niveau : difficile
Le problème typique est que Cobalt Strike, après avoir chargé sa configuration packée, la déballe en heap mémoire et écrase la version packée avec des octets nuls. 1768.py (Didier Stevens) cherche par défaut la packed config, qui n'existe plus → parsing échoue.

Solution étape par étape :
1️⃣ Étendre la recherche à la heap du processus (pas que la région .data). Avec Volatility 3 : vol -f mem.raw windows.memmap --pid <PID> --dump puis chercher dans tout le dump, pas que dans la région malfind.
2️⃣ Utiliser un extracteur qui cherche la unpacked config : CSCE de Stroz Friedberg gère les deux variantes. À défaut, le script de cyber.wtf (oct. 2023) traite ce cas spécifique.
3️⃣ Sur le dump, lancer un strings -el (wide UTF-16) puis grep http/https — révèle souvent l'URL C2 même quand la conf binaire est inaccessible.
4️⃣ Si la conf a un masking XOR (typiquement 0x2E), brute-force avec CyberChef (recette XOR Brute Force) sur les premiers octets pour valider le pattern config.
5️⃣ Vérifier en parallèle le processus parent et la timeline d'injection (Sysmon EventID 8 — CreateRemoteThread) pour identifier la chaîne d'exécution complète et confirmer un Cobalt Strike vs Sliver/Havoc (les implants modernes ont parfois des patterns similaires mais des configs différentes).
