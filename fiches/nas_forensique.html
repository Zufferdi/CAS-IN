🪣 Le NAS — Cible privilégiée d'une perquisition SME
En Suisse comme partout en Europe, les NAS Synology et QNAP dominent le marché PME : sauvegardes, archives mail, partages de fichiers, surveillance vidéo. Lors d'une perquisition, le NAS contient souvent plus de preuves que les postes de travail (snapshots historiques, logs centralisés, comptes utilisateurs). Mais : RAID, chiffrement, OS propriétaire et FS exotiques (Btrfs, ZFS) compliquent l'acquisition.
Constructeurs & systèmes d'exploitation
Le NAS est avant tout un Linux durci. Connaître l'OS = connaître les chemins.
🏢 Synology — DSM (DiskStation Manager)

Linux 4.4 / 5.10 (BusyBox + outils GNU). FS par défaut Btrfs (DSM 7+) ou ext4 (modèles bas de gamme).

  • Volumes : /volume1/, /volume2/…
  • Config : /etc/synoinfo.conf
  • SSH (à activer) : admin@nas:22
  • Outil exploration : Hyper Backup Explorer (Windows)
🏢 QNAP — QTS / QuTS Hero

QTS sur ext4, QuTS Hero sur ZFS (modèles enterprise). Linux durci avec interface Qfinder.

  • Volumes : /share/CACHEDEV1_DATA/
  • Config : /etc/config/uLinux.conf
  • SSH : admin@nas:22 (port 22 par défaut)
  • Snapshots ZFS ≠ Btrfs (lecture native via zfs list)
🆓 TrueNAS Core / Scale

FreeBSD (Core) ou Debian (Scale) avec ZFS natif. Open source, populaire en SME tech.

  • Pool ZFS : tank par convention
  • Datasets : tank/share, tank/backup
  • Config : /data/freenas-v1.db (SQLite)
  • API REST documentée (Core 13+ / Scale)
📦 Autres : Asustor, Buffalo, Drobo, Netgear ReadyNAS

Ces marques utilisent généralement ext4 / XFS avec mdadm + LVM. Approche acquisition similaire à un Linux Server classique. Drobo : FS propriétaire BeyondRAID, acquisition disque-par-disque inutilisable hors enclosure.

⚠️ Piège forensique : Btrfs et ZFS gardent les versions précédentes des fichiers dans les snapshots ET dans les blocs COW non encore réutilisés. Un fichier "supprimé" peut exister dans 5+ snapshots et dans la zone non réécrite. Approche carving classique inadaptée — utiliser les outils FS-specific.
Stratégies d'acquisition NAS
Trois approches, à choisir selon le scénario, l'urgence et la légalité.
1
Image disque-par-disque (ground truth)
Démontage physique du NAS, écriture des disques un par un avec write-blocker. Préserve l'état exact mais : nécessite recompositer le RAID en post (mdadm/zpool import) et ne capture pas les VM si stoppées.
FTK Imager Lite + write-blocker · 1× par disque
2
Live acquisition via SSH
NAS allumé, SSH activé. Acquisition à chaud des volumes via dd ou dcfldd sur partage NFS forensique. Capture les fichiers en cours d'usage MAIS modifie les ATIME et ne préserve pas les snapshots dormants.
ssh root@nas dcfldd if=/dev/md3 hash=sha256
3
Export logique (smb-snapshot)
Acquisition sélective via SMB + Volume Shadow Copies (Synology) ou NFS export of snapshot (TrueNAS). Plus rapide pour gros volumes, mais documenter exhaustivement la chaîne.
smbclient //nas/share@1234.snap1 -A creds.txt
Workflow Synology — Image Btrfs avec snapshots
# 1. Identifier les volumes mdadm
ssh admin@nas "cat /proc/mdstat"
# Sortie : md2, md3, md4 = volumes RAID

# 2. Identifier le FS Btrfs
ssh admin@nas "sudo btrfs filesystem show"

# 3. Lister les snapshots existants
ssh admin@nas "sudo btrfs subvolume list -t /volume1"

# 4. Imager le bloc RAID complet (vers serveur forensique)
ssh admin@nas "sudo dd if=/dev/md3 bs=64M | gzip" | ssh forensic@srv "dd of=/cases/case-2026-04/nas.img.gz"

# 5. Hash distant pour intégrité
ssh admin@nas "sudo sha256sum /dev/md3"
⚠️ SHR (Synology Hybrid RAID) : RAID propriétaire qui combine RAID-1 + LVM + Btrfs. Reconstruction hors NAS difficile. Préférer l'acquisition avec le NAS branché en mode lecture seule, ou utiliser l'option DSM Migration Assistant pour cloner.
Workflow QNAP/TrueNAS — Image ZFS avec snapshots
# 1. Lister les pools ZFS
ssh admin@nas "sudo zpool status"
ssh admin@nas "sudo zfs list"

# 2. Snapshot forensique (instantané, garanti cohérent)
ssh admin@nas "sudo zfs snapshot tank/share@forensic-2026-04-30"

# 3. Sender le snapshot vers serveur forensique (incrémental possible)
ssh admin@nas "sudo zfs send tank/share@forensic-2026-04-30" | ssh forensic@srv "sudo zfs receive tank/case-2026-04/nas-share"

# 4. Vérifier intégrité côté receiver (ZFS calcule auto les checksums)
ssh forensic@srv "sudo zpool scrub tank"
💡 Avantage ZFS : Le mécanisme zfs send garantit l'intégrité bout-en-bout via les checksums natifs. Pas de hash externe nécessaire, mais documenter le UUID du dataset. C'est plus solide qu'un dd en cas de litige.
Les snapshots — Trésor temporel pour l'enquêteur
Activés par défaut sur DSM 7 et TrueNAS, les snapshots offrent un historique complet. Combiné aux scripts horaires/quotidiens d'usine, ça donne souvent plusieurs mois de versions précédentes.
📸 Synology — Snapshot Replication

Politique d'usine : 1× par heure pendant 24h, 1× par jour pendant 7j, 1× par semaine pendant 4 sem. Soit ~35 snapshots accessibles via DSM ou directement via /volume1/.snapshot/.

  • Lister : btrfs subvolume list -s /volume1
  • Monter : déjà accessible en lecture seule dans /volume1/@sharesnap/
  • Outil DSM : Snapshot Replication
📸 ZFS (QNAP Hero / TrueNAS) — zfs list -t snapshot

Snapshots créés par tâches périodiques (quotidienne, horaire). Visibles en tank/share@autosnap_2026-04-29_03-00.

  • Lister tous : zfs list -t snapshot -o name,creation,used
  • Monter en lecture : zfs clone tank/share@snap mnt/snap
  • Diff entre 2 snapshots : zfs diff snap1 snap2
Cas d'usage — Récupérer un fichier "supprimé"
# Synology : un fichier effacé hier. On parcourt les snapshots du jour.
ls /volume1/.snapshots/ | grep 2026-04-29
find /volume1/.snapshots/2026-04-29-*/share/ -name "contrat-suspect.docx"

# ZFS : diff entre snapshot du jour et snapshot J-1
zfs diff tank/share@autosnap_2026-04-29_03-00 tank/share@autosnap_2026-04-30_03-00
# Légende : - = supprimé, + = créé, M = modifié, R = renommé

# Récupérer une version antérieure depuis ZFS
cp /tank/share/.zfs/snapshot/autosnap_2026-04-29_03-00/contrat-suspect.docx /case/recovered/

# Configuration et historique d'admin (SQLite)

Cadre légal CH — Perquisition et acquisition d'un NAS
Le NAS pose des questions juridiques spécifiques : multi-utilisateurs, données personnelles tierces, accès distant, chiffrement.
⚖️ Art. 246 CPP — Perquisition

Le mandat de perquisition couvre les locaux et leurs installations informatiques. Un NAS branché et accessible physiquement est inclus. Cas litigieux : NAS chez un tiers (cloud Synology C2, partage OneDrive monté) → mandat additionnel ou commission rogatoire.

📜 Art. 248 CPP — Mise sous scellés

Le détenteur peut demander la mise sous scellés. Pour un NAS qui contient des données de tiers non visés (autres employés, clients), c'est fréquent. Tri par tribunal des mesures de contrainte avant exploitation.

🇨🇭 LPD art. 24 — Données de tiers

Acquisition d'un NAS d'entreprise = capture de données personnelles de salariés et clients. Si exfiltration accidentelle (perte de support), notification PFPDT « dans les meilleurs délais ». Documenter la chaîne de custody resserrée.

🔐 Volume chiffré sur NAS

Synology Encrypted Shared Folder, QNAP Volume Encryption, ZFS native encryption. Sans MDP, image inutile. Le suspect peut invoquer nemo tenetur (art. 113 CPP) pour refuser. Chercher la clé en RAM si NAS encore actif (cas Synology : clé chargée tant que volume monté).

🇨🇭 Particularité suisse — DSM Hyper Backup : Synology stocke par défaut des backups versionnés sur 1 an chez les SME. Lors d'une perquisition, vérifier /volume1/HyperBackupVault/. Souvent contient des données antérieures à plusieurs mois, même si l'utilisateur a "tout effacé" — précieux pour reconstituer l'historique de la fraude.
🎓 À retenir pour la pratique — NAS forensique

Synology DSM 7 → Btrfs + snapshots horaires/quotidiens (~35 versions accessibles)

QNAP QuTS Hero / TrueNAS → ZFS + zfs send garantit l'intégrité native

SHR Synology → RAID propriétaire, ne pas démonter à l'aveugle, préférer Migration Assistant

Drobo BeyondRAID → impossible de recomposer hors enclosure, image disque par disque inutile

Snapshots sont la 1re source avant carving — un fichier "effacé" est presque toujours dans un snapshot

Logs DSM/QTS centralisés → exportables CSV/SQLite pour timeline Plaso

Mandat & tiers → Art. 246–248 CPP couvre le NAS local. Données de tiers → scellés probables (art. 248)

Lors d'une perquisition d'une PME, vous saisissez un Synology DS920+ allumé en mode RAID SHR (4 disques). Quelle est la priorité d'acquisition ?Stratégie · Niveau : moyen
Acquisition à chaud via SSH avant tout démontage. Le SHR Synology est un RAID propriétaire combinant RAID-1/5 + LVM + Btrfs : reconstituer hors NAS est très difficile. Ordre d'opérations : (1) noter l'état des LEDs et le câblage (photo), (2) activer SSH si pas déjà fait, (3) exporter les snapshots Btrfs via btrfs send ou imager /dev/md3 en lecture seule via dd over SSH vers serveur forensique, (4) hash SHA-256 distant, (5) seulement après, débrancher pour acquisition disque-par-disque en backup. Si volume chiffré actif, NE PAS éteindre — la clé est en RAM.
Sur un NAS QNAP TS-h973AX (QuTS Hero, ZFS), vous devez prouver qu'un fichier contrat.pdf a été modifié il y a 3 jours. L'utilisateur prétend ne jamais l'avoir touché. Quelle commande utiliser ?ZFS · Niveau : moyen
Lister les snapshots de la période : zfs list -t snapshot tank/share | grep 2026-04-2. Diff entre snapshot J-3 et J-2 : zfs diff tank/share@autosnap_2026-04-27 tank/share@autosnap_2026-04-28. Si le fichier apparaît avec un préfixe M (Modified) entre les deux dates, c'est la preuve. On peut ensuite extraire les deux versions via cp /tank/share/.zfs/snapshot/autosnap_2026-04-27/contrat.pdf v1.pdf et comparer hashes/contenus.
📌 Repères pratiques complémentaires : Synology = Btrfs · QNAP Hero / TrueNAS = ZFS · SHR = RAID propriétaire (pas de démontage à l'aveugle) · Snapshots = trésor pour récupérer fichiers effacés · DSM logs centralisés exportables CSV → Plaso · NAS chez tiers → commission rogatoire · Volume chiffré actif → ne pas éteindre, capturer RAM · Hyper Backup Vault = jusqu'à 1 an d'historique en SME.
