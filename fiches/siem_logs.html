SIEM & Log Management

Splunk · Elastic / ELK · Sigma Rules · Graylog · Investigation SIEM

"A SIEM without proper tuning is a very expensive noisy box. A SIEM with good Sigma rules and correlation is the difference between detecting an attack in 6 minutes vs 6 months."
— SANS SEC555 · SIEM with Tactical Analytics
💡 Contexte IR : Lors d'un incident, le SIEM est souvent la première source consultée — et parfois la seule, si les logs locaux ont été effacés par l'attaquant. Savoir interroger un SIEM efficacement est une compétence forensique fondamentale en contexte entreprise.

🏗️ Architecture SIEM

Composants

  • Collecteurs / Agents : Récupèrent les logs (Winlogbeat, Sysmon, rsyslog)
  • Parsers / Normalisateurs : Transforment les logs en format commun (CEF, ECS)
  • Indexeur : Stocke et indexe pour la recherche (Elasticsearch, Splunk indexer)
  • Moteur de corrélation : Applique les règles de détection
  • Interface de visualisation : Dashboards, alertes, timeline

Sources de logs typiques

  • Windows Event Logs (Security, System, Sysmon)
  • Firewall / IPS (Palo Alto, Fortinet, pfSense)
  • Active Directory / Azure AD
  • Proxy / Web (Squid, BlueCoat, Zscaler)
  • VPN (Cisco, Pulse, OpenVPN)
  • Email (Exchange, O365, Proofpoint)
  • DNS (Windows DNS, Bind, pfSense)
  • Applications (IIS, Apache, nginx)

🔵 Splunk — Investigation forensique

ℹ️
Splunk utilise le SPL (Search Processing Language) — une syntaxe puissante pour interroger, filtrer, agréger et visualiser des millions d'événements.
-- Rechercher tous les echecs d'authentification sur 24h
index=windows EventCode=4625 | stats count by src_ip, user | sort -count

-- Timeline des connexions d'un IP suspect
index=* src_ip="10.0.0.42" | timechart span=1h count by EventCode

-- Détecter des connexions hors horaires de bureau
index=windows EventCode=4624 LogonType=2
| eval hour=strftime(_time,"%H") | where hour<7 OR hour>20
| table _time, user, src_ip, host

🟡 Elastic / ELK Stack

Composants ELK

  • Elasticsearch : Moteur de recherche et d'indexation
  • Logstash : Pipeline d'ingestion et transformation
  • Kibana : Visualisation, dashboards, Discover
  • Beats : Agents légers (Winlogbeat, Filebeat, Packetbeat)
  • ECS : Elastic Common Schema — normalisation des champs

KQL — Kibana Query Language

  • winlog.event_id:4624 AND NOT user.name:SYSTEM
  • event.code:4688 AND process.name:powershell.exe
  • network.direction:outbound AND destination.port:443
  • source.ip:192.168.0.0/16 AND event.action:failed*

🛡️ Sigma Rules — Langage universel de détection

💡
Sigma est un format YAML générique pour les règles de détection. Une règle Sigma peut être convertie vers Splunk SPL, Elastic KQL, Azure Sentinel KQL, etc. — c'est le "YARA des logs".
# Exemple règle Sigma : détection Mimikatz via Sysmon
title: Mimikatz Detection via ProcessAccess
status: stable
logsource:
  product: windows
  service: sysmon
detection:
  selection:
    EventID: 10
    TargetImage|endswith: '\lsass.exe'
  condition: selection
falsepositives:
  - Antivirus scans
level: high
tags:
  - attack.credential_access
  - attack.t1003.001
  • Outils de conversion : sigmac, pySigma
  • Repo communautaire : github.com/SigmaHQ/sigma
  • Intégration : Chainsaw, Hayabusa (sur EVTX), Elastic SIEM, Splunk ES

🔍 Approche forensique dans un SIEM

1
Définir la fenêtre temporelle
Partir de l'incident confirmé (alerte initiale) et élargir. Les attaquants sont souvent présents des semaines avant la détection (dwell time moyen = 9 jours selon Mandiant 2023).
2
Identifier les IOC et pivoter
IP suspecte → chercher tous ses accès. Hash malware → chercher toutes les exécutions. User compromis → chercher tous ses accès sur la période.
3
Reconstruire la timeline
Corréler les logs de sources différentes (VPN login → AD → serveur interne) pour reconstituer le chemin de l'attaquant. Timesketch pour la visualisation.
4
Vérifier les trous dans les logs
Des périodes sans logs = indicateur potentiel de manipulation. Comparer avec la rétention configurée. Vérifier si les agents de collecte ont été arrêtés.
