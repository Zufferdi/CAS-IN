🏗 Docker forensique — Une VM sans noyau dédié
Contrairement aux VMs, les containers Docker partagent le noyau de l'hôte. Forensiquement, cela implique que les artefacts sont répartis entre l'hôte (daemon Docker, layers overlay, logs containerd) et le container (processus, filesystem, réseau). Un container compromis laisse des traces sur l'hôte même après sa suppression.
Stack d'un container Docker — Vue forensique
🖥
Noyau Linux (hôte)
Noyau partagé entre l'hôte et tous les containers. Namespaces + cgroups = isolation. Appels système = traces dans auditd hôte.
Partagé
🔧
containerd / dockerd
Daemon hôte qui gère le cycle de vie des containers. Logs dans /var/log/docker.log ou journald. Toutes les opérations (create/start/stop/exec) y sont tracées.
Hôte
📁
Overlay2 filesystem
Système de fichiers union : layers read-only (image) + layer read-write (container). Dans /var/lib/docker/overlay2/. Persistant sur l'hôte même après arrêt du container.
RW layer hôte
📦
Image layers (read-only)
Couches immuables de l'image Docker. Chacune correspond à une instruction Dockerfile (FROM, RUN, COPY…). Chaque layer a un hash SHA256 unique.
Read-only
🔒
Namespaces Linux
PID, NET, MNT, UTS, IPC, USER — isolent le container. Un process container a un PID dans le namespace container ET un PID sur l'hôte (plus grand). Les deux sont visibles depuis l'hôte.
Isolation
💾
Volumes & Bind mounts
Données persistantes montées depuis l'hôte. Dans /var/lib/docker/volumes/ ou chemin hôte arbitraire. Persistent après suppression du container — source d'artefacts clé.
Hôte persistant
Namespaces Linux — Isolation et visibilité forensique
PID namespace
Le container voit ses processus avec des PID commençant à 1. L'hôte les voit avec leurs vrais PIDs (ex: 3842).
Sur l'hôte : ps aux montre tous les processus de tous les containers.
NET namespace
Chaque container a ses propres interfaces réseau (eth0, lo). L'hôte a une interface veth par container + docker0 bridge.
Trafic capturé sur docker0 ou vethXXXX depuis l'hôte.
MNT namespace
Chaque container a sa propre arborescence de fichiers (via overlay2). L'hôte voit le tout dans /var/lib/docker/overlay2/.
Accès direct au FS du container depuis l'hôte sans l'exécuter.
UTS namespace
Hostname et domainname isolés. Un container peut avoir son propre hostname sans affecter l'hôte.
Le hostname du container est dans sa config JSON.
USER namespace
Mappage d'UIDs container → hôte. Root (0) dans le container peut mapper à un UID non-privilégié sur l'hôte (si user namespaces activés).
Vérifier si le container tourne en root réel ou mappé.
IPC / Cgroup namespace
Isolation des IPC (sémaphores, mémoire partagée) et des groupes de contrôle (ressources CPU/mémoire).
Cgroups dans /sys/fs/cgroup/ — identifier les limites et violations.
📂 Artefacts Docker — Où chercher sur l'hôte
La force forensique des containers : tous les artefacts sont sur l'hôte — même après la destruction du container. Le daemon Docker conserve logs, configs, layers et volumes. La clé est de savoir où regarder.
📁 /var/lib/docker/ — Le dépôt principal
/var/lib/docker/containers/[ID]/ Config + logs de chaque container. Contient config.v2.json (métadonnées complètes), hostconfig.json (montages, réseau, privilèges), et [ID]-json.log (stdout/stderr du container).
/var/lib/docker/overlay2/[hash]/ Filesystem du container. Sous-dossier diff/ = layer RW du container (fichiers créés/modifiés). merged/ = vue complète (visible si container actif).
/var/lib/docker/volumes/[name]/_data/ Volumes nommés persistants. Subsistent après docker rm. Contiennent souvent des bases de données, configs, credentials.
/var/lib/docker/image/overlay2/imagedb/ Métadonnées des images — layers, config, history de build. Permet de reconstituer le Dockerfile originel.
📋 Logs et configuration daemon
journalctl -u docker.service Logs du daemon Docker — toutes les opérations : pull d'image, création, démarrage, arrêt, erreurs. Timestamps précis de chaque événement.
/etc/docker/daemon.json Configuration du daemon : log driver, registry mirrors, insecure registries, userns-remap. Révèle les pratiques de sécurité (ou leur absence).
/var/lib/docker/containers/[ID]/[ID]-json.log Logs stdout/stderr du container (si log driver = json-file, défaut). Contient tout ce que le container a affiché — commandes, erreurs, connexions.
/proc/[PID]/ns/ Namespaces d'un processus container (via son PID hôte). ls -la /proc/[PID]/ns/ montre les namespaces partagés ou dédiés.
🔑 config.v2.json — La fiche d'identité du container
Image / ImageID Hash SHA256 de l'image utilisée — traçable dans Docker Hub ou registry privé.
Created Timestamp de création du container — clé pour la timeline.
Cmd / Entrypoint Commande exécutée au démarrage — peut révéler une commande malveillante.
Env Variables d'environnement — souvent des secrets : API keys, passwords, tokens JWT passés en clair.
Mounts Bind mounts et volumes — quels chemins hôte sont exposés au container.
HostConfig.Privileged true = container sans isolation de sécurité — accès root réel à l'hôte. IOC critique.
HostConfig.Binds Liste des montages — /:/host = le container a accès à tout le FS hôte. IOC extrême.
Commandes d'extraction des artefacts
docker inspect [ID] # Config complète JSON du container docker logs [ID] # stdout/stderr du container docker diff [ID] # Fichiers modifiés dans le layer RW docker history [IMAGE] # Layers de l'image + commandes Dockerfile docker export [ID] | tar -t | head -50 # Lister le FS du container docker export [ID] > container_fs.tar && tar xf container_fs.tar -C /evidence/ cat /var/lib/docker/containers/[ID]/config.v2.json | python3 -m json.tool find /var/lib/docker/overlay2/[HASH]/diff/ -newer /tmp/ref -type f # Fichiers récents
🔍 Protocole d'investigation container — Vivant ou mort
L'investigation diffère selon que le container est encore actif (live forensics = plus de données mais risque d'altération) ou arrêté/supprimé (post-mortem = artefacts statiques sur l'hôte). Dans les deux cas, commencer par l'hôte.
Container actif — Live forensics
1
Inventaire des containers en cours
docker ps -a --format "table {{.ID}}\t{{.Image}}\t{{.Status}}\t{{.CreatedAt}}\t{{.Names}}" docker stats --no-stream # CPU/RAM par container
2
Inspecter la configuration complète
docker inspect [ID] | python3 -m json.tool > inspect_[ID].json # Vérifier les flags dangereux docker inspect [ID] --format '{{.HostConfig.Privileged}} {{.HostConfig.Binds}}'
3
Processus dans le container (via l'hôte)
docker top [ID] auxf # Processus avec PID hôte # Depuis l'hôte — voir le vrai PID ps aux | grep -v grep | grep $(docker inspect [ID] --format '{{.State.Pid}}')
4
Réseau — Connexions actives
docker exec [ID] ss -tupn # Depuis l'intérieur # Depuis l'hôte via nsenter nsenter -t $(docker inspect [ID] --format '{{.State.Pid}}') -n ss -tupn tcpdump -i docker0 -w /evidence/docker_traffic.pcap # Capture réseau hôte
5
Filesystem — Fichiers modifiés et secrets
docker diff [ID] # A=added, C=changed, D=deleted docker exec [ID] find / -newer /proc/1 -not -path '/proc/*' -not -path '/sys/*' 2>/dev/null # Variables d'environnement (potentiels secrets) docker exec [ID] env cat /proc/$(docker inspect [ID] --format '{{.State.Pid}}')/environ | tr '\0' '\n'
6
Exporter le filesystem complet avant arrêt
docker export [ID] | gzip > /evidence/container_[ID]_$(date +%Y%m%d).tar.gz sha256sum /evidence/container_[ID]_*.tar.gz > /evidence/hashes.txt
Container arrêté/supprimé — Post-mortem
1
Retrouver le container ID depuis les logs daemon
journalctl -u docker.service --since "2024-01-01" | grep -E "create|start|stop|kill" grep -r "container" /var/log/docker.log 2>/dev/null | tail -50
2
Layer RW dans overlay2 — souvent encore présent
docker rm supprime le container mais peut laisser des traces dans overlay2 selon la configuration. Inspecter le dossier même si le container n'existe plus.
ls -lat /var/lib/docker/overlay2/ | head -20 # Layers récents find /var/lib/docker/overlay2/*/diff -name "*.log" -o -name "*.sh" -o -name "*.py" 2>/dev/null
3
Volumes — Persistent même après rm
docker volume ls # Volumes encore présents ls -la /var/lib/docker/volumes/ # Vue directe find /var/lib/docker/volumes/ -type f -newer /tmp/ref 2>/dev/null
4
Image — Reconstituer l'historique de build
docker history [IMAGE] --no-trunc # Commandes Dockerfile layer par layer docker image inspect [IMAGE] | python3 -m json.tool # Extraire et analyser une image sans la lancer docker save [IMAGE] | tar xf - -C /evidence/image/
📦 Images Docker — Anatomie forensique des layers
Une image Docker est un empilement de layers immuables. Chaque layer est identifié par un hash SHA256 et correspond à une instruction Dockerfile. Cette structure permet de retrouver l'historique de construction d'une image et d'identifier les couches malveillantes.
Structure d'une image sauvegardée
Contenu de docker save image:tag | tar t
manifest.json Index des layers — liste ordonnée des couches de l'image avec leurs hashes.
[SHA256].json Config de l'image — history complet (commandes Dockerfile), variables d'environnement, entrypoint, architecture, OS, dates de création.
[HASH]/layer.tar Contenu de chaque layer — archive tar des fichiers ajoutés/modifiés par cette couche. Analysable directement avec tar.
[HASH]/json Métadonnées du layer — parent, créé, commande utilisée.
Analyse forensique d'une image suspecte
# 1. Sauvegarder l'image docker save malicious:latest -o image.tar # 2. Extraire mkdir /evidence/image && tar xf image.tar -C /evidence/image/ # 3. Lire l'historique (commandes Dockerfile) docker history malicious:latest --no-trunc --format "{{.CreatedAt}}\t{{.CreatedBy}}" # 4. Analyser chaque layer for layer in /evidence/image/*/layer.tar; do echo "=== $layer ==="; tar tf $layer | grep -E "\.sh|\.py|passwd|shadow|key|\.env" done # 5. Outil dédié — Dive dive malicious:latest # Visualisation interactive des layers # 6. Scanner pour secrets docker run --rm -v /evidence/image:/scan trufflesecurity/trufflehog filesystem /scan
Red flags dans une image
ÉlémentRed flagImplication
Layer RUN curl | bash Exécution de script depuis URL — supply chain attack
Variables ENV PASSWORD= / SECRET= Credentials hardcodés dans l'image
Base image Image inconnue / non officielle Backdoor possible dans l'image de base
USER instruction Absent = root par défaut Container tourne en root — élévation triviale
COPY/ADD depuis URL ADD http:// Téléchargement non authentifié au build
History layer Layer <missing> en milieu de stack Layer importé d'une autre source — non traçable
☸️ Kubernetes forensique — L'orchestrateur comme source d'artefacts
Kubernetes (K8s) ajoute une couche d'abstraction au-dessus des containers. Les artefacts sont distribués entre l'API server (source de vérité), l'etcd (état du cluster), les nodes (containers réels), et les audit logs (actions utilisateurs/système).
Sources de données forensiques K8s
🗄 etcd — Source de vérité
Base de données clé-valeur de K8s. Contient l'état complet du cluster : tous les objets (pods, secrets, configmaps, RBAC). Un backup etcd = snapshot forensique complet de la configuration.
etcdctl get / --prefix --keys-only etcdctl snapshot save /evidence/etcd.db
📋 API Server Audit Logs
Toutes les requêtes API avec : utilisateur, timestamp, verbe (get/create/delete), ressource, namespace. Source principale pour retrouver qui a fait quoi et quand.
# Config dans kube-apiserver --audit-log-path grep '"verb":"create"' audit.log | jq '.user.username,.requestURI'
🐳 Node — Containers réels
Sur chaque node worker, containerd ou docker gère les containers. Les artefacts sont identiques à un hôte Docker standard. Les logs sont dans /var/log/pods/.
ls /var/log/pods/ # Logs par namespace/pod/container crictl ps -a # Tous les containers (containerd)
🔑 Secrets K8s
Stockés en Base64 dans etcd (non chiffrés par défaut). Contiennent credentials, tokens, certificats. Si etcd est compromis, tous les secrets le sont.
kubectl get secrets -A -o json | jq '.items[].data' echo "BASE64" | base64 -d # Décoder un secret
📡 Réseau K8s
CNI (Calico, Flannel…) gère le réseau inter-pods. NetworkPolicies définissent les règles. Les logs CNI et les captures réseau sur les nodes révèlent les flux suspects.
kubectl get networkpolicies -A kubectl get events -A --sort-by=.metadata.creationTimestamp
📜 RBAC — Qui peut faire quoi
Role-Based Access Control — identifier les permissions excessives (cluster-admin attribué à un ServiceAccount), les bindings suspects, les tokens de service compromis.
kubectl get clusterrolebindings -o wide kubectl auth can-i --list --as=system:serviceaccount:default:default
Investigation K8s — Commandes clés
kubectl get pods -A -o wide # Tous les pods sur tous les namespaces kubectl describe pod [POD] -n [NS] # Détail complet + events kubectl logs [POD] -n [NS] --previous # Logs du container précédent (après crash) kubectl exec -it [POD] -n [NS] -- /bin/sh # Shell dans le pod (si encore actif) kubectl get events -A --sort-by=.metadata.creationTimestamp | tail -50 # Exporter le FS d'un pod kubectl cp [NS]/[POD]:/chemin /evidence/pod_files/ # Timeline complète des ressources kubectl get all -A -o json | jq '.items[] | {kind:.kind, name:.metadata.name, created:.metadata.creationTimestamp}'
🚨 Attaques sur les containers — TTPs et IOC
Les containers sont une cible croissante. Les attaques vont de l'escape de container (sortir vers l'hôte) au cryptominage (déploiement de miners), en passant par la supply chain (images malveillantes) et le mouvement latéral via l'API K8s.

Docker socket exposé T1552.007 Mount de /var/run/docker.sock dans le container → contrôle total du daemon depuis le container. Bind mount docker.sock · docker ps depuis l'intérieur · Sysmon EID 11

Outils de détection runtime & scan d'images
🦅 Falco CNCF · Gratuit
Détection comportementale en runtime via eBPF/kprobe. Règles prédéfinies pour : container escape, accès au docker.sock, shell dans un container, lecture de /etc/shadow, connexions réseau suspectes. Génère des alertes JSON/syslog. Standard de facto pour la runtime security K8s.
falco -r /etc/falco/falco_rules.yaml # Lancer avec règles par défaut cat /var/log/falco.log | jq 'select(.priority=="Critical")' kubectl logs -n falco daemonset/falco | grep "Notice\|Warning\|Critical"
🔍 Trivy Aqua Security · Gratuit
Scanner de vulnérabilités, secrets, et misconfigurations dans les images Docker, FS, et manifests K8s. Détecte : CVEs dans les packages, secrets hardcodés (.env, clés API), configurations dangereuses (Dockerfile, K8s YAML). Intégrable en CI/CD.
trivy image nginx:latest # Scanner une image trivy image --severity CRITICAL,HIGH nginx:latest trivy fs /var/lib/docker/overlay2/[HASH]/diff/ # Scanner le layer RW trivy k8s --report summary cluster # Scanner tout le cluster K8s
🤿 Dive wagoodman · Gratuit
Exploration interactive des layers d'une image Docker. Affiche layer par layer les fichiers ajoutés/modifiés/supprimés, l'efficacité de l'image, et les fichiers dupliqués. Idéal pour l'analyse forensique des images suspectes.
dive [IMAGE] # Interface interactive TUI dive [IMAGE] --ci # Mode CI — exit 1 si efficacité < seuil
🔐 Cosign / Notation Sigstore · Gratuit
Vérification de la signature cryptographique des images Docker. Permet de détecter si une image a été altérée depuis sa publication. Si une image n'a pas de signature valide → supply chain attack possible.
cosign verify --key cosign.pub [IMAGE] cosign tree [IMAGE] # Voir attestations et signatures
Anti-forensique Docker — Signaux à connaître
⚠️ Techniques d'évasion forensique spécifiques aux containers
  • --rm flag — container supprimé automatiquement à l'arrêt → pas de config.v2.json résiduelle
  • --log-driver none — docker logs ne retourne rien
  • FROM scratch — image sans shell, sans outils, logs minimaux → analyse difficile
  • Namespace réseau --network host — pas d'interface réseau isolée à capturer
  • Volume monté :ro + écriture vers /dev/null — pas de trace sur disque
  • Contre-mesure : journald hôte capture quand même le démarrage/arrêt même avec --rm
  • Contre-mesure : auditd sur l'hôte trace les syscalls même si le container n'a pas de logs
  • Contre-mesure : Falco détecte les comportements même dans les images FROM scratch
  • Contre-mesure : Réseau capturé depuis l'hôte (docker0/veth) indépendamment du log driver
  • Contre-mesure : overlay2 peut garder le layer diff même après docker rm
Vérifications de sécurité rapides — IOC à chercher
Configurations dangereuses
docker ps --quiet | xargs docker inspect --format '{{.Name}} Privileged={{.HostConfig.Privileged}}' docker ps -q | xargs docker inspect --format '{{.Name}}: {{.HostConfig.Binds}}' | grep "docker.sock\|/:/\|/etc" docker ps -q | xargs docker inspect --format '{{.Name}} User={{.Config.User}}' | grep ": $" # Root # Ports exposés sur 0.0.0.0 docker ps --format '{{.Names}}\t{{.Ports}}' | grep "0.0.0.0"
Activité suspecte
# Containers créés récemment docker ps -a --format '{{.CreatedAt}}\t{{.Names}}\t{{.Image}}' | sort -r | head -10 # Processus réseau inhabituels docker ps -q | xargs -I{} docker exec {} ss -tupn 2>/dev/null | grep -v "127.0.0" # Images non taguées (souvent suspectes) docker images | grep "<none>" # Connexions K8s suspectes kubectl get events -A | grep -i "failed\|error\|forbidden"
💊 Q1 — Quelle est la différence fondamentale entre un container Docker et une VM d'un point de vue forensique ?
✓ Contrairement à une VM qui a son propre noyau isolé, un container Docker partage le noyau de l'hôte via les namespaces Linux. Forensiquement, cela implique : (1) tous les processus du container sont visibles sur l'hôte avec ps aux (avec leur vrai PID hôte) ; (2) le filesystem du container est accessible depuis l'hôte dans /var/lib/docker/overlay2/ sans lancer le container ; (3) le trafic réseau peut être capturé depuis l'hôte sur l'interface veth ou docker0 ; (4) tous les artefacts persistent sur l'hôte même après suppression du container.
💊 Q2 — Un container Docker a été supprimé (docker rm). Quels artefacts peut-on encore retrouver sur l'hôte ?
✓ Plusieurs sources persistent après docker rm : (1) Logs daemon Docker dans journald — toutes les opérations create/start/stop/rm avec timestamps ; (2) Volumes nommés dans /var/lib/docker/volumes/ — non supprimés par docker rm (nécessite docker volume rm) ; (3) Layers overlay2 — peuvent rester sur disque selon la politique de cleanup ; (4) L'image utilisée reste présente (voir avec docker images) ; (5) Audit logs système (auditd) si configurés sur l'hôte.
💊 Q3 — Comment un attaquant peut-il s'échapper d'un container Docker vers l'hôte via le flag --privileged ?
✓ Un container --privileged a accès à tous les devices (/dev/), peut modifier les namespaces, et a toutes les capabilities Linux. L'escape classique : fdisk -l pour identifier le disque hôte → mkdir /mnt/hôte && mount /dev/sda1 /mnt/hôte → accès complet au FS hôte → chroot /mnt/hôte → shell root sur l'hôte. Détection : config.v2.json avec Privileged=true, appels mount dans les logs container.
💊 Q4 — Quels sont les artefacts forensiques clés dans Kubernetes pour identifier qui a créé un pod malveillant ?
✓ La source principale est l'API Server Audit Log — chaque requête API est enregistrée avec : l'identité de l'utilisateur (user.username ou ServiceAccount), le timestamp, le verbe (create), la ressource (pods), le namespace, et l'IP source. Compléter avec : kubectl get events pour la timeline des opérations, kubectl describe pod pour les métadonnées du pod (annotations, labels, créateur), et les bindings RBAC pour comprendre comment l'identité avait ces permissions.
💊 Q5 — Pourquoi le docker.sock monté dans un container est-il un IOC critique ?
✓ /var/run/docker.sock est la socket Unix du daemon Docker. Quand elle est montée dans un container (via -v /var/run/docker.sock:/var/run/docker.sock), le container peut contrôler le daemon Docker de l'hôte directement — créer de nouveaux containers, lancer des containers privilégiés, monter le FS hôte, exécuter des commandes sur l'hôte. C'est un escape de container immédiat : depuis l'intérieur, un attaquant peut faire docker run --privileged -v /:/host alpine chroot /host pour obtenir un shell root sur l'hôte. Détection : docker inspect → HostConfig.Binds contient docker.sock.
