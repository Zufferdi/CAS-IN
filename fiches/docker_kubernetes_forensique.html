🐳 Docker forensique — Le container n'est pas une VM
Un container Docker partage le noyau de l'hôte Linux — il ne s'en isole que par les namespaces et cgroups. Forensiquement, cela signifie que les processus d'un container sont visibles depuis l'hôte via /proc/, que les appels système passent par le même noyau, et que les techniques forensiques Linux s'appliquent. La difficulté : les containers sont éphémères — arrêtés, ils perdent toutes leurs données (sauf volumes). Après suppression (docker rm), les traces sont minimales.

🔑 docker diff — Fichiers modifiés

  • docker diff <ID> compare le filesystem du container avec l'image de base
  • A = Added · C = Changed · D = Deleted
  • Révèle les outils déposés, fichiers config modifiés, malwares téléchargés
  • Stocké dans overlay2 : /var/lib/docker/overlay2/[hash]/diff/
  • Accessible même sur container arrêté (pas supprimé)

⚠️ Signaux d'anti-forensique Docker

  • --rm flag : container supprimé automatiquement à l'arrêt
  • Image FROM scratch : pas de shell, pas d'outils, logs minimaux
  • Log driver none : docker logs ne retourne rien
  • Volume monté en :ro depuis hôte + write vers /dev/null
  • Container avec namespace réseau = host : pas de réseau isolé
Un container suspect a été supprimé (docker rm -f) avant l'arrivée du technicien DFIR. Il reste une image Docker sur l'hôte et des volumes. Quelles sources forensiques sont encore disponibles ?Docker · Niveau : moyen
Encore disponibles après docker rm :

1. Volumes : /var/lib/docker/volumes/ — les volumes nommés survivent à docker rm (sauf docker rm -v). Contiennent les données persistantes de l'application.

2. Image Docker : docker images -a — l'image de base est intacte. docker save image -o image.tar + analyse des layers avec Dive ou Trivy.

3. Logs Docker daemon : /var/log/docker.log ou journalctl -u docker — peut contenir les commandes exécutées, erreurs, timestamps de démarrage/arrêt.

4. /var/lib/docker/containers/[ID]/ : si le répertoire de container n'est pas nettoyé — config.v2.json, hostconfig.json, *-json.log (logs du container). docker rm nettoie ce répertoire mais une image disque peut le révéler via carving ou l'espace non alloué ext4.

5. Auditd / syslog hôte : si auditd était actif, les syscalls du container (execve, open, connect) ont été enregistrés avec le PID de l'hôte.

6. Réseau : iptables rules, connexions dans /var/log/syslog si firewall logging activé, PCAP si tcpdump tournait.
📦 Layers Docker — Chaque couche est un artefact forensique
Une image Docker est composée de layers superposés en lecture seule + une couche de container en lecture/écriture. Chaque layer correspond à une instruction Dockerfile (RUN, COPY, ADD). Forensiquement, les layers révèlent l'historique de construction de l'image : outils installés, fichiers copiés, commandes exécutées — même si ces fichiers ont été supprimés dans des layers ultérieurs (le contenu reste dans le layer précédent).
Structure overlay2 — Filesystem des containers
🗂 Stockage on-disk Docker
/var/lib/docker/
· overlay2/ — layers des images et containers (driver par défaut)
· containers/[ID]/ — metadata, logs, config de chaque container
· image/overlay2/imagedb/ — manifests et configs des images
· volumes/ — données des volumes nommés
· network/files/local-kv.db — config réseau (SQLite)
🔬 Container layer — diff/
overlay2/[hash]/diff/ = fichiers modifiés par le container
overlay2/[hash]/merged/ = vue complète du filesystem (montée)
overlay2/[hash]/work/ = fichiers temporaires overlay

find /var/lib/docker/overlay2/ -name "*.sh" -newer /var/lib/docker/image/
→ Trouver des scripts récents dans les layers
Analyse forensique d'une image Docker
# Exporter l'image et analyser sa structure
docker save suspicious-image:latest -o suspicious.tar
mkdir /tmp/image-analysis && tar xf suspicious.tar -C /tmp/image-analysis

# Voir l'historique de construction (Dockerfile reconstruit)
docker history suspicious-image:latest --no-trunc

# Inspecter le manifest et la config
cat /tmp/image-analysis/manifest.json
cat /tmp/image-analysis/[sha256-config].json | python3 -m json.tool

# Extraire et analyser chaque layer (tar dans tar)
for layer in /tmp/image-analysis/*/layer.tar; do
  echo "=== $layer ===" && tar tf "$layer" | grep -E "(\.sh|\.py|\.bin|cron|passwd)"
done

# Outil dédié : Dive (visualisation interactive des layers)
dive suspicious-image:latest
Fichiers sensibles à chercher dans les layers
Fichier / PatternSignification forensique
.env · secrets.* · .aws/credentials Credentials hardcodés dans l'image — erreur de développement fréquente révélant des clés API, mots de passe, tokens AWS/Azure.
/root/.ssh/ · authorized_keys Clés SSH intégrées dans l'image — accès backdoor. Chercher aussi les clés privées (.pem, id_rsa).
/etc/crontab · /var/spool/cron/ Tâches planifiées dans le container — persistance ou exécution périodique de scripts malveillants.
binaires dans /tmp/ ou /dev/shm/ Binaires dans des zones volatiles — malware fileless ou dropper téléchargé à l'exécution.
ENTRYPOINT / CMD modifiés Supply chain attack : image légitime avec ENTRYPOINT remplacé par un script malveillant. Comparer avec l'image officielle du registry.
Fichier supprimé dans layer N+1 Un fichier supprimé dans un layer reste présent dans le layer précédent. docker history + extraction du layer tar révèle le contenu supprimé.
🎯 Supply Chain Attack — Image Docker compromise
Les attaques de supply chain Docker consistent à publier une image malveillante sur Docker Hub avec un nom similaire à une image populaire (typosquatting : nginx-lastest au lieu de nginx:latest) ou à compromettre directement le pipeline CI/CD d'une image légitime. Pour détecter : vérifier le digest SHA256 de l'image (docker inspect --format='{{.RepoDigests}}'), comparer avec le digest officiel du registry, et analyser l'historique des layers pour détecter des instructions inattendues.
☸️ Kubernetes forensique — L'orchestrateur comme terrain d'enquête
Kubernetes ajoute une couche d'abstraction au-dessus des containers : Pods, Services, Namespaces, RBAC, Secrets, ConfigMaps. En cas d'incident, le technicien DFIR doit analyser deux niveaux simultanément : le cluster K8s (API Server, etcd, audit logs) et les nœuds worker Linux (containers, processus, réseau). L'API Server est la pièce centrale — toute action dans K8s passe par lui et peut être auditée.

Kubernetes Audit Log — Configuration et analyse
🎯 Le Kubernetes Audit Log est l'équivalent du Unified Audit Log M365 pour K8s. Il enregistre toutes les requêtes vers l'API Server : qui a créé quel Pod, qui a accédé à un Secret, qui a exécuté kubectl exec. Il n'est pas activé par défaut sur la plupart des distributions K8s — son absence est une lacune de sécurité majeure et rend la forensique post-incident très difficile.
Champ Audit LogValeur forensique
requestURIRessource K8s accédée (/api/v1/namespaces/default/pods/evil-pod). Révèle l'action précise.
user.usernameQui a fait la requête : user humain, ServiceAccount, ou système (system:node).
sourceIPsIP source de la requête. Comparer avec les IPs attendues pour cet utilisateur.
verbcreate · delete · get · list · patch · update · watch · exec. "exec" = kubectl exec dans un pod.
responseStatus.code200/201 = succès · 403 = accès refusé (tentatives d'escalade) · 404 = ressource inexistante.
⚔️ Attaques sur les environnements conteneurisés
Les environnements Docker/Kubernetes présentent des surfaces d'attaque spécifiques. Les attaquants ciblent : les containers mal configurés (privilèges excessifs, montages dangereux), les API exposées (Docker socket, API Server K8s non authentifiée), la supply chain (images malveillantes), et l'évasion de container vers l'hôte. Chaque technique laisse des traces spécifiques.

Indicateurs de compromission — Containers
🔴 Signaux runtime suspects
  • Container avec --privileged ou --cap-add ALL
  • Montage de /var/run/docker.sock ou / (host root)
  • Processus nmap, masscan, nc, curl, wget dans un container applicatif
  • Connection sortante vers port 443/80 depuis un container backend (ne devrait pas)
  • Modification de /etc/hosts ou /etc/resolv.conf dans le container
🟡 Signaux K8s suspects
  • Pod créé dans le namespace kube-system par un ServiceAccount non-système
  • ClusterRoleBinding donnant cluster-admin à un ServiceAccount d'application
  • Pod avec hostPID: true, hostNetwork: true, ou hostPath: /
  • Image depuis un registry non autorisé (pas le registry interne)
  • kubectl exec dans un pod de production en dehors des heures ouvrables

Falco
CNCF / Sysdig
Détection des comportements suspects en runtime via les syscalls (eBPF/kprobe). Règles prédéfinies pour : container escape, accès au socket Docker, exécution de shells dans des containers. Génère des alertes en JSON/syslog. Standard de facto en runtime security K8s.

Scanner de vulnérabilités et de secrets dans les images Docker. Détecte : CVEs dans les packages, secrets hardcodés (.env, clés API), configurations dangereuses (Dockerfile, K8s YAML). Intégrable en CI/CD.

🎓 Exam Tip — Docker & Kubernetes Forensique

docker diff = fichiers modifiés dans le container vs l'image de base (A/C/D)

docker export = snapshot du filesystem · docker commit = snapshot en nouvelle image

overlay2/[hash]/diff/ = couche d'écriture du container on-disk — accessible même sur container arrêté

docker rm supprime les métadonnées mais pas les volumes (sauf -v)

K8s Audit Log = pas activé par défaut · toutes les requêtes API Server · verb "exec" = kubectl exec

Container Escape : chercher --privileged, montage /var/run/docker.sock, hostPID: true

Falco = runtime security via syscalls · Trivy = scan image (CVE + secrets) · Dive = analyse layers

Un pod Kubernetes nommé kube-update-helper dans le namespace kube-system exécute l'image alpine:latest avec hostPID: true et hostNetwork: true. Il a été créé par le ServiceAccount default du namespace default. Quels sont les indicateurs de compromission et comment investiguer ?K8s · Niveau : difficile
Indicateurs de compromission multiples :

1. Nom trompeur : "kube-update-helper" imite les composants système légitimes. Vérifier avec kubectl get pods -n kube-system — ce pod ne devrait pas exister.
2. Image générique : alpine:latest dans kube-system est suspect. Les composants K8s utilisent des images spécifiques (k8s.gcr.io/).
3. hostPID: true : le container voit tous les processus de l'hôte — permet d'attaquer les processus hôte ou de s'injecter dans un autre processus.
4. hostNetwork: true : le container partage le réseau de l'hôte — accès direct au réseau interne sans isolation.
5. ServiceAccount default/default : un pod système ne devrait pas utiliser le ServiceAccount par défaut d'un namespace applicatif.

Investigation :
· kubectl describe pod kube-update-helper -n kube-system → voir les events et l'historique
· kubectl logs kube-update-helper -n kube-system → activité du container
· K8s Audit Log : verb=create resource=pods → qui a créé ce pod et depuis quelle IP
· kubectl exec kube-update-helper -n kube-system -- ps aux → processus en cours
· Falco : events de type "shell spawned in container" ou "write to sensitive file"
· Ne pas supprimer avant acquisition : kubectl cp pour récupérer les fichiers suspects
