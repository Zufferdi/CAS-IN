🐧 WSL — Linux à l'intérieur de Windows · vecteur d'attaque émergent
Windows Subsystem for Linux (WSL) permet d'exécuter un environnement Linux complet (Ubuntu, Debian, Kali...) nativement sur Windows 10/11, sans VM lourde ni dual-boot. Lancé en 2016 (WSL1), refondu en 2019 (WSL2 avec un vrai noyau Linux dans une VM Hyper-V légère), c'est aujourd'hui un outil standard pour développeurs, mais aussi un vecteur d'attaque privilégié par certains acteurs malveillants. Pourquoi ? (1) Bypass EDR partiel — les EDR Windows surveillent surtout les API Win32 ; les appels système Linux dans WSL passent sous le radar de nombreuses solutions, (2) Outils Linux puissants disponibles nativement (nmap, hydra, john, sqlmap, hashcat, etc.) sans installation suspecte côté Windows, (3) Environnement séparé avec ses propres logs, son propre filesystem (ext4), ses propres credentials. Pour le forensiste, deux complications : (a) les fichiers Linux ne sont pas dans le filesystem Windows classique — ils sont dans un fichier ext4.vhdx caché dans %LocalAppData%\Packages\, (b) il faut connaître les artefacts Linux (.bash_history, /var/log/, /tmp/) en plus des artefacts Windows. Bonne nouvelle : Windows laisse plein de traces de l'usage de WSL (Event Logs, Prefetch, Registre Lxss, Amcache).

📂 Localisation des artefacts WSL
📁 Système de fichiers Windows
  • Ubuntu : %LocalAppData%\Packages\CanonicalGroupLimited.Ubuntu*\LocalState\
  • Debian : %LocalAppData%\Packages\TheDebianProject.DebianGNULinux*\LocalState\
  • Kali Linux : %LocalAppData%\Packages\KaliLinux.*\LocalState\
  • WSL1 : dossier rootfs\ avec arborescence Linux directement
  • WSL2 : fichier ext4.vhdx dans LocalState\
  • Aussi distribué via store Microsoft → chemin Packages/ MS
🗝 Registre Windows
  • HKCU\Software\Microsoft\Windows\CurrentVersion\Lxss\
  • Une clé par distribution installée (UUID GUID)
  • DefaultDistribution = distribution par défaut
  • BasePath = chemin vers les fichiers de la distro
  • DistributionName = nom (Ubuntu, Debian, etc.)
  • Version = 1 (WSL1) ou 2 (WSL2)
  • State = 1 (active)
🔍 Détection de l'usage WSL
📋 Windows Event Logs & Prefetch
  • Event ID 4688 : processus wsl.exe lancé
  • Event ID 4688 : bash.exe, ubuntu.exe, debian.exe, kali.exe
  • Prefetch : WSL.EXE-*.pf, BASH.EXE-*.pf — preuve d'exécution + comptage
  • Sysmon Event 1 (si déployé) : encore plus détaillé avec hash + PPID
  • Amcache : entrées pour wsl.exe et binaires des distros
  • Microsoft-Windows-Hyper-V-Worker (WSL2) : démarrage de la VM légère
🐧 Contenu intéressant dans le ext4.vhdx
  • /root/.bash_history — commandes root
  • /home/<user>/.bash_history — commandes user
  • /home/<user>/.zsh_history · /root/.zsh_history
  • /var/log/ — logs Linux (auth.log, syslog)
  • /tmp/, /root/ — fichiers temporaires
  • Outils réseau : traces nmap, curl, wget, ssh, hydra
  • /etc/passwd · /etc/shadow — comptes Linux
  • ~/.ssh/ — clés SSH générées dans WSL
🔧 Analyser le ext4.vhdx (WSL2) — Workflow
1
Localiser le VHDX — chercher ext4.vhdx dans %LocalAppData%\Packages\*\LocalState\ de chaque profil utilisateur. Hash SHA-256 avant manipulation. Documenter taille et timestamps.
2
Convertir en RAW pour usage avec outils forensiques classiques : qemu-img convert -f vhdx -O raw ext4.vhdx disk.raw
3
Analyser sur Linux en read-only : sudo mount -o ro,loop disk.raw /mnt/wsl puis explorer /root/, /home/, /var/log/. Best practice : mount via copie de travail, jamais l'original.
4
Carving sur l'image RAW — foremost, scalpel, PhotoRec peuvent extraire fichiers supprimés du ext4. ext4magic pour récupération via journal.
5
Timeline cross-OS — combiner timestamps Linux (atime/mtime/ctime ext4) et Windows (Event Logs wsl.exe) pour reconstituer l'activité de l'attaquant à travers les deux mondes.
🧠 Testez-vous
Comment savoir rapidement si un suspect a utilisé WSL sur sa machine Windows ?Détection · Niveau : facile
Plusieurs vérifications rapides : (1) Registre — examiner HKCU\Software\Microsoft\Windows\CurrentVersion\Lxss\ : si la clé existe, WSL est installé. Sous-clés GUID = distributions installées. (2) Filesystem — chercher ext4.vhdx : dir /s /b %LocalAppData%\Packages\*ext4.vhdx. La taille du fichier indique l'ampleur de l'usage. (3) Prefetch — présence de WSL.EXE-*.pf, BASH.EXE-*.pf, UBUNTU.EXE-*.pf dans C:\Windows\Prefetch\ + leur dernière exécution. (4) Event Logs Security — chercher EID 4688 avec NewProcessName contenant wsl.exe, bash.exe, ou un binaire Linux. (5) Amcache — %SystemRoot%\AppCompat\Programs\Amcache.hve : recherche des entrées WSL avec dates et hash SHA-1. (6) Features Windows — HKLM\System\CurrentControlSet\Services\LxssManager : si actif = WSL activé. (7) Network — ipconfig /all peut révéler l'interface vEthernet (WSL) avec IP 172.x.x.x. Conclusion : la combinaison de ces sources donne une image complète de l'usage WSL.
Vous trouvez un ext4.vhdx de 50 GB sur la machine d'un suspect. Que faire ?Acquisition · Niveau : moyen
Procédure forensique : (1) Documenter — chemin exact, taille, timestamps (création, modification, accès), hash SHA-256. Photographier l'arborescence complète %LocalAppData%\Packages\. (2) Copie write-blocked — copier le VHDX sur stockage forensique avec write-blocker, OU travailler depuis l'image disque complète Windows. NE JAMAIS modifier l'original. (3) Conversion en RAW sur station forensique Linux : qemu-img convert -f vhdx -O raw ext4.vhdx wsl_disk.raw · ou usage direct avec outils supportant VHDX (Autopsy/X-Ways). (4) Mount read-only : sudo mount -o ro,loop wsl_disk.raw /mnt/wsl. (5) Analyse standard Linux : ~/.bash_history, /var/log/auth.log, /etc/passwd, /etc/shadow, /tmp/, /root/, ~/.ssh/known_hosts, fichiers récents (find / -mtime -7). (6) Carving : photorec ou foremost pour fichiers supprimés. ext4magic -j /mnt/wsl peut extraire via le journal. (7) Cross-corrélation avec timeline Windows (EID 4688 wsl.exe) → reconstituer chronologie complète. (8) Outils spécifiques : plaso/log2timeline peut intégrer ext4 + EVTX dans une seule timeline.
Pourquoi WSL est-il un vecteur d'attaque privilégié et comment s'en défendre ?Sécurité · Niveau : difficile
WSL = vecteur d'attaque émergent pour plusieurs raisons : (1) Bypass EDR partiel — beaucoup d'EDR Windows surveillent les API Win32 et le kernel NT, mais voient peu les syscalls Linux dans WSL2 (qui passent par le noyau Linux dans la VM Hyper-V). (2) Outils offensifs natifs — l'attaquant a accès direct à nmap, hydra, john, hashcat, sqlmap, mimipenguin, etc. sans installation détectable côté Windows. (3) Persistence furtive — backdoors dans ~/.bashrc, cron WSL, services systemd dans la distro. (4) Pivot vers Windows — depuis WSL on peut accéder au filesystem Windows via /mnt/c/ et y déposer des malwares. (5) Network spoofing — WSL2 a sa propre interface réseau, certains scanners NIDS le voient comme une machine séparée. Défense : (a) Désactiver WSL si non nécessaire — Group Policy Computer Configuration\...\Windows Subsystem for Linux. (b) Activer Sysmon avec règles spécifiques pour wsl.exe, bash.exe. (c) EDR avec support WSL — vérifier que la solution surveille bien WSL (Defender for Endpoint le fait depuis 2022). (d) Logging WSL : activer auditd dans la distro Linux WSL. (e) WDAC / AppLocker : bloquer wsl.exe pour les utilisateurs non-développeurs. (f) Network segmentation : vEthernet WSL doit être isolé. (g) Threat hunting proactif sur EID 4688 wsl.exe + exécution d'outils inhabituels.
🎓 Exam Tip — WSL Forensique

WSL = Windows Subsystem for Linux · Linux dans Windows sans VM lourde

WSL1 (2016) = traduction syscalls · fichiers dans rootfs\ Windows directement lisibles

WSL2 (2019, défaut) = vrai noyau Linux dans VM Hyper-V légère · fichiers dans ext4.vhdx

Localisation :

  • Ubuntu : %LocalAppData%\Packages\CanonicalGroupLimited.Ubuntu*\LocalState\

  • Debian : %LocalAppData%\Packages\TheDebianProject*\LocalState\

  • Kali : %LocalAppData%\Packages\KaliLinux*\LocalState\

Registre : HKCU\Software\Microsoft\Windows\CurrentVersion\Lxss\ — distros installées

Détection d'usage :

  • Event ID 4688 : wsl.exe, bash.exe, ubuntu.exe, etc.

  • Prefetch : WSL.EXE-*.pf, BASH.EXE-*.pf

  • Amcache : entries WSL + hash SHA-1

  • Sysmon Event 1 si déployé

Contenu VHD à analyser :

  • /root/.bash_history · /home/user/.bash_history

  • /var/log/ (auth.log, syslog)

  • /tmp/, /root/, ~/.ssh/

Workflow analyse VHDX :

  1. Hash + copie write-blocked

  2. qemu-img convert -f vhdx -O raw ext4.vhdx disk.raw

  3. sudo mount -o ro,loop disk.raw /mnt/wsl

  4. Analyse standard Linux + carving

Vecteur d'attaque : bypass EDR Windows partiel · outils Linux natifs · persistence furtive · pivot via /mnt/c/
