🔑 Principe "Tout est Fichier" — NTFS
Contrairement à FAT, NTFS n'a pas de zone technique fixe. La $MFT, le $Bitmap, le $LogFile, le $Boot — tout est stocké comme des fichiers ordinaires dans la Data Area et référencé par la $MFT elle-même. La $MFT se référence même elle-même (entrée 0).

🔍 Signatures NTFS essentielles

  • VBR (offset 0) : EB 52 90 (JMP) + "NTFS " à l'offset 3
  • Entrée MFT : 46 49 4C 45 = "FILE" aux 4 premiers octets
  • Chaque entrée = 1 024 octets (1 Ko)
  • Boot signature : 55 AA à l'offset 510
  • MFT Zone : ~12.5% réservé pour la croissance de la $MFT

⚡ Formules de calcul NTFS

  • Taille cluster = BytesPerSector × SectorsPerCluster
  • Offset $MFT = MFTCluster × TailleCluster (BPB offset 0x30)
  • Offset cluster N = N × TailleCluster
  • Byte $Bitmap = cluster ÷ 8 · Bit = cluster mod 8
  • Ex. cluster 42 : byte 5 (42÷8), bit 2 (42%8)

Résident vs Non-résident

✅ Attribut Résident

  • Données stockées directement dans l'entrée MFT
  • Seuil : < ~700 octets (variable selon config)
  • Un fichier vide = seulement les attributs $SI et $FN
  • Petit fichier texte = $DATA résident dans le tuple
  • Forensique : données récupérables même si les clusters sont "libres" car elles sont dans la MFT elle-même

📦 Attribut Non-résident

  • Données dans la Data Area — MFT contient une Run List
  • Run List = liste de runs (LCN + longueur en clusters)
  • Header byte : nibble haut = octets offset · nibble bas = octets longueur
  • Offsets relatifs au run précédent (signés) — sauf le premier
  • Forensique : reconstruire la Run List pour localiser les données physiquement
🔴 ADS (Alternate Data Streams) : un fichier NTFS peut avoir plusieurs attributs $DATA nommés. Syntaxe : fichier.txt:stream_caché. L'Explorateur Windows et la taille visible ignorent les ADS. Détecter : dir /r ou streams.exe (Sysinternals). X-Ways les affiche nativement.

$Bitmap — Visualiseur d'allocation clusters
Le $Bitmap (entrée MFT #6) contient 1 bit par cluster. Bit 0 = libre, Bit 1 = occupé. Cliquez sur un cluster pour basculer son état. Octet = cluster ÷ 8 · Bit = cluster mod 8.
🟢 Clusters 0–127 · 8 clusters par ligne · 16 colonnes
Cliquez sur un cluster pour voir ses coordonnées dans le $Bitmap
Occupé (bit=1) Libre (bit=0)

🗂 Localiser un run dans le $Bitmap

  • Byte = cluster ÷ 8 (division entière)
  • Bit = cluster mod 8 (bit 0 = poids faible)
  • Ex. cluster 42 : byte 5, bit 2 → octet 0x04 = cluster 42 seul occupé
  • Cluster libre mais avec données = espace récupérable !

🔗 Reconstruire un fichier depuis la Run List

  • 1. Lire l'entrée MFT → attribut $DATA non-résident
  • 2. Décoder la Run List : liste de (LCN, longueur) pairs
  • 3. Offset physique = LCN × TailleCluster
  • 4. Lire N × TailleCluster octets à cet offset
  • 5. Répéter pour chaque run → concaténer les fragments

⚠️ Timestomping — Détection anti-forensique
🎯 Timestomping : technique qui modifie $STANDARD_INFORMATION (facilement modifiable par toute application via SetFileTime()) sans toucher $FILE_NAME (mis à jour uniquement par le kernel NTFS).
Signal d'alarme : $SI.Created antérieur à $FN.Created → physiquement impossible → manipulation confirmée.

🎓 Exam Tip — NTFS Timestamps

Epoch NTFS : 1er janvier 1601 · 100 ns · 8 octets (QWORD) Little Endian

$SI (0x10) : modifiable par les applications — cible du timestomping

$FN (0x30) : mis à jour par le kernel uniquement — preuve fiable

Détection timestomping : $SI.Created < $FN.Created → impossible → manipulation

MACB : Modified · Accessed · Changed · Born (création = Birth time)

$SI.Created = 2023-01-01, $FN.Created = 2024-06-15. Que conclure ? Quelle est la date réelle ?Timestomping · Niveau : facile
Timestomping confirmé : un fichier ne peut pas avoir été créé ($SI) avant d'exister dans $FILE_NAME. La date réelle est 2024-06-15 (source $FN, protégée par le kernel). Confirmer avec $UsnJrnl.

🎓 Exam Tip — NTFS complet

Signature MFT : 46 49 4C 45 ("FILE") · entrée = 1 024 octets · entrée #0 = $MFT elle-même

Run List : header byte = nibble haut (octets offset) + nibble bas (octets longueur) · 0x00 = fin · offsets signés relatifs au run précédent

Timestomping : $SI modifiable → $SI.Created peut être antérieur à $FN.Created · si $SI < $FN → manipulation · $FN protégé kernel

ADS : fichier.txt:flux · invisible dans Explorer · taille visible ≠ réelle · détecter : dir /r ou streams.exe

$UsnJrnl : journal long terme · prouve existence d'un fichier supprimé · MFTECmd.exe

$Bitmap : 1 bit/cluster · byte = cluster÷8 · bit = cluster mod 8 · ex: cluster 42 → byte 5, bit 2

Décoder la Run List : 21 1C 7A 0A 11 08 FE 61 00Run List NTFS · Niveau : moyen
Run 1 : Header 0x21 → 2 octets offset, 1 octet longueur
Longueur : 0x1C = 28 clusters · Offset LCN : 7A 0A LE = 0x0A7A = 2682 (absolu, 1er run)
→ 28 clusters débutant au LCN 2682

Run 2 : Header 0x11 → 1 octet offset, 1 octet longueur
Longueur : 0x08 = 8 clusters · Offset : 0xFE = signé négatif = −2 (relatif au run précédent)
→ LCN absolu = 2682 − 2 = 2680 · 8 clusters débutant au LCN 2680

Fin : 0x00
Quel cluster 42 correspond à quel byte et quel bit dans le $Bitmap ? Quelle valeur d'octet si seul le cluster 42 est occupé ?$Bitmap NTFS · Niveau : facile
Byte = 42 ÷ 8 = 5 · Bit = 42 mod 8 = 2 (bit de poids 2²)
Si seul le cluster 42 est occupé : bit 2 = 1 → octet = 0b00000100 = 0x04
Pour vérifier : dans le fichier $Bitmap, lire l'octet à l'offset 5 et isoler le bit 2.
