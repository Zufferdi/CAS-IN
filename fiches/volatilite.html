🧠 Volatility — Le microscope mémoire de la DFIR
La RAM (Random Access Memory) contient en permanence l'état vivant de la machine : tous les processus en cours d'exécution, les fenêtres ouvertes, les connexions réseau actives, les fichiers en cours d'édition, les mots de passe saisis récemment, et — point crucial — les clés de chiffrement déchiffrées (BitLocker FVEK, VeraCrypt master keys, TLS session keys). Tout cela disparaît instantanément à la coupure d'alimentation. C'est pourquoi la norme ISO/IEC 27037 stipule que la RAM doit être capturée avant toute autre action sur un système actif. Volatility (Aaron Walters, 2007) est le framework open source de référence mondiale pour analyser ces dumps RAM. Volatility 2 (Python 2) est obsolète depuis 2020 ; Volatility 3 (Python 3, sortie 2020) est l'actuel standard. Le framework est composé d'un noyau d'analyse + des dizaines de plugins spécialisés. Workflow type : (1) Acquisition RAM avec WinPMem/Magnet/avml/LiME, (2) Identification du profil OS avec windows.info ou linux.banner, (3) Triage avec pslist, pstree, netscan, (4) Approfondissement avec malfind, cmdline, dlllist, handles, (5) Extraction de fichiers, executables, ou clés crypto. Volatility est indispensable pour : détection de process hollowing, process injection, rootkits, exfiltration de credentials (Mimikatz en RAM), récupération de fichiers en cache, et extraction de clés de chiffrement de volumes montés.

🚀 Démarrage rapide Volatility 3
# 1. Installer Volatility 3 (Python 3.8+)
pip install volatility3
# Ou via git pour la dernière version :
git clone https://github.com/volatilityfoundation/volatility3

# 2. Vérifier l'installation et lister les plugins disponibles
python3 vol.py --help
python3 vol.py --list-plugins

# 3. Identifier l'OS du dump (auto-detection en v3, plus de profils)
python3 vol.py -f dump.raw windows.info
python3 vol.py -f dump.raw linux.banner
python3 vol.py -f dump.raw mac.kevents

# 4. Triage initial — qui tourne, qui parle au réseau
python3 vol.py -f dump.raw windows.pslist
python3 vol.py -f dump.raw windows.netscan

# 5. Export en CSV pour timeline ou Timeline Explorer
python3 vol.py -r csv -f dump.raw windows.pslist > pslist.csv

📋 Workflow type analyse RAM en DFIR
  1. Identification — windows.info / linux.banner pour confirmer profil OS et version.
  2. Triage processus — pslist + pstree pour vue d'ensemble. Comparer avec psscan pour détecter rootkits.
  3. Analyse réseau — netscan (Windows) ou linux.netstat pour connexions actives/fermées.
  4. Recherche injection — malfind pour régions RWX suspectes (signature shellcode/CobaltStrike).
  5. Approfondissement processus suspects — cmdline, dlllist, handles, memmap.
  6. Extraction — dumpfiles pour récupérer fichiers cachés, procdump pour processus complet.
  7. Crédentiels — hashdump, cachedump, lsadump pour artefacts auth.
  8. Pour analyse avancée (rootkits, SSDT hooks, structures EPROCESS, timeline mémoire) → Forensique mémoire avancée.
⚖️ Art. 248 CPP : La saisie d'un ordinateur allumé nécessite une décision motivée — éteindre = perte définitive de la RAM. L'acquisition RAM est une mesure de contrainte à documenter scrupuleusement.
Plugins Volatility 3 — Windows
windows.pslist
Liste tous les processus actifs (PID, PPID, nom, heure démarrage)
→ Détecter processus suspects ou masqués
windows.pstree
Arbre des processus parents/enfants — visualiser les chaînes d'exécution
→ cmd.exe enfant de Word = macro malveillante
windows.psscan
Scan mémoire pour les structures EPROCESS — trouve les processus cachés (rootkits)
→ Divergence pslist vs psscan = rootkit
windows.netscan
Connexions réseau actives et fermées (IP, port, protocole, PID)
→ Connexions C2, beacon malware
windows.cmdline
Arguments de ligne de commande de chaque processus
→ PowerShell -enc = commande encodée suspecte
windows.dlllist
DLL chargées par chaque processus — détecter DLL injection
→ DLL injectée dans lsass.exe = credential dumping
windows.handles
Handles ouverts (fichiers, clés registre, mutexes) par processus
→ Fichiers ouverts non visibles sur disque
windows.malfind
Détecte les régions mémoire exécutables sans image disque associée
→ Code injecté, shellcode en mémoire
windows.filescan
Scan les objets FILE_OBJECT en mémoire — fichiers ouverts ou récemment fermés
→ Fichiers supprimés encore référencés
windows.registry.hivelist
Liste les ruches de registre chargées en mémoire
→ Ruches volatiles (HKCU non sauvées)
windows.hashdump
Extrait les hashes NTLM depuis la mémoire (SAM en mémoire)
→ Casser avec Hashcat -m 1000
windows.vadinfo
Virtual Address Descriptor — régions mémoire mappées par processus
→ Analyse des segments de mémoire

Détection de malware en mémoire
Indicateurs de compromission RAM
  • Processus avec nom légitime mais PPID anormal (svchost sans services.exe)
  • Processus dupliqués (2 × lsass.exe)
  • Chemin d'exécution hors %SystemRoot% (lsass.exe dans C:\Temp)
  • Connexions réseau vers IP suspectes depuis processus système
  • malfind → régions PAGE_EXECUTE_READWRITE sans fichier
  • DLL injectée dans processus légitime (hollowing)
Processus système légitimes
  • System — PID 4, toujours, PPID 0
  • smss.exe — 1 seul, enfant de System
  • csrss.exe — 1 par session, enfant smss
  • lsass.exe — 1 seul, enfant winlogon/wininit
  • services.exe — 1 seul, enfant wininit
  • svchost.exe — multiple, enfants services.exe uniquement
Process Hollowing & Injection
Process Hollowing

Le malware crée un processus légitime (svchost.exe) suspendu, remplace son code en mémoire par du code malveillant, puis reprend l'exécution. L'apparence est celle d'un processus légitime.

DLL Injection

Forcer un processus légitime à charger une DLL malveillante via CreateRemoteThread + LoadLibrary. La DLL tourne dans le contexte du processus cible (et ses privilèges).


Détection : dlllist → DLL avec chemin anormal ou sans signature.

Extraction de clés de chiffrement
BitLocker — FVEK

Si le volume BitLocker était monté lors de la capture RAM, la FVEK (Full Volume Encryption Key) est présente en mémoire.

Passware : Analyze Encrypted Disk → sélectionner le dump RAM → extraction automatique.

Volatility : plugin windows.bitlocker (Volatility 3 avec plugin tiers).

VeraCrypt / TrueCrypt

Les clés AES de VeraCrypt sont en mémoire tant que le volume est monté. Passware Kit Forensic les extrait automatiquement depuis le dump RAM.

Aucune attaque de MDP nécessaire — la clé symétrique déchiffre directement.

Hashes NTLM (hashdump)

Les hashes NTLM des comptes locaux sont en mémoire dans le processus lsass.exe.

windows.hashdump → hashes → Hashcat -m 1000

Mimikatz : sekurlsa::logonpasswords peut récupérer les MDP en clair si WDigest est actif.

Attention légale (Suisse)

L'extraction de clés de chiffrement depuis la RAM est une mesure de contrainte (art. 246–248 CPP). Elle doit être autorisée et documentée. Le résultat (clé ou hash) est une pièce à conviction soumise aux règles de la chaîne de possession.

🧠 Testez-vous
Pourquoi pslist et psscan peuvent-ils donner des résultats différents ?Volatility · Niveau : moyen
Différence clé pour détecter les rootkits. pslist parcourt la liste chaînée doublement liée des processus (PsActiveProcessHead) gérée par le noyau Windows — c'est ce que voit tasklist ou Process Explorer. Un rootkit moderne peut déchaîner son processus de cette liste (« Direct Kernel Object Manipulation », DKOM) pour devenir invisible aux outils standards. psscan en revanche fait un scan brut de la RAM à la recherche des structures EPROCESS par signature, indépendamment de leur enchaînement dans la liste. Si pslist montre 50 process et psscan en montre 52 → 2 process cachés volontairement = très fort indicateur de rootkit. Workflow : (1) vol.py -f ram.raw windows.pslist, (2) vol.py -f ram.raw windows.psscan, (3) diff les deux sorties (filtrage Python ou comparaison manuelle). Les process apparaissant uniquement dans psscan sont à investiguer en priorité avec malfind, cmdline, et dumpfiles. Limite : psscan peut aussi détecter des process déjà terminés (structures EPROCESS pas encore réécrites en RAM) — distinction via le champ Exit Time.
Vous trouvez via malfind un process avec une région VAD RWX (Read+Write+Execute). Que signifie cela ?Détection injection · Niveau : difficile
Très fort indicateur d'injection de code. En conditions normales, les pages mémoire d'un process ont des permissions séparées : R (lecture seule pour const/données read-only), RW (lecture+écriture pour heap/stack/data), RX (lecture+exécution pour code/.text). Une page RWX est anormale : elle permet à la fois d'écrire et d'exécuter, ce qui est la signature de : (1) Code shellcode injecté via VirtualAllocEx + WriteProcessMemory + CreateRemoteThread, (2) Process Hollowing — process légitime vidé puis rempli de code malveillant, (3) JIT compilers légitimes (false positive : Java, .NET, V8 dans Chrome) — à exclure par contexte, (4) Packers / unpackers qui décompressent du code en RAM. Workflow d'analyse : (a) vol.py windows.malfind --pid <PID> dump le contenu de la région suspecte, (b) Examiner les premiers octets : 4D 5A = signature MZ d'un PE Windows = code injecté, (c) Examiner le PEB et la VAD pour voir d'où vient l'injection, (d) vol.py windows.cmdline --pid <PID> pour le contexte du process, (e) Sauvegarder le code injecté en .bin et l'analyser avec radare2/Ghidra/IDA. Détection complémentaire : vol.py windows.ldrmodules compare les listes de DLL chargées via 3 sources différentes — un mismatch = injection.
Une machine BitLocker est saisie en cours de fonctionnement. Comment exploiter la situation forensiquement ?BitLocker / RAM · Niveau : difficile
Acquisition RAM IMMÉDIATE est la priorité absolue — c'est la seule chance de récupérer la FVEK (Full Volume Encryption Key) de BitLocker. Procédure : (1) Ne JAMAIS éteindre la machine — coupure d'alimentation = perte totale de la RAM = clé perdue à jamais. (2) Ne pas verrouiller la session non plus (peut déclencher BitLocker re-locking sur certaines configs). (3) Brancher au chargeur si laptop. (4) Acquisition RAM avec WinPMem sur clé USB write-blocked : winpmem.exe -o ram.raw. (5) Hash SHA-256 immédiatement après. (6) Acquisition disque chiffré séparément (via write-blocker physique). (7) Analyse de la RAM avec Volatility : vol.py -f ram.raw windows.bitlocker (plugin tiers Volatility 3) extrait les FVEK, ou avec outils alternatifs comme Elcomsoft Forensic Disk Decryptor. (8) Déchiffrement du disque offline avec la FVEK extraite. Pourquoi cela fonctionne : BitLocker maintient la FVEK déchiffrée en RAM tant que le volume est monté pour pouvoir lire/écrire les secteurs en temps réel. Une fois trouvée, on peut déchiffrer toute l'image disque. Limite : si l'utilisateur a verrouillé la session avec BitLocker en mode "lock on suspend", la FVEK peut être effacée de la RAM. Si le volume est démonté pendant la session, idem. Cadre légal CH : art. 248 CPP autorise l'acquisition RAM si décision motivée — documenter scrupuleusement.
Quelle est la différence entre hashdump et lsadump dans Volatility ?Credentials · Niveau : moyen
Tous deux extraient des credentials de la RAM, mais à des emplacements différents : hashdump extrait les hashes NTLM des comptes locaux depuis la base SAM (équivalent du secretsdump SAM mais en RAM). Sortie : user:RID:LM_hash:NT_hash:::. À cracker avec hashcat -m 1000. Couvre les comptes locaux uniquement, pas les comptes de domaine. lsadump extrait les secrets LSA (Local Security Authority) — c'est-à-dire les credentials cachées par Windows pour les services autonomes : (1) Mots de passe des comptes service (configurés en plain text dans HKLM\SECURITY\Policy\Secrets et déchiffrés en RAM), (2) Cached domain credentials (les 10 derniers logons de domaine), (3) DPAPI master keys (qui chiffrent les passwords sauvegardés des navigateurs, etc.). Plugin associé : cachedump spécifique pour les credentials de domaine cachées (format MS-CACHE, à cracker avec hashcat -m 2100 ou -m 1100). Workflow forensique typique : (1) hashdump pour comptes locaux, (2) lsadump pour service accounts + secrets, (3) cachedump pour cached domain logons, (4) Mimikatz en RAM (via vol.py windows.mimikatz en module communautaire) peut extraire bien plus, y compris des MDP en clair si WDigest était activé. NB : tous ces extractions nécessitent le profil OS correctement détecté (Windows 7 vs Win10 : différentes structures).

━━ ACQUISITION ━━

• Windows : WinPMem (recommandé) · Magnet RAM Capture · FTK Imager

• Linux : avml (Microsoft) · LiME (kernel module)

• macOS : OSXPMem (limité) · Volexity Surge Collect

• Toujours hash SHA-256 immédiatement après · ISO/IEC 27037 = RAM avant tout

━━ PLUGINS PROCESSUS ━━

• windows.info = profil OS (toujours en premier)

• windows.pslist = liste chaînée des process

• windows.psscan = scan brut de la RAM (détecte process cachés)

• windows.pstree = arborescence parent-enfant

• windows.cmdline = lignes de commande (révèle PowerShell encodé)

• windows.dlllist = DLL chargées par chaque process

• windows.handles = handles ouverts (fichiers, mutex, registry)

━━ PLUGINS RÉSEAU ━━

• windows.netscan = connexions réseau actives + processus

• windows.netstat = équivalent netstat en RAM

━━ PLUGINS DÉTECTION MALWARE ━━

• windows.malfind = pages RWX, code injecté

• windows.hollowfind = process hollowing

• windows.ldrmodules = mismatch entre listes DLL = injection

• windows.yarascan = scan signatures YARA dans la RAM

• diff pslist psscan = process cachés (rootkit)

━━ PLUGINS CREDENTIALS ━━

• windows.hashdump = NTLM hashes locaux (SAM en RAM)

• windows.lsadump = secrets LSA (service accounts MDP)

• windows.cachedump = cached domain logons

• vol.py windows.mimikatz = MDP en clair si WDigest actif

━━ CRYPTO ━━

• BitLocker FVEK extractible uniquement si volume monté lors de la capture

• Permet de déchiffrer le disque offline ensuite

• Idem pour VeraCrypt, TrueCrypt, FileVault
