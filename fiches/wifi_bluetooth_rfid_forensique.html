📶 WiFi forensique — du monitor mode à la capture du handshake
Une interface WiFi en mode monitor écoute tout le trafic 802.11 sur un canal donné, sans s'associer à un AP. C'est l'équivalent du promiscuous mode en filaire, mais avec des contraintes matérielles : tous les chipsets ne le supportent pas (Alfa AWUS036ACH, Ralink RT3070, Atheros AR9271 — références habituelles). Sur un canal donné, on capture : beacon frames (APs visibles), probe requests/responses (clients cherchant un réseau), data frames chiffrées, management frames (associations, deauth), et — si on est chanceux — un handshake WPA2 4-way capturé pendant la connexion d'un client.
Workflow capture — suite Aircrack-ng (standard de fait)
# 1. Identifier l'interface WiFi
iwconfig
# wlan0  IEEE 802.11  ESSID:off/any  Mode:Managed ...

# 2. Tuer les processus qui interfèrent (NetworkManager, wpa_supplicant)
sudo airmon-ng check kill

# 3. Passer en mode monitor (crée wlan0mon)
sudo airmon-ng start wlan0

# 4. Scan général : voir tous les APs et clients
sudo airodump-ng wlan0mon
# Lister par canal/BSSID/encryption/clients

# 5. Cibler un AP spécifique et capturer le handshake
sudo airodump-ng -c 6 --bssid AA:BB:CC:DD:EE:FF -w capture wlan0mon
# Sauvegarde dans capture-01.cap / .csv

# 6. Forcer un client à se ré-authentifier (deauth) → handshake recapturé
sudo aireplay-ng -0 5 -a AA:BB:CC:DD:EE:FF -c 11:22:33:44:55:66 wlan0mon
# OU attendre passivement une connexion légitime

# 7. Vérifier la présence du handshake dans la capture
sudo aircrack-ng capture-01.cap
# WPA (1 handshake) → OK

# 8. Cassage offline (dictionary attack)
sudo aircrack-ng -w /usr/share/wordlists/rockyou.txt capture-01.cap
# OU avec GPU : hashcat -m 22000 capture.hc22000 wordlist.txt
Les protocoles WiFi et leurs faiblesses
❌ WEP (1997, brisé)

RC4 + IV 24 bits → collision en quelques minutes avec l'attaque PTW (Pyshkin, Tews, Weinmann, 2007). Jamais utilisable en environnement sérieux. Si trouvé en audit = sanction immédiate.

⚠️ WPA / WPA2-PSK (4-way handshake)

Sensible aux attaques offline dictionary sur le PSK (pre-shared key). Capture du handshake suffit + GPU cracking (hashcat mode 22000). Mot de passe ≥ 14 chars aléatoires = quasi-incassable. Mot de passe dictionnaire = cassé en secondes.

🆕 WPA3-SAE (Dragonfly)

Introduit Simultaneous Authentication of Equals qui résiste aux attaques offline dictionary. Forward secrecy. Mais : vulnérabilités Dragonblood (2019, CVE-2019-9494/9495) sur certaines implémentations + downgrade attacks vers WPA2 si transition mode activé.

🎯 PMKID Attack (2018, hashcat)

Variante WPA/WPA2 qui n'a pas besoin d'un client connecté : capture du PMKID dans le premier RSN-IE de l'AP. Outil : hcxdumptool. Mode hashcat 16800. Encore plus efficace que la capture handshake classique.

🔓 WPS PIN Brute-force

WPS (Wi-Fi Protected Setup) avec PIN 8 chiffres → réduit à 2 tronçons de 4 chiffres (faille protocolaire 2011). Outils : Reaver, Bully. Désactiver WPS sur tout équipement.

📡 Management Frame Protection (802.11w)

Protège les frames de gestion (deauth, dissoc, action) avec une intégrité crypto. Empêche les deauth attacks classiques. Mandatory en WPA3, optionnel en WPA2. Kismet détecte les floods de deauth = signal d'attaque.

📌 Format hashcat 2025 — Le format .hccapx (mode 2500) est déprécié. La capture est maintenant convertie en .hc22000 (mode 22000) via hcxpcapngtool capture.pcapng -o capture.hc22000. Ce format gère à la fois les EAPOL handshakes et les PMKIDs dans un fichier unique.
🛰 Probe requests — le téléphone bavard qui trahit sa présence
Quand un téléphone (ou tout appareil WiFi) cherche un réseau connu, il émet des probe requests contenant le SSID du réseau désiré (« HomeWiFi_Martin est-il là ? »). En écoutant passivement, on capture la liste des SSIDs connus de la victime + son adresse MAC. Avec une base comme WiGLE, on peut géolocaliser chaque SSID → reconstituer le parcours physique d'un individu sur des années. C'est un vecteur de tracking majeur, encore largement sous-estimé.
MAC randomization — la défense (partielle)
🍎 iOS (depuis iOS 8, 2014)

MAC randomisée en mode scan uniquement. Avant connexion, l'iPhone scrute avec une MAC aléatoire. Une fois connecté à un réseau, la MAC réelle est utilisée. Depuis iOS 14 : MAC aléatoire par réseau (option utilisateur).

🤖 Android (depuis Android 10, 2019)

MAC randomisée par réseau par défaut depuis Android 10. Persistante par SSID jusqu'à oubli du réseau (réversible via paramètres). Avant Android 10, MAC réelle constante = traçabilité totale.

🪟 Windows 10/11

Option « Use random hardware addresses » par interface ou par réseau. Désactivée par défaut. Les pros la désactivent souvent pour MAC filtering corporate.

⚠️ Limites de la randomization

(1) Probe SSIDs restent identifiants (« je cherche StarbucksWiFi + EPFL_guest + AirBnB_Berlin_2024 » = profil unique). (2) Sequence numbers, timing patterns, capability bits permettent du fingerprinting passif (recherches académiques 2019-2024).

Outils & bases de données
# Kismet — sniffer + WIDS open-source, scriptable
kismet -c wlan0mon
# Interface web : http://localhost:2501
# Logs JSON, base SQLite. Détecte rogue APs, déauthentication floods,
# attaques karma, captive portals suspects.

# Wireshark filters pour analyse PCAP
wlan.fc.type_subtype == 4    # probe requests uniquement
wlan.sa == AA:BB:CC:DD:EE:FF  # filtrer par MAC source

# WiGLE : base mondiale de SSID/BSSID géolocalisés (~1 milliard)
# wigle.net — recherche par SSID, BSSID, coordonnées GPS
# API gratuite avec compte (rate-limited)
# Usage forensique : "à quels endroits ce téléphone est passé ?"

# hcxdumptool — capture WPA/PMKID moderne
sudo hcxdumptool -i wlan0mon -o capture.pcapng \
    --enable-status=15

# hcxpcapngtool — conversion vers hashcat
hcxpcapngtool capture.pcapng -o capture.hc22000 \
    -E essidlist
🎯 Cas pratique CH — Les Probe Requests sont régulièrement utilisées par les enquêtes pour placer un suspect dans une zone (corrélation MAC ↔ scène). Combiné aux données antenne mobile (rétention 6 mois LSCPT), c'est une preuve forensique solide. Limites : MAC randomization moderne réduit l'utilité, mais les SSIDs probés restent identifiants.
🔵 Bluetooth / BLE — pairing, GATT, advertising
Bluetooth se décompose en deux écosystèmes distincts : Bluetooth Classic / BR-EDR (audio, transfert fichiers, ~10 m, ~24 Mbps) et Bluetooth Low Energy (BLE) introduit en v4.0 (2010), conçu pour IoT et wearables (batterie longue, payload réduit, jusqu'à 2 Mbps en v5). Le pairing BLE utilise le protocole Secure Simple Pairing (SSP) avec 4 méthodes : Just Works, Numeric Comparison, Passkey Entry, Out-Of-Band (OOB). Just Works et Passkey Entry ont des faiblesses documentées exploitées par plusieurs CVE.
Artefacts forensiques Bluetooth (mobile)
🤖 Android — bt_config.conf

Fichier /data/misc/bluedroid/bt_config.conf (root requis). Liste des appareils pairés : MAC, nom, type, link key, services. Aussi : /data/misc/bluetooth/logs/btsnoop_hci.log (logs HCI snoop si activés dev mode).

🍎 iOS — com.apple.MobileBluetooth

/private/var/root/Library/Preferences/com.apple.MobileBluetooth.devices.plist. Aussi com.apple.MobileBluetooth.ledevices.plist pour BLE spécifiquement. Accessibles via Cellebrite UFED, Magnet AXIOM, ou checkra1n + extraction full file system.

🪟 Windows — Registry

Clés HKLM\SYSTEM\CurrentControlSet\Services\BTHPORT\Parameters\Devices\ : un sous-key par appareil pairé (par MAC). Valeurs : Name, LinkKey (chiffrée), LinkKeyLength, LastConnected (FILETIME).

🐧 Linux — BlueZ

/var/lib/bluetooth/<adapter-MAC>/<device-MAC>/info : fichier INI par appareil pairé (Name, LinkKey, Class, supportedTechnologies). btmgmt, bluetoothctl en CLI.

Captures et attaques BLE
📡 Capture trafic BLE

Ubertooth One (open-source, Great Scott Gadgets) · Sniffle (NCC Group, dongle TI CC1352) · Wireshark + nRF Sniffer (Nordic Semiconductor, dongle nRF52840). Capture des advertising packets + connection events.

🎭 Spoofing & rogue devices

Flipper Zero (en mode BadBT/BadUSB) émet des advertising packets BLE pour spoofer des AirTags, Apple devices (cf. iOS BLE spam). BTLEJack permet sniffing actif + hijacking de connexions BLE.

⚠️ Bluesnarfing / Bluejacking

Bluesnarfing = vol données par Bluetooth (obsolète sur appareils modernes). Bluejacking = envoi non sollicité (toujours possible via OPP/Object Push). BlueBorne (2017) : famille de CVE Android/iOS/Linux/Windows permettant RCE via Bluetooth.

🚗 BLE & voitures connectées

Relay attacks contre keyfobs BLE (Tesla, BMW, etc.) : transmetteur + récepteur amplifient le signal du keyfob réel → voiture ouverte. Bypass par challenge-response timing en milliseconde (Tesla a corrigé en 2022).

🏷 RFID / NFC — du badge bureau au passeport biométrique
RFID (Radio-Frequency Identification) recouvre une famille de protocoles court-portée : LF 125 kHz (badges immeubles anciens, EM4100/HID Prox, trivialement clonables), HF 13.56 MHz (Mifare Classic/DESFire, transports publics, badges entreprise modernes, passeports), UHF 860-960 MHz (logistique, antivol). NFC est un sous-ensemble du HF (13.56 MHz) avec extensions pour communications bidirectionnelles (paiement, smartphone). Le forensique RFID/NFC concerne : (1) la copie d'un badge légitime saisi, (2) l'analyse d'un badge cloné saisi à un suspect, (3) la récupération des clés crypto pour relier un badge à un système.
Mifare Classic — la cible la plus courante en CH
🔓 Vulnérabilités historiques

Mifare Classic utilise CRYPTO1, chiffre propriétaire NXP reverse-engineered en 2008. Attaques nested et darkside permettent de récupérer toutes les clés de tous les secteurs si une seule clé est connue (souvent une clé de transport par défaut). Tous les badges entreprise basés Mifare Classic sont à considérer compromis par défaut.

🛠 Outils principaux

Proxmark3 (RDV4, Easy, X — variantes commerciales) : référence pro · Flipper Zero : populaire, lit Mifare Classic et clone NFC simples · ChameleonMini/Ultra : émulation · nfc-tools (libnfc, mfoc, mfcuk) : Linux open-source.

⚡ Workflow Proxmark3 Mifare
pm3> hf mf info
pm3> hf mf chk *1 ? d
   # tente toutes les clés par défaut
pm3> hf mf nested 1 0 A FFFFFFFFFFFF
   # attaque nested avec clé A connue
pm3> hf mf dump
   # dump complet du tag
pm3> hf mf restore --1k
   # restauration sur tag magique
🔐 Mifare DESFire (sécurisé)

Successeur Mifare Classic, 3DES ou AES matériel, pas de faille connue exploitable sur EV2/EV3. Utilisé par CFF (cartes SwissPass), badges entreprises modernes. Forensique : seul moyen d'extraction = clés maîtres → coopération de l'émetteur de la carte (l'employeur, CFF…).

Passeport biométrique & eID

🛂 Le passeport biométrique suisse contient une puce NFC ISO/IEC 14443 (HF 13.56 MHz) protégée par BAC (Basic Access Control) puis PACE (Password Authenticated Connection Establishment). La clé d'accès est dérivée des champs de la MRZ (Machine Readable Zone) imprimée sur la page de garde : document number + date of birth + date of expiry. Sans la MRZ, accès impossible. Sans le passeport physique, attaque impossible (NFC ~10 cm de portée pratique).

📱 La e-ID suisse (loi adoptée en septembre 2025, déploiement 2026) sera basée sur un wallet mobile (smartphone, app fédérale) — donc Bluetooth/NFC pour les présentations en personne, mais identifiants stockés dans le secure element du téléphone (Titan M2 chez Pixel, Secure Enclave chez Apple). Le forensique mobile classique s'applique.

⚖️ Cadre juridique suisse — captures sans fil et preuve
La capture passive d'ondes radio (écoute monitor-mode) est juridiquement ambiguë en CH. Art. 179octies CP incrimine la « mise sur écoute » de communications privées non autorisée. La doctrine considère que le simple écoute d'un signal chiffré dans l'espace public reste licite, mais la décryption ou la collecte ciblée de communications identifiables relève des règles de surveillance pénale (CPP) ou administrative (LRens, LSP cantonale). Pour les forces de l'ordre, la capture WiFi/BLE doit être ordonnée par le Ministère public (art. 269 ss CPP — surveillance de la correspondance) sauf si elle s'inscrit dans une mesure de surveillance préventive autorisée.
Trois cadres juridiques à distinguer
🔍 Enquête pénale (CPP)

Art. 269 CPP — surveillance correspondance par poste et télécommunication : autorisation MP + approbation TMC dans 24h.

Art. 280 CPP — moyens techniques de surveillance (caméras, micros, capteurs).

Capture monitor-mode dans l'enceinte d'une perquisition autorisée = couverte. Hors mandat = problématique.

🛡 Renseignement (LRens)

Service de renseignement de la Confédération (SRC) peut conduire des écoutes wireless dans le cadre de la LRens (2015), avec autorisation TAF + DDPS. Cadre distinct, hors CPP.

🚓 Police administrative

Polices cantonales peuvent utiliser des outils de détection wireless (rogue AP, IMSI catchers) en prévention, dans les limites de leur loi cantonale (LPol) — souvent peu détaillée → contestable en cas d'usage massif.

📞 LSCPT & SCPT

Loi sur la surveillance de la correspondance par poste et télécommunication (LSCPT, 2017) + Service de surveillance (SCPT/PTSS, Berne) : centralise les demandes auprès des opérateurs. Rétention métadonnées 6 mois (cellules téléphone), 12 mois (Internet identifiants).

Cas pratique CH 2025 — SMS Blaster

📱 Le SMS Blaster (faux relais bâti sur la technologie IMSI Catcher) exploite la faiblesse du standard 2G obsolète (« chiffrement nul ») pour forcer les téléphones environnants à s'y connecter, puis envoyer des SMS de phishing massifs sans passer par les opérateurs légitimes — un signal puissant brouille la 3G/4G dans un rayon de 500 à 1'000 m. Premiers cas signalés en CH : OFCS semaine 36/2025 (9.09.2025) pour des SMS de fausses amendes de stationnement en Suisse romande, après des dommages estimés à 2 millions de CHF à Genève et 260'000 CHF dans le canton de Vaud en 2025. Plusieurs arrestations ont suivi : trois hommes interpellés dans l'Ouest CH, puis un ressortissant chinois de 52 ans arrêté à Muttenz (BL) le 14 octobre 2025 (SMS imitant La Poste et Migros) — un appareil saisi à Bâle-Campagne pouvait toucher ~100'000 smartphones par jour. Procédure : art. 143 CP (soustraction de données identifiants), art. 147 CP (utilisation frauduleuse d'un ordinateur), art. 22 et 39 LTC (Loi sur les télécommunications, utilisation du spectre sans concession). Coopération OFCOM (spectre) et OFCS (cyber).

🔍 Forensique : repérage actif par sonde 2G dédiée (le blaster impose un downgrade) + triangulation par signal strength = localisation du véhicule. Saisie matérielle (boîtier type case ordinateur, SDR, modems, batteries) puis analyse offline : logs des MSISDN ciblés, contenus SMS, configuration des fausses identités d'expéditeur (Post, Migros, Police). Lien direct avec la fiche sigma_rules car les SMS pointaient vers des landing pages détectables par règles de réputation domain.

🎓 Exam Tip — WiFi / Bluetooth / RFID

WiFi 802.11 — protocoles : WEP (brisé 2007) · WPA/WPA2-PSK (handshake 4-way + dict attack) · WPA3-SAE (Dragonfly, résiste offline) · PMKID attack (pas besoin de client connecté)

Outils WiFi : aircrack-ng (airmon/airodump/aireplay/aircrack) · Kismet (WIDS + interface web) · hcxdumptool/hcxpcapngtool (PMKID moderne) · Wireshark (analyse)

Format hashcat 2025 : .hc22000 (mode 22000) — remplace .hccapx (mode 2500, déprécié)

Mode monitor : airmon-ng start wlan0 · interface devient wlan0mon · capture tout, n'émet rien

Chipsets compatibles : Alfa AWUS036ACH/036NHA, Ralink RT3070, Atheros AR9271 (réf. historiques)

Probe Requests : SSIDs connus du téléphone → géolocalisation via WiGLE (~1 milliard de BSSIDs)

MAC randomization : iOS 8+ (scan), iOS 14+ (par réseau) · Android 10+ par défaut · Windows 10/11 désactivé par défaut

WPS : PIN 8 chiffres réduit à 2×4 → Reaver/Bully → cassable en heures. Toujours désactiver WPS.

802.11w (MFP) : Management Frame Protection — bloque les deauth attacks · mandatory WPA3

Bluetooth : Classic (BR-EDR, ~10m) vs BLE (depuis v4.0 2010) · SSP avec 4 méthodes (Just Works, Passkey, Numeric Comparison, OOB)

Artefacts BT mobile : Android bt_config.conf · iOS com.apple.MobileBluetooth.*.plist · Windows HKLM\...\BTHPORT\Parameters\Devices · Linux BlueZ /var/lib/bluetooth/

Sniffers BLE : Ubertooth One · Sniffle (NCC Group) · nRF52840 + Wireshark · TI CC1352

RFID fréquences : LF 125 kHz (badges anciens, EM4100) · HF 13.56 MHz (Mifare, NFC, passeport) · UHF 860-960 MHz (logistique)

Mifare Classic : CRYPTO1 reverse-engineered 2008 · attaques nested et darkside · à considérer compromis par défaut

Outils RFID : Proxmark3 (RDV4 référence) · Flipper Zero (grand public) · ChameleonMini · libnfc + mfoc/mfcuk

Mifare DESFire EV2/EV3 : 3DES/AES matériel · pas de faille connue · forensique = coopération émetteur

Passeport biométrique : BAC puis PACE · clé dérivée de la MRZ (n° doc + DDN + expiration) · NFC ~10 cm

Cadre juridique CH : art. 269 CPP (surveillance correspondance, mandat MP + TMC) · art. 280 CPP (moyens techniques) · LRens (SRC) · LSCPT (rétention 6 mois cellule)

Cas CH 2025 : SMS Blaster (OFCS semaine 36 / 9.09.2025) — Suisse romande (GE 2M CHF, VD 260'000 CHF) + arrestation Muttenz BL (14.10.2025) — art. 143/147 CP + art. 22/39 LTC + coordination OFCOM/OFCS

Quels artefacts BLE/WiFi cherchez-vous, et pourquoi sont-ils probants même avec MAC randomization activée ?
WiFi/BLE Forensique · Niveau : difficile
Plusieurs sources convergentes, indépendantes des données opérateur :

1️⃣ WiFi — réseaux mémorisés et probe history
Sur Android (root requis) : /data/misc/wifi/WifiConfigStore.xml liste tous les réseaux connus, avec "lastConnected" et "creationTime" au format epoch ms. Couplé à WiGLE pour géolocaliser chaque SSID, on reconstitue les lieux fréquentés. La MAC randomization n'affecte que la MAC émise — la liste des SSIDs probés reste écrite dans la mémoire du téléphone.

2️⃣ Bluetooth — appareils pairés et derniers usages
/data/misc/bluedroid/bt_config.conf : liste des appareils pairés (MAC, nom, timestamp). Le pairing à une enceinte du domicile, une voiture, un écouteur d'un collègue → liens probants. Le btsnoop_hci.log (si activé) horodate chaque connexion/déconnexion.

3️⃣ Cellebrite/Magnet pour iOS
Via UFED ou checkra1n + full file system, on accède à com.apple.wifi.plist (réseaux mémorisés) et com.apple.MobileBluetooth.ledevices.plist (BLE appareils).

4️⃣ Probants même avec randomization car : (a) la randomization concerne la MAC émise par l'appareil, pas la liste des SSIDs cherchés (qui reste dans le téléphone) ; (b) les SSIDs probés sont des identifiants culturels forts (BoulangerieRueDuLac, FamilleMartin_NAS…) ; (c) WiGLE permet la triangulation de localisation à partir des SSIDs.

⚠ Cadre juridique : l'accès au stockage interne du téléphone après saisie nécessite l'autorisation explicite du Ministère public dans le cadre du mandat (art. 246-248 CPP, perquisition de données + scellés). L'analyse est conduite par expert assermenté.
