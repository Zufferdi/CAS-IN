🔍 Une image acquise n'est qu'un point de départ
L'image bit-à-bit est faite. Le hash est consigné. La chaîne de custody est documentée. Et maintenant ? Une erreur classique consiste à ouvrir Autopsy au hasard et fouiller. Le travail efficace suit un ordre opérationnel en 6 étapes : intégrité → identification système → triage rapide → timeline → artefacts ciblés selon l'hypothèse d'enquête → analyse profonde. Cette fiche est la passerelle vers toutes les autres : elle indique quoi regarder, dans quel ordre, avec quel outil. Elle complète Méthodologie DFIR qui couvre la phase Examen du cycle, et renvoie aux fiches détaillées pour chaque artefact.
🔄 Le workflow Day-1 — De l'image acquise à l'hypothèse étayée
6 ÉTAPES · CHAQUE TRANSITION = DOCUMENT D'AUDIT · TRAVAIL SUR COPIE
① Étape 0 — Vérifier l'intégrité avant toute chose
Une analyse sur une image dont l'intégrité n'a pas été reverifiée juste avant ouverture est inattaquable par la défense.
✅ À faire systématiquement
  • Recalculer le SHA-256 de l'image avec un outil tiers (sha256sum, certutil -hashfile, Get-FileHash)
  • Comparer au hash documenté dans le PV d'acquisition
  • Travailler sur une copie de travail, jamais l'original
  • Monter l'image en read-only (mount -o ro,loop · FTK Imager mount read-only · Arsenal Image Mounter)
  • Documenter chaque ouverture dans le journal d'audit (date · heure · opérateur · outil · version · empreinte hash avant/après)
⛔ Pièges qui invalident la preuve
  • Ouvrir l'image en lecture-écriture (modifie les timestamps de montage)
  • Brancher le disque source sans write-blocker (USB/SATA)
  • Ne pas reverifier le hash avant chaque session de travail majeure
  • Travailler à plusieurs sur la même copie sans journal partagé
  • Décompresser une image E01 dans un dossier sans noter le hash de chaque fichier extrait
💡 Pourquoi cette étape n'est pas négociable
Le contre-examen typique de la défense commence ainsi : « Pouvez-vous prouver que l'image que vous avez analysée est exactement celle que vous avez saisie ? » Sans hash recalculé et tracé à chaque ouverture, la réponse est non — et l'art. 141 al. 2 CPP devient une menace concrète. Voir Hash & intégrité pour le détail des algorithmes et des outils, et Méthodologie DFIR pour les 5 questions du magistrat (Manuel CAS-IN ch. 29.6).
② Étape 1 — Identifier le système avant de l'examiner
Sans ces 5 informations, toute timeline est inexploitable et tout artefact est interprétable de travers.

OS · version · build Détermine les artefacts disponibles (AmCache ≥ Win8, ETL ≥ Win10) et les outils compatibles SYSTEM\CurrentControlSet\Control\Windows · SOFTWARE\Microsoft\Windows NT\CurrentVersion Linux : /etc/os-release · /proc/version

macOS : systemsetup -gettimezone
Utilisateurs et SIDs Attribution des actions · profils à examiner · comptes locaux vs domaine vs Microsoft Account SAM hive · SOFTWARE\Microsoft\Windows NT\CurrentVersion\ProfileList Linux : /etc/passwd · /etc/shadow
macOS : dscl . -list /Users · /private/var/db/dslocal/nodes/Default/users/
Date dernière utilisation Cadrer la fenêtre temporelle utile · détecter une éventuelle altération post-saisie Event Log System.evtx Event ID 6005/6006/6008 · NTUSER.DAT lastWrite Linux : last · lastlog · journalctl --since
macOS : last · unified logs
Configuration réseau Interfaces · DHCP leases · WiFi historique · proxy → corrélation avec logs externes SYSTEM\CurrentControlSet\Services\Tcpip\Parameters · SOFTWARE\Microsoft\WlanSvc Linux : /var/log/syslog · NetworkManager logs
macOS : /Library/Preferences/SystemConfiguration/
⏰ La timezone est la source d'erreur n°1
Un timestamp 2024-08-15 14:32:11 dans un Event Log Windows est en heure locale du système, mais celui d'un fichier MFT est en UTC. Sans correction, une chronologie peut se retrouver décalée de plusieurs heures et faire passer un suspect pour innocent (ou l'inverse). Note systématiquement la TZ du système et la TZ de chaque artefact.
③ Étape 2 — Triage rapide : 30 minutes au lieu de plusieurs heures
Plutôt que d'attendre la fin de l'indexation Autopsy (souvent 12-48h), on extrait d'abord les artefacts à forte valeur. Fiche dédiée : KAPE / Velociraptor.
OutilOS cibleApprocheSortie typique
KAPE (Kroll Artifact Parser and Extractor) Windows (image montée ou live) Targets (collecte) + Modules (parsing) · !SANS_Triage est le point de départ standard MFT · Registry hives · Event Logs · Prefetch · LNK · Jump Lists · Browser history · USN Journal
Velociraptor Cross-OS (Win / Linux / macOS) Offline Collector (binaire autonome) avec hunts VQL prédéfinis · sortie en .zip ou Elastic Artefacts orientés endpoint detection · timelines · IoC hunts
CyLR Cross-OS Outil ligne de commande ultra-léger · idéal pour Linux/macOS où KAPE ne va pas Logs · bash history · cron · systemd · /tmp · /var/log
AChoir Windows (live) Script free de collecte live · alternative open-source à KAPE Memory · registry · event logs · browsers · network state
Exemple — Triage Windows avec KAPE
# Image montée en lettre F:
kape.exe --tsource F: --tdest C:\Triage --tflush ^
         --target !SANS_Triage --vhdx Triage ^
         --mdest C:\Triage_Parsed --module !EZParser

# Résultat : tous les artefacts SANS triage extraits + parsés au format CSV
# Temps moyen : 15-30 minutes (vs 12h+ pour une analyse Autopsy complète)
Exemple — Triage Linux avec CyLR
# Sur image montée en /mnt/evidence (read-only)
cylr -od /tmp/cylr_output -of evidence_$(date +%F).zip \
     -id evidence-001 -i /mnt/evidence

# Collecte : /var/log · /etc · /home/*/.bash_history · /etc/cron* · systemd timers · ssh
④ Étape 3 — Construire la timeline maître
La timeline est la colonne vertébrale de toute investigation. Fiche dédiée : Timeline forensique.
🛠 Outils standards
  • log2timeline / Plaso (open-source · cross-OS) : extrait événements de 200+ types de sources → fichier .plaso
  • psort (Plaso suite) : filtre/exporte le .plaso en CSV, JSON, ELK
  • Timesketch (visualisation web) ou Timeline Explorer d'Eric Zimmerman (Windows)
  • MFTECmd + Timeline Explorer pour une timeline NTFS pure (rapide, ciblée)
⚠ Les pièges des timestamps
  • MACB : Modified · Accessed · Changed · Born — chaque événement modifie 1 à 4 timestamps
  • $SI vs $FN : NTFS stocke 2 jeux de timestamps. $STANDARD_INFORMATION est modifiable par l'utilisateur (timestomping), $FILE_NAME ne l'est que par le système
  • Last Access désactivé par défaut sur Windows 7+ (NtfsDisableLastAccessUpdate) → ne pas tirer de conclusion de l'absence d'accès
  • FAT/exFAT n'a pas de timezone embarquée — interprétation locale par défaut
Pipeline timeline complet — Plaso
# 1. Extraction
log2timeline.py --storage_file evidence.plaso /mnt/image_ro

# 2. Filtrage par fenêtre temporelle (24h autour d'un événement)
psort.py -o l2tcsv -w timeline_window.csv evidence.plaso \
         "date > '2024-08-14 00:00:00' AND date < '2024-08-16 00:00:00'"

# 3. Filtrage par source (Event Logs Security uniquement)
psort.py -o l2tcsv -w security_events.csv evidence.plaso \
         "source contains 'WinEvtX' AND log_source contains 'Security'"
⑤ Étape 4 — Cibler selon l'hypothèse — Windows
Les 8 grandes questions de l'enquête forensique Windows et leurs artefacts associés. Détail complet dans Poster artefacts Windows.
⚡ 1. Qu'a été exécuté ?

Prefetch (C:\Windows\Prefetch\*.pf) · AmCache (Amcache.hve) · ShimCache (SYSTEM\AppCompatCache) · UserAssist (NTUSER\Software\Microsoft\Windows\CurrentVersion\Explorer\UserAssist) · BAM/DAM (Background Activity Moderator)

📂 2. Qu'a été ouvert ?

LNK files (%AppData%\Roaming\Microsoft\Windows\Recent) · Jump Lists (...\AutomaticDestinations + ...\CustomDestinations) · RecentDocs (NTUSER) · OpenSavePidlMRU · Office MRU

🗑️ 3. Qu'a été supprimé ?

Recycle Bin ($Recycle.Bin\$I* + $R*) · USN Journal ($Extend\$UsnJrnl:$J) · $LogFile · VSS (Shadow Copies — souvent négligées, parfois vitales)

📥 4. D'où vient ce fichier ?

Zone.Identifier ADS (Mark-of-the-Web) · Browser downloads DB (détail) · Outlook/Thunderbird · SMB shares mounted

🔌 5. Quel USB a été branché ?

USBSTOR (SYSTEM\CurrentControlSet\Enum\USBSTOR) · setupapi.dev.log · EMDMgmt · MountedDevices · Event Log Microsoft-Windows-Partition

🌐 6. Quelle activité web ?

Chrome/Edge : History, Cookies, Login Data · Firefox : places.sqlite · IE/Edge legacy : WebCacheV01.dat · Cache · Form History (voir Browser forensique)

👤 7. Qui s'est connecté ?

Event Log Security.evtx : 4624 (logon) · 4625 (failed) · 4634 (logoff) · 4672 (privilèges) · 4720 (compte créé) · Logon types 2/3/10 (interactive, network, RDP)

📡 8. Quelle activité réseau ?

Event Log Microsoft-Windows-DNS-Client · SRUM (Network Data Usage) · WLAN profiles · ARP cache historique (rare) · corrélation avec logs FW/proxy externes

📚 Tout est dans le Registre — ou presque
Cinq hives à parser systématiquement : SYSTEM, SOFTWARE, SAM, SECURITY, NTUSER.DAT (un par user) et UsrClass.dat. Outils : Registry Explorer (Zimmerman) · RegRipper · Autopsy Registry Module. Voir Registre Windows et Forensique Registre avancée pour les hives transactionnelles (LOG1/LOG2) et la récupération de clés supprimées.
⑤ Étape 4bis — Cibler selon l'hypothèse — Linux & macOS
Les artefacts changent radicalement hors Windows. Fiches détaillées : Linux forensique et Commandes Linux forensique.
🐧 Linux — Premiers regards
  • Logs système : /var/log/syslog, auth.log, kern.log, journalctl --since
  • Historique shell : ~/.bash_history, ~/.zsh_history, ~/.python_history (attention : HISTFILE=/dev/null = effacement volontaire)
  • Persistance : /etc/cron*, /etc/systemd/system/*.service, ~/.config/systemd/user/, ~/.bashrc, /etc/rc.local
  • SSH : ~/.ssh/known_hosts, authorized_keys, config, /var/log/auth.log
  • Connexions : last, lastlog, wtmp, btmp, utmp
  • Network : /etc/resolv.conf, NetworkManager logs, iptables-save, nftables list
  • Fichiers cachés : ~/.local/share/, ~/.cache/, /tmp, /var/tmp
🍎 macOS — Premiers regards
  • Unified Logs : log show --predicate ... --last 24h (remplace syslog depuis macOS Sierra)
  • FSEvents : /.fseventsd/ — journal de tous les changements de fichiers
  • Spotlight metadata : ~/.Spotlight-V100/ — métadonnées indexées
  • knowledgeC.db : ~/Library/Application Support/Knowledge/knowledgeC.db — apps lancées, écran allumé, position, AirDrop
  • TCC.db : ~/Library/Application Support/com.apple.TCC/TCC.db — permissions accordées (caméra, mic, Bureau, Photos…)
  • Préférences : ~/Library/Preferences/*.plist (binaires — outil plutil -p)
  • Quarantine : ~/Library/Preferences/com.apple.LaunchServices.QuarantineEventsV2 — fichiers téléchargés
  • Persistance : ~/Library/LaunchAgents/, /Library/LaunchDaemons/, login items
⑥ Étape 5 — Analyse mémoire (si dump RAM disponible)
Une RAM dumpée est de l'or pur — surtout pour les enquêtes malware ou chiffrement. Fiche dédiée : Volatility.
Volatility 3 — 8 plugins à lancer dans l'ordre
# 1. Identifier le profil (Vol3 le détecte automatiquement)
vol -f memory.raw windows.info

# 2. Processus — vue arbre + liste
vol -f memory.raw windows.pstree
vol -f memory.raw windows.pslist
vol -f memory.raw windows.psscan      # détecte processus cachés (rootkits)

# 3. Connexions réseau au moment du dump
vol -f memory.raw windows.netscan
vol -f memory.raw windows.netstat

# 4. Détection de malware courant
vol -f memory.raw windows.malfind
vol -f memory.raw windows.dlllist     # DLL injectées
vol -f memory.raw windows.cmdline     # arguments des processus

# 5. Extraction de credentials
vol -f memory.raw windows.hashdump
vol -f memory.raw windows.lsadump
vol -f memory.raw windows.cachedump   # cached domain creds
🔑 La RAM contient ce que le disque ne donnera jamais
Clés de chiffrement (FVEK BitLocker, master keys LUKS, FileVault), mots de passe en clair, sessions VPN actives, contenu déchiffré de conteneurs, processus malveillants ne touchant jamais le disque (fileless malware). Une enquête avec BitLocker actif et sans dump RAM est souvent une enquête morte. Voir aussi Cassage de mots de passe et la fiche Acquisition (RFC 3227).

❌ Pièges fréquents qui ruinent une analyse post-acquisition
⛔ Erreurs techniques
  • Travailler sur l'image originale au lieu d'une copie de travail
  • Ne pas recalculer le hash avant chaque session majeure
  • Confondre $SI (manipulable) et $FN (résistant au timestomping)
  • Ignorer la timezone du système ou des artefacts
  • Tirer une conclusion d'un artefact unique sans corrélation
  • Oublier d'examiner les Volume Shadow Copies (VSS)
  • Ne pas dumper la RAM quand la machine était allumée
  • Considérer l'absence d'artefact comme preuve d'absence d'action (Last Access désactivé par défaut)
⛔ Erreurs méthodologiques
  • Sauter directement à l'étape ⑤ sans timeline ⊕ identification système
  • Lancer Autopsy/X-Ways sur image full et attendre 24h avant d'extraire les artefacts de triage
  • Ne pas documenter chaque commande exécutée (journal d'audit)
  • Mélanger plusieurs hypothèses dans la même session sans les séparer
  • Communiquer un résultat préliminaire de triage comme conclusion d'enquête
  • Oublier de relier les artefacts au cadre légal de la saisie (mandat MP · périmètre · proportionnalité art. 197 CPP)
🧠 Testez-vous
Tu reçois une image E01 d'un poste Windows 10 d'un suspect saisi il y a 3 jours. Par où commences-tu ?Workflow · Niveau : facile
Étape ① Intégrité avant tout : (1) recalculer le SHA-256 de l'E01 avec FTK Imager ou ewfverify, (2) comparer au hash du PV d'acquisition, (3) noter dans le journal d'audit (date · heure · outil · version · résultat), (4) monter l'image en read-only via Arsenal Image Mounter ou FTK Imager. Surtout pas : ouvrir directement dans Autopsy sans avoir reverifié le hash, ni travailler sur l'E01 d'origine. Si le hash diverge → STOP et documenter — l'analyse devient nulle au sens de l'art. 141 CPP.
Tu cherches à savoir si un fichier précis a été ouvert sur la machine il y a 2 semaines. Quels artefacts Windows examines-tu en priorité ?Ciblage · Niveau : moyen
Plusieurs artefacts à corréler — jamais un seul : (1) LNK files dans %AppData%\...\Recent (lien créé à l'ouverture) · (2) Jump Lists (AutomaticDestinations) · (3) RecentDocs dans NTUSER.DAT · (4) Office MRU si fichier bureautique · (5) Shellbags pour les dossiers parents · (6) UserAssist si lancé par un raccourci · (7) Browser history si ouvert depuis un téléchargement. Attention : Last Access ($SI Accessed) est désactivé par défaut depuis Win7, donc absent ≠ jamais ouvert. Outil : LECmd + JLECmd (Zimmerman). Voir Poster artefacts Windows.
Un avocat de la défense te demande : « Comment savez-vous que ce timestamp NTFS n'a pas été falsifié ? » Que réponds-tu ?Présentation · Niveau : difficile
Réponse type : « NTFS stocke deux jeux de timestamps par fichier — l'attribut $STANDARD_INFORMATION ($SI) est modifiable par l'utilisateur ou un outil de timestomping, mais l'attribut $FILE_NAME ($FN) ne l'est qu'au niveau du système d'exploitation lors d'opérations spécifiques (création, rename, déplacement entre volumes). J'ai vérifié les deux : ils convergent (ou divergent — auquel cas je documente la divergence et la signale). De plus, j'ai corrélé ce timestamp avec d'autres artefacts indépendants : USN Journal ($Extend\$UsnJrnl:$J), les Event Logs Security.evtx, le Prefetch, le Registry UserAssist. Une falsification cohérente sur 5 artefacts est techniquement quasi-impossible à réaliser à postériori. » Toujours ramener à la corrélation multi-sources et à la reproductibilité. Voir Timeline forensique.
🎓 À retenir pour la pratique — Analyse post-acquisition

6 étapes ordonnées : Intégrité → Identification système → Triage rapide → Timeline → Ciblage hypothèse → Analyse profonde

Avant tout : recalculer SHA-256, monter en read-only, travailler sur copie, documenter au journal d'audit

5 infos système minimum : OS+version · Timezone · Users+SIDs · Date dernière utilisation · Config réseau

Triage rapide : KAPE (Windows) · Velociraptor (cross-OS) · CyLR (Linux/macOS) — 30 min vs 24 h+ d'Autopsy

Timeline maître : Plaso / log2timeline → psort → Timesketch ou Timeline Explorer · attention $SI vs $FN · TZ documentée

Windows — 8 questions : Exécuté ? Ouvert ? Supprimé ? Téléchargé ? USB ? Web ? Connecté ? Réseau ?

Linux : journalctl · ~/.bash_history · cron · systemd · auth.log · ~/.ssh/

macOS : log show · FSEvents · knowledgeC.db · TCC.db · plists · Quarantine

RAM : Volatility 3 — pstree · netscan · malfind · cmdline · hashdump

Mobile : iLEAPP (iOS) · ALEAPP (Android) — Manifest.db, knowledgeC.db, SQLite per-app

Règle d'or : jamais de conclusion sur artefact unique — corréler ≥ 3 sources indépendantes

Art. 141 CPP : intégrité non documentée = preuve potentiellement nulle
