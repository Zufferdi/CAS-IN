🏛 La PKI — Distribuer des clés publiques avec confiance
Sans PKI, comment savoir que la clé publique reçue appartient bien au serveur attendu ? La PKI (Public Key Infrastructure) résout ce problème par une chaîne de signatures : une Autorité de Certification (CA) signe des certificats qui lient une clé publique à une identité vérifiée. C'est le socle de HTTPS, S/MIME, SSH certificates, et des signatures électroniques qualifiées (ZertES en Suisse).

CT — Certificate Transparency

Depuis 2018, tous les certificats TLS publics doivent être loggués dans des logs CT publics et append-only. Permet de détecter les certificats frauduleux émis pour un domaine.

Forensiquement : crt.sh permet de retrouver tous les certificats historiques émis pour un domaine — y compris des sous-domaines cachés.

curl -s "https://crt.sh/?q=entreprise.ch&output=json" | jq '.[].name_value' | sort -u
📜 X.509 v3 — Structure d'un certificat
X.509 v3 est le format standard de certificat numérique (RFC 5280). Il contient l'identité, la clé publique, la durée de validité, et des extensions qui précisent l'usage autorisé. Chaque champ est forensiquement exploitable.
Champs X.509 — Valeur forensique
ChampExempleValeur forensiqueFlag
Subject CN entreprise.ch Domaine ou identité prétendue. Vérifier cohérence avec l'URL réelle. Clé
Subject Alternative Name (SAN) DNS:*.entreprise.ch, IP:1.2.3.4 Liste des domaines/IPs couverts. Extension obligatoire depuis 2017 (CN seul ignoré). Clé
Issuer DigiCert SHA2 Secure CA CA ayant signé le cert. Vérifier si CA connue/légitime ou self-signed. Clé
Serial Number 0A:1B:2C:3D:... Unique par CA. Utilisé pour la révocation CRL. Traçable dans CT logs. Clé
Not Before / Not After 2024-01-15 → 2025-01-15 Validité. Cert expiré utilisé = red flag. Durée >398j depuis 2020 = non conforme CA/B Forum. Critique
Public Key RSA 2048 / ECDSA P-256 Algorithme et taille. RSA <2048 = faible. ECDSA P-256 = moderne. ED25519 = très robuste. Critique
Key Usage / Extended Key Usage TLS Web Server Auth, Code Signing Usage autorisé. Un cert TLS utilisé pour signer du code = mauvaise pratique / compromission. Critique
Signature Algorithm sha256WithRSAEncryption MD5 ou SHA1 = vulnérable (collision attacks). SHA-256 minimum requis. Critique
CRL Distribution Points http://crl.digicert.com/... URL de la liste de révocation. Si inaccessible = fail-open dans la plupart des clients. Clé
Authority Information Access (AIA) OCSP: http://ocsp.digicert.com URL OCSP pour vérification en temps réel. Contient aussi l'URL du certificat de la CA intermédiaire. Clé
Analyser un certificat — Commandes essentielles

🔒 TLS 1.3 — Handshake et Perfect Forward Secrecy
TLS 1.3 (RFC 8446, 2018) est la version courante du protocole de transport sécurisé. Il élimine les algorithmes faibles, réduit la latence (1-RTT vs 2-RTT pour TLS 1.2), et impose le Perfect Forward Secrecy (PFS) — ce qui a des implications forensiques majeures pour l'interception légale.
TLS 1.3 Handshake — Flux étape par étape
CLIENT ←→ SERVEUR · TLS 1.3 (1-RTT)
→
Client → ClientHello Versions supportées, cipher suites, extensions, key_share (Diffie-Hellman public value) 🔍 Cipher suites → fingerprint JA3
←
Serveur → ServerHello Cipher suite choisie, key_share serveur. Tout ce qui suit est chiffré. 🔍 TLS version négociée
←
Serveur → {EncryptedExtensions} Extensions supplémentaires chiffrées (ALPN, server name) 🔒 Chiffré dès ici
←
Serveur → {Certificate} Certificat X.509 du serveur (chiffré). La chaîne complète est envoyée. 🔍 Voir avec SSLKEYLOGFILE
←
Serveur → {CertificateVerify} Signature du handshake avec la clé privée du serveur
←
Serveur → {Finished} MAC du handshake — authentification complète
→
Client → {Finished} MAC du handshake côté client. Connexion établie. ✅ Application data commence
Perfect Forward Secrecy (PFS) — L'enjeu forensique majeur
PFS — Ce que ça signifie

TLS 1.3 utilise exclusivement des échanges de clés éphémères (ECDHE, DHE). Une nouvelle clé de session est générée pour chaque connexion et jamais stockée. Même si on capture la clé privée du serveur après coup, on ne peut pas déchiffrer les sessions passées.

Impact forensique : l'interception légale (wiretapping) de sessions TLS 1.3 capturées avant l'investigation est impossible sans la clé de session au moment de la capture.

Solutions pour déchiffrer TLS forensiquement
  • SSLKEYLOGFILE — variable d'environnement Firefox/Chrome qui logue les clés de session. Si le poste était sous monitoring → déchiffrement possible dans Wireshark.
  • Proxy MITM légal — inspection TLS sur le périmètre réseau avec certificat racine installé (préalablement autorisé).
  • RAM dump — clés de session parfois encore en mémoire. Volatility + extraction de clés TLS.
  • Application logs — le contenu applicatif peut être dans les logs même si le transport est chiffré.
SSLKEYLOGFILE=/tmp/keys.log firefox & # Capturer les clés
ECH — Encrypted Client Hello (2024+)

TLS 1.3 laisse encore le SNI (Server Name Indication) en clair dans le ClientHello — un observateur réseau voit le domaine visité même si le contenu est chiffré. ECH (RFC en cours de standardisation) chiffre également le SNI à l'aide d'une clé publique publiée en DNS. Déploiement progressif depuis 2024 (Cloudflare, Firefox). Impact forensique : la corrélation trafic ↔ domaine devient impossible sans accès DNS.

# Dans Wireshark : Edit → Preferences → TLS → (Pre)-Master-Secret log
JA3 — Fingerprinting TLS sans déchiffrement
JA3 — Identifier un client TLS par son ClientHello

Le ClientHello est en clair même dans TLS 1.3. JA3 calcule un hash MD5 à partir des cipher suites, extensions, courbes elliptiques proposées — créant un fingerprint unique du client TLS sans déchiffrer.

Utilisation forensique : identifier un malware par son fingerprint JA3 (même s'il utilise TLS), détecter des outils comme Metasploit ou Cobalt Strike par leur signature TLS, ou identifier un navigateur/version spécifique.

tshark -r capture.pcap -Y tls.handshake.type==1 -T fields -e tls.handshake.ciphersuite # JA3 dans Zeek zeek-cut ja3 ja3s src_ip < ssl.log | sort | uniq -c | sort -rn | head
Certificate Pinning — Le frein au MITM légal
⚠️ Pinning — Pourquoi le proxy d'inspection échoue sur l'app bancaire

Le pinning intègre l'empreinte du certificat (ou de la clé publique) directement dans l'application. L'app refuse tout certificat différent, même s'il est signé par une CA valide. Un proxy MITM légal avec certificat racine installé sera rejeté par l'app. Solutions : bypass via Frida (hook SSL), désassembler l'APK, ou saisir le device physiquement et dumper la RAM.

❌ Révocation — Invalider un certificat avant son expiration
Un certificat doit être révoqué si sa clé privée est compromise, si l'entité n'est plus autorisée, ou si le certificat a été émis par erreur. Deux mécanismes coexistent : CRL (liste téléchargeable) et OCSP (vérification en temps réel). Leurs limites sont forensiquement importantes.
CRL — Certificate Revocation List
Liste signée par la CA de tous les certificats révoqués avec leur numéro de série et raison. Téléchargée périodiquement (toutes les 24h–7j selon la CA). Peut peser plusieurs MB pour les grandes CAs.
⚠️ Délai entre révocation et mise à jour = fenêtre de vulnérabilité
openssl crl -in crl.der -inform DER -text -noout openssl crl -in crl.pem -text | grep -A2 "Serial"
OCSP — Online Certificate Status Protocol
Vérification en temps réel du statut d'un certificat via requête HTTP vers le serveur OCSP de la CA. Réponse : Good, Revoked, ou Unknown. Problème de vie privée (la CA sait quels certificats vous visitez).
⚡ OCSP Stapling : le serveur intègre la réponse OCSP dans le handshake TLS
openssl ocsp -issuer chain.pem -cert cert.pem -url http://ocsp.ca.com -resp_text echo QUIT | openssl s_client -connect site.ch:443 -status 2>&1 | grep -A10 "OCSP"
OCSP Must-Staple
Extension X.509 qui oblige le serveur à fournir une réponse OCSP valide dans le handshake. Si absent → navigateur refuse la connexion (fail-closed). Renforce la révocation mais complique la forensique réseau.
Extension: 1.3.6.1.5.5.7.1.24 dans le certificat
openssl x509 -in cert.pem -text | grep -A5 "TLS Feature"

S/MIME — Pièges (terrain) & forensique
📧 S/MIME — Concepts clés
  • Signature = chiffrer le hash du message avec sa clé privée
  • Chiffrement = chiffrer le message avec la clé publique du destinataire
  • Signature valide ≠ identité personne physique (la clé peut être volée)
  • Signature qualifiée ZertES = équivalent juridique de la signature manuscrite (Art. 14 CO)
  • Providers CH : SwissSign, QuoVadis, SwissID, Swisscom
🔍 S/MIME forensique
  • Emails S/MIME signés = preuve d'intégrité du message + horodatage
  • Extraction du certificat depuis l'email (.p7s) → identifier l'expéditeur
  • Vérifier la chaîne de confiance du certificat de signature
  • Signature valide mais CA inconnue = red flag (certificat autosigné)
openssl smime -verify -in email.eml -CAfile chain.pem openssl pkcs7 -in signature.p7s -inform DER -print_certs -noout
🔍 PKI Forensique — Cas pratiques et outils
Les certificats X.509 laissent des traces dans les navigateurs, les logs réseau, les stores OS, et les logs applicatifs. Leur analyse permet d'identifier des MITM, des malwares utilisant TLS, des infrastructures C2, et des certificats frauduleux.
Scénarios forensiques PKI
🎯 Scénario 1 — MITM détecté via anomalie de certificat
Un utilisateur signale que son navigateur a montré une alerte certificat sur le site de sa banque. Vous suspectez un proxy d'interception ou un malware.

Investigation : Récupérer le certificat présenté au navigateur (openssl s_client -connect banque.ch:443), comparer le Subject, l'Issuer, et le fingerprint SHA-256 avec le certificat légitime visible depuis un autre réseau. Vérifier dans le store de certificats Windows (certmgr.msc) si une CA douteuse a été installée. Analyser le cache DNS pour un éventuel hijacking.
🎯 Scénario 2 — C2 malware identifié via JA3 / certificat auto-signé
Le SIEM alerte sur des connexions TLS sortantes vers une IP inconnue depuis un poste Windows. Le certificat est auto-signé avec un CN aléatoire.

Investigation : Extraire le certificat depuis Zeek (x509.log) ou via tshark. Calculer le JA3 pour identifier l'outil (Metasploit = JA3 769,47-53-5...). Vérifier sur VirusTotal l'IP et le fingerprint du certificat. Corréler avec Sysmon EID 3 pour identifier le processus source.
🎯 Scénario 3 — Certificat de signature de code compromis
Un binaire suspect est signé numériquement avec un certificat valide d'une entreprise légitime.

Investigation : Extraire le certificat de signature (signtool verify /v binaire.exe ou osslsigncode verify), vérifier la date de signature vs la date de révocation du certificat, chercher le serial dans les CRL, vérifier sur crt.sh si le certificat apparaît dans les CT logs avec l'historique attendu.

💊 Q1 — Pourquoi TLS 1.3 avec PFS rend-il difficile le déchiffrement rétrospectif des sessions capturées ?
✓ TLS 1.3 impose le Perfect Forward Secrecy en utilisant exclusivement des échanges de clés éphémères (ECDHE). Une clé de session unique est générée pour chaque connexion et immédiatement détruite après la session. Même si on obtient la clé privée du serveur après coup, on ne peut pas recalculer les clés de session passées. Pour déchiffrer rétrospectivement, il faut avoir capturé les clés au moment de la session : via SSLKEYLOGFILE, un proxy MITM préinstallé, ou un dump RAM contemporain.
💊 Q2 — Qu'est-ce que le JA3 fingerprint et comment est-il utile en forensique réseau ?
✓ JA3 est un hash MD5 calculé à partir des paramètres du ClientHello TLS — cipher suites proposées, extensions, courbes elliptiques — qui sont en clair même dans TLS 1.3. Ce fingerprint identifie uniquement un client/outil TLS indépendamment du contenu chiffré. Utilité forensique : identifier un malware par son JA3 (Metasploit, Cobalt Strike ont des signatures connues), détecter des outils d'attaque même si tout le contenu est chiffré, identifier la version d'un navigateur ou d'un SDK.
💊 Q3 — Une CA racine inconnue est présente dans LocalMachine\Root d'un poste Windows. Quelles sont les implications forensiques ?
✓ C'est un IOC critique — cette CA racine inconnue peut signer des certificats TLS arbitraires qui seront acceptés par le navigateur sans alerte. Cela permet un MITM transparent sur tout le trafic HTTPS du poste. Causes possibles : (1) malware installant sa propre CA pour inspecter/modifier le trafic ; (2) proxy d'entreprise non documenté (Forcepoint, BlueCoat) ; (3) intrusion pour intercepter les sessions bancaires/email. Investigation : noter le Subject et Thumbprint, vérifier dans les Event Logs l'ajout du certificat (EID 1796), croiser avec les dates d'infection suspectées.
💊 Q4 — Quelle est la différence entre CRL et OCSP, et pourquoi le comportement "fail-open" est-il forensiquement important ?
✓ CRL = liste téléchargeable de tous les certificats révoqués, mise à jour toutes les 24h-7j — délai de propagation important. OCSP = vérification en temps réel via requête HTTP. Le comportement fail-open signifie que si le serveur CRL/OCSP est inaccessible, la plupart des clients acceptent quand même le certificat (pour ne pas bloquer les utilisateurs). Un attaquant peut exploiter ceci : révoquer la capacité à joindre le serveur OCSP (firewall, DDoS) pour utiliser un certificat révoqué. OCSP Must-Staple (fail-closed) résout ce problème mais reste peu déployé.
💊 Q5 — Qu'est-ce que la Certificate Transparency (CT) et comment l'utiliser en investigation OSINT ?
✓ La Certificate Transparency oblige depuis 2018 toutes les CAs publiques à enregistrer chaque certificat émis dans des logs publics, append-only et auditables. Forensiquement : (1) crt.sh permet de retrouver tous les certificats historiques émis pour un domaine, y compris des sous-domaines cachés utilisés pour du C2 ou de l'infrastructure d'attaque ; (2) détecter des certificats frauduleux émis pour un domaine dont on est propriétaire ; (3) reconstituer l'infrastructure d'un attaquant en pivotant sur les noms dans les SAN. Commande : curl -s "https://crt.sh/?q=%.domaine.ch&output=json" | jq '.[].name_value' | sort -u
