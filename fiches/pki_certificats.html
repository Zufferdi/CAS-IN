Chaîne de certification PKI
🏛 Root CA
Autorité de certification racine — auto-signée, stockée hors ligne (air-gap). Signe uniquement les CA intermédiaires. Compromission = invalidation de toute la PKI.
Ex: DigiCert Global Root CA, SwissSign Gold CA
↓ signe
🏢 Intermediate CA
CA intermédiaire — opérationnelle (en ligne), signe les certificats end-entity. Permet la révocation sans toucher à la Root CA. Une PKI peut avoir plusieurs niveaux d'intermédiaires.
Ex: DigiCert SHA2 Secure Server CA
↓ signe
📄 End-Entity
Certificat final — serveur TLS, utilisateur S/MIME, code signing. Contient la clé publique du sujet + identité vérifiée par la CA. Durée ≤ 398 jours (depuis 2020).
Ex: *.example.com (SAN wildcard)
Certificat X.509 v3 — champs clés forensiques
SubjectCN, O, C — identité du titulaire
IssuerCA qui a signé → chaîne de confiance
Serial NumberUnique par CA → utilisé pour CRL/OCSP
SANSubject Alternative Names → vrais domaines couverts
ValidityNot Before / Not After → durée de validité
Key UsagedigitalSignature, keyEncipherment, etc.
Certificat auto-signé — red flag forensique
  • Émis par soi-même (Issuer = Subject)
  • Aucune CA de confiance dans la chaîne
  • Légitime : développement local, intranet d'entreprise non exposé
  • Suspect : serveur HTTPS public, C2 de malware, MITM proxy
  • Certificat .p12/.pfx = contient clé privée + certificat → très sensible
  • En forensique : rechercher *.p12, *.pfx, *.pem avec clé privée non chiffrée
# Inspecter un certificat serveur en live
openssl s_client -connect suspect.ch:443 -showcerts 2>/dev/null | openssl x509 -noout -text

# Extraire tous les certificats d'un fichier PCAP (Wireshark / tshark)
tshark -r capture.pcap -Y "ssl.handshake.type == 11" -T fields -e x509sat.uTF8String
TLS 1.3 — Handshake forensique
1
Client Hello — SNI (Server Name Indication) en clair, cipher suites, version TLS, random 32 bytes. Forensique : SNI révèle le domaine même si le trafic est chiffré.
2
Server Hello + Certificate — serveur envoie son certificat. Clé publique utilisée pour l'échange de clé (ECDHE). La chaîne complète est transmise.
3
Client Finished — vérification de la chaîne de certification. Si CA inconnue ou certificat expiré/révoqué → alerte. Certificate pinning bloque ici.
4
Application Data — trafic chiffré (AEAD : AES-GCM ou ChaCha20-Poly1305). Sans clé de session ou SSLKEYLOGFILE, trafic illisible.
Certificate Pinning — impact forensique
  • L'app accepte uniquement son certificat hard-codé
  • Bloque les proxies MITM légaux (Charles, Burp Suite, mitmproxy)
  • Utilisé par : banques, WhatsApp, Signal, apps financières
  • Bypass : Frida (hook SSL_verify), apktool + patch, Magisk TrustUserCerts
  • Forensique mobile : impossible d'intercepter sans bypass → analyse statique du APK/IPA
Déchiffrement TLS forensique
  • SSLKEYLOGFILE — variable d'env. Chrome/Firefox exporte les clés de session → Wireshark peut déchiffrer
  • Clé privée du serveur — uniquement pour RSA (pas ECDHE/PFS)
  • PFS (Perfect Forward Secrecy) — ECDHE génère une clé de session éphémère, irrecupérable a posteriori même avec la clé privée
  • TLS 1.3 impose ECDHE → PFS obligatoire → sans SSLKEYLOGFILE, trafic TLS 1.3 est opaque
Révocation — CRL vs OCSP
CRL — Certificate Revocation List
  • Fichier signé par la CA listant tous les serials révoqués
  • Publié à intervalle régulier (24h–7j)
  • Problème : délai entre révocation et mise à jour + fichier volumineux
  • Forensique : vérifier si un certificat était révoqué au moment des faits
  • openssl crl -in crl.pem -text -noout
OCSP — Online Certificate Status Protocol
  • Requête temps réel à l'OCSP responder de la CA → statut good / revoked / unknown
  • OCSP Stapling : le serveur inclut la réponse OCSP signée dans le handshake TLS (meilleure perf + vie privée)
  • OCSP Must-Staple : extension forçant l'utilisation du stapling
  • openssl ocsp -issuer inter.pem -cert end.pem -url [OCSP URL]
S/MIME — Signature et chiffrement email
S/MIME — deux opérations distinctes
  • Signature : expéditeur chiffre le hash avec sa clé privée → prouve l'identité + intégrité
  • Chiffrement : expéditeur chiffre le message avec la clé publique du destinataire → seul le destinataire peut lire
  • Piège examen : une signature S/MIME valide prouve qu'une clé privée a signé, pas qu'une personne physique spécifique a envoyé (vol de clé possible)
  • Art. 269 CPP → surveillance TLC autorisée pour infractions graves

VeraCrypt — forensique et chiffrement plausible
Déni plausible (Plausible Deniability)
  • Un volume VeraCrypt peut contenir deux volumes cachés dans le même fichier
  • Mot de passe A → volume externe (contenu "innocent")
  • Mot de passe B → volume caché (vrai contenu)
  • Impossible de prouver l'existence du volume caché cryptographiquement
  • Art. 113 CPP : nemo tenetur — pas d'obligation de fournir son mot de passe
  • Forensique : chercher l'entropie du conteneur + traces d'utilisation dans les artefacts Windows
Entropie de Shannon — identifier le chiffrement

Entropie H = −∑ pᵢ log₂(pᵢ), max = 8 bits/octet

Fichier texte (~1 bit/octet)
1.2
ZIP compressé (~7.5 bits/octet)
7.5
Volume VeraCrypt / fichier AES (≈8 bits/octet)
7.99

Entropie ≥ 7.9 → chiffrement ou compression. X-Ways affiche la colonne Entropie + attribut e (chiffrement avéré) / e? (probable).

💡 Différencier chiffrement et compression : les deux donnent une entropie proche de 8. Vérifiez la signature (magic bytes) : un ZIP commence par PK\x03\x04, un conteneur VeraCrypt n'a aucun header reconnaissable — 512 premiers octets aléatoires.
Erreurs fréquentes à l'examen
❌ Confondre chiffrer et signer — On chiffre avec la clé publique du destinataire. On signe avec sa propre clé privée. L'opération inverse dans les deux cas.
❌ Croire que signature = identité de la personne — La signature prouve qu'une clé privée a signé. Si la clé a été volée ou compromise, la signature ne prouve rien sur la personne physique.
❌ TLS 1.3 + clé privée = déchiffrement possible — Faux avec ECDHE (PFS). La clé privée du serveur ne permet pas de déchiffrer les sessions passées sous TLS 1.3.
❌ Confondre CRL et OCSP — CRL = liste complète téléchargée, OCSP = requête unitaire temps réel. OCSP Stapling = serveur inclut la réponse dans le handshake.
✅ VeraCrypt fermé → aucune preuve cryptographique possible. L'enquêteur peut seulement montrer : traces d'utilisation dans les artefacts (LNK, Recent, NTUSER.DAT), présence du logiciel, historique de montage dans le registre (HKCU\Software\VeraCrypt\), mais pas le contenu.
❌ Ignorer le Certificate Pinning — Expliquer pourquoi l'interception TLS échoue sur une app mobile est un sujet d'examen récurrent. Réponse : pinning + comment le contourner (Frida).
