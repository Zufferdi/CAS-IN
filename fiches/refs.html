ReFS — Resilient File System

Windows Server 2012+ · Object Table B+ Tree · Pas de $MFT · Checksums SHA-256 · Storage Spaces · Hyper-V
Prérequis : 📖 NTFS 📖 Encodage 📖 Comparaison FS
Pratiquer : 🧪 📐 Calcul d'offset
Voir aussi : 🔗 NTFS 🔗 VM Forensique 🔗 Windows Forensique 🔗 Data Carving

"ReFS was designed for large-scale storage infrastructure. Forensically, its lack of $MFT and sparse tool support means investigators often miss critical artefacts."

— DFIR.training · ReFS Forensics 2023

🔑 Pourquoi ReFS existe et où le rencontrer
ReFS (Resilient File System) a été introduit avec Windows Server 2012 pour répondre aux besoins des datacenters : intégrité des données à grande échelle, résilience aux corruptions hardware, volumes massifs. Il n'est pas conçu pour remplacer NTFS sur les postes de travail — il cible les serveurs, le stockage NAS/SAN, les clusters Hyper-V, et les espaces de stockage Windows (Storage Spaces).

En forensique, le rencontrer signifie presque toujours : infrastructure d'entreprise, serveur de fichiers, NAS Windows, ou stockage de machines virtuelles Hyper-V.
Où rencontrer ReFS en investigation
Contextes typiques
  • Windows Server 2012 / 2016 / 2019 / 2022 — volumes de données
  • Storage Spaces — pools de disques avec parité ou miroir
  • Hyper-V — recommandé par Microsoft pour les VHDX
  • Windows Server Backup — destination de sauvegarde native
  • Scale-Out File Server (SOFS) — clusters haute disponibilité
Ce que ReFS n'est PAS
  • Absent des postes Windows 10/11 grand public (sauf Pro for Workstations)
  • Pas sur les disques de démarrage système
  • Pas sur les partitions EFI / Recovery
  • Pas sur les disques amovibles (USB, cartes SD)
  • Incompatible avec BitLocker sur Server 2012 (supporté depuis 2016)

🏗 Architecture ReFS — Tout est B+ Tree
Là où NTFS organise ses métadonnées dans une table plate ($MFT), ReFS utilise des arbres B+ imbriqués pour tout : répertoires, fichiers, identifiants, checksums. Cette architecture garantit l'intégrité mais rend la récupération forensique radicalement plus difficile.

Composants principaux détaillés
Superblock (offset 0x00)

Première structure lisible. Contient la signature ReFS, la version (1.x ou 3.x), la taille de page (4KB par défaut), le GUID du volume, et un checksum de l'ensemble. Offset 0 → 0x200 (512 octets). Forensiquement : identification rapide du volume.

52 65 46 53 Signature "ReFS"
01 00 00 00 Version majeure
Object Table (B+ Tree racine)

Remplace la $MFT. Chaque fichier/répertoire = un Object ID 64-bit qui pointe vers un sous-arbre B+. La suppression d'un fichier supprime son entrée dans l'arbre — immédiatement et sans résidu, contrairement à NTFS. Pas de "slack space" dans les nœuds d'arbre exploitable.

Schema Table

Définit la structure des attributs pour chaque type d'objet (fichier, répertoire, lien, etc.). En pratique invisible pour l'investigateur — mais cruciale pour les parsers qui doivent comprendre la structure avant de la lire.

Journal de transactions

ReFS maintient un journal write-ahead pour garantir la cohérence. Les transactions non commitées peuvent rester dans le journal après un crash. Source potentielle d'artefacts si le journal n'a pas été rejoué (recovery incomplète).

Versioning ReFS — Impact forensique
VersionOS hôteNouveautésImpact forensique

💡 Identifier la version : fsutil fsinfo refsinfo X: sous Windows, ou lire l'offset 0x08 du Superblock (Major version).
🌳 L'Object Table — Le cœur forensique de ReFS
Comprendre l'Object Table est essentiel pour saisir pourquoi la récupération de fichiers supprimés est quasi impossible sur ReFS. Contrairement à la $MFT de NTFS (table plate avec marquage), le B+ Tree de ReFS se réorganise activement à chaque suppression.

Pourquoi NTFS permet la récupération et pas ReFS
NTFS — Suppression
  • Entrée $MFT marquée comme libre (0xE5 dans le nom)
  • Attributs $FILE_NAME, $DATA toujours présents
  • Run list intacte → clusters connus
  • MFTECmd / Autopsy peuvent lire l'entrée résiduelle
  • Récupération possible tant que les clusters ne sont pas réalloués
ReFS — Suppression
  • Entrée retirée du B+ Tree immédiatement
  • Arbre rééquilibré — pas de "trou" exploitable
  • Object ID libéré et réutilisable
  • Clusters marqués libres dans l'allocation map
  • Aucune trace dans les métadonnées FS
Checksums par page — Mécanisme d'intégrité

Chaque page de données (4KB par défaut) dans ReFS est accompagnée d'un checksum 64-bit stocké séparément dans les métadonnées. Lors d'une lecture, le FS recalcule le checksum et le compare — toute divergence déclenche une réparation automatique (si Storage Spaces avec miroir) ou une alerte.

$UsnJrnl sur ReFS — Ce qu'on peut en tirer
📊 USN Journal — Artefact exploitable
ReFS maintient un $UsnJrnl (Update Sequence Number Journal) similaire à NTFS. Il enregistre les opérations sur les fichiers (création, modification, suppression, renommage) avec horodatage. La structure est légèrement différente de NTFS mais lisible par certains outils (MFTECmd en mode USN, Log2Timeline).

Ce qu'on y trouve : nom du fichier, type d'opération (USN_REASON_*), timestamp FILETIME, Object ID parent. C'est souvent la seule trace d'un fichier supprimé sur ReFS. fsutil usn readjournal X: csv > usn_refs.csv

Identifier un volume ReFS — Checklist rapide
1
Signature Superblock : 52 65 46 53 à l'offset 0x00 du volume. Si absent → pas ReFS.
2
Via Windows live : fsutil fsinfo refsinfo X: — retourne version, taille de page, features.
3
Via X-Ways : File System Info dans le panneau Volume — affiche "ReFS" si reconnu, avec version.
4
Via FTK Imager : Properties du volume → File System = ReFS. Montage possible pour navigation.
🔍 Protocole d'investigation ReFS — Ordre des opérations
La résilience de ReFS est son atout principal — et son défaut forensique majeur. Le protocole doit être adapté : VSS en premier, $UsnJrnl en second, carving en dernier recours.
Étapes d'investigation — Flux recommandé
1
Acquisition — Image bit-à-bit du volume ReFS
FTK Imager, dcfldd, ou X-Ways (avec write-blocker). Format E01 recommandé pour les métadonnées d'acquisition. Hasher avant et après. Sur Storage Spaces : imager chaque disque physique séparément puis reconstruire le pool logiquement.
FTK Imager → Add Evidence Item → Physical/Logical Drive → Format E01
2
Volume Shadow Copy — Première source à exploiter
VSS fonctionne sur ReFS. C'est souvent la seule façon de retrouver des fichiers supprimés. Lister toutes les shadows disponibles, les monter et les comparer au volume actuel.
vssadmin list shadows /for=X: mklink /D C:\shadow \\?\GLOBALROOT\Device\HarddiskVolumeShadowCopy1\ ShadowExplorer.exe # GUI alternative
3
$UsnJrnl — Journal des opérations fichiers
Extraire et parser l'USN Journal. Sur ReFS, le journal est présent mais la structure diffère de NTFS. Les entrées contiennent nom, type d'opération, timestamp, et Object ID. Traces de suppression récentes visibles ici.
fsutil usn readjournal X: csv > usn_refs.csv MFTECmd.exe -f "$UsnJrnl" --csv output\ # Zimmerman — support partiel ReFS
4
Event Logs Windows — Corrélation système
Les événements système Windows tracent les accès, erreurs ReFS, et opérations VSS. Corrélation avec les timestamps du $UsnJrnl pour reconstituer une timeline.
Get-WinEvent -LogName System | Where-Object {$_.ProviderName -like "*ReFS*"} EvtxECmd.exe -f System.evtx --csv output\
5
Carving sur espace non alloué
En dernier recours : carver l'espace non alloué pour les types de fichiers ciblés. Rendement faible car le B+ Tree libère les clusters immédiatement, mais possible si la suppression est récente et les clusters non réalloués.
photorec image_refs.E01 # Extraire l'espace non alloué d'abord mmls image_refs.E01 && blkls -A image_refs.E01 > unalloc.raw
!
BitLocker — Vérifier avant tout sur ReFS 2.x+
Depuis Server 2016, ReFS supporte BitLocker. Si le volume est chiffré, toute analyse FS est impossible sans la clé de récupération. Identifier le chiffrement dès l'acquisition.
manage-bde -status X: # Vérifier chiffrement manage-bde -unlock X: -RecoveryPassword XXXXXX-... # Déverrouiller
Scénarios forensiques ReFS
🖥️ Scénario 1 — Serveur Hyper-V compromis
Un attaquant a accédé à un serveur Hyper-V avec stockage ReFS. Les VHDX des VMs sont stockés sur un volume ReFS. L'attaquant a supprimé des VMs pour effacer ses traces.

Approche : (1) Lister les VSS du volume ReFS — les snapshots Hyper-V créent souvent des shadow copies. (2) Parser le $UsnJrnl pour retrouver les suppressions de fichiers .VHDX avec timestamps. (3) Carver l'espace non alloué pour les headers VHDX (76 68 64 78 66 69 6C 65). (4) Corréler avec les Event Logs Hyper-V (ID 12100, 12104).
💾 Scénario 2 — Storage Spaces avec parité
Un NAS Windows Server utilise Storage Spaces en parité sur 5 disques physiques avec un volume ReFS. Un suspect a supprimé des données.

Enjeu : Le pool Storage Spaces est une abstraction au-dessus des disques physiques. Il faut reconstruire le pool logiquement avant d'y accéder.

Approche : Imager les 5 disques séparément. Utiliser X-Ways (support Storage Spaces) ou monter les images dans une VM Windows Server pour reconstruire le pool en lecture seule via PowerShell : Get-StoragePool. Puis appliquer le protocole standard ReFS.
⚖️ Scénario 3 — Anti-forensique via ReFS intentionnel
Un suspect a formaté un volume NTFS en ReFS avant de supprimer des fichiers — sachant que la récupération serait beaucoup plus difficile.

Enjeu juridique : L'acte de reformatage intentionnel avant suppression peut être constitutif d'entrave à l'action pénale (Art. 305 CP suisse). Documenter : (1) la date du formatage (Event Log, $UsnJrnl du nouveau volume), (2) que des données existaient avant (carving de l'espace qui était NTFS, résidus de signatures NTFS dans les zones non réécrites).
🛠 Support ReFS dans les outils DFIR — État 2025
Le support de ReFS dans les outils forensiques reste inégal. Contrairement à NTFS ou EXT4, ReFS est un FS jeune et non documenté officiellement — chaque outil a sa propre implémentation basée sur la rétro-ingénierie.
Tableau de support par outil
X-Ways Forensics Support le plus complet
Navigation du volume, extraction de fichiers actifs, parsing partiel de la structure B+ Tree. Support Storage Spaces. Récupération de fichiers supprimés très limitée (B+ Tree oblige). Référence judiciaire pour ReFS.
Open Image → File System Info → ReFS Navigator
FTK Imager / FTK Partiel
Montage du volume et navigation de la structure existante. Acquisition fiable. Pas de recovery avancée sur fichiers supprimés. FTK 7+ améliore le support.
Autopsy + TSK Expérimental
TSK (The Sleuth Kit) a un support ReFS expérimental depuis 4.x. Navigation basique possible. Recovery très limitée. Ne pas compter dessus pour une investigation sérieuse sur ReFS.
fls -r -o [offset] image.dd # TSK — support limité
Suite Zimmerman Partiel (USN)
MFTECmd : inutilisable sur l'Object Table ReFS. EvtxECmd : pleinement fonctionnel pour les Event Logs corrélés. MFTECmd en mode $UsnJrnl : support partiel du journal ReFS.
MFTECmd.exe -f "$UsnJrnl:$J" --csv C:\output\
Windows natif PowerShell Complet (live)
Sur un système Windows live, PowerShell donne accès complet au volume ReFS via le FS driver. Utile pour l'acquisition logique rapide et l'interrogation du $UsnJrnl.
Get-ChildItem -Path X:\ -Recurse -Force | Export-Csv listing.csv fsutil usn readjournal X: csv > usn.csv fsutil fsinfo refsinfo X:
ShadowExplorer VSS — Complet
GUI pour parcourir les Volume Shadow Copies — fonctionne parfaitement sur ReFS. Permet de comparer les versions antérieures, exporter des fichiers supprimés qui existaient lors d'un snapshot. Premier outil à utiliser sur ReFS.
ShadowExplorer.exe → sélectionner volume + date VSS
PhotoRec / Scalpel Carving — Partiel
Carving brut sur l'espace non alloué extrait. Efficacité réduite sur ReFS (clusters libérés rapidement) mais pas nulle. À utiliser en dernier recours sur l'image brute.
blkls -A image.E01 > unalloc.raw && photorec unalloc.raw
ReFS Parser (communauté) Recherche
Des parsers Python open-source ont été développés par la communauté DFIR (ex: github.com/horensic/ARIN). Utiles pour la recherche et le développement d'outils, mais non validés pour usage judiciaire.
python refs_parser.py --image image.dd --output out/

💊 Q1 — Pourquoi ReFS rend-il la récupération de fichiers supprimés quasi impossible, contrairement à NTFS ?
✓ ReFS utilise un B+ Tree (Object Table) dont les entrées sont retirées immédiatement lors d'une suppression — sans laisser de résidu exploitable. NTFS en revanche conserve l'entrée $MFT avec le premier octet du nom marqué 0xE5, ce qui permet de retrouver la run list et de reconstruire le fichier tant que ses clusters n'ont pas été réalloués.
💊 Q2 — Quelle est la première action à effectuer lors d'une investigation sur un volume ReFS dont des fichiers ont été supprimés ?
✓ Vérifier l'existence de Volume Shadow Copies (VSS) : vssadmin list shadows /for=X:. C'est souvent la seule source permettant de retrouver des fichiers supprimés sur ReFS. Si des shadows existent, les monter et comparer leur contenu au volume actuel avant toute autre manipulation.
💊 Q3 — Quelles 3 fonctionnalités NTFS sont absentes de ReFS ?
✓ ReFS ne supporte pas : (1) Alternate Data Streams (ADS) — pas de Zone.Identifier, pas de malware se cachant en ADS ; (2) Compression EFS — pas de chiffrement fichier natif (BitLocker possible sur le volume depuis 2016) ; (3) Noms 8.3 courts — moins d'artefacts de nommage alternatif. En revanche, ReFS apporte les checksums SHA-256 par page absents de NTFS.
💊 Q4 — Sur quels systèmes et contextes est-il probable de rencontrer ReFS lors d'une investigation ?
✓ ReFS apparaît sur : Windows Server 2012+ (volumes de données), Storage Spaces (pools de disques avec parité/miroir), volumes de stockage Hyper-V (recommandé par Microsoft pour les VHDX), destinations Windows Server Backup, et Scale-Out File Servers. Il est absent des postes grand public, disques de démarrage, et supports amovibles.
💊 Q5 — Un suspect a reformaté intentionnellement un volume NTFS en ReFS avant de supprimer des fichiers sensibles. Quels artefacts recherchez-vous et quelle infraction cela peut-il constituer ?
✓ Artefacts à rechercher : (1) Date du formatage dans les Event Logs Windows et le $UsnJrnl du nouveau volume ReFS ; (2) résidus de signatures NTFS (FILE0000, INDX) dans les zones non écrasées par le formatage ; (3) carving sur l'intégralité de l'image pour les types ciblés. Infraction potentielle : Art. 305 CP suisse (entrave à l'action pénale / destruction de preuves). Documenter l'intentionnalité (chronologie de l'investigation, date de la plainte vs date du formatage).
💊 Q6 — Quelle commande PowerShell permet d'identifier la version de ReFS et les fonctionnalités activées sur un volume X: en live ?
✓ fsutil fsinfo refsinfo X: — retourne la version ReFS (1.x / 3.x), la taille de page, et les feature flags activés (integrity streams, etc.). Compléter avec Get-Volume -DriveLetter X | Select-Object * pour les métadonnées PowerShell et manage-bde -status X: pour vérifier BitLocker.
