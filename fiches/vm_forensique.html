Snapshots — Artefact forensique clé
⚡ Un snapshot est un arrêt sur image à un instant T. Il peut capturer l'état exact au moment d'une attaque — avant que les logs aient été effacés, avant le chiffrement par un ransomware. Ne jamais supprimer un snapshot sans l'analyser.
VMware — Fichiers snapshot
  • .vmdk — disque delta du snapshot
  • .vmsn — état mémoire RAM au moment du snapshot
  • .vmsd — métadonnées des snapshots
  • .vmem — mémoire paginée → analysable avec Volatility 3
  • Chaîne de snapshots : s'emboîtent chronologiquement
Hyper-V — Fichiers checkpoint
  • .avhd / .avhdx — delta disk du checkpoint
  • .vmrs — état RAM du checkpoint
  • Dossier Snapshots\ — métadonnées XML
  • Event IDs Hyper-V : 18590 (start), 18592 (stop), 13000 (snapshot)
  • Log : Microsoft-Windows-Hyper-V-Worker/Operational
Acquisition sans démarrage — Workflow
1
Copier les fichiers VM (offline) — sur l'hôte hyperviseur, accéder directement aux fichiers VMDK/VHD. Hash avant et après copie. Ne jamais travailler sur les originaux.
2
Convertir au format RAW si nécessaire — qemu-img convert -f vmdk -O raw vm.vmdk vm.raw
3
Monter et analyser — FTK Imager ouvre directement VMDK et VHD. Autopsy via TSK. X-Ways les monte comme disques physiques.
4
Analyser le fichier mémoire — .vmem (VMware) ou .vmrs (Hyper-V) = RAM au moment du snapshot → vol.py -f vm.vmem windows.pslist
ESXi — Forensique sur hyperviseur compromis
🔴 Ransomware ciblant ESXi : Depuis 2022, ESXiArgs, Royal, BlackBasta ciblent VMware ESXi pour chiffrer toutes les VMs en une seule opération — impactant potentiellement des dizaines de serveurs en minutes.
Logs ESXi à analyser
  • /var/log/vmkernel.log
  • /var/log/hostd.log
  • /var/log/vpxa.log
  • /etc/passwd, /etc/shadow — comptes créés
  • esxcli vm process list — VMs actives
Indicateurs ESXiArgs
  • VMDK chiffrés avec extension .args / .locked
  • Fichiers VMX lisibles (pas chiffrés)
  • Compte vpxuser compromis → première cible
  • Vulnérabilité OpenSLP exploitée (CVE-2021-21985)
