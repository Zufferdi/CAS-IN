🖥️ VM Forensique — La preuve numérique encapsulée
Une machine virtuelle (VM) est un système informatique complet (RAM, disques, CPU, NIC) encapsulé dans des fichiers sur le disque de l'hôte hyperviseur. Pour le forensiste, c'est une aubaine : (1) le « disque » de la VM est un simple fichier .vmdk ou .vhdx que l'on peut copier sans débrancher de matériel, (2) un snapshot capture l'état exact du système (disque + RAM) à un instant T — preuve figée idéale, (3) le fichier .vmem (VMware) ou .vmrs (Hyper-V) contient la RAM de la VM, directement analysable avec Volatility 3 sans avoir à acquérir un dump RAM live. Conséquence pratique : la majorité des serveurs d'entreprise tournent sur VMware vSphere ou Hyper-V. Les ransomwares modernes (ESXiArgs 2022, Royal, BlackBasta) ciblent directement l'hyperviseur ESXi pour chiffrer toutes les VMs en une seule opération — impactant des dizaines de serveurs en quelques minutes. L'enquêteur DFIR moderne doit maîtriser la forensique des VMs et des hyperviseurs.

📸 Snapshots — Artefact forensique clé
⚡ Un snapshot est un arrêt sur image à un instant T. Il peut capturer l'état exact au moment d'une attaque — avant que les logs aient été effacés, avant le chiffrement par un ransomware. Ne jamais supprimer un snapshot sans l'analyser.
🟢 VMware — Fichiers snapshot
  • .vmdk — disque delta du snapshot (différence avec parent)
  • .vmsn — état mémoire RAM au moment du snapshot
  • .vmsd — métadonnées de tous les snapshots de la VM
  • .vmem — mémoire paginée → analysable avec Volatility 3
  • Chaîne de snapshots : s'emboîtent chronologiquement (parent → child → grand-child)
  • Suspended VM : .vmss (memory state file)
🔵 Hyper-V — Fichiers checkpoint
  • .avhd / .avhdx — delta disk du checkpoint
  • .vmrs — état RAM du checkpoint (Hyper-V Runtime State)
  • Dossier Snapshots\ — métadonnées XML
  • Event IDs Hyper-V : 18590 (start) · 18592 (stop) · 13000 (snapshot)
  • Log : Microsoft-Windows-Hyper-V-Worker/Operational
  • Les checkpoints production = consistant via VSS
🔧 Acquisition sans démarrage — Workflow
Procédure forensique pour copier et analyser une VM sans l'allumer ni la modifier.
1
Copier les fichiers VM (offline) — sur l'hôte hyperviseur, accéder directement aux fichiers VMDK/VHD via SSH (ESXi : /vmfs/volumes/datastore/VM/) ou SMB (Hyper-V). Hash SHA-256 avant et après copie. Ne jamais travailler sur les originaux.
2
Convertir au format RAW si nécessaire — pour utilisation avec outils forensiques classiques : qemu-img convert -f vmdk -O raw vm.vmdk vm.raw · vboxmanage clonemedium disk vm.vdi vm.raw --format RAW
3
Monter et analyser — FTK Imager ouvre directement VMDK et VHDX. Autopsy via TSK reconnaît les formats. X-Ways les monte comme disques physiques. Sur Linux : guestmount -a vm.vmdk -i --ro /mnt/vm (avec libguestfs).
4
Analyser le fichier mémoire — .vmem (VMware) ou .vmrs (Hyper-V) = RAM au moment du snapshot → vol.py -f vm.vmem windows.pslist · vol.py -f vm.vmem windows.netscan pour les connexions réseau au moment du snapshot.
5
Reconstituer la chaîne de snapshots — lire le .vmsd pour comprendre l'ordre chronologique. Chaque .vmdk delta dépend de son parent. Pour analyser un état précis, monter la chaîne complète jusqu'à ce snapshot.
🚨 ESXi — Forensique sur hyperviseur compromis
🔴 Ransomware ciblant ESXi : Depuis 2022, ESXiArgs, Royal, BlackBasta, Akira ciblent VMware ESXi pour chiffrer toutes les VMs en une seule opération — impactant potentiellement des dizaines de serveurs en minutes. La vulnérabilité historique CVE-2021-21974 (OpenSLP) a été massivement exploitée en février 2023.
📜 Logs ESXi à analyser
  • /var/log/vmkernel.log — événements kernel · I/O
  • /var/log/hostd.log — gestion VMs · API calls
  • /var/log/vpxa.log — communication vCenter
  • /var/log/auth.log — connexions SSH
  • /var/log/shell.log — commandes ESXi shell
  • /etc/passwd, /etc/shadow — comptes créés
  • esxcli vm process list — VMs actives
  • esxcli network connection list — connexions réseau
🔍 Indicateurs ESXiArgs / ransomwares ESXi
  • VMDK chiffrés avec extension .args / .locked / .crypt
  • Fichiers VMX lisibles (pas chiffrés — choix volontaire pour redémarrer)
  • Compte vpxuser compromis → première cible
  • Vulnérabilité CVE-2021-21974 (OpenSLP) → port 427
  • Fichier encrypt.sh ou encrypt dans /tmp/
  • Service SLP activé (devrait être désactivé)
  • Connexions sortantes vers C2 dans vmkernel.log
🧠 Testez-vous
Vous saisissez un serveur ESXi avec 30 VMs en production. L'hyperviseur tourne. Que faire en premier ?Procédure terrain · Niveau : moyen
Ne pas éteindre l'hyperviseur. Procédure : (1) Isoler réseau — déconnecter du LAN/Internet sauf pour la station forensique (éviter exfiltration C2 et propagation), (2) Capturer la RAM ESXi via esxcli ou outils Linux si shell accessible (rare et difficile), (3) Lister les VMs actives : esxcli vm process list, (4) Snapshot live de chaque VM critique via vSphere — chaque snapshot crée un .vmsn et .vmem capturant l'état RAM (preuve gelée), (5) Copier les fichiers : SSH puis scp ou montage NFS depuis station forensique vers stockage write-only, (6) Hash SHA-256 de tout, (7) Préserver les logs /var/log/*.log, /scratch/log/*.log, (8) Documenter : configuration vCenter, comptes, dates de création des VMs, snapshots existants. Ne pas redémarrer — perte de la RAM ESXi qui peut contenir le malware actif.
Vous trouvez un fichier vm.vmem de 8 GB dans un dossier de snapshot VMware. Que pouvez-vous faire avec ?Volatility · Niveau : facile
Le fichier .vmem est la RAM brute de la VM au moment du snapshot — analysable directement avec Volatility 3 sans conversion. Commandes essentielles : (1) vol.py -f vm.vmem windows.info — identifier le profil OS et la version, (2) vol.py -f vm.vmem windows.pslist — lister tous les processus à l'instant T, (3) vol.py -f vm.vmem windows.pstree — arborescence parents-enfants, (4) vol.py -f vm.vmem windows.netscan — connexions réseau actives (cherche IP suspectes), (5) vol.py -f vm.vmem windows.cmdline — lignes de commande des process (révèle PowerShell encodé), (6) vol.py -f vm.vmem windows.malfind — détection injection de code, (7) vol.py -f vm.vmem windows.dlllist — DLL chargées par chaque process. Bonus : la RAM contient potentiellement les clés de chiffrement de BitLocker/VeraCrypt si la VM était déchiffrée au moment du snapshot. Avantage VM : pas besoin d'avoir capturé un dump RAM live, le snapshot l'a fait pour toi.
Pourquoi les ransomwares modernes ciblent-ils en priorité ESXi plutôt que les machines individuelles ?Stratégie attaquant · Niveau : moyen
Plusieurs raisons stratégiques : (1) Effet de levier maximal — un seul ESXi peut héberger 50+ VMs critiques (DC, Exchange, ERP, fichiers). Chiffrer l'ESXi = paralyser instantanément toute l'infrastructure. (2) EDR/AV moins déployés — les hyperviseurs ESXi sont souvent moins surveillés que les serveurs Windows (peu d'EDR supportent ESXi nativement). (3) Vulnérabilités exploitables — CVE-2021-21974 (OpenSLP), CVE-2023-20887 (vCenter) ouvertes pendant des mois sur des hyperviseurs jamais patchés (ops production "intouchable"). (4) Comptes privilégiés — un compte vpxuser ou root ESXi compromis = god mode sur toutes les VMs. (5) Pas besoin d'AD — chiffrer les VMDK depuis ESXi évite de devoir compromettre Active Directory, Group Policy, etc. (6) Restauration difficile — sauvegardes elles-mêmes souvent stockées sur des datastores ESXi (donc chiffrés aussi). (7) Rançon plus élevée — paralyser une infrastructure entière justifie des demandes de millions vs des dizaines de milliers pour un ransomware classique. Mitigation : ESXi en VLAN dédié · access management avec MFA · patching strict · backups offline (air-gap).
