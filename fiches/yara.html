🔑 YARA — créer des « signatures comportementales » de malware
YARA (créé par Victor Alvarez chez VirusTotal) est un outil de pattern matching open-source qui permet de décrire — dans un langage déclaratif simple — des signatures de malwares ou de familles de fichiers. Au-delà des hashes (qui changent au moindre bit modifié), YARA capture des caractéristiques durables : strings caractéristiques, structure d'imports PE, séquences hex, entropie, organisation des sections… Une règle YARA bien écrite détecte une famille entière, y compris ses variantes futures. C'est le standard du malware analyst depuis 2013, intégré à VirusTotal, ClamAV, Volatility, EDR commerciaux, et pratiquement tout outil DFIR.
Structure d'une règle YARA — les 4 composants
📜 rule NAME : tags { meta · strings · condition }
HEADER rule MAL_RANSOM_LockBit_v3 : ransomware lockbit
Nom unique de la règle + tags optionnels (filtrage)
META author, description, hash, date, reference, score
Documentation de la règle — non utilisable dans condition
STRINGS $a = "..." · $b = { 6A 40 68 } · $r = /reg.*ex/
Patterns à chercher : texte, hex, regex (optionnel)
CONDITION all of ($a, $b) and filesize < 1MB and pe.is_pe
Mandatory — expression booléenne qui décide du match
ℹ️ Cliquez sur un composant ci-dessus pour ses détails.
Exemple complet — règle de référence
import "pe"
import "hash"

rule MAL_RANSOM_LockBit_v3_Generic : ransomware lockbit critical {
    meta:
        description = "Detects LockBit 3.0 / Black ransomware variants"
        author      = "DFIR Lab"
        date        = "2026-04-15"
        version     = "1.0"
        reference   = "https://example.org/lockbit-analysis"
        score       = 90
        hash1       = "1f3e87c4...c2b9"  // SHA-256 sample 1
        hash2       = "a8f2b1d9...4e51"  // SHA-256 sample 2
        attack      = "T1486"             // MITRE ATT&CK ID

    strings:
        // ── Strings textuelles caractéristiques ──
        $s1 = "LockBit 3.0" ascii wide
        $s2 = "All your important files have been encrypted" ascii
        $s3 = "Restore-My-Files.txt" nocase

        // ── Hex pattern : début de l'algo de chiffrement ──
        $hex1 = { 48 8B ?? 48 89 ?? E8 [4-8] 33 C0 }

        // ── Regex : domaines C2 .onion typiques ──
        $r1 = /[a-z2-7]{56}\.onion/ ascii

        // ── Anti-FP : éviter les faux positifs sur strings communes ──
        $fp1 = "Microsoft Visual Studio"

    condition:
        // En-tête PE valide
        uint16(0) == 0x5A4D                  // "MZ"
        and pe.is_pe
        and pe.machine == pe.MACHINE_AMD64
        // Au moins 2 strings caractéristiques sur 3
        and 2 of ($s*)
        // ET le pattern hex
        and $hex1
        // ET au moins une URL .onion
        and $r1
        // ET pas de match sur les FP
        and not $fp1
        // Limite de taille
        and filesize < 5MB
}

🔤 Trois types de strings : texte, hex, regex
Toute règle YARA repose sur la déclaration de patterns (strings) puis leur évaluation dans la condition. Trois syntaxes, chacune avec ses modificateurs.
① Text strings — "…"
strings:
    $s1 = "This program cannot be run in DOS mode"
    $s2 = "cmd.exe" nocase           # cmd.exe = CMD.EXE = Cmd.Exe
    $s3 = "/etc/passwd" ascii         # 1 octet par char (par défaut)
    $s4 = "Microsoft" wide            # UTF-16 LE (2 octets) — typique PE
    $s5 = "rundll32" ascii wide       # match les deux encodages
    $s6 = "DEBUG" fullword            # pas dans "DEBUGGER" ni "DEBUGED"
    $s7 = "secret" xor(0-255)          # cherche "secret" XORé toute clé
    $s8 = "data" base64               # cherche "ZGF0YQ==" et variantes
    $s9 = "/* private */" private      # utilisable mais pas dans output
Modificateurs disponibles
Modificateur Effet Cas d'usage
nocase Insensible à la casse Noms de DLL, paths, API
ascii 1 octet par char (défaut) À combiner explicitement avec wide
wide UTF-16 LE (2 octets/char) Strings dans PE Windows, registre, COM
fullword Mot entier (délimité par non-alphanumériques) Réduit FP — éviter sous-chaînes accidentelles
xor(min-max) Cherche string XORée avec toute clé 1 octet Strings obfusquées par malware (config XOR)
base64 Match les 3 variantes Base64 d'alignement PowerShell encoded commands, payloads
base64wide Base64 + UTF-16 Combo PowerShell -EncodedCommand
private String non affichée dans le rapport Anti-FP, ne révèle pas la signature
② Hex strings — { … }
strings:
    $h1 = { 4D 5A 90 00 03 00 00 00 }            # PE header (MZ)
    $h2 = { 6A 40 68 00 30 00 00 6A 14 8D 91 }   # Pattern code

    # Wildcards : ? = nibble (4 bits) any
    $h3 = { 48 8B ?? 48 89 ?? }                  # 2e/4e octet libre
    $h4 = { 48 8B ?A 48 89 ?5 }                  # nibble haut libre

    # Jumps : [n] = exactement n octets · [n-m] = n à m octets
    $h5 = { E8 [4] 33 C0 }                       # call + 4 octets + xor eax,eax
    $h6 = { E8 [4-8] 33 C0 }                     # 4 à 8 octets entre
    $h7 = { E8 [-] 33 C0 }                       # sans limite (attention perf!)

    # Alternation : ( ... | ... ) = OU logique
    $h8 = { 48 ( 8B | 89 ) C0 }                  # mov eax OU mov [eax]
③ Regex — /…/
strings:
    $r1 = /[a-z2-7]{56}\.onion/ ascii    # onion v3 (56 chars base32)
    $r2 = /\b(?:\d{1,3}\.){3}\d{1,3}\b/  # IPv4 (approx)
    $r3 = /md5: [a-f0-9]{32}/i           # /i = nocase équivalent

    # Métacaractères supportés :
    # . \w \s \d ^ $ * + ? {n,m} | () [...] \b
    # NON supportés : capture groups, backreferences,
    # POSIX classes ([[:alpha:]])
⚠️ Attention performance : les regex et hex avec jumps illimités [-] sont très coûteux. Sur des téraoctets de stockage, une mauvaise règle peut bloquer un scanner pendant des heures. Bonnes pratiques : (1) toujours ancrer avec un préfixe litéral, (2) limiter la longueur des jumps, (3) tester avec yara --print-stats ou yarac pour compiler.
🧠 La condition — l'âme logique de la règle
La section condition est obligatoire. C'est une expression booléenne qui combine les strings (référencées par $nom), des fonctions sur le fichier (filesize, uint16…), et des opérateurs logiques. La règle match si la condition est vraie.
Opérateurs disponibles

== · != · < · <= · > · >=
+ · - · * · \ · %
& · | · ^ · << · >> · ~  (bitwise)

uint16be(offset)  # word BE

🎯 Quantifieurs sur strings
$a                 # présent au moins 1 fois
#a                 # nb d'occurrences
@a[N]              # offset Nème occurrence
!a[N]              # longueur match
any of ($a, $b, $c)
all of ($s*)       # tous ceux préfixés $s
2 of ($a, $b, $c, $d)
none of them
🔁 Boucles for
for any i in (1..#a) :
    ( @a[i] > 0x1000 )
for all section in pe.sections :
    ( section.name == ".text" )
for any s in ("h1", "h2") :
    ( pe.imphash() == s )
Patterns de conditions courants
// ── Filtrage par taille ──
condition:
    filesize < 1MB and any of ($s*)

// ── Match à l'entry point (typique packer) ──
condition:
    $upx_marker at entrypoint

// ── Validation magic bytes en hex ──
condition:
    uint16(0) == 0x5A4D       # MZ (PE Windows)
    or uint32(0) == 0x464C457F # ELF Linux

// ── Score de confiance par accumulation ──
condition:
    (#a + #b + #c) > 5
    and 2 of ($strong*)

// ── Anti-FP avec rules privées ──
private rule IsPE { condition: uint16(0) == 0x5A4D }
private rule IsPDF { condition: uint32(0) == 0x46445025 }

rule MAL_GenericMacroDoc {
    condition: not IsPE and not IsPDF and ...
}

// ── Combinaison avec module pe ──
condition:
    pe.is_pe
    and pe.imports("kernel32.dll", "VirtualAlloc")
    and pe.imports("kernel32.dll", "CreateRemoteThread")
    and pe.number_of_sections < 4
    and 2 of ($s*)
📦 Modules — étendre YARA au-delà du pattern matching
Les modules ajoutent des capacités d'inspection fine selon le format de fichier ou le besoin. Ils s'importent via import "nom" en début de fichier YARA. La distribution officielle (≥ v4.5) contient : pe, elf, cuckoo, magic, hash, math, dotnet, time, console, string.
Module pe — Portable Executable Windows
import "pe"

condition:
    pe.is_pe                                   # validation MZ + PE\0\0
    and pe.machine == pe.MACHINE_AMD64          # 64-bit
    and pe.number_of_sections < 4              # packing suspect
    and pe.imphash() == "8a705c3e7c4..."        # import hash
    and pe.imports("kernel32.dll", "VirtualAlloc")
    and pe.imports("user32.dll", /^Get.*Window/) # regex sur API
    and pe.exports("DllRegisterServer")
    and pe.entry_point > 0x10000                # EP haut = packer
    and pe.timestamp > 1577836800               # > 2020-01-01
    and pe.number_of_signatures == 0            # non signé
    and pe.rich_signature.toolid(0x60, 0x77)    # Rich header

# Itérer sur les sections
    and for any sect in pe.sections : (
        sect.name == ".text"
        and sect.entropy > 7.5             # section chiffrée/packée
    )

Conditions temporelles — utile pour règles « campagne active »
⭐ imphash : un IOC plus robuste que le hash de fichier. pe.imphash() calcule un MD5 sur la liste ordonnée des imports (kernel32.VirtualAlloc, user32.MessageBoxA…). Deux variantes du même malware compilées avec le même code source ont souvent le même imphash, même si leurs hashes complets diffèrent (timestamp PE, optimisations compilateur). Excellent pivot CTI.
🔧 Utiliser YARA — du CLI au pipeline industriel
YARA tourne sous Linux, macOS, Windows. Binaires : yara (scan), yarac (compilateur). Disponible aussi via yara-python (bindings Python) — utilisé par la majorité des outils DFIR.
Commandes essentielles
# Scan d'un fichier ──
$ yara rules.yar suspicious.exe

# Scan récursif d'un répertoire (DFIR triage) ──
$ yara -r rules.yar /mnt/forensic_image/

# Print les strings matchées (-s) + offsets ──
$ yara -s rules.yar suspicious.exe

# Multi-règles combinées ──
$ yara -r combined.yar /target          # 1 fichier groupant plusieurs rules

# Filtrer par tag (ex. uniquement règles tagguées 'critical') ──
$ yara -t critical rules.yar /target

# Compiler en binaire (perf, anti-réécriture) ──
$ yarac rules.yar rules.yarc
$ yara -C rules.yarc /target            # load compilé (-C)

# Scan d'un processus en mémoire (par PID) ──
$ yara rules.yar 4328                   # scan process 4328 RAM

# Définir une variable externe ──
$ yara -d filename=evil.exe rules.yar /target

# Stats & performance ──
$ yara --print-stats rules.yar /target  # temps par règle

YARA-X — la nouvelle génération
YARA-X (virustotal.github.io/yara-x/) est une réécriture en Rust par Victor Alvarez, lancée en 2024. Compatible avec les règles YARA 4.x, mais avec :
  • Performance améliorée (compilateur plus efficace, exécution parallèle)
  • Sécurité mémoire native (Rust)
  • Meilleurs messages d'erreur à la compilation
  • Modules étendus (LNK, macho, plus complets)
YARA classique reste la référence en 2026, mais YARA-X est l'avenir — l'écosystème migrera progressivement. Compatible drop-in pour la plupart des règles.

Vous écrivez une règle YARA pour un malware Windows qui contient la string « LockBit 3.0 ». Pour la rendre robuste face aux variantes, quels modificateurs et quelle condition utiliseriez-vous ?
YARA · Niveau : moyen
Modificateurs minimum : 
$s_lockbit = "LockBit 3.0" ascii wide nocase
  • ascii : pour matcher dans les strings 8-bit (typique sections .data, .rsrc)
  • wide : pour matcher en UTF-16 LE (typique strings de PE Windows compilés)
  • nocase : variantes en majuscules/minuscules (LOCKBIT, lockbit…)
Condition robuste (anti-FP, contextualisée) : 
condition:
    uint16(0) == 0x5A4D                  // PE valide
    and pe.is_pe
    and filesize < 5MB                   // ransom typique petit
    and 2 of ($s_lockbit, $s_ransom_note, $s_extension)
    and not pe.imphash() == "<benign_known_hash>"
Pourquoi : (1) le marqueur PE évite de matcher des fichiers texte (rapports, logs), (2) la taille filtre les binaires légitimes plus gros, (3) 2 of exige plusieurs indicateurs concordants — détecter LockBit 3.0 sur la base d'une seule string serait FP-prone (la presse cite cette string partout), (4) anti-FP avec imphash connu de fichiers benins. Bonus : on pourrait ajouter pe.timestamp > 1672531200 (post-2023, date de release LockBit 3.0).
Quelle est la différence entre le hash SHA-256 d'un fichier et le pe.imphash() en termes de pivot CTI ?
YARA · Niveau : moyen
Le SHA-256 couvre tout le contenu binaire — un seul bit modifié change radicalement le hash (effet avalanche). Bonne propriété pour l'intégrité, mauvaise propriété pour la détection de famille : recompiler le même code source change le timestamp PE → SHA-256 différent. Repacker avec UPX/Themida → SHA-256 différent. Le SHA-256 est donc un IOC « atomic » dans la pyramide de Bianco — facile à éviter pour l'attaquant (changer 1 octet suffit).

L'imphash est un MD5 calculé sur la liste ordonnée des imports PE (DLL + nom de fonction, dans l'ordre exact où ils sont déclarés dans la table d'import). Il capture le comportement appellatif du binaire : « ce malware appelle kernel32.VirtualAlloc puis kernel32.WriteProcessMemory puis kernel32.CreateRemoteThread puis... ». Deux variantes du même code source compilées avec le même compilateur partagent généralement le même imphash, même si leurs SHA-256 diffèrent. C'est un IOC « tools » dans la pyramide — beaucoup plus coûteux à modifier (il faut changer la structure du programme).

Mantra CTI : SHA-256 pour la confirmation, imphash pour le pivot. Un nouveau échantillon trouvé via VirusTotal Hunting avec le même imphash qu'un APT connu = match très robuste, même si le hash global est inédit. Caveat : les binaires .NET et les compilateurs Go produisent des imphashes peu discriminants (toujours les mêmes imports génériques) — pour eux, on utilise plutôt typelib (.NET) ou de l'analyse de strings.
