📋 Unified Audit Log — La source centrale M365
Le Unified Audit Log (UAL) est le journal centralisé de Microsoft 365 qui enregistre les activités de tous les services : Exchange Online, SharePoint, OneDrive, Teams, Azure AD, Power Platform. C'est la première source forensique dans tout incident M365. Il n'est pas activé par défaut sur tous les tenants — son absence ou sa désactivation est elle-même un indicateur forensique majeur. Rétention : 90 jours (E3) ou 365 jours (E5 / Microsoft 365 Audit Premium).
⚠️ Vérification critique en début d'investigation : Get-AdminAuditLogConfig | Select UnifiedAuditLogIngestionEnabled
Si False → les logs n'ont pas été collectés. Chercher des sources alternatives : Microsoft Defender XDR, Entra ID Sign-in logs (30j), Exchange Message Tracking (90j).

📧 Exchange Online Forensique — BEC & compromission mailbox
Exchange Online est au cœur de la majorité des incidents M365. Les BEC (Business Email Compromise) — arnaque au président, fraude au virement, usurpation de fournisseur — représentent les pertes financières les plus importantes en Suisse liées à la cybercriminalité. Le technicien DFIR doit maîtriser les artefacts Exchange pour reconstituer : accès non autorisé à une mailbox, création de règles de redirection, usurpation d'identité, et exfiltration de données via email.
Scénarios BEC — Artefacts forensiques
Technique 1
Règles de redirection
Transfert silencieux de tous les mails vers compte externe.
Technique 2
Délégation mailbox
Accès total à la boîte sans connexion au compte.
Technique 3
OAuth App Consent
Application tierce autorisée à lire les mails.
Technique 4
Impersonation / Send As
Envoi de mails en se faisant passer pour un autre.
Technique 5
Exfiltration massive
Téléchargement en masse via Graph API ou IMAP.
Technique 6
Hard Delete / effacement
Suppression définitive pour couvrir les traces.
Message Tracking Log — Traçabilité des emails
📋 Message Tracking Log
Trace chaque email : sender, recipient, subject, IP source, timestamp, statut de livraison. Rétention 90 jours.

Get-MessageTrace -SenderAddress attacker@evil.com `
  -StartDate "2024-03-01" -EndDate "2024-03-31"

Get-MessageTrace -RecipientAddress victim@corp.ch `
  -StartDate "2024-03-01" -EndDate "2024-03-31" |
  Get-MessageTraceDetail
📬 Mailbox Audit Log
Log spécifique à la mailbox : qui a accédé, quels mails lus, actions effectuées. Activé par défaut depuis 2019 (E3/E5 seulement pour MailItemsAccessed).

Search-MailboxAuditLog -Identity victim@corp.ch `
  -LogonTypes Delegate,Admin,Owner `
  -StartDate "2024-03-01" -EndDate "2024-03-31" `
  -ResultSize 10000
Headers Exchange — Champs forensiques clés
HeaderValeur forensique
X-MS-Exchange-Organization-SCL Spam Confidence Level (SCL). -1 = confiance totale (whitelist). Si mail malveillant avec SCL -1 = règle de transport contournée.
X-Originating-IP IP réelle d'envoi avant passage par Exchange. Comparer avec l'IP habituelle de l'expéditeur. IP étrangère = compte compromis.
Authentication-Results Résultats SPF/DKIM/DMARC. spf=fail = domaine usurpé. dmarc=fail = potentiel spoofing.
X-MS-Exchange-Organization-AuthAs Comment l'expéditeur s'est authentifié : Internal, Anonymous, Partner. Anonymous depuis l'interne = red flag.
X-Microsoft-Antispam Résultats du filtrage antispam Microsoft. BCL (Bulk Complaint Level), PCL (Phishing Confidence Level). PCL > 3 = phishing probable.
Un directeur financier signale qu'il n'a jamais reçu la réponse à un email important envoyé par un fournisseur. L'investigation révèle une règle Outlook "si sujet contient 'virement' ou 'facture' → déplacer vers Éléments supprimés + marquer comme lu". Quels artefacts forensiques M365 permettent de dater la création de cette règle et d'identifier depuis quelle IP elle a été créée ?BEC · Niveau : moyen
1. Unified Audit Log — Operation UpdateInboxRules :
Search-UnifiedAuditLog -Operations "UpdateInboxRules","New-InboxRule" -UserIds "cfo@corp.ch" -StartDate "2024-01-01" -EndDate "2024-04-01"
→ Timestamp exact de création, ClientIP depuis laquelle la règle a été créée, UserAgent (Outlook Web vs application).

2. Entra ID Sign-in Logs : croiser le ClientIP avec les connexions au compte — trouver la session depuis laquelle la règle a été créée. Comparer avec les pays/IPs habituels de l'utilisateur.

3. Message Tracking Log : Get-MessageTrace pour les 30-90 jours → retrouver les emails "virement/facture" qui ont disparu. Confirmer qu'ils ont bien été reçus et supprimés automatiquement.

4. Mailbox Audit Log — HardDelete / SoftDelete : confirmer que les emails ont été supprimés par la règle et non par l'utilisateur manuellement.

5. Litigation Hold / Recoverable Items : si Litigation Hold activé, les emails supprimés sont récupérables depuis le dossier Recoverable Items — indispensable pour la preuve.
🔐 Entra ID (Azure AD) — Identités et accès cloud
Microsoft Entra ID (anciennement Azure Active Directory) est le système d'identité central de M365. Chaque connexion, chaque attribution de rôle, chaque consentement OAuth est tracé. Les logs Entra ID sont indispensables pour reconstituer la compromission initiale (credential stuffing, phishing, MFA bypass) et la progression des droits de l'attaquant dans le tenant.
Sign-in Logs — Connexions Entra ID
Type de logContenuRétentionAccès
Interactive Sign-ins Connexions avec interaction utilisateur (formulaire, MFA prompt). IP, UserAgent, pays, résultat MFA, Conditional Access. 30 jours Entra Portal / Graph API
Non-interactive Sign-ins Connexions automatiques (refresh tokens, apps). Souvent ignorées — révèle les accès persistants via token volé. 30 jours Entra Portal / Graph API
Service Principal Sign-ins Connexions d'applications (OAuth, service accounts). Activité d'apps tierces sur le tenant. 30 jours Graph API / Entra
Audit Logs (Entra) Modifications d'objets AD : création comptes, attribution rôles, reset MFA, consentements OAuth. Très riche. 30 jours Entra Portal / PowerShell
Techniques de compromission Entra ID — Artefacts
🎣 AiTM Phishing (Adversary-in-the-Middle)
Mécanisme : proxy entre victime et Microsoft → capture le session token post-MFA.
Résultat : attaquant contourne le MFA avec le token volé.
Artefacts :
· Sign-in réussi depuis IP inhabituelle immédiatement après le sign-in légitime
· Token replay depuis pays/ASN différent
· Non-interactive sign-in avec le même refresh token
· UAL : accès mailbox depuis nouvelle IP dans les minutes suivant le phishing
🔓 Illicit OAuth App Consent
Mécanisme : l'utilisateur consent à une app tierce malveillante qui reçoit des permissions Mail.Read, Files.ReadWrite, etc.
Résultat : accès persistant sans MFA, même si le mot de passe est changé.
Artefacts :
· Entra Audit Log : "Consent to application" avec AppDisplayName suspect
· UAL : "Add service principal", permissions accordées
· Graph API : GET /oauth2PermissionGrants — consentements actifs
👑 Privilege Escalation Entra
Techniques : ajout d'un rôle Global Admin, création d'un compte backdoor, ajout d'un fédération de confiance.
Artefacts :
· Entra Audit Log : "Add member to role" avec RoleDisplayName = "Global Administrator"
· UAL : "Add-RoleGroupMember"
· Moment anormal : hors heures ouvrables, depuis IP inhabituelle
🔑 MFA Reset / Bypass
Techniques : reset de la méthode MFA d'un compte (nécessite admin), enregistrement d'un nouvel appareil MFA.
Artefacts :
· Entra Audit Log : "Update user" avec ModifiedProperties contenant StrongAuthenticationMethod
· "User registered security info" depuis IP/pays inhabituel
· Connexion réussie depuis nouveau pays sans alerte MFA
# Connexions depuis pays inhabituels (30 derniers jours)
Get-MgAuditLogSignIn -Filter "createdDateTime ge 2024-03-01" `
  | Where {$_.Location.CountryOrRegion -ne "CH"} `
  | Select UserPrincipalName, IPAddress, Location, Status, CreatedDateTime

# Consentements OAuth actifs (apps tierces)
Get-MgOauth2PermissionGrant | Select ClientId, Scope, PrincipalId | Sort Scope

# Membres Global Admin
Get-MgDirectoryRoleMember -DirectoryRoleId (Get-MgDirectoryRole | Where {$_.DisplayName -eq "Global Administrator"}).Id
🎯 Impossible Travel — Détection automatique
Microsoft Entra ID détecte automatiquement l'Impossible Travel : connexion réussie depuis Zurich à 09h00 et depuis une IP russe à 09h15 — physiquement impossible. Cette détection déclenche une alerte dans Microsoft Defender for Identity / Entra ID Protection. Forensiquement, chercher dans les Sign-in Logs deux connexions réussies avec le même compte dans un intervalle de temps inférieur au temps de trajet entre les deux localisations. Attention aux VPN légitimes qui peuvent générer des faux positifs.
🔍 eDiscovery & Microsoft Purview — Collecte légale
Microsoft Purview (anciennement Microsoft 365 Compliance Center) est la plateforme de conformité et d'eDiscovery intégrée à M365. Elle permet de collecter, préserver et exporter des données M365 (emails, Teams, SharePoint, OneDrive) dans le cadre d'une investigation légale ou d'une réquisition. En Suisse, cette plateforme est utilisée conjointement avec les procédures MLAT (mutual legal assistance) et les réquisitions judiciaires cantonales.

Litigation Hold & eDiscovery Hold — Préservation des preuves
🎯 Première action en cas d'incident : placer les mailboxes et comptes concernés sous Litigation Hold (ou eDiscovery Hold) AVANT toute investigation. Le Hold préserve tous les éléments — y compris les emails supprimés, les Teams messages, les fichiers SharePoint — dans le dossier Recoverable Items, invisible pour l'utilisateur mais accessible via eDiscovery. Sans Hold, les données peuvent être supprimées définitivement par les politiques de rétention automatiques.
# Activer Litigation Hold sur une mailbox
Set-Mailbox -Identity "victim@corp.ch" -LitigationHoldEnabled $true `
  -LitigationHoldDuration 2555 # 7 ans

# Vérifier les mailboxes sous hold
Get-Mailbox -ResultSize Unlimited | Where {$_.LitigationHoldEnabled -eq $true} |
  Select Name, LitigationHoldEnabled, LitigationHoldDate

# Récupérer les éléments supprimés (Recoverable Items)
New-ComplianceSearch -Name "RecoverDeleted" -ExchangeLocation "victim@corp.ch" `
  -ContentMatchQuery "subject:'virement' AND ItemClass:IPM.Note"
Start-ComplianceSearch -Identity "RecoverDeleted"
New-ComplianceSearchAction -SearchName "RecoverDeleted" -Export -Format FxStream

Un technicien DFIR doit préserver les preuves d'une compromission de compte M365 découverte un vendredi soir. La politique de rétention de l'entreprise supprime automatiquement les emails > 90 jours le lundi matin. Quelles sont les actions immédiates à effectuer dans l'ordre ?eDiscovery · Niveau : moyen
1. (Immédiat) Activer Litigation Hold sur la mailbox compromise :
Set-Mailbox -Identity "victim@corp.ch" -LitigationHoldEnabled $true
→ Suspend toutes les suppressions automatiques, préserve Recoverable Items.

2. (Immédiat) Bloquer le compte compromis :
Set-MsolUser -UserPrincipalName "victim@corp.ch" -BlockCredential $true
→ Invalider toutes les sessions actives : Revoke-AzureADUserAllRefreshToken

3. (Dans l'heure) Exporter les Sign-in Logs Entra ID :
Les logs Entra ne sont conservés que 30 jours — exporter immédiatement en CSV ou JSON via Graph API.

4. (Dans l'heure) Exporter le Unified Audit Log de la période suspecte :
Search-UnifiedAuditLog -UserIds "victim@corp.ch" -StartDate "2024-01-01" -EndDate "2024-04-01" -ResultSize 5000

5. (Dans les 24h) Créer un eDiscovery case dans Microsoft Purview et placer un eDiscovery Hold sur la mailbox + OneDrive + Teams du compte compromis.

Règle d'or : Litigation Hold en premier — avant toute autre action. Sans lui, les preuves peuvent disparaître avant lundi matin.

🎓 Exam Tip — Microsoft 365 Forensique

UAL = source centrale · pas activé par défaut · rétention 90j (E3) / 365j (E5)

Litigation Hold = première action en incident · préserve Recoverable Items contre suppressions automatiques

UpdateInboxRules = règle de redirection (BEC) · HardDelete = suppression définitive

AiTM Phishing = contourne MFA via vol de session token · chercher deux connexions successives depuis IPs différentes

OAuth Consent Abuse = app tierce avec Mail.Read → accès persistant même après reset du mot de passe

Sign-in Logs Entra = seulement 30j · exporter en priorité au début de l'investigation

🇨🇭 nLPD : violation de données → notification dans les 72h à l'autorité de contrôle (PFPDT) + personnes concernées si risque élevé
