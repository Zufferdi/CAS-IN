🌲 HFS+ · B-Tree Internals

HFS+ — Arbres B-Tree (Catalog, Extents, Attributes)

Header Node, leaf et index nodes, clés trois-types, key compare, fork records, Extents Overflow et Attributes File. Comment HFS+ stocke tout dans des B-Trees Big Endian — et pourquoi les nœuds libérés sont une mine pour l'analyse forensique.

Prérequis :📖 HFS+ (Volume Header, CNID)📖 Endianness
Voir aussi :🔗 B+ Trees NTFS🔗 B-Trees APFS🔗 MAC Times🔗 macOS Forensique
⚠️ Big Endian partout ! Contrairement à NTFS / FAT (Little Endian), HFS+ stocke toutes les valeurs multi-octets — y compris dans les nœuds B-Tree — en Big Endian. À chaque lecture hex manuelle, inverser l'ordre des octets. X-Ways, Autopsy, hfsinspect et mac_apt convertissent automatiquement.
🧭 Vue d'ensemble — HFS+ est fait de B-Trees

Le Volume Header (offset 1024) pointe vers 5 fichiers spéciaux. Trois d'entre eux sont des B-Trees, et c'est dans ces arbres que vit toute l'organisation logique du volume.

FichierCNIDStructureContenu
Catalog File 4 🌲 B-Tree Arborescence complète : noms, dates, tailles, fork pointers, hiérarchie parent/enfant
Extents Overflow 3 🌲 B-Tree Extents supplémentaires des fichiers très fragmentés (au-delà des 8 premiers)
Attributes File 8 🌲 B-Tree Attributs étendus (xattr), ACL POSIX, Finder Info, quarantine, hard-link refs
Allocation File 6 Bitmap (1 bit / bloc) Pas un B-Tree — bitmap d'allocation classique
Startup File 7 Données brutes Pas un B-Tree — booting non-Mac (rare)
💡 Différence majeure avec APFS : APFS introduit un Object Map (omap) qui découple object_id et adresse physique, et place les extents directement dans l'arbre principal. HFS+ garde un modèle plus simple : 3 B-Trees parallèles avec des clés différentes, sans indirection. C'est pédagogique mais aussi fragile : un seul B-Tree corrompu peut rendre tout un volume inutilisable.
📐 Structure générique d'un B-Tree HFS+
Tous les B-Trees HFS+ partagent la même structure : un fichier découpé en nœuds de taille fixe (4096 octets typiquement), chaque nœud étant un type parmi quatre.

🧱 Nœuds = blocs de taille fixe

  • Taille définie dans le Header Node (toujours nœud #0 du fichier)
  • Tailles courantes : 4096 octets (Catalog moderne) · 1024 ou 2048 (volumes anciens / Extents)
  • Indexés par numéro 32 bits depuis le début du fichier
  • Chaînés horizontalement via fLink (next) et bLink (previous) au sein du même niveau

🎭 Quatre types de nœuds

  • Header Node (kind = 0x01) — toujours nœud #0, métadonnées du B-Tree
  • Map Node (kind = 0x02) — bitmap des nœuds libres (extension du header)
  • Index Node (kind = 0x00) — nœud interne, contient des pointeurs vers nœuds enfants
  • Leaf Node (kind = 0xFF, soit -1 signé) — feuille, contient les vrais records
⚠️ Le piège du kind signé : dans la spec Apple (hfs_format.h), kind est un SInt8. Donc 0xFF = -1 = leaf, et 0xFE = -2 = index dans certaines docs anciennes. Implémentation moderne utilise plus souvent : 0x00=index, 0x01=header, 0x02=map, 0xFF=leaf. Toujours valider en croisant avec le height du nœud (0 = leaf).
🧬 Layout commun à tous les nœuds : Node Descriptor (14 octets)
Chaque nœud commence par cet en-tête fixe de 14 octets, suivi des records puis d'une table d'offsets en fin de nœud.
OffsetTailleChampNotes forensiques
0x004 octetsfLinkNuméro du nœud suivant au même niveau (0 si dernier). Permet le parcours séquentiel des feuilles.
0x044 octetsbLinkNuméro du nœud précédent au même niveau (0 si premier).
0x081 octetkind (SInt8)0x00=index · 0x01=header · 0x02=map · 0xFF(-1)=leaf
0x091 octetheightProfondeur du nœud : 0 pour leaf · 1 au-dessus des leaves · n = racine. Dans le Header Node : 0.

📑 Layout interne d'un nœud : records + table d'offsets

Après le node descriptor de 14 octets, les records sont stockés linéairement vers l'avant. En parallèle, une table d'offsets est stockée en fin de nœud, croissant vers l'arrière. C'est cette table qui rend la taille des records variable.

┌─────────────────────────────────────────────────────────────────┐
│ Node Descriptor (14 octets)                                     │
├─────────────────────────────────────────────────────────────────┤
│ Record 0  : key + data (taille variable)                        │  ← grandit vers le bas
│ Record 1  : key + data                                          │
│ Record 2  : key + data                                          │
│ ...                                                             │
│                                                                 │
│            ← espace libre (free space) ←                        │
│                                                                 │
│ ...                                                             │
│ off[2] : offset du record 2  (2 octets BE)                      │  ← table grandit vers le haut
│ off[1] : offset du record 1                                     │
│ off[0] : offset du record 0                                     │
│ off[free] : offset de la fin des records (= début free space)   │
└─────────────────────────────────────────────────────────────────┘     fin du nœud (offset 4096)
💡 Pourquoi cette double direction ? Permet d'ajouter / supprimer un record sans déplacer les autres (juste l'offset de la table change). En forensique, c'est aussi pourquoi un record « supprimé » peut subsister : son offset est retiré de la table, mais ses octets restent dans la zone des records jusqu'à la prochaine compaction du nœud.
🗂 Le Header Node (nœud #0 de chaque B-Tree)
Le tout premier nœud du fichier B-Tree contient les métadonnées de l'arbre lui-même. Il a toujours numRecords = 3.

🌲 B-Tree #1 — Catalog File (CNID 4)
Le plus important : il décrit toute la hiérarchie de fichiers et dossiers du volume. C'est ici que vivent les noms, les timestamps, les CNID et les fork pointers.

🔑 Structure de la clé Catalog (CatalogKey)

┌─────────────┬──────────────┬─────────────────────────────┐
│ keyLength   │ parentID     │ nodeName (HFSUniStr255)     │
│ 2 octets    │ 4 octets     │ 2 + 2N octets               │
│             │ CNID parent  │ 2 oct length + UTF-16 BE   │
└─────────────┴──────────────┴─────────────────────────────┘
  • parentID = CNID du dossier parent (4 octets BE) → garantit que tous les enfants d'un dossier sont contigus dans l'arbre
  • nodeName : 2 octets de longueur en caractères Unicode (max 255) + chaîne UTF-16 Big Endian
  • Forme normalisée : NFD canonique (Normalization Form D) — les accents sont décomposés. Un fichier café.txt est stocké comme cafe + ́ + .txt (4 + combining acute + 4)
  • Comparaison : selon keyCompareType du Header (case-folded HFS+ ou binary HFSX)
⚠️ Piège forensique sur les noms unicode : un fichier nommé café en macOS HFS+ ne se compare pas octet-à-octet avec un fichier café créé en NTFS / APFS / Linux (qui utilisent généralement NFC). Pour matcher des noms entre systèmes, normaliser explicitement (unicodedata.normalize('NFC', name) en Python).

📋 Trois types de records dans le Catalog

Premier champ d'un record : recordType (2 octets BE) qui distingue :

  • 0x0001 — Folder Record (HFSPlusCatalogFolder, 88 octets)
  • 0x0002 — File Record (HFSPlusCatalogFile, 248 octets) — c'est ici que vivent les fork pointers !
  • 0x0003 — Folder Thread Record (HFSPlusCatalogThread)
  • 0x0004 — File Thread Record (HFSPlusCatalogThread)
🔗 Le mécanisme des Thread Records

🤔 Pourquoi des "thread records" ?

La clé Catalog est (parentID, nodeName). Pour descendre du parent vers les enfants, c'est efficace. Mais comment remonter d'un fichier vers son parent à partir de son seul CNID ?

Réponse : un Thread Record est ajouté avec une clé spéciale (CNID_du_fichier, "") et son contenu donne (parentID, nodeName) du fichier.

💎 Valeur forensique majeure

  • Thread record d'un fichier supprimé peut subsister dans une feuille libérée → retrouver le chemin complet via le seul CNID
  • Hard links HFS+ utilisent ce mécanisme : le "fichier" pointe vers une entrée dans /.HFS+ Private Directory Data
  • Croiser CNID résiduel d'un .lnk macOS (Alias) avec un thread record orphelin → reconstitution d'un fichier renommé/déplacé

💡 Le mécanisme des "8 extents" : chaque fork stocke ses 8 premiers extents directement dans le File Record. Si le fichier est plus fragmenté, les extents 9, 10, … vont dans le Extents Overflow B-Tree. C'est pourquoi un fichier peu fragmenté n'apparaît jamais dans le second arbre — alors qu'un fichier de log croissant pendant des années y aura des dizaines d'entrées.
📑 B-Tree #2 — Extents Overflow File (CNID 3)

🔑 Clé Extents (10 octets de payload)

┌──────────┬─────────┬──────┬─────────────┐
│ keyLen   │forkType │ pad  │ fileID      │ startBlock
│ 2 oct    │ 1 oct   │ 1    │ 4 oct       │ 4 oct
└──────────┴─────────┴──────┴─────────────┘
  • forkType : 0x00 = data fork · 0xFF = resource fork
  • fileID : CNID du fichier propriétaire
  • startBlock : numéro du premier bloc logique du fork couvert par cet extent (au-delà des 8 inline)

📊 Record (HFSPlusExtentRecord)

Chaque record contient un tableau de 8 extents :

HFSPlusExtentDescriptor[8]:
  startBlock (4 oct BE) — premier bloc physique
  blockCount (4 oct BE) — nombre de blocs

= 8 × 8 = 64 octets par record

Un record permet donc 8 extents supplémentaires. S'il en faut plus → un autre record avec un startBlock plus élevé.

🔬 Valeur forensique de l'Extents Overflow

  • Extents orphelins dans des nœuds libérés : pointent vers des blocs physiques qui peuvent encore contenir les données fichier supprimé
  • Permet de récupérer la suite d'un fichier dont on a déjà les 8 premiers extents via Catalog (cas de très gros fichiers fragmentés)
  • Sleuth Kit, hfsinspect parcourent automatiquement Catalog → Extents Overflow pour reconstruire le fork complet
🏷 B-Tree #3 — Attributes File (CNID 8)
Stocke les attributs étendus (xattr) : Finder Info, quarantine (com.apple.quarantine), Spotlight metadata, ACL POSIX. Équivalent fonctionnel de $EA NTFS.

🔑 Clé Attributes (HFSPlusAttrKey)

┌──────────┬──────┬──────────┬──────────────┬───────────────────────┐
│ keyLen   │ pad  │ fileID   │ startBlock   │ attrName UTF-16 BE    │
│ 2 oct    │ 2    │ 4 oct    │ 4 oct        │ 2 + 2N oct            │
└──────────┴──────┴──────────┴──────────────┴───────────────────────┘
  • fileID : CNID du fichier auquel l'attribut est rattaché
  • startBlock : pour attributs trop gros stockés en plusieurs blocs (rare en pratique)
  • attrName : ASCII converti en UTF-16 BE — exemples : com.apple.FinderInfo, com.apple.quarantine, com.apple.metadata:_kMDItemUserTags

📦 Trois formats de record

  • Inline data (kHFSPlusAttrInlineData = 0x10) : la valeur est stockée dans le record (≤ ~3800 octets typique)
  • Fork data (0x20) : pour valeurs > nodeSize, stockées dans des blocs avec un fork descriptor
  • Extents (0x30) : suite d'extents si la valeur dépasse 8 extents
💡 Forensique des xattr :
  • com.apple.quarantine → preuve qu'un fichier a été téléchargé depuis Internet. Format : flags;timestamp_hex;agent;UUID. Permet de remonter le navigateur, l'horodatage et un identifiant unique de la session.
  • com.apple.metadata:kMDItemWhereFroms → URL source (Safari, Chrome, AirDrop)
  • com.apple.macl → ACL TCC pour permissions caméra/micro/disque (macOS 10.14+)
  • Ces attributs survivent à la copie sur volume HFS+, sont perdus sur FAT/NTFS sauf via AppleDouble (._fichier)
🪦 Récupération forensique : nœuds libérés

🔄 Que se passe-t-il à la suppression d'un fichier ?

  1. 1. File Record retiré du Catalog → décrémentation de numRecords dans le nœud, suppression de l'offset dans la table.
  2. 2. Si le nœud devient vide → marqué libre dans le bitmap du Header Node (freeNodes++).
  3. 3. Le contenu binaire du nœud n'est pas écrasé tant qu'il n'est pas réutilisé par un nouveau record.
  4. 4. Les blocs de données du fork sont marqués libres dans l'Allocation File (bitmap) — pas effacés.
  5. 5. Le journal HFS+ (.journal, ~8–64 Mo circulaire) peut conserver une trace récente de l'opération.

🔨 Stratégie de carving B-Tree

  1. 1. Lire le Header Node du Catalog → obtenir nodeSize
  2. 2. Lire le bitmap (record #2) → liste des nœuds libres
  3. 3. Pour chaque nœud libre : parser quand même les records orphelins
  4. 4. Pour chaque nœud actif : parser le slack (entre fin records et table d'offsets)
  5. 5. Reconstruire les chaînes parent via Thread Records orphelins

📜 Le journal comme source secondaire

  • Transactions séquentielles : header + block list (numéro nœud + données)
  • Conserve l'état précédent de nœuds B-Tree avant réécriture
  • Visible uniquement si volume HFS+ journalisé (signature HX ou flag kHFSVolumeJournaledBit)
  • Outils : hfsinspect --journal, parsers Python custom
  • Durée de vie : courte sur volume actif, plusieurs heures à jours sur disque externe peu sollicité

💻 Commandes essentielles
# hfsinspect — header du Catalog
hfsinspect -d image.dd --btree catalog --header

# hfsinspect — dumper un nœud précis
hfsinspect -d image.dd --btree catalog --node 42

# hfsinspect — énumérer toutes les feuilles (chaîne fLink depuis firstLeafNode)
hfsinspect -d image.dd --btree catalog --leaf

# Extents Overflow — voir les fichiers très fragmentés
hfsinspect -d image.dd --btree extents --leaf

# Attributes — lister tous les xattr quarantine
hfsinspect -d image.dd --btree attributes --leaf | grep quarantine

# Sleuth Kit — lister tout le volume (descend B-Tree Catalog)
fls -r -p -f hfs image.dd

# Stat d'un fichier par CNID — montre forks, extents, perms
istat -f hfs image.dd 12345

# Extraire un attribut étendu via xattr (sur système monté)
xattr -p com.apple.quarantine fichier.dmg

# Repérer la signature 'INDX' n'existe pas en HFS+ — chercher Header Node
# Pattern : 8 octets de zéros (fLink+bLink) + kind=01 + height=00 + numRecords=0003
xxd image.dd | grep "0000 0000 0000 0000 0100 0003"
⚠ Pièges et nuances
  • Big Endian partout : un parser hex non-Apple-aware lira 0x00001000 comme 16 ou 4096 selon l'endianness — vérifier toujours.
  • Normalisation NFD vs NFC : les noms de fichiers en HFS+ sont décomposés (café = cafe + combining acute + .txt). Comparaison cross-FS impose une normalisation explicite.
  • HFSX vs HFS+ : signature HX au lieu de H+, et keyCompareType = 0xBC (binary, case-sensitive). Affecte le tri des clés.
  • Hard links : un hard link HFS+ est une entrée pointant vers /.HFS+ Private Directory Data/iNodeX. Le vrai fichier vit là-bas. Suivre la chaîne via special.iNodeNum.
  • FileVault 2 / CoreStorage : volume entièrement chiffré → B-Trees inaccessibles sans clé.
  • Time Machine : sur disque externe HFS+, chaque snapshot est un dossier avec hard links de répertoires (technologie Apple non-standard) → multiplie les sources B-Tree à analyser.
  • nodeSize variable : Catalog en 4096, Extents Overflow et Attributes parfois en 1024 ou 2048. Toujours lire le BTHeaderRec de chaque arbre individuellement.
🎓 Exam Tip — HFS+ B-Trees
  • Trois B-Trees : Catalog (CNID 4), Extents Overflow (CNID 3), Attributes (CNID 8)
  • Allocation File (CNID 6) est un bitmap, pas un B-Tree
  • Endianness : Big Endian — inverser pour comparer avec NTFS / FAT
  • Quatre kinds de nœuds : header (0x01), map (0x02), index (0x00), leaf (0xFF = -1 signé)
  • Header Node = nœud #0, contient toujours 3 records (BTHeaderRec, UserData, Bitmap)
  • nodeSize dans BTHeaderRec offset 0x12 — typiquement 4096
  • Catalog key : (parentID, nodeName UTF-16 BE) → enfants contigus dans l'arbre
  • Quatre record types Catalog : Folder (0x0001), File (0x0002), FolderThread (0x0003), FileThread (0x0004)
  • Thread records : permettent de remonter d'un CNID vers son parent
  • 8 extents inline par fork dans le File Record · au-delà → Extents Overflow
  • Extents Overflow key : (forkType, CNID, startBlock) — forkType 0x00=data, 0xFF=resource
  • 5 timestamps par File Record (epoch 1904) : created, contentMod, attributeMod, access, backup
  • Récupération : nœuds libres du bitmap + slack des nœuds actifs + journal récent
Combien de B-Trees y a-t-il dans un volume HFS+ et quels sont leurs CNID ?Architecture HFS+ · Niveau : facile
Trois B-Trees :
· Catalog File (CNID 4) — hiérarchie, noms, timestamps, fork pointers
· Extents Overflow (CNID 3) — extents au-delà des 8 inline
· Attributes File (CNID 8) — xattr et ACL
L'Allocation File (CNID 6) est un bitmap classique, pas un B-Tree. Le Startup File (CNID 7) ne l'est pas non plus.
Lors d'un parcours hex, vous voyez : 00 00 00 00 00 00 00 00 01 00 00 03 au début d'un nœud B-Tree HFS+. De quoi s'agit-il ?Identification de nœud · Niveau : moyen
C'est un Header Node :
· fLink = 0 (pas de nœud suivant — Header Node est unique)
· bLink = 0 (pas de nœud précédent)
· kind = 0x01 (header)
· height = 0x00
· numRecords = 0x0003 (Big Endian → 3 records : BTHeaderRec, UserData, Map)
Donc on est au début du fichier B-Tree (Catalog, Extents Overflow ou Attributes). Lire les 106 octets suivants pour récupérer nodeSize, rootNode, firstLeafNode, etc.
Un fichier HFS+ très fragmenté a 47 extents au total. Combien d'entrées contiendra-t-il dans le Catalog vs Extents Overflow ?Mécanisme des forks · Niveau : difficile
Catalog : 1 File Record contenant les 8 premiers extents dans dataFork.extents[0..7] (ou resourceFork selon le fork concerné).
Extents Overflow : 5 records supplémentaires (chaque record = jusqu'à 8 extents).
· Record 1 : extents 9 à 16 (clé : forkType + CNID + startBlock=8)
· Record 2 : extents 17 à 24
· Record 3 : extents 25 à 32
· Record 4 : extents 33 à 40
· Record 5 : extents 41 à 47 (rempli partiellement, avec startBlock+blockCount = 0 pour les emplacements libres)
Total : 1 entrée Catalog + 5 entrées Extents Overflow = 6 endroits à parser pour reconstruire le fork complet.
