🏗 Comprendre les structures Windows = lire la mémoire comme le kernel
Volatility reconstruit les structures internes du kernel Windows depuis le dump RAM. Pour interpréter correctement ses sorties — et détecter les manipulations malveillantes — il faut comprendre les structures fondamentales : EPROCESS, ETHREAD, PEB, VAD, et la SSDT.
EPROCESS — La structure de base d'un processus
Champs forensiquement critiques
ActiveProcessLinks Liste doublement chaînée de tous les EPROCESS — manipulée par les rootkits (DKOM)
ImageFileName Nom du processus (15 cars max) — falsifiable
UniqueProcessId PID — comparaison pslist vs psscan révèle les processus cachés
CreateTime Timestamp FILETIME de création — clé pour la timeline
Peb Pointeur vers Process Environment Block (voir ci-dessous)
VadRoot Racine du VAD Tree — cartographie de la mémoire virtuelle
PEB — Process Environment Block

Structure en user-space qui décrit l'environnement du processus. Contient les chemins, les variables d'environnement, et la liste des DLLs chargées.

ImageBaseAddress Adresse de base de l'EXE en mémoire
Ldr Liste des DLLs chargées (InLoadOrderModuleList) — falsifiable par les rootkits user-mode
ProcessParameters Ligne de commande complète, répertoire courant, variables env.
BeingDebugged Flag anti-debug — certains malwares quittent si =1
vol.py -f ram.raw windows.dlllist --pid [PID]
Cartographie de l'espace mémoire Windows x64
VIRTUAL ADDRESS SPACE — Processus Windows x64 (simplifié)
0xFFFF800000000000+ Kernel Space
SSDT, drivers, kernel heap. Non accessible depuis user-mode sans vulnérabilité.
0x00007FF000000000 ntdll.dll / DLLs sys
DLLs système Windows (ntdll, kernel32, user32). Zone cible des hooks user-mode.
0x00007FFF00000000 Stack (threads)
Piles d'exécution des threads. Croissance vers le bas. Shellcodes parfois ici.
variable Pages RWX 🚨
Read+Write+Execute = IOC majeur. Shellcodes, code injecté. Détecté par malfind.
variable Heap (tas)
Allocations dynamiques. Données applicatives. Credentials souvent ici.
0x0000000000400000 Image (EXE)
Code et données de l'exécutable. Process hollowing = EXE légitime remplacé ici.
pslist vs psscan — La différence fondamentale
windows.pslist — Suit la liste chaînée

Parcourt ActiveProcessLinks dans l'EPROCESS. Un rootkit DKOM qui retire son processus de cette liste le rend invisible à pslist. Résultats fiables pour les processus normaux.

vol.py -f ram.raw windows.pslist
windows.psscan — Scan les structures EPROCESS

Scanne toute la mémoire à la recherche de la signature PROC (magic bytes EPROCESS). Trouve les processus cachés par DKOM ET les processus terminés encore en mémoire.

vol.py -f ram.raw windows.psscan
⚠️ Processus dans psscan mais PAS dans pslist = rootkit DKOM probable
💉 Les 6 techniques d'injection de code — Du classique à l'évasif
L'injection de code est la technique de persistance et d'évasion favorite des malwares Windows. Chaque technique laisse des traces différentes en mémoire — connaître le mécanisme permet de cibler le bon plugin Volatility.
1. DLL Injection classique malfind
Mécanisme : OpenProcess → VirtualAllocEx → WriteProcessMemory → CreateRemoteThread(LoadLibrary). La DLL malveillante est mappée dans le processus cible et exécutée via un thread distant.

Traces mémoire : DLL visible dans la liste des modules du PEB (InLoadOrderModuleList). Path souvent suspect (temp, AppData).
vol.py -f ram.raw windows.dlllist --pid [PID] vol.py -f ram.raw windows.ldrmodules # Discordances PEB vs VAD
2. Process Hollowing malfind
Mécanisme : Créer un processus légitime en état suspendu (CREATE_SUSPENDED) → NtUnmapViewOfSection pour vider son image → écrire le payload à la place → reprendre l'exécution. Le nom du processus reste légitime (ex: svchost.exe).

Traces mémoire : ImageBaseAddress dans le PEB ≠ adresse de base réelle du VAD. malfind détecte les pages RWX dans la section image.
vol.py -f ram.raw windows.malfind --pid [PID] vol.py -f ram.raw windows.vadinfo --pid [PID] # Base mismatch
3. Process Doppelgänging Difficile
Mécanisme : Utilise les transactions NTFS (TxF) pour créer un fichier exécutable temporaire dans une transaction non commitée — invisible au FS et à l'antivirus. Mappe l'image depuis cette transaction puis rollback.

Traces mémoire : Pas de fichier sur disque correspondant. Discordance entre le path affiché et le contenu réel. Détection complexe, peu d'outils supportent.
vol.py -f ram.raw windows.cmdline # Path suspect vol.py -f ram.raw windows.dumpfiles --pid [PID] # Extraire pour analyse
4. Reflective DLL Injection Manuel
Mécanisme : La DLL embarque son propre loader — elle se charge elle-même en mémoire sans appeler LoadLibrary. Ne laisse aucune trace dans le PEB (InLoadOrderModuleList vide pour ce module).

Traces mémoire : Plage mémoire RWX sans module correspondant dans le PEB. ldrmodules montre une discordance VAD vs DLL list. Popularisé par Metasploit (meterpreter).
vol.py -f ram.raw windows.ldrmodules # Pas dans PEB mais dans VAD vol.py -f ram.raw windows.malfind # RWX sans PE header légitime
5. Thread Execution Hijacking psscan
Mécanisme : Suspendre un thread existant d'un processus légitime → modifier son contexte (registre RIP/EIP) pour pointer vers du shellcode → reprendre. Pas de nouveau thread créé.

Traces mémoire : Thread légitime avec RIP pointant vers une zone RWX inhabituelle. windows.threads peut révéler des contextes suspects.
vol.py -f ram.raw windows.threads --pid [PID] vol.py -f ram.raw windows.malfind # Zone RWX cible
6. AtomBombing Très difficile
Mécanisme : Exploite la Global Atom Table Windows pour écrire du shellcode dans le processus cible via NtSetContextThread + QueueUserAPC. N'utilise pas WriteProcessMemory — invisible pour les hooks API classiques.

Traces mémoire : Shellcode dans des plages mémoire qui semblent légitimes. Très peu de traces directes. Corrélation APC queue + plages RWX nécessaire.
vol.py -f ram.raw windows.malfind # RWX + vérification APC strings ram.raw | grep -i "atom" # Signatures d'exploitation
Flux de détection recommandé
1
malfind — Première passe : pages RWX avec PE header ou shellcode. Couvre DLL injection, hollowing, reflective.
2
ldrmodules — Discordances entre les 3 listes PEB (InLoad, InMem, InInit) et les VAD entries. Reflective DLL = présent dans VAD, absent du PEB.
3
vadinfo + dumpfiles — Pour chaque candidat suspect : extraire le binaire, vérifier le PE header, soumettre à YARA ou VirusTotal.
4
cmdline + dlllist — Vérifier la cohérence entre le nom du processus, son chemin d'exécution, et ses DLLs chargées. Un svchost.exe depuis %TEMP% = IOC majeur.
👻 Rootkits — Manipulation des structures kernel pour l'invisibilité
Les rootkits kernel-mode (ring 0) modifient les structures internes du Windows kernel pour cacher leur présence. Les deux techniques principales forensiquement sont le DKOM (Direct Kernel Object Manipulation) et le SSDT Hooking.
DKOM — Direct Kernel Object Manipulation
Principe du DKOM

Le rootkit modifie directement la liste doublement chaînée ActiveProcessLinks dans l'EPROCESS pour retirer son propre processus. Le Task Manager, pslist, et tout outil qui suit cette liste ne le voient plus.

ProcA.Flink → ProcMalware → ProcB
après DKOM :
ProcA.Flink → ProcB (ProcMalware retiré)
Détection DKOM avec Volatility

La clé : comparer pslist (suit la liste chaînée) avec psscan (scanne les structures EPROCESS directement).

vol.py -f ram.raw windows.psscan vol.py -f ram.raw windows.psxview # Compare toutes les sources
⚠️ PID dans psscan absent de pslist = DKOM probable
SSDT Hooking — Interception des appels système
SSDT = System Service Descriptor Table
La SSDT est un tableau qui mappe les numéros de syscall Windows vers les adresses des fonctions kernel correspondantes (NtCreateProcess, NtOpenFile, etc.). Un rootkit peut remplacer ces adresses pour intercepter tous les appels système et filtrer les résultats — rendant fichiers, processus, et connexions invisibles.
SyscallAdresse légitimeAdresse hookée (exemple)Type de hookEffet
NtQuerySystemInformation 0xfffff800`12345678 0xfffff800`DEADBEEF Inline Cache processus dans le Task Manager
NtEnumerateKey 0xfffff800`23456789 0xfffff800`CAFEBABE Detour Cache clés de registre
NtQueryDirectoryFile 0xfffff800`34567890 0xfffff800`BADF00D1 Filter Cache fichiers dans l'explorateur
NtDeviceIoControlFile 0xfffff800`45678901 0xfffff800`FEEDFACE Inline Cache connexions réseau
vol.py -f ram.raw windows.ssdt # Lister toutes les entrées SSDT et détecter les hooks vol.py -f ram.raw windows.callbacks # Callbacks kernel enregistrés (PsSetCreateProcessNotifyRoutine etc.) vol.py -f ram.raw windows.driverirp # IRP handlers des drivers (hooks bas niveau)
💡 Astuce — Sur Windows 10+ avec Kernel Patch Protection (KPP / PatchGuard), le SSDT hooking direct provoque un BSOD. Les rootkits modernes utilisent plutôt des minifilters (callbacks légitimes) et des techniques user-mode plus sophistiquées. PatchGuard n'est pas parfait — des bypass existent mais sont complexes à maintenir.
🗺 VAD Tree — Virtual Address Descriptor
Le VAD Tree est la structure kernel qui cartographie toutes les plages de mémoire virtuelle allouées pour un processus : leur type (privée, mappée, image), leurs permissions (RWX), et leur origine (fichier sur disque, mémoire anonyme, section partagée). C'est la source de vérité pour détecter les injections — même quand le PEB a été manipulé.
Structure d'un nœud VAD
Champs clés d'un VAD node
StartingVpn Adresse de début de la plage (en page number)
EndingVpn Adresse de fin
u.VadFlags.Protection Permissions : PAGE_EXECUTE_READWRITE = 🚨
u.VadFlags.VadType VadNone (privé), VadImageMap (image EXE/DLL), VadAwe
Subsection.ControlArea.FileObject Pointeur vers le fichier sur disque (si image mappée)
IOC dans le VAD Tree
  • PAGE_EXECUTE_READWRITE (RWX) sans fichier associé = shellcode / injection
  • VadImageMap avec chemin %TEMP% = DLL suspecte mappée depuis un répertoire inhabituel
  • Discordance PEB vs VAD = reflective injection (DLL dans VAD absente du PEB Ldr)
  • Grande plage privée RX = code injecté après déchiffrement
  • VadNone avec permissions RX = shellcode alloué dynamiquement
ldrmodules — La discordance révélatrice
3 listes PEB + VAD = 4 sources à comparer

windows.ldrmodules compare simultanément :

PEB InLoadOrderModuleList
DLLs dans l'ordre de chargement
PEB InMemOrderModuleList
DLLs dans l'ordre en mémoire
PEB InInitOrderModuleList
DLLs dans l'ordre d'initialisation
VAD Entries (VadImageMap)
Fichiers images mappés en mémoire virtuelle
vol.py -f ram.raw windows.ldrmodules --pid [PID]
Colonnes : InLoad | InMem | InInit | MappedPath
False | False | False dans les 3 listes PEB mais présent en VAD → Reflective DLL injection
True | True | True mais MappedPath = chemin suspect → DLL hijacking
Commandes VAD essentielles
vol.py -f ram.raw windows.vadinfo --pid [PID] # Dump complet du VAD Tree vol.py -f ram.raw windows.vadwalk --pid [PID] # Parcours récursif vol.py -f ram.raw windows.malfind # Filtre automatiquement les VAD RWX suspects vol.py -f ram.raw windows.ldrmodules # Comparaison PEB vs VAD pour tous les processus
⏱ Timeline mémoire — Reconstituer la séquence d'une attaque
La mémoire RAM contient des timestamps précieux : création des processus (EPROCESS.CreateTime), connexions réseau (netscan timestamps), modifications du registre en cache. Combinés avec les artefacts disque et les logs, ils permettent de reconstruire la kill chain complète.
Sources de timestamps dans la RAM
EPROCESS.CreateTime
Timestamp de création de processus
Présent dans chaque structure EPROCESS. Fiable même pour les processus cachés (psscan le récupère). Format FILETIME 100ns. Clé pour ordonner l'exécution des payloads.
vol.py -f ram.raw windows.pstree # Affiche CreateTime de chaque processus
Netscan timestamps
Connexions réseau avec horodatage
windows.netscan extrait les structures _TCP_ENDPOINT et _UDP_ENDPOINT avec leurs timestamps de création. Connexions actives ET fermées encore en mémoire.
vol.py -f ram.raw windows.netscan --include-corrupt
Hive timestamps (registre)
Clés de registre modifiées en cache
Le registre Windows est partiellement en mémoire. windows.hivelist + windows.printkey permettent d'accéder aux clés de persistance (Run, Services) avec leurs LastWriteTime.
vol.py -f ram.raw windows.hivelist vol.py -f ram.raw windows.printkey --key "SOFTWARE\Microsoft\Windows\CurrentVersion\Run"
Thread CreateTime
Création de threads (injection via CreateRemoteThread)
Chaque ETHREAD a un CreateTime. Un thread créé dans un processus légitime à un moment suspect (juste après un email ouvert, après une connexion web) est un IOC fort.
vol.py -f ram.raw windows.threads --pid [PID]
NTLM / Kerberos tickets
Tickets Kerberos avec validité temporelle
Les tickets Kerberos en mémoire (LSASS) ont des timestamps StartTime/EndTime. Un Golden Ticket a souvent une durée anormale (10 ans). Pass-the-Hash = tickets NTLM sans expiration normale.
vol.py -f ram.raw windows.hashdump # NTLM hashes vol.py -f ram.raw windows.cachedump # Domain cached creds
Intégration avec Plaso / log2timeline
Exporter depuis Volatility pour Plaso
vol.py -f ram.raw windows.pstree > pstree.txt vol.py -f ram.raw windows.netscan > netscan.txt log2timeline.py --parsers volatility plaso.db ram.raw
Corrélation avec les sources disque
  • EPROCESS.CreateTime ↔ Event Log 4688 (Process Creation)
  • Netscan connexion ↔ firewall logs / Zeek conn.log
  • Thread CreateTime ↔ Sysmon Event ID 8 (CreateRemoteThread)
  • Hive LastWriteTime ↔ Autoruns / Registry forensics
🎯 Cas pratiques — De la mémoire à la preuve
Ces 3 cas illustrent comment appliquer les techniques précédentes dans des scénarios réels d'Incident Response. Chaque cas suit le flux : symptôme → hypothèse → commandes → findings → conclusion.
🎯 Cas 1 — Meterpreter en mémoire (Red Team détecté)
Symptôme : L'EDR alerte sur un comportement réseau anormal depuis explorer.exe. Connexion sortante vers une IP externe sur le port 4444. L'antivirus ne détecte rien sur disque.

Hypothèse : Meterpreter injecté par reflective DLL injection dans explorer.exe — pas de fichier sur disque, donc l'AV ne voit rien.
vol.py -f ram.raw windows.pslist # Confirmer PID de explorer.exe vol.py -f ram.raw windows.netscan # Confirmer connexion 4444 vol.py -f ram.raw windows.ldrmodules --pid 1234 # Discordances PEB vs VAD vol.py -f ram.raw windows.malfind --pid 1234 # Pages RWX sans PE légitime vol.py -f ram.raw windows.dumpfiles --pid 1234 # Extraire toutes les régions
Finding : ldrmodules révèle une plage mémoire RWX présente dans le VAD mais absente des 3 listes PEB — signature classique de reflective DLL injection. malfind confirme le PE header MZ dans cette plage. Le binaire extrait match les signatures YARA Meterpreter (stageless).
🎯 Cas 2 — Rootkit DKOM (processus fantôme)
Symptôme : Activité réseau détectée par le pare-feu vers un domaine C2 connu, mais aucun processus correspondant visible dans le Task Manager ou les outils live.

Hypothèse : Rootkit kernel-mode avec DKOM — processus retiré d'ActiveProcessLinks mais toujours actif.
vol.py -f ram.raw windows.pslist # Liste "officielle" — processus absent vol.py -f ram.raw windows.psscan # Scan brut — processus détecté! vol.py -f ram.raw windows.ssdt # Vérifier hooks SSDT vol.py -f ram.raw windows.modules # Comparer avec modscan vol.py -f ram.raw windows.modscan # Modules kernel cachés
Finding : psscan révèle un PID (2744) présent en mémoire mais absent de pslist — DKOM confirmé. Le processus a le nom svchost.exe mais son chemin d'image est C:\Users\user\AppData\Local\Temp\svch0st.exe. windows.ssdt révèle NtQuerySystemInformation hookée → module rootkit identifié.
🎯 Cas 3 — Credential dumping via LSASS (Mimikatz)
Symptôme : Sysmon Event ID 10 (ProcessAccess) sur lsass.exe depuis un processus non autorisé. Pas de fichier dump lsass.dmp trouvé sur disque.

Hypothèse : Mimikatz utilisé en mémoire (réflexif) ou credentials extraits directement depuis la RAM via ReadProcessMemory sur LSASS.
vol.py -f ram.raw windows.pslist # Trouver PID lsass.exe vol.py -f ram.raw windows.handles --pid [lsass_pid] # Handles ouverts sur lsass vol.py -f ram.raw windows.hashdump # NTLM hashes depuis SAM en mémoire vol.py -f ram.raw windows.lsadump # Secrets LSA vol.py -f ram.raw windows.cachedump # Domain cached credentials vol.py -f ram.raw windows.cmdline # Commandes exécutées (Mimikatz CLI?)
Finding : windows.handles révèle que le PID 3892 (powershell.exe) avait un handle PROCESS_VM_READ + PROCESS_QUERY_INFORMATION sur lsass.exe — permissions exactes nécessaires à Mimikatz. windows.hashdump extrait 14 hashes NTLM dont celui de l'administrateur du domaine. Corréler avec Sysmon EID 10 pour confirmer l'heure exacte de l'accès.
💊 Q1 — Un processus apparaît dans windows.psscan mais PAS dans windows.pslist. Que cela indique-t-il, et quel est le mécanisme ?
✓ C'est la signature d'un rootkit DKOM (Direct Kernel Object Manipulation). Le rootkit a retiré le processus de la liste doublement chaînée ActiveProcessLinks dans l'EPROCESS — pslist suit cette liste et ne le voit plus. En revanche, psscan scanne toute la mémoire à la recherche de la signature des structures EPROCESS directement — il le trouve car la structure est toujours en mémoire.
💊 Q2 — Qu'est-ce que le Process Hollowing et quelle est sa trace caractéristique détectable par Volatility ?
✓ Le Process Hollowing crée un processus légitime en état suspendu (ex: svchost.exe), vide son image avec NtUnmapViewOfSection, écrit le payload malveillant à la place, puis reprend l'exécution. Trace caractéristique : l'ImageBaseAddress dans le PEB ne correspond pas à l'adresse de base réelle dans le VAD Tree. windows.malfind détecte les pages RWX dans la section image. windows.vadinfo montre la discordance d'adresse.
💊 Q3 — Comment windows.ldrmodules permet-il de détecter une Reflective DLL Injection ?
✓ La Reflective DLL Injection charge une DLL en mémoire sans passer par LoadLibrary — elle ne s'enregistre donc pas dans les 3 listes PEB (InLoad, InMem, InInit). windows.ldrmodules compare simultanément ces 3 listes PEB avec les entrées VAD de type VadImageMap. Une DLL présente dans le VAD (True dans la colonne VAD) mais False | False | False dans les 3 colonnes PEB = Reflective DLL injection. C'est la signature exacte de Meterpreter stageless, par exemple.
💊 Q4 — Qu'est-ce que la SSDT et pourquoi un hook SSDT rend-il des artefacts invisibles aux outils forensiques classiques ?
✓ La SSDT (System Service Descriptor Table) mappe les numéros de syscall Windows vers les adresses des fonctions kernel (NtCreateProcess, NtQuerySystemInformation, etc.). Tous les appels système passent par elle. Un rootkit qui remplace l'adresse de NtQuerySystemInformation dans la SSDT intercepte tous les appels à cette fonction — y compris ceux de Volatility — et peut filtrer les résultats (cacher un processus, une clé de registre, un fichier). windows.ssdt de Volatility détecte ces hooks en comparant les adresses actuelles avec celles attendues dans les modules légitimes.
💊 Q5 — Quelles permissions mémoire (flags VAD) indiquent un shellcode ou du code injecté ? Comment les détecter ?
✓ PAGE_EXECUTE_READWRITE (RWX) — une région mémoire à la fois exécutable, lisible et modifiable est anormale pour du code légitime. Les EXE et DLL normaux chargés par Windows ont des sections séparées (code = RX, données = RW). Une plage RWX sans fichier image correspondant dans le VAD est un IOC majeur. Détection : windows.malfind filtre automatiquement les plages RWX suspectes et affiche un hexdump + désassemblage des premiers octets.
💊 Q6 — Dans le cadre d'un dump LSASS pour credential dumping, quels handles sur lsass.exe sont révélateurs d'un accès malveillant ?
✓ Les handles révélateurs sont ceux combinant PROCESS_VM_READ (lecture de la mémoire du processus) et PROCESS_QUERY_INFORMATION (query des informations) sur lsass.exe depuis un processus non système. Ce sont exactement les permissions utilisées par Mimikatz, ProcDump (-ma lsass), et les outils de credential dumping. windows.handles --pid [lsass_pid] liste tous les handles ouverts sur lsass — identifier quel autre processus tient ces handles révèle l'attaquant.
