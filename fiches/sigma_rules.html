🔑 Sigma — un format de détection portable, agnostique du SIEM
Sigma est à YARA ce que Snort est aux paquets réseau : un format ouvert, lisible humain, qui décrit une logique de détection sur des logs. Le format est YAML, sans dépendance vendeur. Une même règle Sigma se convertit en requête Splunk SPL, Elastic ES|QL, KQL Microsoft Sentinel, Chronicle YARA-L, QRadar AQL, etc. Créé en 2017 par Florian Roth (Nextron Systems) et Thomas Patzke, maintenu sous l'organisation SigmaHQ (GitHub), le dépôt officiel compte aujourd'hui plus de 3'000 règles couvrant Windows, Linux, macOS, cloud (AWS/Azure/GCP/Okta/M365), proxy web, etc. C'est devenu le standard de fait du detection engineering ouvert.
Structure minimale d'une règle Sigma
title: Suspicious Whoami Execution
id: 929a690e-bef0-4204-a928-ef5e620d6fcc
status: stable
description: Détecte l'exécution de whoami.exe, fréquente en reconnaissance post-exploitation
references:
    - https://attack.mitre.org/techniques/T1033/
author: Florian Roth
date: 2019-10-23
modified: 2025-04-12
tags:
    - attack.discovery
    - attack.t1033
logsource:
    category: process_creation
    product: windows
detection:
    selection:
        Image|endswith: '\whoami.exe'
    condition: selection
falsepositives:
    - Scripts d'administration légitimes
level: medium
Les 5 sections clés (spec officielle SigmaHQ)
📛 Métadonnées

title (court, max 100 chars), id (UUID v4 obligatoire, unique), status (stable · test · experimental · deprecated · unsupported), description, author, date (création), modified, references.

🪵 logsource

Source de logs ciblée. Trois champs : product (windows, linux, aws, azure, okta…), category (process_creation, file_event, network_connection, registry_event…), service (security, sysmon, terminalservices…). Définit la taxonomie à appliquer.

🔍 detection

Cœur de la règle. Une ou plusieurs selections (chacune = un dictionnaire de field/value), combinées par la condition finale. La selection par défaut s'appelle selection. Synonymes possibles : filter, keywords.

⚖️ condition

Expression booléenne combinant les selections. Opérateurs : and · or · not. Quantifieurs : 1 of selection_*, all of selection_*. Exemple : selection and not filter_legit.

⚠️ falsepositives

Liste libre de scénarios connus de faux positifs (scripts admin, outils de monitoring, etc.). Indispensable pour calibrer le seuil d'alerte côté SOC.

🚨 level

Sévérité : informational · low · medium · high · critical. Utilisé par les SIEM pour le routage (auto-investigate, alerte SOC L1/L2, page-out).

⚠ Convention de nommage des fichiers — Selon la spec SigmaHQ : YYYYMM_short_description.yml ou plus simplement category_target_description.yml (ex. proc_creation_win_susp_whoami.yml). Encodage UTF-8, retours ligne LF (jamais CRLF), indentation 4 espaces, clés en minuscules, strings entre apostrophes simples.
🧠 La logique Sigma : YAML → ET/OU implicites
Sigma utilise la structure YAML elle-même pour exprimer la logique : un dictionnaire (clé:valeur) = AND entre les champs, une liste (- item) = OR entre les valeurs. C'est élégant mais déstabilisant pour les débutants. Maîtriser ces deux constructions, plus l'usage des selections multiples, suffit à 95 % des règles écrites.
Les 4 patterns essentiels
① OR sur une valeur
selection:
    EventID:
        - 4728   # ajout à groupe
        - 4729   # retrait de groupe
        - 4730   # création de groupe
condition: selection

Liste de valeurs → match si l'une des valeurs apparaît.

② AND entre champs
selection:
    EventID: 4624
    LogonType: 10       # RDP
    SourceIP|startswith: '192.168.'
condition: selection

Dictionnaire de plusieurs champs → match si tous matchent (AND implicite).

③ Selections multiples + condition
selection_proc:
    Image|endswith: '\powershell.exe'
selection_args:
    CommandLine|contains|all:
        - '-enc'
        - 'http'
filter_admin:
    User|contains: 'admin_'
condition: selection_proc and selection_args
           and not filter_admin

Selections nommées + condition explicite. C'est la forme la plus puissante.

④ Quantifieurs & wildcards
selection_1: { EventID: 1 }
selection_2: { EventID: 11 }
selection_3: { EventID: 13 }
filter_x:    { Image|endswith: '\legit.exe' }
condition: 1 of selection_* and not filter_x

1 of, all of, any of + wildcard selection_* pour grouper.

Pièges fréquents

Erreur #1 — confondre dict et list. Une liste de field:value n'est PAS un OR sur champs, c'est invalide. Pour OR sur plusieurs champs, on crée plusieurs selections + condition selection_a or selection_b.

Erreur #2 — oublier la backslash escaping. Dans Image|endswith: '\powershell.exe', le \ simple dans une string entre apostrophes simples passe — mais en double-quotes "\\powershell.exe" est nécessaire.

Erreur #3 — match insensible à la casse non garanti. Le comportement par défaut est backend-dependent. Pour forcer l'insensibilité, certains backends nécessitent un modificateur explicite (cf. tab 3).

🔧 Les modificateurs — la signature Sigma
Les modificateurs (value modifiers) s'appliquent aux field names via le séparateur |. Ils sont chaînables : fieldname|mod1|mod2: valeur. Le backend (Splunk, Elastic…) traduit ensuite la combinaison en syntaxe native. Maîtriser une douzaine de modificateurs couvre 95 % des cas réels.
Modificateurs essentiels
📍 Position dans la string

|startswith : commence par
|endswith : finit par
|contains : contient (n'importe où)

Ex. Image|endswith: '\mimikatz.exe'

🧮 Combinatoires

|all : toutes les valeurs doivent matcher (au lieu du OU par défaut)
|cidr : interprétation CIDR pour adresses IP
|re : interprète comme regex

Ex. CommandLine|contains|all: ['-enc', 'http'] (les 2 doivent être présents)

🔢 Comparaisons numériques

|lt : strictement inférieur
|lte : inférieur ou égal
|gt : strictement supérieur
|gte : supérieur ou égal

Ex. FileSize|gt: 1000000

📦 Transformations

|base64 : encode la valeur en base64 avant match
|base64offset : variantes d'alignement (offsets 0/1/2 — important PowerShell -EncodedCommand)
|wide : interprétation UTF-16 LE (strings Windows)

Ex. CommandLine|base64offset|contains: 'DownloadString'

🪞 Existence & null

|exists: true|false : le champ est présent / absent

Permet de détecter quand un champ attendu manque (anti-forensique).

↻ Récents (post-2024)

|fieldref : référence à un autre champ (self-reference)
|expand : expansion de placeholders
|windash : tolérance aux variations de tiret (-, /, —) dans les arguments CLI

|windash est devenu essentiel pour contrer les obfuscations côté CLI Windows.

⚒ L'écosystème outillé autour de Sigma
Une règle Sigma ne s'exécute pas seule : elle doit être compilée vers le langage natif du SIEM cible (SPL Splunk, ES|QL Elastic, KQL Sentinel, etc.) ou interprétée par un moteur dédié sur des fichiers de logs locaux. Deux mondes coexistent : la conversion en ligne pour alimenter un SIEM, et le hunting offline (DFIR pure) directement sur des EVTX/journaux extraits d'un disque.
⚒ Conversion vers SIEM — sigma-cli (Python)
# Installation (officielle SigmaHQ)
pip install sigma-cli
pip install pysigma-backend-splunk pysigma-backend-elasticsearch \
            pysigma-backend-microsoft365defender pysigma-pipeline-sysmon

# Conversion d'une règle vers Splunk SPL
sigma convert -t splunk -p sysmon rule.yml

# Conversion vers Elastic ES|QL (avec mapping ECS)
sigma convert -t elasticsearch -p ecs_windows rule.yml

# Conversion vers Microsoft Sentinel (KQL)
sigma convert -t microsoft365defender rule.yml

# Batch d'un dossier entier
sigma convert -t splunk -p sysmon rules/ -o output/

# Lister les backends & pipelines disponibles
sigma list targets
sigma list pipelines

Note historique : l'ancien outil sigmac (Python) est déprécié depuis 2022 ; le projet officiel est sigma-cli (basé sur la librairie pySigma). Tous les guides récents l'utilisent.

🎯 Hunting offline — Chainsaw & Hayabusa
⚡ Chainsaw (Rust, WithSecure / F-Secure Countercept)

Scan rapide d'EVTX avec règles Sigma. Particulièrement adapté au triage de forensique. Sortie ASCII, CSV ou JSON. Détections built-in en plus de Sigma (audit log cleared, brute force…).

chainsaw hunt evtx_samples/ \
  -s sigma/rules/windows/ \
  --mapping mappings/sigma-event-logs-all.yml \
  --json -o results.json

Repo : WithSecureLabs/chainsaw · Compétences supplémentaires : analyse MFT, Shimcache/Amcache, SRUM, dump registry/ESE.

🦅 Hayabusa (Rust, Yamato Security)

🎯 Écrire des règles qui survivent à la production
Une règle Sigma écrite à chaud génère typiquement trop de bruit en production. Les règles SOC durables suivent quelques principes simples : logsource précise (pas category: any), tags MITRE obligatoires, falsepositives documentés, versioning Git, et tests unitaires avec EVTX d'attaque (EVTX-ATTACK-Samples).
Workflow detection engineering moderne
1️⃣ Source — TTPs MITRE

Toute règle commence par une technique MITRE ATT&CK ciblée (ex. T1059.001 — PowerShell). Le mapping tags: attack.execution / attack.t1059.001 est obligatoire pour le routage SOC.

2️⃣ Source de log précise

Préférer logsource: { category: process_creation, product: windows, service: sysmon } à un any. Pipeline approprié à la conversion (sigma convert -p sysmon ...).

3️⃣ Tests unitaires

Tester avec SBousseaden/EVTX-ATTACK-Samples (références de l'industrie). Chainsaw + Sigma lance la règle sur l'EVTX, vérifie le match (TP) et l'absence sur baseline (TN).

4️⃣ Versioning Git

Repository dédié org/detection-rules. Pull-request reviews. CI auto avec sigma-check (validation YAML + spec) avant merge. Tag de version + changelog.

5️⃣ Déploiement progressif

Canary : déployer en status: experimental ou test d'abord, observer 14 jours en SIEM en mode silencieux, mesurer FP rate, basculer en stable avec alerte SOC.

6️⃣ Mise à jour

Re-tester périodiquement contre les nouvelles versions d'OS, nouveaux EDR, nouvelles techniques (les attaquants changent leurs obfuscations). Le champ modified: doit refléter la dernière révision.

Anatomie d'une règle solide — exemple complet
title: Suspicious PowerShell Download via EncodedCommand
id: 3b0047b3-5f8a-4c25-9c6b-6d5a96f9c8d7
status: test
description: Détecte PowerShell exécuté avec -EncodedCommand téléchargeant
    un fichier depuis Internet. Tactique d'initial access ou
    ingress tool transfer typique des attaquants (Akira, etc.).
references:
    - https://attack.mitre.org/techniques/T1059/001/
    - https://attack.mitre.org/techniques/T1105/
author: CAS-IN
date: 2026/03/15
modified: 2026/05/18
tags:
    - attack.execution
    - attack.t1059.001
    - attack.command_and_control
    - attack.t1105
logsource:
    category: process_creation
    product: windows
detection:
    selection_proc:
        Image|endswith: '\powershell.exe'
    selection_args:
        CommandLine|contains|all:
            - '-enc'
            - 'http'
    selection_args_b64:
        CommandLine|base64offset|contains:
            - 'DownloadString'
            - 'DownloadFile'
            - 'Invoke-WebRequest'
    filter_known_admin:
        ParentImage|endswith: '\sccm_admin_console.exe'
    condition: selection_proc
               and (selection_args or selection_args_b64)
               and not filter_known_admin
falsepositives:
    - Scripts d'administration légitimes utilisant -enc + URL interne
    - Outils SCCM/MECM (à inclure dans filter_known_admin)
level: high

Lien CTI : Sigma + YARA + MISP + STIX = stack standard du detection engineering moderne

Vous écrivez une règle Sigma pour détecter PowerShell téléchargeant via -EncodedCommand. L'attaquant peut encoder le payload en base64. Quel modificateur utilisez-vous pour détecter quand même la string DownloadString dans le contenu encodé, et pourquoi pas simplement |base64 ?
Sigma · Niveau : moyen
On utilise CommandLine|base64offset|contains: 'DownloadString'. Le modificateur |base64offset (et non |base64) génère trois variantes d'encodage selon l'offset d'alignement (0, 1, 2 octets de padding au début), parce que PowerShell -EncodedCommand encode la string entière incluant les octets précédents — l'alignement n'est pas garanti. |base64 simple ne génère qu'une variante et raterait 2/3 des matches. Combiné à |contains, on cherche n'importe où dans la string. C'est l'idiome standard pour détecter du PowerShell obfusqué en SOC moderne.
