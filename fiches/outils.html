🔍 X-Ways & WinHex — Le standard judiciaire allemand
X-Ways Forensics et WinHex (X-Ways Software AG, Allemagne · Stefan Fleischmann) constituent le couple forensique de référence en Suisse pour les expertises judiciaires. Trois caractéristiques en font le choix par défaut des experts : (1) Portabilité totale — installation entièrement sur clé USB, aucune trace sur la machine d'analyse, license sur dongle USB physique. (2) Vitesse exceptionnelle — moteur ultra-optimisé, parsing de MFT 100x plus rapide qu'Autopsy, snapshot d'un disque 1 To en quelques minutes. (3) Reconnaissance judiciaire — utilisé par BKA Allemagne, Europol, fedpol, TPF, ministères publics cantonaux suisses ; tous les rapports sont reconnus comme méthodologiquement valides. Le Volume Snapshot est le concept central : un index virtuel du système de fichiers qu'on raffine progressivement (carving, hash lookup, type detection, OCR…) pour faire émerger toutes les preuves. WinHex est l'ancêtre et le microscope chirurgical de X-Ways : éditeur hexadécimal bas-niveau pour analyser MBR, GPT, structures FAT/NTFS à la main, ou déboguer un secteur corrompu.

② Installation portable
📦 Décompression

Archive .zip à décompresser dans un dossier dédié (ex. C:\Forensics\X-Ways\). Ne jamais lancer depuis le ZIP.

🔑 Dongle USB

Clé matérielle USB obligatoire. Sans elle : logiciel qui ne démarre pas, ou version limitée. Modèle BYOD — Bring Your Own Dongle.

▶️ Lancement

Double-clic sur xwforensics.exe. Aucun setup.exe, aucune modification du registre Windows de la machine hôte.

🚀 Mode nomade

X-Ways installable sur une clé USB ou un SSD externe. Sur la scène : brancher · lancer · analyser — sans rien installer sur la machine cible. Essentiel en intervention.

③ Créer un Cas (.xfc)
⚠️ Règle absolue : aucune manipulation de preuve sans un .xfc actif. Le Cas produit automatiquement un journal d'actions (Case Log) — c'est lui qui démontre la traçabilité devant un tribunal.
1
Fichier → Créer un nouveau cas. X-Ways génère un fichier .xfc — petit fichier texte, aucun contenu de preuve, sert d'index.
2
Dossier de stockage — choisir un emplacement qui n'est PAS le disque de preuve. Y iront les fichiers temporaires, index et rapports.
3
Métadonnées — nom de l'examinateur · numéro de dossier · agence · commentaires. Ces champs apparaissent automatiquement dans le rapport final.
4
Validation. Le .xfc est créé. Mémoire vivante de l'enquête : preuves · signets · chemins · hashs · log.

On ne travaille jamais sur le disque original — toujours sur une copie forensique.

📂 Procédure d'ajout

Menu Fichier → Ajouter une image (ou clic droit dans l'arborescence de cas).

Si l'image est segmentée (.e01, .e02, .e03…), sélectionner uniquement le premier segment — X-Ways charge automatiquement la suite.

✅ Choisir : Disque physique

Accès au MBR, aux zones non partitionnées, au slack space et à tous les fichiers effacés.

✗ Éviter : Partition logique

Perte de l'espace non alloué, des anciens fichiers effacés et du slack space.

🔐 Vérification du Hash (intégrité)

X-Ways calcule automatiquement MD5 / SHA-256 lors de l'acquisition. Image reçue ? Outils → Compute Hash et comparer avec le PV de saisie. Les deux empreintes coïncident → la copie est conforme.

F10 = raccourci hash dans X-Ways.

💡 Copie bit-à-bit vs Snapshot — à ne pas confondre. Copie bit-à-bit = véritable sauvegarde physique (secteurs 0→N, slack & non alloué). Format .E01 ou .DD, produite via Tools → Disk Tools → Create Disk Image. Volume Snapshot = simple photo logique interne à X-Ways, pour comprendre où sont les fichiers. Ce n'est pas une sauvegarde.
⑤ Volume Snapshot — cœur de l'analyse

Sans Snapshot, X-Ways est aveugle. Concept le plus important de l'outil.

📸 À quoi sert le Snapshot ?

Au chargement d'une image, X-Ways ne voit que des secteurs bruts. Le Snapshot est une reconstruction logique du contenu : fichiers existants, supprimés, fragments résiduels, structures internes (archives, emails). Toute l'analyse ultérieure en dépend.

  • Lit la table des fichiers (MFT en NTFS, FAT en FAT32)
  • Reconstitue l'arborescence des dossiers
  • Détecte les fichiers supprimés encore référencés
  • Identifie les vrais types de fichiers (par signature)
⌨️ Lancer le Snapshot : F9 — ou menu Spécialiste → Raffiner le snapshot de volume. À ce moment, X-Ways demande la profondeur d'analyse (cases à cocher).
☑️ Options essentielles à cocher
  • Fichiers supprimés — récupération depuis les entrées marquées deleted
  • Vérification des signatures — détecte les extensions falsifiées
  • Calcul de hash (MD5 / SHA-256 par fichier)
  • Recherche rapide de fichiers communs
⚠️ Règle du Snapshot — à bien comprendre. On peut relancer un Refine Snapshot plusieurs fois avec des options différentes — chaque passe enrichit le snapshot existant. Par contre, il ne faut jamais interrompre un Refine en cours (corruption des références internes), ni relancer avec des options incompatibles qui écraseraient les précédentes. Workflow recommandé : ① Snapshot simple (rapide) pour exploration → ② Refine Snapshot ciblé.

🔄 La récursivité — voir tous les fichiers d'un coup

Par défaut, cliquer sur Documents n'affiche que les fichiers directs, pas les sous-dossiers. Activer la récursivité (icône flèche recourbée · List all files in subdirectories) pour aplatir toute l'arborescence en une seule liste.

Indispensable pour trier par date : « tout ce qui a été modifié le 12 mars, peu importe où c'est rangé ».

🏷 Colonnes indispensables

Clic droit sur un en-tête → activer :

  • Name · nom du fichier
  • Ext · extension déclarée
  • Type (réel) · détecté par signature — un .jpg qui est en fait un .exe est immédiatement visible
  • Created / Modified / Accessed · les trois dates MAC
  • Size · Attr (H=caché · S=système · D=deleted)
  • Sender / Recipient / Subject — se remplissent automatiquement si PST/OST parsé
🔎 Le Data Interpreter (fenêtre Hexa). Sélectionner 4 octets dans le volet hex → affichage comme entier, date, GUID… Attention au réglage : 32 bit Unsigned Integer pour la taille d'un fichier FAT. Et ne pas oublier que FAT stocke en Little Endian (00 E4 00 00 se lit 00 00 E4 00 = 58 368 octets).

⑧ Recherche — Logique vs Physique
ModePortéeVitesseUsage

⏱ Coût de la recherche physique : sur 1 To → plusieurs heures. Toujours limiter le périmètre selon l'hypothèse d'enquête — sinon l'analyse se noie dans le bruit et la démonstration devant tribunal s'en trouve affaiblie. Contexte de résultat par défaut : 128 octets avant/après.
⑨ Type Status & entropie — détection de dissimulation
✅ OK

L'extension correspond à la signature binaire détectée.

🎭 Mismatch

L'extension ne correspond pas à la signature — dissimulation probable (rapport.pdf qui est en réalité un .exe).

❓ Unknown

Type non reconnu dans la base interne de X-Ways.

🔐 e / e?

e = chiffré probable · e? = haute entropie (chiffrement possible ou compression forte).

📊 Analyse d'entropie

Mesure du caractère aléatoire des données. Entropie ≈ 1.0 → chiffrement ou compression forte. Dans X-Ways : icône loupe → afficher l'entropie. Alternative externe : CyberChef avec la recette Entropy.

Essentiel pour détecter les conteneurs TrueCrypt / VeraCrypt, qui ne reposent sur aucune extension — seule l'analyse statistique révèle leur nature chiffrée.

Faux positif classique : une vidéo H.265 très compressée peut aussi avoir une haute entropie sans être chiffrée.

⑩ Carving — récupération par signature
✂️ Principe

Parcours séquentiel de l'espace non alloué à la recherche de signatures connues. Fonctionne même sans entrée de répertoire valide — parfait pour les supports FAT après effacement (octet 0xE5).

Magic bytes les plus courants à connaître :

🎯 Stratégie de reconstruction
  1. Chercher d'abord un fichier existant dans le système
  2. Si supprimé → vérifier si les clusters sont contigus
  3. Contigus → reconstruction directe depuis le cluster de début + taille lue dans le SFN
  4. Fragmentés → carving multi-fragment beaucoup plus complexe
  5. Résultat potentiellement corrompu si certains clusters ont été réalloués
🎬 Preuve de présence par hash sectoriel. Une vidéo présente une structure répétitive sur un grand nombre de secteurs consécutifs. En identifiant un bloc caractéristique, l'analyste calcule son empreinte et recherche des occurrences ailleurs sur le support. Si un bloc identifiable est retrouvé, on peut affirmer que la vidéo a existé à un moment donné, même si la reconstruction complète est impossible. Une preuve de présence peut suffire judiciairement, indépendamment de la lisibilité finale.
⑪ Fuzzy Doc & emails
🧩 Fuzzy Doc — logique floue

Recherche de fichiers similaires mais non identiques. X-Ways crée un set de hashs fuzzy à partir d'un fichier de référence.

  • Variantes d'une même facture
  • Modèles légèrement modifiés
  • Doublons partiels sur plusieurs supports
  • Enquêtes financières / fraude documentaire
📧 PST / OST / MBOX

Conteneurs complexes de milliers d'objets. Workflow :

  1. Identifier le type via Type Status (pas l'extension)
  2. Refine Snapshot → extraire les emails
  3. Filtrer par expéditeur / destinataire / date
  4. Exporter avec pièces jointes
  5. Vérifier le dossier Deleted Items

Nom se terminant par « … » dans l'interface = contenus internes explorables.

⚠️ Un seul fichier actif à la fois. Lors de l'analyse de mails, ne conserver qu'un seul fichier PST/OST actif dans le snapshot — sinon doublons et incohérences.
⑫ Récupération de fichiers supprimés

Les fichiers effacés apparaissent grisés, avec un ? en première lettre.

♻️ Le fichier ?APPORT.docx

Dans FAT, quand un fichier est supprimé, le premier octet de son entrée SFN est remplacé par 0xE5. La première lettre du nom est donc perdue → X-Ways affiche ?.

L'astuce LFN : si le fichier avait un nom long, l'entrée LFN juste au-dessus contient le nom complet intact. X-Ways lit cette entrée et restitue automatiquement la lettre manquante.

Action : clic droit → Récupérer / Copier.

💡 Ouvrir un disque physique (pas une lettre de lecteur). Menu File → Open Disk. Ignorer les lecteurs C:, D:, E: (listes des Logical Drives) et choisir Physical Media → Disk 1, 2, 3. On accède alors au MBR, à l'espace non partitionné, aux restes de fichiers effacés.
⑬ WinHex — le microscope chirurgical

Si X-Ways est la salle d'autopsie, WinHex est le scalpel.

🧬 Parenté avec X-Ways

WinHex est le père de X-Ways. X-Ways, c'est WinHex augmenté de fonctionnalités de tri, rapport et analyse automatisée. Le moteur bas-niveau est commun. WinHex intervient quand X-Ways n'est plus suffisant : inspection manuelle (MBR, en-tête), réparation d'un disque corrompu, récupération manuelle (Data Carving), compréhension d'un fichier qui refuse de s'ouvrir.

⚙️ Installation & droits
  • Portable — décompresser le .zip sur la clé USB d'analyse
  • Lancer WinHex.exe
  • Clic droit → Exécuter en tant qu'administrateur — impératif pour accéder aux disques physiques. Sinon, seulement les fichiers logiques seront visibles.
🧱 L'interface — la « matrice »
┌────────────────┬──────────────────────────────────┬──────────────┐
│ Offset (gauche)│ Hexadécimal (centre)             │ ASCII (droit)│
│ 000001F0       │ 41 6E 61 6C 79 73 65 20 66 6F 72 │ Analyse for..│

Offset = adresse en octets depuis le début
Hexa   = donnée brute (55 AA, FF D8, etc.)
ASCII  = traduction humaine (41 = 'A') · '.' si non imprimable
💿 Ouvrir un disque — F9

Tools → Open Disk. Deux listes :

  • Logical Drive (C:, D:) — à éviter · passage par Windows
  • Physical Media (Disk 0, Disk 1) — choix obligatoire · accès brut secteur par secteur, MBR inclus
🧠 Ouvrir la RAM

Tools → Open RAM. Permet d'ouvrir la mémoire vive d'un processus en cours (ex. chrome.exe) pour y chercher des mots de passe déchiffrés ou des artefacts éphémères.

🧭 Navigation chirurgicale
Ctrl+GGo To — se déplacer à un secteur/offset précis (ne jamais scroller à la souris sur 1 To)
Ctrl+FText Search — « password », « Jean »… attention ASCII vs UNICODE
Ctrl+FHex Value Search — signature binaire : FF D8 FF pour JPEG effacés
PageDownDescendre d'une page écran
📐 Templates — la fonction pédagogique reine

View → Template Manager (ou Alt+F12). WinHex plaque une grille de lecture sur les données brutes.

Cas pratique — analyser le MBR :

  1. Ouvrir le disque physique → se placer au secteur 0
  2. Alt+F12 → choisir le template Master Boot Record
  3. WinHex décode automatiquement la structure des 512 octets :
// Structure totale d'un MBR = 512 octets

Offset 0   → 446 octets   Code bootloader (chargé au boot BIOS)
Offset 446 →  64 octets   Table de partitions (4 entrées × 16 octets)
                           • Offset 446 : Partition 1
                           • Offset 462 : Partition 2
                           • Offset 478 : Partition 3
                           • Offset 494 : Partition 4
Offset 510 →   2 octets   Signature 55 AA (little-endian : AA 55)

// TOTAL : 446 + 64 + 2 = 512 octets

Idéal pour vérifier ses cours sur les structures FAT, NTFS, exFAT. Autres templates utiles disponibles : FAT32 Boot Record · NTFS Boot Sector · GPT Header · $MFT Entry.

📦 Clonage & imagerie

File → Create Disk Image :

  • Raw (dd) — copie brute
  • .E01 — uniquement si licence Specialist ou supérieure

WinHex gère automatiquement le découpage (splitting) et le hash MD5.

⚠️ WinHex est un ÉDITEUR — danger. Contrairement à X-Ways (read-only par défaut), WinHex peut modifier le disque. Avant toute analyse d'une preuve : Options → Security → cocher « Write protection ».
📋 Extraire une preuve — Copy Block
  1. Marquer début : clic droit → Beginning of block ou Alt+1
  2. Marquer fin : clic droit → End of block ou Alt+2
  3. Ne pas faire Save — cela écraserait le disque !
  4. Edit → Copy Block → Into New File
  5. Bloc extrait dans un fichier propre sur la clé USB de l'analyste
🔧 Cas avancé — reconstruction manuelle (undelete)

Scénario : ressusciter _NTOUCHABLES.TXT en modifiant directement les structures FAT (sur une copie !).

Étape 1 — Rétablir le nom (entrée répertoire)

// Localiser l'entrée dans le Root Directory
// Curseur sur 0xE5 (premier octet)
// Mode édition : taper 49 (hexa pour 'I')
// Résultat : INTOUCHABLES.TXT

Étape 2 — Rétablir la chaîne (Table FAT)

// Cluster de départ = 100, fichier sur 2 clusters
// Aller à l'offset du cluster 100 dans la FAT
cluster 100 : 00 00  (libre)  →  65 00  (101 en Little Endian)
cluster 101 : 00 00           →  FF FF  (fin de fichier)

Étape 3 — Sauvegarder — Windows considère à nouveau le fichier comme valide.

🔒 Jamais sur la preuve originale. Cette procédure ne se pratique que sur une copie forensique. Enseignement pour comprendre les structures — en pratique, on utilise les fonctions X-Ways / Autopsy.
🧮 Hex vs Binaire & attributs

Pour déchiffrer un octet d'attribut FAT :

Valeur hexa à l'offset 11  :  0F
Conversion binaire         :  0000 1111
Bits R · H · S · V actifs  →  c'est un LFN (Long File Name)
⑭ Report Tables — le mécanisme pro de catégorisation

Au-delà du simple tag : la vraie manière de structurer une preuve pour le rapport.

🏷 Tag vs Report Table — ne pas confondre
Tag (coche)Report Table (catégorie nommée)
Marquage binaire (coché / non coché) Catégorie structurée avec nom, couleur, description
Un seul tag par fichier Un fichier peut appartenir à plusieurs Report Tables
Utile pour le triage rapide Utile pour la structure du rapport final
Non exporté dans le rapport officiel Apparaît comme section dédiée dans le rapport
📋 Créer & utiliser les Report Tables
1
Accéder : menu Case → Edit Report Table Associations (ou clic droit sur un fichier dans le Directory Browser).
2
Créer les catégories métier pertinentes : Documents financiers · Échanges suspects · Images illicites · Malware · Mots de passe récupérés · Contact personnes d'intérêt…
3
Assigner couleur + description à chaque catégorie. La description apparaîtra dans le rapport pour expliquer au magistrat ce que signifie la catégorie.
4
Associer les fichiers au fil de l'analyse (un fichier peut être dans plusieurs catégories — ex. un PDF suspect = Documents financiers + Échanges suspects).
5
Générer le rapport final — chaque Report Table devient une section du rapport, avec la liste des fichiers, hashs, chemins, dates, commentaires.
💡 Commenter au fil de l'eau. Pour chaque fichier ajouté à une Report Table, X-Ways propose un champ Comment. Toujours le remplir (même brièvement) : « reçu le 12/03, envoyé à X », « contient des numéros de compte IBAN ». Ces commentaires apparaissent dans le rapport final et guident le magistrat.
🎯 Workflow professionnel : pas de Tag à la volée sans plan. Définir d'abord les Report Tables à partir de l'hypothèse d'enquête (ex. blanchiment → catégories Relevés bancaires · Transferts crypto · Contacts étrangers). Puis l'analyse remplit ces catégories. Le rapport écrit littéralement tout seul à la fin.
⑮ Flux de travail anti-erreurs

L'ordre compte — un pas manqué et l'analyse s'écroule.

1
Brancher le dongle USB. Sans dongle : X-Ways refuse de démarrer ou reste en version limitée.
2
Lancer X-Ways (ou WinHex en admin — exige les droits administrateur pour l'accès aux disques physiques).
3
Créer le Cas (.xfc). Dossier de stockage distinct du disque de preuve.
4
Ajouter l'image disque. Sélectionner le .e01 de départ — choisir Disque physique.
5
Vérifier le hash (F10). Comparer MD5/SHA-256 avec le PV de saisie.
6
Volume Snapshot (F9). Cocher : fichiers supprimés · signatures · hash · fichiers communs.
7
Activer la récursivité. Aplatir toute l'arborescence en une liste.
8
Trier / Filtrer / Refine. Par date, type, mot-clé · Refine Snapshot ciblé sur les objets pertinents.
9
Visualiser & valider la pertinence. Viewer interne ou Associations externes (VLC, DB Browser SQLite…).
10
Marquer : Tag (coche rapide) ou Report Table (catégorisation professionnelle : « Documents financiers », « Malware »…).
11
Extraire (Recover/Copy). Le fichier est extrait sans modifier la preuve.
12
Générer le rapport — Menu Case → Report. Formats : HTML · PDF · Texte. Inclut hashs, catégories, journal d'actions.
🧠 Testez-vous
Vous travaillez sur une image E01. Vous voulez voir tous les fichiers, y compris ceux carvés en unallocated. Quelle commande dans X-Ways ?Refine Snapshot · Niveau : facile
Lancer le Volume Snapshot (F9) sur le volume, puis Refine Volume Snapshot (Specialist menu) avec les options : (1) File header signature search (carving par signature), (2) Browse all data structures, (3) cocher tous les magic bytes à carver (JPEG, PNG, PDF, ZIP, MP4...). Les fichiers carvés apparaissent en italique dans la Directory Browser avec le tag « Carved ». Ils n'ont pas de timestamps fiables (pas d'entrée MFT) — c'est une particularité importante pour le rapport. Si possible, configurer dans Options → Directory Browser pour différencier visuellement les fichiers carvés des fichiers natifs.
Sur un fichier vacances.jpg, X-Ways affiche un Type Status : Mismatch. Que signifie cela et quelle est la priorité ?Type Status · Niveau : moyen
Le « Mismatch » signifie que l'extension du fichier (.jpg) ne correspond pas aux magic bytes détectés par X-Ways. Exemple typique : un fichier nommé vacances.jpg dont les premiers octets sont 4D 5A (PE/EXE Windows) ou 50 4B 03 04 (ZIP/archive). C'est un signal fort de dissimulation intentionnelle — souvent utilisé pour cacher des malwares, archives chiffrées, ou contenu illicite. Priorité : (1) tagger le fichier en Report Table « À investiguer », (2) ouvrir avec WinHex pour confirmer le vrai type, (3) calculer SHA-256, (4) tenter l'extraction du contenu réel (renommer en .exe/.zip et analyser dans une VM isolée), (5) toujours documenter dans le rapport — le fait de la dissimulation est en lui-même une preuve d'intention.
Différence entre Tag et Report Table dans X-Ways ?Catégorisation · Niveau : moyen
Tag = marquage booléen simple (un fichier est « tagué » ou non). Sert à identifier rapidement les fichiers d'intérêt pendant l'analyse, similaire à un favori. Report Table = catégorisation structurée : un fichier peut appartenir à plusieurs Report Tables simultanément (ex: « Photos suspect », « Communications », « Pièce à conviction n°5 »). Chaque Report Table devient une section du rapport final avec ses fichiers, hashs, captures. Les Report Tables sont la structure de l'argumentaire judiciaire : elles permettent au juge ou au procureur de naviguer logiquement dans les preuves. Best practice : créer les Report Tables en début d'enquête selon le plan d'analyse, puis les remplir au fur et à mesure. Tags = workflow personnel · Report Tables = livrables judiciaires.
Avec WinHex, vous voulez analyser manuellement un MBR (Master Boot Record). Que faut-il taper et quelle est sa structure exacte ?WinHex bas-niveau · Niveau : difficile
Procédure WinHex : (1) Tools → Open Disk → Physical disk (PAS la partition logique), (2) activer Write Protection dans Options (impératif !), (3) le secteur 0 affiché est le MBR. Pour parser automatiquement : Alt+F12 ouvre les Templates · choisir « Master Boot Record ». Structure exacte du MBR (512 octets) : (a) Bytes 0–445 (446 octets) = code de boot (instructions x86 du bootloader), (b) Bytes 446–509 (64 octets) = table de partitions = 4 entrées × 16 octets chacune (boot flag · CHS début · type · CHS fin · LBA début · taille), (c) Bytes 510–511 = signature MBR = 55 AA (en little endian, lu AA 55). Si la signature manque → MBR corrompu. Type partition fréquents : 0x07=NTFS · 0x0B=FAT32 · 0x83=Linux · 0xEE=GPT (protective MBR).
