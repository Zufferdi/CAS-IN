🔌 USB Forensique — Tracer le passage d'une clé
La question forensique fondamentale est : « Est-ce qu'une clé USB précise a été branchée sur cet ordinateur, par quel utilisateur, et quand ? ». Cette question est centrale dans les enquêtes pour vol de données, fuite d'informations confidentielles, introduction de malware, ou BadUSB. La réponse passe par la corrélation de plusieurs sources : (1) USBSTOR dans le registre SYSTEM (modèle, fabricant, numéro de série unique, dates de connexion), (2) setupapi.dev.log (timestamp immuable de la première connexion), (3) MountPoints2 dans NTUSER.DAT de chaque utilisateur (quel utilisateur a connecté la clé), (4) ShellBags (dossiers parcourus sur la clé), (5) Fichiers .lnk Recent (fichiers ouverts depuis la clé avec son Volume Serial Number). Identifiant unique : la combinaison VID (Vendor ID, fabricant) + PID (Product ID, modèle) + Serial Number identifie de manière unique une clé USB physique parmi des millions. Aucun deux exemplaires d'une clé n'ont le même Serial. Pour le forensiste, retrouver le même Serial sur deux machines = preuve quasi-irréfutable que la même clé physique a connecté les deux. Combinée à l'attribution utilisateur (SID), la chaîne devient juridiquement solide.
🔌 Chaîne de corrélation USB Windows — 5 sources convergentes
USBSTOR + SETUPAPI + MOUNTPOINTS2 + SHELLBAGS + .LNK = ATTRIBUTION COMPLÈTE
① USBSTOR (registre SYSTEM) ② setupapi.dev.log (1re fois) ③ MountPoints2 (user/SID) ④ ShellBags (navigation) ⑤ .lnk (fichiers ouverts)
🎯 Question forensique typique
« Est-ce qu'une clé USB donnée a été branchée sur cet ordinateur, par quel utilisateur, et quand ? »

Chaque connexion d'un périphérique USB à Windows laisse des traces dans au moins 5 emplacements du système. Croiser ces artefacts permet de reconstruire une timeline précise et d'attribuer l'action à un utilisateur.

  • Identifier chaque device par VID/PID/Serial (fingerprint matériel)
  • Dater la première connexion et les suivantes
  • Retrouver le ou les utilisateurs qui l'ont branché
  • Déterminer la lettre de lecteur attribuée (ex : E:)
  • Vérifier s'il s'agissait d'un vrai stockage ou d'un HID malveillant (Rubber Ducky, BadUSB)
🔑 Identifiants uniques : VID / PID / Serial
Exemple — clé SanDisk branchée
HKLM\SYSTEM\CurrentControlSet\Enum\USBSTOR\Disk&Ven_SanDisk&Prod_Cruzer_Blade&Rev_1.26\4C530000071127120234&0

Décomposition
VID = 0781 (SanDisk, assigné par USB-IF)
PID = 5567 (Cruzer Blade, assigné par le fabricant)
Serial = 4C530000071127120234 (unique à ce device)
Piège : si le dernier caractère du serial est un & (ex : ...234&0), cela signifie que le device n'a pas fourni de numéro de série unique — Windows en a généré un. Ces serials ne sont pas fiables pour identifier un device unique. Typique des clés low-cost, chinois génériques, ou chipset VIA Labs.
🪟 Windows — artefacts clés
🗄 USBSTOR (Registry)
HKLM\SYSTEM\CurrentControlSet\Enum\USBSTOR
Liste tous les périphériques de stockage USB jamais connectés. Sous-clé par device (VID+PID+Serial). Les valeurs importantes :
  • FriendlyName → nom lisible (« SanDisk Cruzer Blade USB Device »)
  • Properties\...\0064 → timestamp première installation
  • Properties\...\0066 → timestamp dernière connexion
  • Properties\...\0067 → timestamp dernière déconnexion
📜 setupapi.dev.log
C:\Windows\INF\setupapi.dev.log
Log texte horodaté — enregistre la première installation du pilote pour chaque device. Ligne typique : 
>>>  [Device Install (Hardware initiated) - SWD\WPDBUSENUM\_??_USBSTOR#Disk&Ven_SanDisk...
>>>  Section start 2024/03/14 14:22:08.318
Intérêt majeur : ce timestamp est le plus ancien fiable de la première connexion du device à ce PC. Souvent persistant même après DriveCleanUp.
👤 MountPoints2 (par utilisateur)
NTUSER.DAT\Software\Microsoft\Windows\CurrentVersion\Explorer\MountPoints2
Clé cruciale pour l'attribution user ↔ device. Liste les volumes montés par cet utilisateur. Si un device apparaît ici, c'est ce compte qui l'a branché/monté (session active).
  • Sous-clés de type {GUID} ou ##?#Volume{GUID}
  • Croiser le GUID avec HKLM\SYSTEM\MountedDevices pour le matcher au VID/PID/Serial USBSTOR
📝 Event Logs
%SystemRoot%\System32\winevt\Logs\Microsoft-Windows-Partition%4Diagnostic.evtx
Depuis Windows 8+, traces riches dans Event Logs :
  • Event ID 1006 (Partition/Diagnostic) — informations complètes sur le device branché : VID, PID, Serial, Capacity, Manufacturer, Model, PartitionStyle
  • Event ID 400/410 (DriverFrameworks-UserMode) — installation du driver
  • Event ID 2003/2004/2006/2100/2101 (USB-Hub3) — connexion/déconnexion, utile pour une timeline fine
  • Event ID 6416 (Security) — uniquement si Object Access auditing est activé (rare sur workstation)
📋 MountedDevices
HKLM\SYSTEM\MountedDevices
Liste tous les volumes jamais montés sur ce système, indexés par lettre de lecteur (\DosDevices\E:) et GUID. Permet de savoir à quelle lettre un device a été monté.
🕰 Reconstruction d'une timeline USB

📐 Corrélation multi-source

Pour une investigation sérieuse, croiser plusieurs sources et valider chaque timestamp :

  1. VID/PID/Serial depuis USBSTOR → fingerprint device
  2. setupapi.dev.log → première installation (ancre temporelle la plus fiable)
  3. USBSTOR Properties\0064/0066/0067 → first install / dernière connexion / dernière déconnexion
  4. Microsoft-Windows-Partition%4Diagnostic.evtx → liste de toutes les connexions successives avec détails device
  5. NTUSER.DAT\...\MountPoints2 → utilisateur qui a monté le volume
  6. MountedDevices → lettre de lecteur attribuée (E:, F:, G:…)
  7. Shellbags / LNK / JumpLists → prouver l'utilisation du device (fichiers ouverts depuis E:)
Astuce pro : pour automatiser, utiliser USBDetective, USB Detective ou USBDeview (NirSoft) sur une image montée. Zimmerman Tools RECmd avec le batch file SANS_Triage.reb extrait et formate tout ce qui est nécessaire pour une timeline USB complète.
🎯 Attribution user ↔ device (cas concret)

📁 Workflow d'enquête

  • Suspect : bob.smith soupçonné d'avoir exfiltré des fichiers vers une clé USB
  • Étape 1 : dans HKLM\...\USBSTOR, trouver les clés USB branchées sur le PC
  • Étape 2 : noter le GUID de volume de chaque clé (via HKLM\...\MountedDevices)
  • Étape 3 : charger C:\Users\bob.smith\NTUSER.DAT dans Regripper / RegRecon
  • Étape 4 : extraire \Software\Microsoft\Windows\CurrentVersion\Explorer\MountPoints2
  • Étape 5 : si le GUID de la clé USB s'y trouve → bob.smith a monté ce device
  • Étape 6 : croiser avec Shellbags / RecentDocs / OpenSaveMRU pour voir les fichiers consultés
  • Étape 7 : rechercher dans UserAssist si un .exe a été lancé depuis le device
  • Étape 8 : LNK / JumpLists sur le bureau de Bob → preuves d'ouverture de fichiers depuis E:\
🔎 BadUSB / HID — détecter un device malveillant

Un périphérique peut se présenter comme plusieurs classes USB simultanément (stockage + HID clavier + HID souris). Les attaques Rubber Ducky et BadUSB se font passer pour un clavier pour exécuter des commandes automatiquement.

  • Event Log USB-Hub3 EID 2003 révèle les classes USB réelles du device
  • Si une clé « USB » apparaît aussi comme HID → suspect
  • Les OMG Cables (câbles USB piégés) sont quasi-indétectables — cherchez des câbles suspects sur la scène
  • Dans les Event Logs de sécurité : exécutions soudaines de cmd/powershell peu après insertion USB
🍎 macOS — USB artifacts
  • /private/var/log/system.log (pré-Big Sur) — connexions USB loggées
  • log show --predicate 'eventMessage contains "USB"' --last 7d (macOS moderne, Unified Logs)
  • ioreg -p IOUSB -l → liste des devices actuellement branchés
  • KnowledgeC.db et PowerLog (CurrentPowerlog.PLSQL) — traces de connexions
  • /Users/<user>/Library/Preferences/.GlobalPreferences.plist → historique volumes montés
  • Outil : mac_apt (Yogesh Khatri) parse la plupart de ces artefacts automatiquement
🐧 Linux — USB artifacts
  • journalctl -k | grep -i usb — messages kernel (connexions, VID/PID, vendeur)
  • dmesg — même info, circular buffer (perdu au reboot)
  • /var/log/syslog ou /var/log/messages — entries udev et kernel
  • /var/log/udev (si rsyslog config) — events udev détaillés
  • lsusb -v → snapshot des devices actuellement branchés
  • /etc/udev/rules.d/ — règles custom (peuvent révéler une préparation)
  • ~/.bash_history et ~/.local/share/gvfs-metadata — traces d'utilisation
  • /run/media/$USER/ ou /media/$USER/ — points de montage actuels

📋 Mémo — checklist enquête USB
  • Lister tous les USBSTOR (jamais branchés sur ce PC), noter VID/PID/Serial de chacun
  • Pour chaque device suspect : timestamps 0064, 0066, 0067
  • Corréler avec setupapi.dev.log pour la première install
  • Event Log Microsoft-Windows-Partition%4Diagnostic : toutes les connexions avec détails
  • Pour chaque utilisateur : parser NTUSER.DAT\...\MountPoints2 → attribution
  • Vérifier MountedDevices pour la lettre de lecteur
  • Suivre l'usage : shellbags, LNK, JumpLists, RecentDocs, UserAssist, OpenSaveMRU
  • Si clé saisie : imager la clé (write blocker !) et comparer Serial avec USBSTOR
  • Attention aux Serials se terminant par & (non-unique, faux positifs possibles)
  • Documenter les fuseaux horaires : USBSTOR = UTC, setupapi.dev.log = local time

🧠 Testez-vous
Vous trouvez la même clé USB (même Serial Number) connectée sur deux ordinateurs distincts. Que pouvez-vous conclure ?Identification · Niveau : facile
Le Serial Number dans USBSTOR est généré par le contrôleur de la clé et est globalement unique — aucun deux exemplaires d'un même modèle de clé n'ont le même Serial. Combinaison VID + PID + Serial = empreinte unique. Donc trouver le même VID:PID:Serial sur deux machines = preuve quasi-irréfutable que la même clé physique a été branchée sur les deux. Subtilités : (1) Certaines clés USB contrefaites/cheap (typiquement chinoises bas de gamme) reproduisent un Serial commun (« 0123456789ABCDEF » ou similaire) — vérifier si le pattern est suspicieusement générique. (2) Certains périphériques (notamment USB hubs et certains lecteurs SD) n'ont pas de vrai Serial — Windows en génère alors un par instance (commençant par &) qui change à chaque port → moins fiable pour identification. (3) Cartes SD insérées dans lecteurs USB : c'est le lecteur USB qui a un Serial, pas la carte SD elle-même. Application juridique : ce résultat permet de prouver qu'un suspect a transporté physiquement la même clé entre deux machines — preuve clé pour vol de données ou exfiltration.
Une clé USB suspecte est branchée. Comment savoir quel utilisateur spécifique l'a connectée (et pas un autre du même PC) ?Attribution · Niveau : moyen
USBSTOR (ruche SYSTEM) montre que la clé a été branchée sur la machine, mais ne dit pas qui de session. L'attribution utilisateur passe par HKCU\Software\Microsoft\Windows\CurrentVersion\Explorer\MountPoints2 dans la ruche NTUSER.DAT de chaque utilisateur. Cette clé contient une entrée pour chaque clé USB que cet utilisateur a montée pendant sa session. Procédure : (1) Identifier la clé suspecte dans USBSTOR (via VID:PID:Serial), récupérer son ParentIdPrefix ou GUID. (2) Pour chaque utilisateur du PC, ouvrir son NTUSER.DAT hors ligne (Registry Explorer / RegRipper). (3) Examiner MountPoints2 : si la clé y figure → cet utilisateur a connecté la clé. (4) Cross-check : examiner aussi les fichiers .lnk Recent dans C:\Users\<user>\AppData\Roaming\Microsoft\Windows\Recent\ — si des .lnk pointent vers la lettre de drive de la clé avec le bon Volume Serial → confirmation. (5) Cross-check 2 : ShellBags dans USRCLASS.DAT de l'utilisateur — y trouver la navigation sur la clé. (6) Logs Windows EID 6416 (PnP device installed) inclut le SID de l'utilisateur connecté au moment du branchement. La combinaison de ces sources = preuve juridique solide d'attribution.
Le suspect prétend qu'il n'a jamais branché la clé. Cependant USBSTOR la liste. Comment lever l'ambiguïté ?Stratégie · Niveau : difficile
Plusieurs scénarios possibles, à investiguer méthodiquement : (1) Quelqu'un d'autre a branché la clé sur la machine — un collègue, un visiteur. À vérifier : (a) plusieurs utilisateurs ont-ils des comptes locaux ? (b) MountPoints2 du suspect contient-il la clé ? Si NON et qu'un autre user l'a → la clé a été branchée par cet autre. (c) EID 6416 (PnP device) avec quel SID utilisateur ? (2) La clé a été branchée mais à un moment où le suspect n'était pas physiquement présent (collègue dans son bureau, vol de session non verrouillée). À cross-check : pointage badge, vidéosurveillance bureau, EID 4624/4647 (logon/logoff sessions) au moment du branchement. (3) Le suspect dit la vérité, c'est une homonymie ou erreur — vérifier avec précision le VID:PID:Serial. (4) La clé a été virtuellement « branchée » sans présence physique — pas possible techniquement, sauf cas USB-over-IP ou rares attaques USB déportées. (5) Le suspect ment et toutes les preuves convergent. Procédure de levée d'ambiguïté : (a) Construire une timeline complète de la première et dernière connexion de la clé, (b) cross-check avec sessions actives (4624/4634/4647), (c) cross-check avec mouvements physiques du suspect (badging, témoins, vidéo), (d) chercher des artefacts d'usage sur la clé : les fichiers/dossiers du suspect y sont-ils ? Cela renforce ou affaiblit l'hypothèse, (e) interroger les autres utilisateurs avec accès au PC. Principe judiciaire : le simple fait que USBSTOR mentionne la clé ne prouve pas qui l'a branchée — il faut la chaîne complète d'attribution.
🎓 Exam Tip — USB Forensique

Identifiant unique d'une clé USB : VID:PID:SerialNumber

  • VID = Vendor ID (4 hex digits, fabricant — Kingston, SanDisk...)

  • PID = Product ID (4 hex digits, modèle)

  • Serial = unique par exemplaire physique

━━ 5 SOURCES DE CORRÉLATION ━━

① USBSTOR : SYSTEM\CurrentControlSet\Enum\USBSTOR

  → Modèle, fabricant, Serial, dates 1re/dernière connexion

② setupapi.dev.log : C:\Windows\INF\setupapi.dev.log

  → Timestamp immuable de la 1re connexion (très fort juridiquement)

③ MountPoints2 : HKCU\Software\Microsoft\Windows\CurrentVersion\Explorer\MountPoints2

  → ⭐ Par utilisateur (SID) = QUI a connecté la clé

④ ShellBags : USRCLASS.DAT

  → Dossiers parcourus sur la clé USB

⑤ Fichiers .lnk Recent : %APPDATA%\Microsoft\Windows\Recent\

  → Fichiers ouverts depuis la clé + Volume Serial Number

━━ AUTRES SOURCES UTILES ━━

• EID 6416 (PnP device installed) : avec SID utilisateur

• EID 4624 (logon) : qui était connecté au moment du branchement

• Amcache : programmes lancés depuis la clé (avec hash SHA-1)

• Prefetch : programmes exécutés depuis la clé

━━ MULTI-OS ━━

• macOS : system.log · /var/log/install.log · IORegistry · plist diskutil

• Linux : journalctl -k · /var/log/syslog · dmesg · /sys/bus/usb/devices/

━━ BAD USB ━━

HID device (clavier émulé) qui injecte des commandes au branchement. Détection : EID 6416 pour HID device avec serial inhabituel + EID 4688 immédiat.
