🔑 Définition — Le carving opère sans système de fichiers
Le data carving (ou file carving) consiste à reconstruire des fichiers directement depuis les secteurs bruts d'un disque ou d'une image, sans s'appuyer sur les structures du FS (FAT, MFT, inode). L'outil parcourt le flux d'octets à la recherche de signatures connues (magic bytes d'en-tête et de pied de fichier) pour délimiter des candidats.

C'est la technique de dernier recours : elle s'applique quand les métadonnées du FS sont corrompues, écrasées, ou que des fichiers ont été intentionnellement supprimés pour effacer des traces.
Pourquoi ça fonctionne
Les données persistent après suppression

Supprimer un fichier ne détruit pas son contenu — seules les entrées d'annuaire (FAT, MFT, inode) sont marquées libres. Les blocs restent intacts jusqu'à réallocation. Sur SSD avec TRIM actif, la fenêtre est beaucoup plus courte.

Les formats ont des structures prévisibles

La quasi-totalité des formats courants (JPEG, ZIP, PDF, SQLite…) commencent par une séquence d'octets fixe — le magic number — et se terminent par un marqueur de fin (EOF marker). Ces invariants permettent la détection sans FS.

Quand l'utiliser
1
FS détruit ou corrompu — ransomware, formatage rapide, partition GPT corrompue, header MBR écrasé.
2
Fichiers supprimés récupérés partiellement — les outils FS-aware (Autopsy, FTK) n'ont pas retrouvé tout le contenu.
3
Support sans FS connu — flash brut, dump NAND, espace non alloué d'une image DD.
4
Anti-forensique détecté — wiping partiel, overwrite des métadonnées FS mais pas des données elles-mêmes.
!
Réaliser le carving en dernier — toujours épuiser les méthodes FS-aware d'abord ; le carving génère des faux positifs et des fichiers incomplets.
⚖️ Recevabilité — Chaîne de custody
Travailler toujours sur une copie image (E01, DD, AFF4). Ne jamais carver le disque original. Documenter : hash avant/après, commande exacte, version de l'outil, horodatage. En procédure suisse (Art. 248 CPP), la traçabilité de chaque opération est exigée.
✨ Magic Bytes — La base du carving
Chaque format de fichier est identifiable par sa séquence d'octets initiale. Le carver scanne l'image octet par octet (ou par bloc de 512 B) en cherchant ces headers. Quand il en trouve un, il avance jusqu'au footer correspondant (ou jusqu'à la taille max configurée) pour délimiter le fichier candidat.
Signatures forensiques clés
Extension Header (hex) Footer (hex) Notes forensiques Type
JPEG FF D8 FF FF D9 Très commun ; EXIF dans le header. Multiple JPEG possible bout à bout. Image
PNG 89 50 4E 47 0D 0A 1A 0A 49 45 4E 44 AE 42 60 82 Footer IEND chunk fiable. Taille dans le header IHDR. Image
GIF 47 49 46 38 37 61 / ..38 39 61 00 3B GIF87a / GIF89a. Animations = frames multiples. Image
PDF 25 50 44 46 2D (%PDF-) 25 25 45 4F 46 (%%EOF) Streams compressés. Version dans header (%PDF-1.7). xref table localisable. Document
DOCX / XLSX / PPTX 50 4B 03 04 50 4B 05 06 + 18 B Conteneur ZIP. Même magic que tout ZIP. Distinguer par [Content_Types].xml interne. Document
ZIP 50 4B 03 04 50 4B 05 06 + 18 B Central directory à la fin. Taille variable. Carving sur le footer est plus fiable. Archive
GZIP / .gz 1F 8B CRC32 + taille (4 B) Pas de footer fixe — taille dans le footer. Difficile à délimiter sans parsing. Archive
SQLite 53 51 4C 69 74 65 20 66 6F 72 6D 61 74 Taille dans header (offset 16) "SQLite format 3\000". Taille du fichier = page_size × nb_pages (offset 28). Très fiable. Base de données
MP4 / MOV offset 4 : 66 74 79 70 (ftyp) mdat atom (taille variable) Structure atoms ISO/IEC 14496-12. Taille dans atom header. Carving complexe. Vidéo
PE / EXE / DLL 4D 5A (MZ) Pas de footer standard DOS stub + PE header. Taille dans Optional Header SizeOfImage. Carving par taille max. Exécutable
ELF 7F 45 4C 46 (\x7fELF) Pas de footer standard Linux/Unix. e_shoff + section headers donnent la taille complète. Exécutable
OLE2 (DOC/XLS/PPT) D0 CF 11 E0 A1 B1 1A E1 Structure FAT interne Format Microsoft composé. Ancêtre de OOXML. Macros VBA souvent ici. Document
💡 Astuce hex — Pour identifier rapidement un fichier inconnu : xxd fichier | head -4 affiche les 64 premiers octets. Comparer avec la table ci-dessus ou la base GCK's File Signatures.
⚙️ Trois familles d'algorithmes de carving
La difficulté principale du carving est la fragmentation — un fichier dont les blocs ne sont pas contigus sur disque. Les algorithmes modernes vont bien au-delà du simple header/footer scan.
1. Header/Footer Carving (classique)
①
Scan séquentiel
Parcours byte-by-byte (ou bloc par bloc) de l'image brute. Recherche de tous les headers connus dans la base de signatures.
②
Délimitation par footer
Quand un header est détecté, recherche du footer correspondant jusqu'à la taille maximale configurée (ex : 50 MB pour JPEG). Si aucun footer → taille max utilisée.
③
Extraction
Les octets entre header et footer sont écrits dans un fichier de sortie avec l'extension correspondante.
Foremost, Scalpel (mode basique)
⚠
Problème : fragmentation
Si le fichier est fragmenté (blocs non contigus), le carver extrait des données appartenant à un autre fichier entre les fragments → fichier corrompu.
2. SmartCarving — Validation interne
→
Analyse de la structure interne
Après extraction, validation du format : parsing des chunks PNG, verification du xref PDF, contrôle CRC JPEG, validation du Central Directory ZIP. Les fichiers invalides sont rejetés ou marqués suspects.
PhotoRec, Autopsy (Unallocated Carver), Scalpel avec validation
→
Utilisation des métadonnées internes
Certains formats encodent leur taille dans le header (SQLite, BMP, PE). Le carver utilise cette info pour délimiter précisément le fichier sans dépendre du footer.
3. Carving de fichiers fragmentés
→
JPEG assembly (bi-fragmentation)
Pour JPEG : scanner tous les headers, tous les footers, tenter toutes les combinaisons header[i] + footer[j] → valider par décompression partielle JFIF. Complexité O(h×f).
PhotoRec (mode assemblage), Adroit Photo Forensics
→
Algorithme de bifurcation (Garfinkel 2007)
Quand un fragment inconnu interrompt un fichier en cours de carving, l'algorithme bifurque : tente de sauter le fragment et de continuer avec le bloc suivant. Arbre de décision avec backtracking.
Implémenté dans bulk_extractor (partiellement)
→
Entropie & classification
Les blocs sont classifiés par entropie de Shannon : haute entropie = données chiffrées/compressées, basse entropie = texte/code. Permet d'identifier des fragments probables d'un type de fichier.
bulk_extractor, Sleuth Kit fragment classifier
📚 Référence — Garfinkel, S. (2007). Carving contiguous and fragmented files with fast object validation. DFRWS. La taxonomie Garfinkel reste la référence académique du domaine.
Outils principaux
PhotoRec Gratuit / Open Source
Le plus polyvalent : 480+ types de fichiers supportés, fonctionne sur tous les FS (FAT, NTFS, EXT, HFS+, APFS). Interface texte (ncurses) ou GUI via TestDisk. Validation interne forte — taux de faux positifs bas. Travaille sur l'espace non alloué uniquement si demandé.
photorec /log /d /path/to/output /cmd image.dd search photorec image.dd # mode interactif
⚠ Renomme tous les fichiers (f0000001.jpg…) — métadonnées FS perdues. Toujours hasher avant/après.
Scalpel Gratuit / Open Source
Fork de Foremost, plus rapide. Configuration entièrement dans /etc/scalpel/scalpel.conf — décommenter les types voulus. Supporte les expressions régulières pour headers/footers. Performant sur grandes images (multi-thread).
scalpel -c /etc/scalpel/scalpel.conf -o /output image.dd scalpel -t jpg,pdf,zip -o /output image.dd
Config : décommenter jpg, pdf etc. dans scalpel.conf — tout est commenté par défaut.
Foremost Gratuit
L'original (USAF OSI, 2000). Plus lent que Scalpel mais compatible partout. Bonne référence pour les audits car très bien documenté dans les rapports judiciaires américains.
foremost -t jpg,pdf,doc -i image.dd -o /output -v
bulk_extractor Gratuit / Open Source
Carver spécialisé dans l'extraction d'artefacts structurés : emails, URLs, numéros de carte de crédit, hash JPEG, clés WiFi, coordonnées GPS, sessions Skype. Extrêmement rapide (multi-cœur). Produit des histogrammes et des rapports exploitables.
bulk_extractor -o /output -E all image.dd bulk_extractor -o /output -e email -e url -e jpeg image.dd
Extracteurs disponibles : email, url, domain, jpeg, pdf, zip, elf, aes_keys, vcard, gps…
Autopsy (Unallocated Space Carving) Gratuit
Module intégré dans Autopsy 4+ basé sur Tesseract + TSK. Carvé automatiquement lors de l'ingestion de l'image. Les résultats apparaissent dans Carved Files dans l'arborescence. Pratique pour les workflows tout-en-un.
Menu : Add Data Source → Disk Image → cocher "Carve files from unallocated space"
X-Ways Forensics — Refine Volume Snapshot + Carving Commercial
Carving intégré avec validation interne forte. Accès via Specialist → Refine Volume Snapshot → Carve for missing files types. Supporte le carving dans l'espace non alloué ET dans les fichiers existants (archives, DB). Incontournable en contexte judiciaire CH/EU.
Voir fiche : X-Ways & WinHex
python-magic + scalpel custom Python
Pour des signatures personnalisées ou des formats propriétaires, écrire un carver ad hoc en Python est souvent plus rapide que de configurer Scalpel.
pip install python-magic mmap
Pattern : ouvrir l'image en mmap, scanner avec re.finditer sur les signatures, extraire les slices.

💾 Le FS influence le carving, pas l'inverse
Le carving opère sur des octets bruts — mais le système de fichiers sous-jacent détermine comment les blocs sont alloués et libérés, ce qui impacte directement le taux de succès et la complétude des fichiers récupérés.
Matrice de faisabilité par système de fichiers
FS Récupération après suppression Fragmentation typique Particularités pour le carving
NTFS Bonne
Modérée $MFT garde des résidus même après suppression. $Bitmap marque les clusters libres. La $MFT elle-même peut contenir des fichiers résiduels (resident data). Carver FS-aware d'abord (MFT recovery), puis carving brut.
FAT32 / exFAT Très bonne
Modérée Le premier octet de l'entrée directory devient 0xE5 à la suppression mais la chaîne FAT est libérée. Nom de fichier partiellement lisible. FATCarve / PhotoRec excellent ici. Cluster size = clé : carver par multiple de cluster size.
EXT2/3/4 Moyenne
Élevée EXT3/4 journalisé — le journal peut contenir des versions antérieures. Les inodes supprimés conservent parfois les block pointers (EXT2 surtout). extundelete avant carving. Sur EXT4, les extent trees compliquent le carving fragmenté.
APFS Difficile
Faible (CoW) Copy-on-Write + snapshots. Le chiffrement natif (FileVault) rend le carving inutile sans clé. Les snapshots peuvent contenir des versions précédentes accessibles via mount. Carving brut = très faible rendement.
HFS+ Bonne
Modérée Journal HFS+ (si activé) = source d'artefacts. Catalog File B-Tree contient des infos résiduelles post-suppression. PhotoRec très efficace ici.
F2FS (Android) Très difficile
Très élevée Log-structured : données écrites séquentiellement puis garbage-collectées. Flash encryption (FDE/FBE) sur Android 6+. TRIM quasi-immédiat sur SSD. Carving = rendement minimal hors cas particuliers (chip-off).
ReFS Difficile
Élevée Pas de $MFT. B+ tree différent. Très peu d'outils supportent la recovery native. Carving brut reste une option mais sans validation FS-level.
🔴 SSD + TRIM activé — Le TRIM efface les blocs libérés quasi-immédiatement. Le carving sur SSD moderne donne souvent des fichiers vides ou corrompus. Investiguer rapidement (live forensics > image > carving) et documenter la présence du TRIM dans le rapport.
⚠️ Le carving produit des faux positifs et des fichiers incomplets
Contraindre le carving à ses véritables limites est essentiel pour rédiger un rapport forensique honnête. Exagérer les résultats du carving peut invalider une procédure.
Limites fondamentales
🔴 Fragmentation
  • Un fichier fragmenté carve = données de deux fichiers mélangées
  • JPEG fragmenté → image corrompue ou tronquée
  • ZIP fragmenté → archive invalide (Central Directory manquant)
  • Taux de fragmentation sur HDD ancien : 5-15 % des fichiers
🟠 Faux positifs
  • Magic bytes apparaissant dans des données aléatoires
  • FF D8 dans un flux vidéo → JPEG fantôme
  • 50 4B dans une DB → archive ZIP inventée
  • Taux typique Scalpel sur HDD : 20-40 % de faux positifs
🟡 Métadonnées perdues
  • Nom de fichier original inconnu
  • Timestamps MAC originaux non récupérables
  • Chemin/répertoire original inconnu
  • Numéro d'inode/entrée MFT d'origine perdu
🟣 Chiffrement
  • Contenu chiffré → entropie élevée → aucune signature détectable
  • BitLocker, VeraCrypt, FileVault = carving aveugle
  • Seul le container chiffré peut être carver, pas son contenu
  • Exception : keyslots non chiffrés dans certains containers
Scénarios forensiques et implications
🗂 Scénario 1 — Défense invoque l'absence de fichier
Un suspect affirme n'avoir jamais possédé de fichiers incriminants. Le carving retrouve des JPEG dans l'espace non alloué.

Enjeu : Prouver que ces fichiers ont bien existé sur ce disque (et pas été générés par un faux positif). Le rapport doit inclure : hash du fichier carver, validation de son intégrité interne (JFIF parser), plage de secteurs source, et exclusion de toute origine d'injection externe.
🧹 Scénario 2 — Anti-forensique avec wiping partiel
L'examen montre que l'espace non alloué a été partiellement wiped (patterns 00 00 ou AA AA). Certaines zones sont intactes.

Approche : Carving sur les zones non wipées. Documenter les zones wipées (début/fin des plages). En droit suisse, l'acte de wiping lui-même peut être pertinent (Art. 158 CP — entrave à l'action pénale).
💥 Scénario 3 — Ransomware — récupération post-chiffrement
Disque chiffré par ransomware. Certains fichiers originaux restent dans l'espace non alloué si le ransomware les a chiffrés in-place puis supprimés.

Approche : Carving immédiat avant toute tentative de déchiffrement. Les fichiers originaux récupérés par carving peuvent valider la clé de déchiffrement retrouvée ou servir comme copies de travail.
📋 Dans le rapport (Art. 182 CPP) : Toujours mentionner (1) l'outil et sa version, (2) le hash de l'image source, (3) la commande exacte, (4) le nombre de fichiers extraits vs fichiers valides, (5) la méthode de validation utilisée (parser interne, ouverture manuelle, hash). Ne jamais présenter un fichier carver comme "retrouvé" sans validation de son intégrité.
💊 Q1 — Quelle est la différence fondamentale entre le carving et la récupération basée sur le système de fichiers ?
✓ Le carving ne dépend d'aucune structure FS (MFT, FAT, inode) — il reconstruit des fichiers uniquement à partir des magic bytes (header/footer) présents dans le flux d'octets brut. La récupération FS-aware utilise les entrées d'annuaire et les tables d'allocation pour retrouver les fichiers supprimés.
💊 Q2 — Vous carvez une image DD et trouvez 3 000 fichiers JPEG. Que faites-vous avant de les présenter comme preuves ?
✓ (1) Valider l'intégrité interne de chaque JPEG (parser JFIF, vérification des marqueurs SOS/EOI) ; (2) éliminer les faux positifs ; (3) vérifier les métadonnées EXIF disponibles ; (4) hasher chaque fichier extrait ; (5) documenter précisément les secteurs sources (début/fin) dans l'image originale. Un fichier carver sans validation n'est pas une preuve recevable.
💊 Q3 — Sur un SSD moderne avec TRIM activé, quelles sont vos chances de succès avec le carving ?
✓ Très faibles. Le TRIM envoie une commande au contrôleur SSD pour effacer physiquement les blocs libérés (souvent dans les secondes qui suivent la suppression). Les blocs "libres" retournent des zéros ou des données indéfinies. Le carving ne trouvera que ce qui n'a pas encore été trimmé. Documentation obligatoire dans le rapport + investigation live ou mémoire vive si possible.
💊 Q4 — Quel outil utiliseriez-vous pour extraire des adresses email et des URLs depuis une image disque de 500 GB le plus rapidement possible ?
✓ bulk_extractor — conçu spécifiquement pour cette tâche, multi-thread, produit des histogrammes et des listes dédupliquées. Exemple : bulk_extractor -o output -e email -e url image.dd. Bien plus rapide que de carver des fichiers complets puis les parser.
💊 Q5 — Comment le carving peut-il aider dans une investigation ransomware, alors que les fichiers sont chiffrés ?
✓ Beaucoup de ransomwares chiffrent les fichiers puis suppriment les originaux (delete + parfois wiping partiel). Si la suppression a été faite sans wiping complet, les fichiers originaux en clair peuvent encore exister dans l'espace non alloué. Carving immédiatement après acquisition permet parfois de récupérer des copies pré-chiffrement, utilisables pour valider une clé retrouvée ou comme sauvegarde de travail.
💊 Q6 — La magic sequence 50 4B 03 04 apparaît. De quels types de fichiers peut-il s'agir ?
✓ C'est le magic number du format ZIP — mais aussi de DOCX, XLSX, PPTX, ODP, JAR, APK (tous sont des archives ZIP). Pour distinguer, il faut parser le ZIP et vérifier la présence de [Content_Types].xml (Office), META-INF/MANIFEST.MF (JAR/APK), ou mimetype (ODP).
