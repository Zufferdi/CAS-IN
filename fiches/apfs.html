🍏 Apple File System · 2017+

APFS — Apple File System

Container partagé, volumes multiples, snapshots copy-on-write, clones, chiffrement natif multi-clés, Sealed System Volume, Data Protection iOS — le filesystem omniprésent sur Mac et iOS depuis 2017.

Prérequis :📖 HFS+📖 MAC Times
Voir aussi :🔗 Comparaison FS🔗 FileVault / Chiffrement
⚡ Pourquoi APFS est incontournable
iOS 10.3+ (2017), macOS 10.13+ (2017), watchOS 4+, tvOS 10.2+ — absolument tous les appareils Apple récents utilisent APFS. En investigation Mac/iOS moderne, HFS+ est devenu l'exception ; APFS est la règle. Les enjeux forensiques (snapshots, chiffrement multi-clés, SSV) changent radicalement la méthodologie.
🏗 Architecture — Container et volumes
Rupture conceptuelle avec HFS+ : au lieu d'un filesystem par partition, APFS introduit un container (pool d'espace partagé) qui héberge plusieurs volumes dynamiques.

🧩 Concepts clés

  • Container (apfs_container) : pool d'espace physique, géré par le Container Superblock (NXSB)
  • Volume (apfs_volume) : filesystem logique dans le container, peut grossir/rétrécir dynamiquement — pas de partitionnement fixe
  • Un container peut héberger jusqu'à ~100 volumes qui se partagent l'espace libre
  • Chaque volume a son propre Object Map (omap), son propre B-Tree, ses propres snapshots
  • Volume roles (role) : SYSTEM, DATA, PREBOOT, VM, RECOVERY, UPDATE, XART, HARDWARE, BACKUP
  • Identifier le container : diskutil apfs list
📅 Epoch APFS et précision nanoseconde
APFS epoch : 1er janvier 1970 00:00:00 UTC (Unix epoch, contrairement à HFS+ qui utilise 1904)
Unité : nanosecondes depuis epoch, stockées sur 64 bits signés
Conversion : unix_ts = apfs_ts / 1_000_000_000
Précision pratique : 1 ns — permet d'ordonner des événements très rapprochés (exécution d'un script rapide, ouverture en rafale)
Gain forensique : timeline beaucoup plus fine que HFS+ (1 s) — ordre chronologique exact sur opérations groupées

🕐 Timestamps par inode APFS

  • create_time — création (crtime, équivalent btime Linux)
  • mod_time — dernière modification contenu (mtime)
  • change_time — dernière modif métadonnées (ctime)
  • access_time — dernier accès (atime, désactivé par défaut sur APFS pour préserver SSD)
📸 Snapshots — copy-on-write

Un snapshot APFS est un état gelé et cohérent de tout un volume à un instant T. Le snapshot partage les blocs avec le volume actif ; seules les différences (blocs modifiés après la prise du snapshot) consomment de l'espace supplémentaire.

  • Mécanisme : copy-on-write au niveau bloc. Modifier un fichier copie le bloc modifié, le snapshot garde le pointeur vers l'ancien
  • Création : tmutil snapshot (macOS) · diskutil apfs createSnapshot /
  • Liste : tmutil listlocalsnapshots / ou diskutil apfs listSnapshots /
  • Time Machine local (macOS 10.13+) : crée automatiquement des snapshots horaires, conservés jusqu'à 24h ou contrainte d'espace
  • Auto snapshots avant update : macOS crée un snapshot avant chaque Software Update → rollback possible
1Un snapshot est pris → pointeur vers l'omap actuel. Aucune copie de données, juste une référence figée.
2L'utilisateur modifie un fichier → un nouveau bloc est alloué pour la version modifiée. L'ancien bloc reste, référencé par le snapshot.
3Le snapshot peut être monté en lecture seule → accès à la version T0 des fichiers : mount_apfs -s snapshot_name ...
4Supprimer un fichier sans vider les snapshots → le fichier reste récupérable via n'importe quel snapshot antérieur à la suppression.
💎 Valeur forensique des snapshots
Les snapshots APFS sont la mine d'or forensique de macOS moderne. Un Mac actif peut contenir : plusieurs snapshots Time Machine locaux (jusqu'à 24h d'historique), un snapshot pré-update, et des snapshots utilisateur manuels. Chacun est un état complet et montable du système. Un fichier supprimé il y a 6 heures est probablement encore accessible dans un snapshot Time Machine local.

🔍 Monter un snapshot

# Lister les snapshots locaux du volume racine
tmutil listlocalsnapshots /

# Ou plus bas-niveau
diskutil apfs listSnapshots /

# Monter un snapshot en lecture seule
mkdir /tmp/snap
mount_apfs -o nobrowse,ro \
  -s com.apple.TimeMachine.2025-01-15-143022.local \
  /dev/disk1s1 /tmp/snap
🧬 Clones — déduplication à la copie

Un clone APFS est une copie d'un fichier qui partage instantanément ses blocs avec l'original — zéro coût disque au moment de la copie. Les modifications ultérieures déclenchent du COW bloc par bloc.

  • Créé par : cp -c source dest (option -c spécifique APFS)
  • Finder duplique désormais les fichiers via clones automatiquement
  • Valeur forensique : deux fichiers clonés partagent un CNID distinct mais les mêmes blocs physiques jusqu'à divergence
  • Outil : mac_apt détecte les clones via analyse de l'extentref_tree
🔒 Sealed System Volume (SSV) — macOS 11+

Depuis Big Sur (2020), le volume System (/) est cryptographiquement scellé :

  • Un arbre de Merkle est calculé sur tous les fichiers système
  • La racine du Merkle Tree (SSV seal) est signée par Apple
  • Au boot, le système vérifie l'intégrité de chaque bloc lu → toute modification rompt le sceau
  • Le volume / est read-only en opération normale — même root ne peut l'écrire
  • Firmlinks : /Applications, /Users etc. pointent vers Data volume (dual-layer)
  • Impact forensique : inutile de chercher des traces de compromission dans les binaires système — soit le sceau est intact (rien de modifié), soit le Mac ne bootait plus
⚠️ Conséquence pratique : tous les malwares macOS modernes ciblent le volume Data (LaunchAgents utilisateur, ~/Library/, profils MDM), pas le volume System. Concentrer l'analyse sur Data et les artefacts utilisateur (voir fiche macOS/Linux).

🍏 FileVault sur APFS Apple Silicon

  • La clé du volume n'est jamais extractible du Secure Enclave
  • Le volume Data est toujours chiffré, même sans FileVault actif — FileVault ajoute juste la dépendance au mot de passe utilisateur
  • Impossible de déplacer le SSD vers un autre Mac : la clé est liée à l'UID de cette puce Apple Silicon précise
  • Voir fiche dédiée : Chiffrement de Volumes
📱 APFS sur iOS — Data Protection

iOS utilise APFS depuis iOS 10.3, avec une couche supplémentaire : Data Protection. Chaque fichier est chiffré avec une per-file key, elle-même protégée par une classe de protection.

Classe Constante Comportement
Complete NSFileProtectionComplete Clé purgée à chaque verrouillage. Fichier illisible tant que le device est verrouillé. Défaut apps tierces iOS 7+.
Complete Unless Open NSFileProtectionCompleteUnlessOpen Accessible si le fichier était déjà ouvert avant verrouillage (téléchargements en cours).
Complete Until First User Auth NSFileProtectionCompleteUntilFirstUserAuthentication Protégé jusqu'au premier déverrouillage post-boot. Après : accessible même verrouillé. Défaut système.
None NSFileProtectionNone Chiffré avec clé liée au device seulement. Accessible dès le boot (avant déverrouillage). Rare en apps modernes.
BFU vs AFU : un iPhone saisi éteint est en état BFU (Before First Unlock) — toutes les classes de protection sont actives, la plupart des données inaccessibles. Un iPhone saisi allumé-verrouillé est en AFU (After First Unlock) — les classes CompleteUntilFirstUserAuth et plus faibles sont déjà déchiffrables. Toujours préserver l'état AFU : laisser l'iPhone allumé, le mettre dans une cage de Faraday en charge.
🌳 Structures B-Tree APFS

🔑 Object Map (omap)

  • B-Tree qui traduit object_id → bloc physique
  • Un omap par volume + un pour le container
  • Les snapshots ont leur propre omap figé
  • Transaction ID (XID) incrémenté à chaque checkpoint → ordre temporel des modifications

📂 File System Tree

  • B-Tree principal du volume
  • Clés typées : inode, file_extent, dir_rec, xattr, sibling_link
  • Hard links : un inode, plusieurs dir_rec
  • Extents stockés directement dans l'arbre (pas de fichier Extents séparé comme HFS+)

🔎 Checkpoint mapping

Les superblocs APFS sont stockés dans une zone circulaire (checkpoint area). À chaque modification majeure, un nouveau NXSB est écrit dans la zone — les anciens restent temporairement lisibles.

  • Fenêtre forensique : ~100–200 Mo d'anciens états du container
  • Permet de reconstituer des états antérieurs du container avant certaines opérations destructives
  • Parsers : apfs-fuse, fleischer/apfs-tools
💾 Time Machine sur APFS (macOS 11+)

Depuis Big Sur, Time Machine privilégie les snapshots APFS plutôt que les hard links de répertoires HFS+.

  • Sauvegarde locale : snapshots horaires sur le volume interne (purgés après 24h)
  • Sauvegarde externe : disque formaté APFS → snapshots envoyés avec apfs_snapshot_diff (incrémental natif)
  • Si le disque externe est HFS+ : fallback sur l'ancien mode hard-links
  • Stockage : /Volumes/<TM>/<Mac>.backupbundle/ (sparsebundle)
  • Valeur forensique : historique complet des modifications fichier, parfois sur plusieurs années

Questions d'entraînement
Quelle différence fondamentale d'architecture APFS vs HFS+ change tout pour la forensique ?APFS architecture · Niveau : moyen
APFS introduit le Container : un pool d'espace partagé qui héberge plusieurs volumes dynamiques (System, Data, Preboot, Recovery, VM). Chaque volume grossit/rétrécit dynamiquement — pas de partitionnement fixe. Forensiquement : on doit monter le container entier, pas juste une partition, pour accéder à tous les volumes et leurs snapshots.
Un fichier est supprimé sur macOS 13 à 14h00. Il est 14h45. Comment le récupérer ?APFS snapshots · Niveau : moyen
macOS crée automatiquement des snapshots Time Machine locaux horaires. Le snapshot de 13h00 ou 14h00 contient encore le fichier. Commande : tmutil listlocalsnapshots / → identifier le snapshot → mount_apfs -s <snapshot> ou passer par Time Machine. Les snapshots sont conservés jusqu'à 24h ou contrainte d'espace.
APFS vs HFS+ : quelle est la différence d'epoch et d'endianness ?APFS timestamps · Niveau : facile
APFS : epoch = 1er janvier 1970 UTC (Unix), précision nanoseconde, stockage sur 64 bits, Little Endian.
HFS+ : epoch = 1er janvier 1904, précision 1 seconde, Big Endian.
Conversion APFS : unix_ts = apfs_ts / 1_000_000_000
⚖️ Cadre suisse face à Apple

iCloud Recovery Key : en cas de FileVault avec escrow iCloud activé, la recovery key est détenue par Apple (USA). Requête par entraide pénale internationale (EIMP / art. 18 Convention de Budapest) — procédure lente (mois à années), Apple résiste systématiquement sauf ordonnance US.


Apple Business Manager / MDM : si le Mac est enrôlé en MDM d'entreprise, la recovery key peut être stockée côté gestionnaire MDM (Jamf, Intune, Kandji). Accessible rapidement via l'employeur si l'enquête le justifie (art. 265 CPP).


Apple Silicon & FileVault : l'extraction physique n'est pas faisable. Seules voies : mot de passe utilisateur, recovery key, ou consentement. Voir fiche Chiffrement de Volumes pour la méthodologie détaillée.

🎓 Exam Tip — APFS
  • Introduction : iOS 10.3 (2017), macOS 10.13 High Sierra (2017)
  • Endianness : Little Endian (contrairement à HFS+)
  • Epoch : 1er janvier 1970 UTC (Unix), précision nanoseconde
  • Architecture : Container → plusieurs Volumes → partage d'espace dynamique
  • Snapshots : copy-on-write, montables read-only, base de Time Machine local
  • Clones : cp -c, deduplication à la copie, diverge par COW
  • SSV : volume System scellé (Merkle tree signé Apple), read-only, depuis Big Sur
  • Chiffrement : natif multi-clés (per-file), Secure Enclave sur Apple Silicon
  • iOS : Data Protection classes (Complete, UntilFirstUserAuth, None…), BFU vs AFU
  • Outils : X-Ways v20.3+, mac_apt, apfs-fuse, diskutil apfs
