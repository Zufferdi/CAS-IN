🔑 Principe FAT32 — Table d'allocation chaînée
FAT32 stocke la carte d'allocation des clusters dans une table (la FAT) qui fonctionne comme une liste chaînée. Chaque entrée de 32 bits dans la FAT correspond à un cluster du volume et contient soit le numéro du cluster suivant (si le fichier continue), soit la valeur EOC (End Of Chain = 0x0FFFFFFF) si c'est le dernier cluster. Les Directory Entries pointent vers le premier cluster du fichier.

🔍 Valeurs FAT32 spéciales

  • 0x00000000 = cluster libre
  • 0x0FFFFFF7 = cluster défectueux (bad cluster)
  • 0x0FFFFFF8–0x0FFFFFFF = EOC (dernier cluster)
  • Entrées 0 et 1 réservées — ne correspondent pas à des clusters réels
  • Cluster #2 = début de la Data Area (premier cluster utilisable)

⚡ Formules FAT32 essentielles

  • Taille FAT = SectorsPerFAT32 × BytesPerSector
  • Début Data Area = (ReservedSectors + NumFATs × SectorsPerFAT32) × BPS
  • Offset cluster N = Début_Data + (N − 2) × ClusterSize
  • Cluster N dans FAT = offset (N × 4) dans la FAT
  • Ex. cluster 5 → FAT[5] à offset 20 (0x14) dans la FAT
🔑 BPB — BIOS Parameter Block
Le BIOS Parameter Block est la carte de géométrie du volume FAT32. Il occupe les 90 premiers octets du Boot Sector (secteur 0 de la partition). Tous les champs sont en Little Endian. Sans lui, impossible de localiser la FAT, le Root Directory, ni la Data Area. C'est le premier élément à analyser.

🔍 Signatures FAT32 essentielles

  • JMP : EB 58 90 (≠ NTFS EB 52 90)
  • OEM Name @ 0x03 : "MSWIN4.1" ou "MSDOS5.0"
  • RootEntryCount @ 0x11 : 0x0000 (FAT32 uniquement)
  • FATSz16 @ 0x16 : 0x0000 (FAT32 utilise 0x24 à la place)
  • Signature Boot : 55 AA @ offset 0x1FE
  • FAT[0] : F8 FF FF 0F · FAT[1] : FF FF FF FF

⚡ FAT32 vs FAT16 vs FAT12

  • FAT12 : entrées 12 bits · max ~4 Mo · disquettes
  • FAT16 : entrées 16 bits · max 2 Go · RootEntryCount fixe
  • FAT32 : entrées 32 bits (28 utilisés) · max 2 To · Root dans Data Area
  • Identification par nombre de clusters (pas par le type MBR seul)
  • FAT12 : < 4 085 clusters · FAT16 : 4 085–65 524 · FAT32 : ≥ 65 525
🔑 Directory Entry — 32 octets par fichier
Chaque fichier ou sous-répertoire est décrit par une directory entry de 32 octets. Le Root Directory (et chaque sous-répertoire) est une liste contiguë d'entries de 32 octets stockée dans la Data Area. L'entrée donne le nom, les attributs, les timestamps, le premier cluster, et la taille du fichier — c'est le point d'entrée de toute récupération forensique.

Octet d'attributs — offset 0x0B
Bit Valeur Attribut Signification forensique
0 0x01 Read-Only Modification bloquée par l'OS. Peut indiquer un fichier système protégé ou une configuration.
1 0x02 Hidden Invisible dans l'Explorateur par défaut. Combiné avec System (0x06) → fichier système caché. IOC si on le voit sur des données utilisateur.
2 0x04 System Fichier système OS. Hidden + System (0x06) = invisibilité totale dans l'Explorateur.
3 0x08 Volume ID Label du volume. Une seule entrée par volume, dans le répertoire racine. Taille = 0.
4 0x10 Directory L'entrée pointe vers un sous-répertoire. Taille = 0 (ignorée par l'OS). Premier cluster = début du contenu du répertoire.
5 0x20 Archive Mis à 1 à la création ou modification. Remis à 0 par les logiciels de backup. Utile pour la timeline d'activité.
0–3 0x0F LFN Entry Combinaison spéciale : Read-Only + Hidden + System + Volume ID = entrée LFN (Long File Name). Précède l'entrée SFN 8.3 correspondante.
Premier octet de l'entry — État du fichier
0x41–0x5A
Fichier actif
Premier caractère du nom en ASCII. L'entrée est valide et utilisée.
0xE5
Fichier supprimé
L'OS écrase le 1er octet par 0xE5. Tous les autres champs intacts — récupération possible si clusters non réalloués.
0x00
Fin de répertoire
Marqueur de fin : toutes les entries suivantes sont libres. La lecture s'arrête ici.
🔴 0xE5 — Clé de récupération : lors d'une suppression FAT32, seul le premier octet de l'entry est remplacé par 0xE5. Le nom (moins le 1er caractère), les timestamps, le premier cluster, et la taille restent intacts. La FAT libère la chaîne (clusters remis à 0x00) mais les données sur disque ne sont PAS effacées. Récupération quasi-certaine si les clusters n'ont pas été réalloués.
Timestamps FAT32 — Encodage
⏱ Time Word (2 octets LE)
bits 15–11 : Heures (0–23)
bits 10–5 : Minutes (0–59)
bits 4–0 : Secondes ÷ 2 (0–29)
⚠ Précision : 2 secondes — limite structurelle. Un fichier créé à 14h32:07 est enregistré à 14h32:06.
📅 Date Word (2 octets LE)
bits 15–9 : Année − 1980 (0–127 → 1980–2107)
bits 8–5 : Mois (1–12)
bits 4–0 : Jour (1–31)
Epoch = 1er janvier 1980. Date 0 = 00/00/1980 (invalide) → entrée non initialisée.
Exemple : WrtTime = 4A 6D LE → 0x6D4A → binaire : 0110 1101 0100 1010
Heures = 01101 = 13 · Minutes = 101010 = 42 · Secondes = 01010 × 2 = 20
→ 13:42:20
🔍 FAT32 — Cible forensique fréquente
FAT32 est le système de fichiers le plus répandu sur les clés USB, cartes SD et disques amovibles — vecteurs d'exfiltration et supports saisis en priorité. Sa simplicité le rend très analysable manuellement. Sa faiblesse principale : pas de journal, pas de métadonnées étendues, pas de contrôle d'accès — ce qui simplifie aussi la récupération.
Workflow d'analyse FAT32
1
Lire le BPB
Extraire BPS, SPC, ReservedSectors, NumFATs, SectorsPerFAT32, RootCluster. Calculer les offsets de la FAT 1 et de la Data Area. Vérifier OEM Name pour confirmer FAT32 vs exFAT.
2
Cartographier le Root Directory
Localiser via RootCluster × ClusterSize + Début_Data. Lire les entries de 32 octets — noter les 0xE5 (supprimés) et les 0x00 (fin). Un répertoire peut s'étendre sur plusieurs clusters.
3
Reconstruire les chaînes FAT
Pour chaque fichier : lire FAT[FirstCluster], suivre la chaîne jusqu'à 0x0FFFFFF8+. Pour les fichiers supprimés : les entrées FAT sont remises à 0 — utiliser la taille de l'entry pour estimer la chaîne théorique (clusters contigus).
4
Scanner les clusters libres
Clusters marqués libres dans la FAT mais contenant des données = résidus de fichiers supprimés. Carving par magic bytes si la chaîne FAT n'est plus reconstructible.
5
Comparer FAT 1 et FAT 2
Les deux FAT doivent être identiques. Une divergence indique une corruption ou une manipulation anti-forensique ciblée de la FAT principale.
Récupération de fichiers supprimés — Mécanisme
✅ Ce qui reste après suppression
  • Directory entry intacte (sauf byte 0x00 → 0xE5)
  • Timestamps Write, Create, Access
  • Premier cluster (champ 0x1A–0x1B + 0x14–0x15)
  • Taille du fichier (champ 0x1C–0x1F)
  • Données physiques sur disque (non effacées)
  • LFN entries précédentes (si présentes)
❌ Ce qui est effacé
  • Premier octet du nom (remplacé par 0xE5)
  • Chaîne FAT (tous les clusters remis à 0x00)
  • Les données elles-mêmes NE sont PAS effacées
  • Sur SSD avec TRIM : données potentiellement zeroisées
Slack Space FAT32
RAM Slack (Sector Slack)
Fin du fichier → fin du dernier secteur utilisé. Rempli de zéros sous Windows NT+. Pas de contenu RAM sur les OS modernes.
Drive Slack
Secteurs entiers non utilisés jusqu'à la fin du dernier cluster alloué. Contient les résidus de l'ancien fichier — zone forensiquement exploitable.
Formule File Slack
slack = ClusterSize − (FileSize mod ClusterSize)
Formule RAM Slack
ram_slack = BPS − (FileSize mod BPS)

Limitations forensiques de FAT32
❌ Pas de journal
Contrairement à NTFS ($LogFile, $UsnJrnl), FAT32 n'a pas de journal d'opérations. Impossible de prouver qu'un fichier a existé s'il n'y a plus d'entry et plus de données.
❌ Précision timestamps 2 secondes
La résolution de 2 secondes (bits 4–0 = sec÷2) empêche la corrélation précise avec des logs réseau (secondes précises). Limitation structurelle non contournable.
❌ Pas de contrôle d'accès
Pas d'ACL, pas de SID propriétaire, pas de permissions. Impossible d'attribuer un fichier à un utilisateur spécifique sur la base du FS seul.
❌ Timestamp local (pas UTC)
FAT32 stocke l'heure locale sans information de fuseau. Problème de corrélation si le support a été utilisé dans des fuseaux différents. NTFS stocke en UTC.
❌ Fichier max 4 Go − 1 octet
Champ FileSize sur 32 bits non signé. Images disque, dumps RAM, vidéos 4K dépassent souvent cette limite — inutilisable dans ces cas.
✅ Avantage : simplicité
Structure entièrement analysable manuellement avec un éditeur hex. Pas de chiffrement natif, pas de compression opaque. Récupération plus directe que NTFS.

🔑 Volume ID — corrélation Windows

  • Volume ID (Serial) @ 0x43 dans le BPB — 4 octets
  • Référencé dans HKLM\SYSTEM\MountedDevices
  • Visible dans vol C: (Windows) ou blkid (Linux)
  • Corrélable avec les logs d'événements de connexion USB (Event ID 20001, 2003)
  • Incohérence Volume ID ↔ registre = volume cloné ou modifié

🔑 FAT2 — indicateur de manipulation

  • FAT 1 (principale) et FAT 2 (backup) doivent être identiques
  • Windows maintient la FAT 2 en sync automatiquement
  • Divergence FAT1 ≠ FAT2 → corruption, arrachage ou manipulation ciblée
  • Comparer : dd les deux zones et diff les dumps
  • Certains outils d'anti-forensique ne modifient que FAT 1

❓ Questions de révision
Quels champs du BPB FAT32 permettent de calculer l'offset de la Data Area ?BPB · Niveau : moyen
Formule :
Offset_Data = (ReservedSectors + NumFATs × SectorsPerFAT32) × BytesPerSector

Champs nécessaires :
· ReservedSectors @ 0x0E (2 o LE) — typiquement 32
· NumFATs @ 0x10 (1 o) — typiquement 2
· SectorsPerFAT32 @ 0x24 (4 o LE) — variable
· BytesPerSector @ 0x0B (2 o LE) — typiquement 512

Exemple : 32 + 2 × 64 = 160 secteurs × 512 = 81 920 octets = offset de la Data Area.
Un fichier a été supprimé sur une clé FAT32. Quelles informations subsistent dans la directory entry, et lesquelles ont disparu ?Suppression FAT32 · Niveau : facile
Ce qui subsiste (intact) :
· Octets 1–10 du nom (8.3), sauf le byte 0 remplacé par 0xE5
· Tous les timestamps (Write, Create, Access)
· Premier cluster (0x1A–0x1B + 0x14–0x15)
· Taille du fichier (0x1C–0x1F)
· Attributs
· Données physiques sur disque (non effacées)

Ce qui est effacé :
· Premier octet du nom → 0xE5
· Chaîne FAT (tous les clusters de la chaîne remis à 0x00000000 = libre)

La récupération est possible tant que les clusters n'ont pas été réalloués à un autre fichier.
Pourquoi RootEntryCount (offset 0x11) doit être à 0 en FAT32 ? Quelle est la différence avec FAT16 ?FAT32 vs FAT16 · Niveau : facile
En FAT16, le Root Directory est une zone fixe de taille prédéfinie immédiatement après les FAT. RootEntryCount indique le nombre maximal d'entries (souvent 512 = 512 × 32 octets = 16 384 octets).

En FAT32, cette limitation a été supprimée : le Root Directory est un répertoire ordinaire dans la Data Area, identifié par le champ RootCluster (@ 0x2C). Il peut grandir dynamiquement en occupant plusieurs clusters. RootEntryCount doit donc être 0x0000 — une valeur non nulle ici indique FAT12 ou FAT16, pas FAT32.
Comment distinguer FAT32 de exFAT en analysant le secteur de boot ? Les deux ont le type MBR 0x07 — que faire ?FAT32 vs exFAT · Niveau : moyen
Le type byte MBR 0x07 est effectivement partagé par NTFS et exFAT, tandis que FAT32 utilise plutôt 0x0B/0x0C — mais des cas existent où 0x07 est mis pour FAT32. Le type MBR seul ne suffit pas.

Méthode fiable : lire l'OEM Name @ offset 0x03 du Boot Sector (8 octets ASCII) :
· "MSWIN4.1" ou "MSDOS5.0" → FAT32
· "EXFAT " (5 lettres + 3 espaces) → exFAT
· "NTFS " (4 lettres + 4 espaces) → NTFS

Confirmer FAT32 : vérifier RootEntryCount = 0x0000 et que le champ SectorsPerFAT32 @ 0x24 est non nul.
La FAT 1 et la FAT 2 d'un disque saisi divergent sur 3 entrées. Quelle est ton interprétation et que fais-tu ?FAT1 vs FAT2 · Niveau : difficile
Interprétations possibles :
· Arrachage brutal du support — Windows n'a pas eu le temps de synchroniser FAT 2 après avoir modifié FAT 1. Signe de corruption non intentionnelle.
· Manipulation ciblée — outil anti-forensique qui modifie uniquement FAT 1 pour cacher une chaîne de clusters (les clusters modifiés en FAT 1 restent visibles dans FAT 2).
· Formatage partiel — certains outils "rapides" ne mettent à jour que FAT 1.

Actions :
· Identifier précisément les clusters divergents (numéros d'entrée × 4 = offset)
· Analyser les données aux clusters concernés — présence de données malgré FAT 1 à 0 = suppression incomplète
· Documenter la divergence dans le rapport comme indice d'altération potentielle
· Travailler sur une image — ne jamais monter l'original
⚖️ Examen CAS-IN : FAT32 = BPB + FAT(s) + Data Area · Cluster 2 = premier cluster Data Area · EOC = 0x0FFFFFFF · Suppression = 0xE5 sur byte 0 + clusters remis à 0 dans FAT · RootEntryCount = 0 en FAT32 (≠ FAT16) · Timestamps = précision 2 s, heure locale (pas UTC) · Volume ID @ 0x43 corrélable au registre Windows · FAT1 ≠ FAT2 = corruption ou manipulation · Slack : RAM Slack = zéros (NT+), Drive Slack = résidus.
