📬 SMTP = Simple Mail Transfer Protocol (RFC 5321)
Protocole standard envoi emails. Client SMTP → envoie → serveur SMTP → relaye vers serveur destination. Chaque étape = logguée en Received headers.
SMTP Flow (Simplifié)
CLIENT → SMTP-SERVER-1 (compose + send)

SMTP-SERVER-1 → SMTP-SERVER-2 (relaye)
Ajoute: Received: from server1.com by server2.com

SMTP-SERVER-2 → SMTP-SERVER-3 (relaye)
Ajoute: Received: from server2.com by server3.com

SMTP-SERVER-3 → RECIPIENT (inbox)
Final Received: from server3.com

Result: Email header = FULL ROUTING PATH 🎯
🔍 Forensique SMTP
  • Routing path = Trace attacker IP(s)
  • Timestamps = quand exactement envoyé
  • Headers = vérifier cohérence (From ≠ Return-Path?)
  • Authentication = SPF/DKIM/DMARC passed/failed?
📋 Email Header Structure (RFC 5322)
Headers = paires clé-valeur qui décrivent email (qui, quand, route, contenu, etc). Ordre des headers Received : chaque serveur ajoute son Received en TÊTE — donc le plus récent est en haut, le plus ancien (le client expéditeur) tout en bas. Pour reconstituer la route, on lit du bas vers le haut.
Headers Critiques pour Forensique
Header Contenu Forensique
From Sender apparent (affiché) 🟠 MODIFIABLE! Peut être spoofé
Return-Path Vrai expéditeur (serveur SMTP) 🟢 AUTHENTIQUE (serveur ajoute)
Received (multiple) Each relay adds this 🔴 CRITICAL! Trace routing path
Date Sent timestamp (client clock) 🟠 Client clock (peut être faux)
Subject Sujet email 📌 Intent (phishing subject?)
Message-ID Unique ID per server 🔑 Track emails from same source
Authentication-Results SPF/DKIM/DMARC results 🟢 Pass/Fail = vérification
Exemple: Header Complet
From: attacker@gmail.com ← SPOOFABLE
To: victim@example.com
Subject: Urgent: Verify Account! ← Phishing clue
Date: Wed, 20 Mar 2024 14:32:00 +0000
Message-ID: <abc123@gmail.com>

← Start Received headers (oldest first)

Received: from mail.google.com (mail.google.com [142.250.185.46])
    by mail.example.com with SMTP id pass
    for <victim@example.com>;
    Wed, 20 Mar 2024 14:33:00 +0000

← Gmail added this (verified sender)

Received: from client.home [192.168.1.100]
    by mail.google.com with SMTP
    Wed, 20 Mar 2024 14:32:00 +0000

← Attacker's local IP (earliest)

Authentication-Results: mail.example.com;
    spf=fail;
    dkim=fail;
    dmarc=fail

↑ RED FLAGS!
🚨 Email Spoofing = Fake From Header
Attacker envoie email avec faux "From" (ex: boss@company.com). Destinataire voit fake From, mais Received headers = vraie source.
Detections Indicateurs Spoofing
🚩 From ≠ Return-Path
From: boss@company.com
Return-Path: attacker@gmail.com
→ SUSPICIOUS!
🚩 From Domain ≠ Last Received
From: john@company.com
Received: from attacker.tk
→ Spoofed!
🚩 SPF/DKIM/DMARC Failed
spf=fail
dkim=fail
→ No authentication
🚩 Weird IPs in Received
from [192.168.0.1] (home ISP)
claiming to be company employee
→ Unlikely
Detection Workflow
  1. Extract Received headers (reverse order = timeline)
  2. Identify first hop IP (attacker origin)
  3. Compare From domain vs Received domain
  4. Check SPF/DKIM/DMARC pass/fail
  5. IP reverse lookup (geolocation suspicious?)
  6. Timestamp consistency (Date vs Received)
🔐 Email Authentication: SPF, DKIM, DMARC
Trois standards pour vérifier que email est vrai (pas spoofé). SPF = IP vérification, DKIM = signature, DMARC = policy enforcement.
Les 3 Protocols Expliqués
Protocol Comment Résultat
SPF (RFC 7208) Receiver cherche SPF record du From domain (DNS TXT). Vérifie: "est-ce IP du serveur SMTP autorisée?" pass / fail / softfail
DKIM (RFC 6376) Sender ajoute signature cryptographique. Receiver vérifie signature avec clé publique (DNS). pass / fail / neutral
DMARC (RFC 7489) Policy: "Si SPF + DKIM fail, qu'est-ce que tu fais?" Peut quarantine/reject/report. pass / fail
⚠️ Forensique: Authentication-Results Header
Authentication-Results: mail.example.com;
    spf=fail smtp.mailfrom=attacker@gmail.com;
    dkim=fail header.d=company.com;
    dmarc=fail header.from=company.com

→ ALL FAILED = Phishing likely! 🚨

👆 Collez headers pour analyse spoofing
CLI Quick Commands
# Extract headers from email file
$ head -100 email.txt | grep -E "^(From|Return-Path|Received|Date|Authentication)"

# Check SPF record
$ dig company.com TXT | grep spf

# Check DKIM record
$ dig default._domainkey.company.com TXT

# Check DMARC policy
$ dig _dmarc.company.com TXT

# Extract IPs from Received headers
$ grep "Received:" email.txt | grep -oP '\[[\d.]+\]' | sort

# Reverse IP lookup
$ dig -x 192.168.1.100
✅ Workflow Complet Email Forensique
  1. Extraire tous headers (Thunderbird ou CLI)
  2. Identifier Received headers (reverse order = timeline)
  3. Trouver première IP (attacker origin)
  4. Reverse IP lookup (geolocation)
  5. Compare From ≠ Return-Path (spoofing?)
  6. Check SPF/DKIM/DMARC results
  7. Verify Date vs Received timestamps
  8. Rapport: Spoofing likelihood, source IP, authentication
