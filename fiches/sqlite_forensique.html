SQLite — omniprésence forensique
Magic bytes & identification
  • Header SQLite : 53 51 4C 69 74 65 20 66 6F 72 6D 61 74 20 33 00
  • ASCII : "SQLite format 3\0" — 16 premiers octets
  • Extension variable : .db, .sqlite, .sqlite3, .db3, sans extension
  • Taille de page : offset 16, 2 octets big-endian (512–65536, puissance de 2)
  • Version SQLite : offset 96, 4 octets
Présence dans les systèmes forensiques
  • Navigateurs : History, Cookies, Login Data, Web Data (Chrome/Edge/Firefox/Safari)
  • iOS : Messages (sms.db), Contacts (AddressBook.sqlitedb), Photos (Photos.sqlite), Mail
  • Android : mmssms.db, contacts2.db, calendar.db, WhatsApp (msgstore.db)
  • Windows : ActivityCache.db (Timeline), SRUDB.dat, thumbcache, Cortana
  • Autopsy : toute la base de cas (autopsy.db)
Structure interne — pages et B-tree
Type de page Taille typ. Contenu forensique
Header
Page 1
100 bytes Magic bytes, taille de page, version, nombre de pages, free list, numéro de schéma
B-tree interior
4 KB Nœuds internes — clés de tri pour naviguer dans l'arbre. Peu de données utilisateur.
B-tree leaf
4 KB Données des lignes (records) — format variable length. Stocke les valeurs de chaque colonne.
Free page
4 KB Pages libérées après DELETE / VACUUM — les données peuvent subsister jusqu'à réutilisation. Clé de la récupération forensique.
Overflow
variable Données trop volumineuses pour une page (BLOBs, textes longs). Chaîne de pages overflow.
📌 Free list forensique : SQLite ne wipe pas les pages libérées — il les ajoute à une liste chaînée. Les données supprimées restent lisibles jusqu'au prochain VACUUM ou réutilisation de la page. DB Browser for SQLite ne montre pas ces pages — utiliser un éditeur hex ou un outil forensique (SQLiteRecovery, Oxygen, AXIOM).
WAL — Write-Ahead Log
1
Transaction démarrée — SQLite crée ou utilise le fichier database.db-wal. Les nouvelles pages modifiées sont écrites dans le WAL, pas directement dans la DB principale.
2
Checkpoint — périodiquement (ou au COMMIT/CLOSE), les pages du WAL sont recopiées dans la DB principale. Le WAL peut être truncated ou preserved.
3
Valeur forensique — le WAL peut contenir des versions antérieures de lignes (avant mise à jour) et des lignes supprimées. Même si la DB principale est intacte, le WAL ajoute un layer de données récupérables.
Fichiers associés à une DB SQLite
  • database.db — base principale
  • database.db-wal — Write-Ahead Log (transactions en cours)
  • database.db-shm — Shared Memory (index WAL, fichier temporaire)
  • database.db-journal — mode journal rollback (alternatif au WAL)

Toujours acquérir les 4 fichiers ensemble — le WAL non checkpointé peut contenir les données les plus récentes.

Pièges d'acquisition
  • DB chiffrée (SQLCipher) → entropie ~8, impossible sans clé. Clé souvent dérivée du mot de passe ou stockée dans la mémoire du processus.
  • DB verrouillée (processus actif) → copier à chaud peut donner un état inconsistant. Préférer l'acquisition via API (iTunes Backup, ADB) ou dump RAM pour la clé SQLCipher.
  • VACUUM récent → free pages écrasées, pages WAL checkpointées. Vérifier les sauvegardes système.
Requêtes SQL forensiques — exemples clés
-- Historique Chrome : URLs triées par date (epoch microsecondes depuis 1601)
SELECT url, title,
  datetime((visit_time/1000000)-11644473600, 'unixepoch') AS visit_date,
  visit_count
FROM urls JOIN visits ON urls.id = visits.url
ORDER BY visit_time DESC LIMIT 50;
-- Firefox : historique (epoch microsecondes depuis 1970)
SELECT url, title,
  datetime(last_visit_date/1000000, 'unixepoch') AS last_visit,
  visit_count
FROM moz_places
WHERE visit_count > 0 ORDER BY last_visit_date DESC;
-- iOS sms.db : messages SMS avec timestamps (epoch Mac Absolute, depuis 2001)
SELECT text, is_from_me,
  datetime(date+978307200, 'unixepoch') AS message_date,
  service
FROM message
ORDER BY date DESC LIMIT 100;
-- Lister toutes les tables d'une base inconnue
SELECT name, type, sql FROM sqlite_master
WHERE type IN ('table', 'view') ORDER BY name;

-- Nombre de lignes par table (vue d'ensemble)
SELECT 'messages', COUNT(*) FROM messages
UNION ALL SELECT 'contacts', COUNT(*) FROM contacts;

Récupération de records supprimés
Méthode 1 — DB Browser + hex
  • Ouvrir la DB en hex (010 Editor, HxD)
  • Rechercher les patterns de données dans les free pages (offset après le header de page)
  • Les records SQLite commencent par un varint encodant la taille du payload
  • DB Browser → onglet "Parcourir les données" : les lignes supprimées n'apparaissent plus, mais elles sont dans le fichier
Méthode 2 — Outils spécialisés
  • Oxygen Forensic Detective — parse les free pages automatiquement
  • AXIOM (Magnet) — récupération SQLite intégrée
  • SQLiteRecovery (open source) — extrait les records des free pages
  • Autopsy — module SQLite Parser inclut les free pages optionnellement
  • Undark — outil CLI spécialisé récupération SQLite
# Vérifier l'intégrité d'une base SQLite (détecte corruption)
sqlite3 suspect.db "PRAGMA integrity_check;"

# Lister les pages libres
sqlite3 suspect.db "PRAGMA freelist_count;"

# Extraire le WAL et le merger dans la DB principale (checkpoint)
sqlite3 suspect.db "PRAGMA wal_checkpoint(FULL);"

# Rechercher un terme dans toutes les tables (forensique rapide)
grep -a "suspect@email.ch" database.db | strings
💡 Astuce examen : Une base de données chiffrée (SQLCipher) se reconnaît à l'absence du magic bytes SQLite dans les 16 premiers octets — à la place, du pseudo-aléatoire (entropie ~8). La taille de page peut rester lisible à l'offset 16 selon la version de SQLCipher.
