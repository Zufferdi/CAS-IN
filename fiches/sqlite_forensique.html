🗄️ SQLite — La base de données la plus déployée au monde
SQLite est la base de données la plus répandue de la planète — installée sur des milliards d'appareils. Pourquoi ? Légère (un seul fichier .db ou .sqlite), portable (aucun serveur requis), fiable (transactions ACID, formal verification). Conséquence forensique : presque toutes les applications mobiles et desktop stockent leurs données dans des bases SQLite. Chrome, Firefox, Edge, Safari, WhatsApp, Signal, Telegram, iOS (SMS, Contacts, Calls), Android (apps), Slack Desktop, Skype Desktop... Tous utilisent SQLite. Pour un enquêteur, c'est la mine d'or : un seul fichier copié = une base complète interrogeable avec un client SQL standard. Bonus : SQLite ne supprime pas physiquement les données effacées (il les marque comme libres dans la freelist), donc les messages supprimés peuvent souvent être récupérés via carving avec undark ou sqlite_dissect.

🗃 Bases SQLite forensiquement critiques
Localisation et requêtes types pour les bases les plus importantes en investigation.
🌐 Google Chrome / Chromium

Chemins :

  • Windows : %LOCALAPPDATA%\Google\Chrome\User Data\Default\History
  • macOS : ~/Library/Application Support/Google/Chrome/Default/History
  • Linux : ~/.config/google-chrome/Default/History

Tables clés : urls (url, title, visit_count, last_visit_time) · visits (timestamps précis, transition) · downloads (URL source, chemin local, état) · keyword_search_terms (termes de recherche)

SELECT url, title, visit_count,
       datetime(last_visit_time/1000000-11644473600, 'unixepoch') AS last_visit
FROM urls
ORDER BY last_visit_time DESC
LIMIT 50;
⚠️ Chrome utilise l'epoch Windows (microsecondes depuis 1601-01-01). Conversion : datetime(ts/1000000-11644473600, 'unixepoch')
💬 WhatsApp (Android · msgstore.db)

Chemins :

  • Android (root) : /data/data/com.whatsapp/databases/msgstore.db
  • Backup chiffré : /sdcard/WhatsApp/Databases/msgstore.db.crypt15
  • iOS : AppDomainGroup-group.net.whatsapp.WhatsApp.shared/ChatStorage.sqlite

Tables clés : messages (key_remote_jid, data, timestamp) · media_refs (médias) · jid (contacts) · chat (conversations)

SELECT m.key_remote_jid, m.data,
       datetime(m.timestamp/1000, 'unixepoch') AS date,
       m.media_url
FROM messages m
WHERE m.data IS NOT NULL
ORDER BY m.timestamp DESC
LIMIT 100;
🔑 Déchiffrement crypt15 : Cellebrite UFED, wa-crypt-tools, ou WhatsApp Viewer (avec la clé exportée depuis /data/data/com.whatsapp/files/key).
🦊 Firefox

Chemins :

  • Windows : %APPDATA%\Mozilla\Firefox\Profiles\xxxx.default\places.sqlite
  • macOS : ~/Library/Application Support/Firefox/Profiles/xxxx.default/places.sqlite

Tables clés : moz_places (url, title, visit_count, last_visit_date) · moz_historyvisits (timestamps + visit_type) · moz_bookmarks

SELECT p.url, p.title,
       datetime(v.visit_date/1000000, 'unixepoch') AS visited
FROM moz_historyvisits v
JOIN moz_places p ON v.place_id = p.id
ORDER BY v.visit_date DESC
LIMIT 50;
⚠️ Firefox utilise l'epoch UNIX en microsecondes. Conversion : datetime(ts/1000000, 'unixepoch')
📱 iOS — Points d'intérêt forensiques

Bases clés :

  • SMS : /var/mobile/Library/SMS/sms.db (table message)
  • Contacts : /var/mobile/Library/AddressBook/AddressBook.sqlitedb
  • Appels : /var/mobile/Library/CallHistoryDB/CallHistory.storedata
  • Photos : /var/mobile/Media/PhotoData/Photos.sqlite
  • Knowledge : /var/mobile/Library/CoreDuet/Knowledge/knowledgeC.db (timeline d'usage)

Accès : extraction logique (iTunes backup non chiffré) ou physique (Cellebrite, GrayKey). Backups iTunes chiffrés contiennent plus de données mais nécessitent le mot de passe.

SELECT datetime(date+978307200, 'unixepoch') AS date_msg,
       text, is_from_me
FROM message
ORDER BY date DESC LIMIT 50;
⚠️ iOS utilise l'epoch Mac/Cocoa (secondes depuis 2001-01-01 = +978307200 secondes UNIX). Conversion : datetime(ts+978307200, 'unixepoch')
✈️ Telegram (Desktop / Android)

Chemins :

  • Android : /data/data/org.telegram.messenger/files/cache4.db (SQLite standard, non chiffré côté local)
  • Desktop Windows : %APPDATA%\Telegram Desktop\tdata\ (format propriétaire, pas pur SQLite)

Telegram Desktop utilise un format propriétaire (les messages sont dans des fichiers binaires tdata/). Outils : TelegramDesktop-Dumper. Sur Android, la base cache4.db est SQLite accessible avec root, table messages.

🔍 Récupération de données supprimées
🗑 Pages non réallouées : la freelist

SQLite ne supprime jamais physiquement les données effacées. Il les marque comme libres dans la freelist (liste chaînée de pages disponibles pour réutilisation). Les données restent jusqu'à :

  • Une commande VACUUM manuelle (ne JAMAIS exécuter en forensique !)
  • Une réutilisation par insertion d'autres données
  • Un auto_vacuum activé sur la base
-- Voir le nombre de pages libres (= données supprimées potentielles)
PRAGMA freelist_count;

-- Voir si auto_vacuum est activé (0 = non · 1 = full · 2 = incremental)
PRAGMA auto_vacuum;

-- ⚠️ NE JAMAIS faire VACUUM sur une base forensique !
-- VACUUM efface définitivement les pages libres

Outils de récupération : undark (carving CLI), sqlite_dissect (CIA, robuste), Autopsy SQLite module (intégré), SQLite Deleted Records Recoverer, Cellebrite Physical Analyzer.

🧠 Testez-vous
Vous voulez analyser le fichier msgstore.db de WhatsApp en Python avec sqlite3. Quelle est la première précaution à prendre ?Bonnes pratiques · Niveau : facile
Travailler sur une COPIE, jamais sur l'original. Procédure : (1) copier les fichiers msgstore.db + msgstore.db-wal + msgstore.db-shm + éventuellement msgstore.db-journal dans un dossier de travail, (2) calculer le SHA-256 de chaque fichier copié, (3) ouvrir la copie en read-only avec sqlite3 : conn = sqlite3.connect('file:msgstore.db?mode=ro', uri=True). Pourquoi : si tu ouvres en write par accident, SQLite peut checkpointer le WAL (intégrer les modifications en attente dans le fichier principal) → modifie le fichier original → chaîne de custody brisée. Toujours documenter les hashes avant et après l'analyse pour prouver l'intégrité.
Vous trouvez un fichier signal.db dans une extraction. La requête SELECT * FROM sqlite_master renvoie file is not a database. Pourquoi ?SQLCipher · Niveau : moyen
Le fichier est chiffré avec SQLCipher. Signal utilise SQLCipher (AES-256-CBC) avec une clé dérivée du Signal PIN + Android Keystore / iOS Keychain. Le fichier ressemble à du SQLite mais il manque les magic bytes SQLite format 3\0 en clair — tout est chiffré dès le premier octet. Pour ouvrir : utiliser le client sqlcipher au lieu de sqlite3, et fournir la clé : sqlcipher signal.db puis PRAGMA key = 'x''CLEHEX''';. Récupérer la clé : (1) si l'appareil est déverrouillé, dump la RAM (clé en clair pendant la session), (2) extraire depuis Android Keystore avec accès root, (3) sur Desktop, la clé est dans config.json du dossier Signal — lisible si l'OS est accessible. Sans la clé, déchiffrement impossible en pratique (PBKDF2 avec 256 000 itérations).
Vous analysez une base SQLite. PRAGMA freelist_count renvoie 847. Que faire ?Récupération · Niveau : moyen
847 pages libres = 847 pages potentiellement contenant des données supprimées récupérables. Procédure : (1) NE JAMAIS exécuter VACUUM ou modifier la base (efface définitivement la freelist), (2) toujours travailler sur une copie hashée, (3) lancer un outil de carving SQLite spécialisé : undark -i base.db -o records.txt pour extraire tous les enregistrements y compris ceux marqués supprimés, OU sqlite_dissect de la CIA (plus robuste, gère mieux les formats complexes), OU le module SQLite d'Autopsy qui propose une vue « Deleted Records ». (4) Croiser les enregistrements récupérés avec ceux actuellement actifs pour identifier ce qui a été supprimé. Bonus : analyser aussi le fichier .db-wal qui contient les modifications les plus récentes (peut révéler des messages effacés juste avant la saisie).
Une base Chrome History contient last_visit_time = 13340285970000000. Quelle date ?Conversion epoch · Niveau : difficile
Chrome utilise l'epoch WebKit = microsecondes depuis 1601-01-01 UTC. Calcul : (13340285970000000 / 1000000) − 11644473600 = 1695812370 Unix timestamp = 2023-09-27 11:39:30 UTC. En SQL : SELECT datetime(13340285970000000/1000000-11644473600, 'unixepoch');. En Python : datetime.utcfromtimestamp(13340285970000000/1e6 - 11644473600). Outil pratique : DCode (Digital Detective). Pourquoi 1601 ? Microsoft a choisi cette date pour le FILETIME Windows car elle simplifie les calculs grégoriens (cycle calendaire de 400 ans). Ne pas confondre avec Firefox (Unix µs) ou iOS (Cocoa s. depuis 2001).
🎓 Exam Tip — SQLite Forensique

SQLite = base de données la plus déployée au monde · 1 fichier .db / .sqlite

Magic bytes : SQLite format 3\0 (16 octets en début de fichier)

Toujours copier : .db + .db-wal + .db-shm + .db-journal

Travailler en read-only : sqlite3 file:base.db?mode=ro

Pages supprimées = freelist · contenu PRÉSERVÉ · récupération via carving

JAMAIS exécuter VACUUM sur une base forensique (efface définitivement freelist)

Outils de carving : undark, sqlite_dissect, Autopsy, AXIOM

SQLCipher = chiffrement AES-256-CBC pour bases mobiles (Signal, parfois WhatsApp)

  • iOS : datetime(ts+978307200, 'unixepoch')

  • Firefox : datetime(ts/1000000, 'unixepoch')
