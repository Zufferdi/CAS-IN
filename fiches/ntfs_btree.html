🌳 NTFS · Index B+ Trees

NTFS — Arbres B+ ($I30, INDX records)

$INDEX_ROOT, $INDEX_ALLOCATION, $BITMAP, INDX records, fixup multisector, slack des nœuds — pourquoi un répertoire NTFS est un arbre B+ et pourquoi les fichiers supprimés survivent souvent dans les nœuds non réorganisés.

Prérequis :📖 NTFS (MFT, attributs)📖 Encodage / Endianness
Voir aussi :🔗 B-Trees HFS+🔗 B-Trees APFS🔗 MAC Times🔗 Timestamps FS
⚠️ Little Endian + Fixup multisector ! Toutes les valeurs multi-octets sont en Little Endian. Avant toute lecture brute d'un nœud INDX (ou d'une entrée MFT), il faut appliquer le fixup : les 2 derniers octets de chaque secteur de 512 octets ont été remplacés par 2 octets de l'Update Sequence Array. Sans fixup, la fin de chaque secteur paraîtra corrompue.
🔑 Pourquoi un B+ Tree pour les répertoires ?

📐 Le problème NTFS

Une partition NTFS moderne peut contenir des dizaines de millions d'entrées. Lister un dossier de 100 000 fichiers via une liste linéaire (FAT) imposerait O(n) à chaque accès. NTFS utilise un arbre B+ trié par nom (ordre de tri Unicode défini dans $UpCase).

  • Hauteur typique < 3–4 niveaux même pour des millions de fichiers
  • Recherche / insertion / suppression : O(log n)
  • Tri stable : énumération en ordre alphabétique gratuite

🌳 B+ Tree (vs B-Tree)

Microsoft documente "B-Tree" dans la spec NTFS, mais l'implémentation est en réalité un B+ Tree :

  • Toutes les données utiles sont dans les feuilles (entrées de fichiers complètes)
  • Les nœuds internes ne contiennent que des clés de routage + VCN du nœud enfant
  • Pas de chaînage horizontal entre feuilles (contrairement aux B+ classiques)
  • Variante propriétaire — plus simple à parser que les vrais B+ databases
📦 Trois attributs, un seul arbre
Un index NTFS combine 2 ou 3 attributs au sein d'une même entrée MFT. Pour un répertoire, le triplet est $INDEX_ROOT + $INDEX_ALLOCATION + $BITMAP, tous portant le nom de stream $I30.
AttributTypeRésident ?Rôle dans l'arbre
0x90 $INDEX_ROOT Toujours résident Petit répertoire entier, OU racine de l'arbre + premier niveau d'index. Tient dans l'entrée MFT (1 Ko).
0xA0 $INDEX_ALLOCATION Toujours non-résident Stocke les nœuds INDX (4 Ko chacun) en clusters séparés via Run List. N'apparaît que si le dossier dépasse $INDEX_ROOT.
0xB0 $BITMAP Souvent résident 1 bit par INDX block dans $INDEX_ALLOCATION : 1 = en usage, 0 = libre. Permet la réutilisation des nœuds.
💡 Le mystère du nom $I30 : tous les attributs d'index de répertoires portent ce nom de stream. Convention héritée du driver NTFS : $I = Index, 30 = type d'attribut indexé en hexadécimal, c'est-à-dire 0x30 = $FILE_NAME. L'index de répertoire est donc « l'index sur les attributs $FILE_NAME ».

🧱 Anatomie d'une entrée d'index (Index Entry)
Pour un répertoire, chaque entrée embarque une copie quasi-complète de l'attribut $FILE_NAME du fichier indexé. C'est ce qui rend les nœuds INDX si précieux en forensique : timestamps + nom + parent y sont stockés indépendamment de la MFT.

🧮 Comment parcourir un répertoire pas à pas

🎯 Algorithme de lecture (Sleuth Kit / X-Ways font ça pour vous)

  1. 1. Lire l'entrée MFT du dossier → trouver $INDEX_ROOT ($I30).
  2. 2. Si flag racine = 0x00 (feuille) : toutes les entrées sont là, pas de $INDEX_ALLOCATION. Petit dossier, fini.
  3. 3. Si flag racine = 0x01 : suivre le SubNodeVCN de chaque entrée d'index → lire le bloc INDX correspondant dans $INDEX_ALLOCATION.
  4. 4. Pour chaque INDX lu : appliquer le fixup, vérifier la signature, parser les entrées.
  5. 5. Récursion : si une entrée a flag 0x01, descendre encore.
  6. 6. Arrêt sur entrée flag 0x02 (end marker) — typiquement une entrée vide qui pointe vers le dernier sous-nœud.
⚠️ Fixup obligatoire avant parsing : pour un nœud de 4096 octets sur des secteurs de 512 octets, il y a 8 secteurs. Avant écriture, NTFS sauvegarde les 8 « derniers 2 octets » de chaque secteur dans l'Update Sequence Array, puis les remplace par la même valeur USN (Update Sequence Number). À la lecture : si les 8 valeurs ne sont pas toutes égales à l'USN attendu → écriture interrompue (crash) → nœud potentiellement incohérent.
🪦 Le trésor forensique : entrées tombstone
C'est la raison de comprendre les B+ trees NTFS : les entrées supprimées peuvent rester dans la zone slack des nœuds tant que ceux-ci ne sont pas réorganisés.

🔄 Que se passe-t-il à la suppression ?

  1. 1. L'entrée d'index est retirée du flux logique (TotalEntriesSize diminue).
  2. 2. L'entrée elle-même n'est pas effacée — elle se retrouve dans la zone slack du nœud.
  3. 3. Le bit dans $BITMAP du nœud reste à 1 (le nœud est toujours utilisé pour les autres entrées).
  4. 4. Tant que le nœud n'est pas compacté ni réorganisé par une réécriture, les bytes anciens persistent.

🔬 Ce qu'on récupère

  • Nom de fichier complet (UTF-16) — long et 8.3
  • Référence MFT (entry# + seq#) → cibler l'entrée MFT, même si réutilisée
  • Référence MFT du parent → reconstruction du chemin
  • 4 timestamps $FN (créé, modifié, MFT-modifié, accédé)
  • Tailles allouée et logique du fichier
  • Flags système / archive / compressé

Tout cela sans avoir touché à la Data Area.

💡 Comparaison avec les entrées MFT supprimées : une entrée MFT marquée libre (Flags 0x00) sera réutilisée tôt ou tard pour un nouveau fichier — elle peut donc disparaître. Une entrée d'index tombstone, elle, ne survit que jusqu'à la prochaine réécriture du nœud INDX qui la contient — souvent plus longtemps car les nœuds B+ peu sollicités sont rarement réorganisés. Croiser les deux sources est la clé.

🛠 Outils d'analyse

🆓 Open source / gratuit

  • INDXParse (Willi Ballenthin) — Python, scan disque entier pour INDX orphelins, extraction tombstones
  • MFTECmd (Eric Zimmerman) — extrait $I30 avec --ds (--dirEnum)
  • Sleuth Kit — fls avec option -r traverse les B+ trees, istat sur entrée MFT répertoire montre $INDEX_ROOT
  • analyzeMFT — parser MFT incluant attributs 0x90/0xA0
  • indxparse + bulk_extractor en chaîne : carving brut → reconstruction logique

  • X-Ways Forensics — onglet "FILE_NAME entries (slack)" exhibe automatiquement les tombstones
  • EnCase — EnScript "INDX Slack" pour extraction
  • Magnet AXIOM / FTK — parsing transparent, intégré aux artefacts Windows
  • WinHex — éditeur hex avec template "NTFS INDX record"
💻 Commandes essentielles
# MFTECmd — extraire toutes les entrées d'index ($I30 + slack)
MFTECmd.exe -f "C:\Image\$MFT" --csv "C:\Out" --csvf mft.csv --de 1234

# Sleuth Kit — lister un répertoire NTFS récursivement (suit les B+ trees)
fls -r -p -f ntfs image.dd

# INDXParse — carver tout le disque pour blocs INDX orphelins
python INDXParse.py -d image.dd -o tombstones.csv

# INDXParse — extraire un INDX record d'un offset connu
python INDXParse.py -t 4096 image.dd

# Identifier la signature INDX dans un dump hex
xxd image.dd | grep -i "494e 4458"     # INDX en LE

# icat — extraire l'attribut $INDEX_ROOT d'une entrée MFT
icat -f ntfs image.dd 1234-144-1     # 144 = 0x90 = $INDEX_ROOT
icat -f ntfs image.dd 1234-160-1     # 160 = 0xA0 = $INDEX_ALLOCATION

# Repérer le slack d'un nœud INDX (offset trouvé via parser)
dd if=image.dd bs=1 skip=$OFFSET count=4096 | xxd -s $TOTAL_ENTRIES_SIZE
🎯 Cas pratique — Détecter un fichier supprimé puis re-créé

🔎 Scénario forensique typique

L'utilisateur a supprimé contrat.docx hier, vidé la corbeille, puis créé aujourd'hui un nouveau fichier contrat.docx au même emplacement.

  1. 1. Dans le slack du nœud INDX du dossier parent : deux entrées contrat.docx existent — l'ancienne (tombstone) et la nouvelle (vivante).
  2. 2. Les MFT References diffèrent (entry# différent OU même entry# mais sequence# différent).
  3. 3. Les timestamps $FN.Created divergent → preuve qu'il s'agit de deux fichiers distincts.
  4. 4. Croiser avec $UsnJrnl:$J → confirmation des opérations DELETE puis CREATE.
  5. 5. Croiser avec $LogFile → fenêtre récente des écritures dans le nœud INDX.
💡 Détecter le timestomping via $I30 : l'entrée MFT a $SI (modifiable) et $FN (protégée). Mais l'entrée d'index dans le nœud INDX du parent embarque aussi une copie des timestamps $FN. Un attaquant qui modifie $SI et $FN dans la MFT laisse souvent la copie INDX intacte — divergence entre $FN.MFT et $FN.INDX = signature forte de timestomping. Outils : MFTECmd + comparaison $I30 vs $FN.
⚠ Pièges et nuances
  • Fixup non appliqué = les 2 derniers octets de chaque secteur 512 paraîtront identiques (la valeur USN). En lecture brute on voit donc des « blancs » réguliers tous les 512 octets — penser à restaurer.
  • Ordre de tri Unicode : NTFS trie selon $UpCase (table de mapping casse-insensible). Deux noms ne se comparent pas naïvement octet-à-octet.
  • NTFS 3.x sur Windows 10/11 : nœuds INDX souvent 4 Ko. Sur très anciens systèmes (NT 3.51, 4.0), les tailles pouvaient varier (2 Ko).
  • Réorganisation : chkdsk, défragmentation, opérations massives provoquent une réécriture des nœuds → effacement des tombstones. L'analyse doit être rapide.
  • Volume Shadow Copies (VSS) : chaque snapshot fige un état antérieur des nœuds INDX → multiplier les sources de tombstones. vshadowmount + parsing.
  • BitLocker : tant que le volume n'est pas déchiffré, $INDEX_ROOT et $INDEX_ALLOCATION sont chiffrés — analyse impossible sans la clé.
  • Compression / chiffrement EFS : le contenu fichier est touché, pas les nœuds INDX du dossier parent. Les noms restent en clair.
🎓 Exam Tip — NTFS B+ Trees
  • Les 3 attributs d'index : $INDEX_ROOT (0x90, résident) · $INDEX_ALLOCATION (0xA0, non-résident) · $BITMAP (0xB0)
  • Stream name pour les répertoires : $I30 (= index sur attribut $FILE_NAME 0x30)
  • Signature d'un nœud : 49 4E 44 58 = ASCII "INDX"
  • Taille typique : 4096 octets (4 Ko) sur Windows moderne
  • Fixup multisector : 2 derniers octets de chaque secteur 512 → USA en fin de nœud · à restaurer avant parsing
  • Endianness : Little Endian partout
  • Trésor forensique : slack dans la zone AllocatedEntriesSize − TotalEntriesSize = entrées tombstone
  • Chaque entrée d'index embarque : nom UTF-16, MFT ref + parent MFT ref, 4 timestamps $FN, tailles, flags
  • Détection timestomping : divergence $FN.MFT vs $FN.INDX (la copie d'index est rarement touchée par l'attaquant)
  • Hauteur de l'arbre : O(log n), typiquement < 4 niveaux même pour des millions de fichiers
Quelle est la signature ASCII d'un nœud d'index NTFS et où la trouve-t-on ?Identification INDX · Niveau : facile
Signature "INDX" en ASCII = 49 4E 44 58 en hex (Little Endian, mais ASCII donc même ordre).
Présente aux 4 premiers octets de chaque nœud dans $INDEX_ALLOCATION (0xA0). Recherchable au grep -P pour identifier des nœuds orphelins dans l'unallocated.
Pourquoi un fichier supprimé d'un répertoire NTFS peut-il être plus récupérable que via la MFT seule ?Slack INDX · Niveau : moyen
À la suppression, l'entrée MFT est marquée libre (Flags = 0x00) et l'entrée d'index est retirée du flux logique. Mais la copie d'index dans le nœud INDX du parent persiste dans la zone slack jusqu'à la prochaine réorganisation du nœud — qui peut prendre des semaines.
De plus, l'entrée MFT peut être réutilisée pour un nouveau fichier, écrasant ses données ; la copie INDX (nom + parent ref + timestamps $FN + tailles) reste intacte. Croiser MFT-libres + INDX-slack offre donc une fenêtre forensique plus large.
L'entrée MFT d'un fichier indique $SI.Created = 2020-01-01 et $FN.Created = 2020-01-01. Le nœud INDX du parent contient une entrée pour ce fichier avec Created = 2024-06-15. Quelle est l'interprétation ?Timestomping · Niveau : difficile
L'attaquant a très probablement modifié $SI ET $FN dans la MFT (technique classique : SetMACE, timestomp.exe avec privilèges) pour faire reculer artificiellement la création.
Mais la copie embarquée dans l'entrée d'index $I30 du dossier parent n'est mise à jour que sur opérations de directory (création, renommage, déplacement) — pas par les outils de timestomping classiques. Elle conserve donc la vraie date 2024-06-15.
Diagnostic : timestomping confirmé. Procédure : extraire l'entrée d'index complète (MFTECmd --de), comparer aux timestamps MFT, documenter la divergence dans le rapport.
