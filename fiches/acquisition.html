Acquisition & Préservation de la preuve

Image vs Clone · Formats E01 / AFF / DD · Write Blocker · Slicing FAT32 · RAM Dump · Ordre de volatilité

"L'acquisition forensique est l'acte le plus critique de toute investigation numérique. Une erreur ici — un disque branché sans write blocker, un hash non calculé — peut invalider des mois de travail d'analyse."
— ISO/IEC 27037 · Guidelines for identification, collection, acquisition and preservation of digital evidence
💡 Principe de Locard numérique : Tout contact laisse une trace. Tout accès à un disque sans write blocker risque de modifier les timestamps, créer des fichiers cachés ou écrire dans le swap. Ces modifications invalident la preuve (art. 141 CPP).

🔀 Image forensique vs Clone physique

Image forensique — Méthode standard

Copie de tout le contenu (secteurs, espaces vides, fichiers supprimés) dans un fichier conteneur sur un autre support. Inclut métadonnées, hash intégré, compression possible.

  • Ne peut pas démarrer — nécessite un outil forensique
  • Immuable : l'analyste travaille sur des copies
  • Formats : DD, E01, AFF, EWF2
  • Hash calculé avant/après = preuve d'intégrité

Clone — Copie physique exacte

Copie bit-à-bit sur un disque physique de même capacité (ou supérieure). Peut démarrer comme l'original.

  • Problème : les disques "1 To" de marques différentes n'ont pas exactement le même nombre de secteurs
  • Travailler sur un clone risque de l'altérer
  • Réservé aux cas où démarrer le système est nécessaire
  • Risque de contamination élevé si mal géré
⚠️
Recommandation : Toujours préférer l'image forensique au clone. Travailler uniquement sur des copies de l'image. Ne jamais ouvrir l'image originale en écriture.

🔒 Write Blocker — Outil n°1 de l'intervenant

Pourquoi matériel, pas logiciel ?

Dispositif matériel interposé entre le disque suspect et l'ordinateur. Laisse passer tous les ordres de lecture, bloque physiquement tout ordre d'écriture.

  • Le write blocker logiciel peut être contourné par l'OS (ex. Windows qui met à jour une date d'accès)
  • Le matériel agit au niveau du bus — incontournable
  • Marques courantes : Tableau (Guidance), WiebeTech, FRED

Sans write blocker — Risques

  • Mise à jour des dates d'accès (timestamps)
  • Création de fichiers cachés (thumbnails, index)
  • Mise à jour d'un index de recherche
  • Écriture dans le swap / fichier d'hibernation
  • Modification de la Recycle Bin
  • → Toutes ces modifications invalident la preuve (art. 141 CPP)

📊 Ordre de volatilité (RFC 3227)

Collecter en priorité les données qui disparaissent le plus vite :

1
Registres CPU et cache
Perdus dès que le processeur change de contexte. Très rarement capturables en pratique.
2
RAM (mémoire vive)
Perdue à l'extinction du système. Contient : clés de chiffrement, processus actifs, connexions réseau, mots de passe en clair.
WinPmem, DumpIt, Magnet RAM Capture, avml (Linux)
3
État réseau, connexions actives
Connexions TCP actives, table ARP, processus avec ports ouverts.
netstat -ano · ss -tulpn · arp -a
4
Processus et services en cours
Liste des processus, services démarrés, utilisateurs connectés.
tasklist / ps aux · sc query · who -a
5
Image disque
Contenu stable — peut attendre que les éléments volatils aient été capturés. Hash obligatoire avant/après.
FTK Imager · dd if=/dev/sda of=/mnt/evidence.img bs=4M · dcfldd
6
Logs distants, sauvegardes
Logs sur serveur distant, SIEM, sauvegardes cloud. Derniers à collecter car les plus stables.

Règle absolue : Toujours exécuter l'outil de capture RAM depuis une clé USB forensique — ne jamais écrire sur le disque suspect. Chaque écriture sur le disque = modification de la preuve.
# Capture RAM Windows
winpmem_mini_x64.exe C:\Forensics\ram.raw   # WinPmem
DumpIt.exe /O C:\Forensics\ram.raw           # DumpIt

# Analyse avec Volatility 3
python vol.py -f ram.raw windows.pslist      # Processus
python vol.py -f ram.raw windows.netscan     # Connexions
python vol.py -f ram.raw windows.cmdline     # Commandes lancées
python vol.py -f ram.raw windows.hashdump    # Hashes SAM

✂️ Slicing FAT32 — Limite des 4 Go

⚠️
Problème : FAT32 limite la taille d'un fichier à 4 Go − 1 byte. Une image disque dépasse souvent plusieurs centaines de Go. Si le support de destination est FAT32 → l'image doit être découpée en segments.

Solution : utiliser exFAT ou NTFS comme système de fichiers de destination → aucune limite de taille de fichier. Les logiciels forensiques (FTK Imager, dd) découpent automatiquement en segments si le format E01 / dd est utilisé avec un support FAT32.

  • E01 : segmenté automatiquement → preuve.E01, preuve.E02, preuve.E03…
  • Perdre un segment rend l'image complète inutilisable
  • Hash de chaque segment + hash global de l'image complète
