DNS Forensique

Logs DNS · Exfiltration · Beaconing · DGA · Tunneling · Passive DNS · Zeek · Windows DNS Server
Principe fondamental
"DNS is the most important protocol you'll ever overlook. Every attack leaves DNS breadcrumbs — if you know where to look."
— SANS SEC503, Network Forensics
🎯 Pourquoi le DNS est critique en forensique : Le DNS est souvent le seul protocole non filtré en sortie d'un réseau d'entreprise. Les pare-feux bloquent HTTP, HTTPS, FTP — mais laissent passer le DNS port 53. C'est pour cette raison que les attaquants l'utilisent massivement pour le C2, l'exfiltration de données, et la persistance. Et c'est souvent la source de preuves la plus négligée par les équipes défensives.

🌐 Le DNS — Architecture et flux forensiques
Chaque requête DNS suit un chemin : client → résolveur local → forwarder → résolveurs racine → NS autoritaire. Chaque étape peut laisser des logs. En forensique, la priorité est le résolveur local (voit toutes les requêtes internes) et les logs Windows DNS Server (si l'entreprise héberge son propre DNS). Les requêtes directes vers des résolveurs externes (8.8.8.8, 1.1.1.1) sans passer par le résolveur interne sont elles-mêmes un indicateur suspect — technique pour éviter la journalisation.

⚠️ DNS over HTTPS (DoH) et DNS over TLS (DoT) — angle mort majeur : depuis l'adoption de DoH par les navigateurs (Chrome, Firefox) et les OS (Windows 11), une partie croissante des requêtes DNS passe par le port 443 chiffré. Elle est invisible aux captures DNS classiques (port 53). Un attaquant utilisant DoH pour son C2 ne laissera aucune trace dans les logs DNS traditionnels — seule une analyse du trafic HTTPS vers des résolveurs DoH connus (1.1.1.1, 8.8.8.8, 9.9.9.9) permettra la détection.

🪟 Activer le DNS Debug Log Windows

  • DNS Manager → serveur → Propriétés → Debug Logging
  • Ou PowerShell : Set-DnsServerDiagnostics -All $true
  • Log dans %SystemRoot%\System32\dns\dns.log
  • Format : timestamp, client IP, query name, type, response
  • Attention : très verbeux — activer uniquement pour investigation ciblée

🚨 Indicateurs DNS suspects — triage rapide

  • Requêtes DNS directes vers 8.8.8.8 depuis des postes internes = bypass résolveur interne
  • Sous-domaines > 30 caractères = potentielle exfiltration
  • Type TXT/NULL/CNAME en quantité = tunneling
  • TTL < 30 secondes = infrastructure C2 dynamique
  • Requêtes NXDOMAIN en masse = DGA (Domain Generation Algorithm)
📤 Exfiltration DNS & Command-and-Control
Le DNS est le canal d'exfiltration et de C2 préféré des attaquants avancés car il est rarement bloqué ou monitoré. Deux techniques principales : l'exfiltration DNS (données encodées dans des sous-domaines) et le tunneling DNS (protocole complet encapsulé dans DNS pour bypasser les restrictions réseau). Les deux nécessitent que l'attaquant contrôle un serveur DNS autoritaire pour recevoir les requêtes.
Techniques — Cliquez pour les détails et IOCs
Technique 1
Exfiltration par sous-domaines
Données Base64 encodées dans les labels DNS. Simple et discret.
Technique 2
Tunneling DNS
Protocole complet (SSH, TCP) encapsulé dans DNS. iodine, dns2tcp.
Technique 3
C2 via DNS TXT/NULL
Instructions C2 dans les réponses TXT. CobaltStrike, Sliver.
Technique 4
Fast Flux
IP changeante à chaque résolution pour éviter le blocage.

# Détecter labels > 30 chars
cat dns.log | zeek-cut query |
  awk '{n=split($0,a,"."); if(length(a[1])>30) print}' |
  sort | uniq -c | sort -rn

# Requêtes TXT suspectes
cat dns.log | zeek-cut query qtype_name |
  grep "TXT" | sort | uniq -c | sort -rn

# Tous les domaines DNS uniques

  -e dns.qry.name \
  -Y "dns.flags.response==0" | sort -u

# Volume par domaine
tshark -r cap.pcap -T fields \
  -e dns.qry.name -Y "dns" |

🎲 DGA & Beaconing — Deux techniques de résilience C2
Les attaquants ont besoin que leur malware puisse toujours joindre le serveur C2, même si des domaines sont bloqués. Deux techniques : le DGA (Domain Generation Algorithm) génère des milliers de domaines pseudo-aléatoires, dont seuls quelques-uns sont enregistrés — le malware les essaie jusqu'à en trouver un actif. Le beaconing est la communication périodique régulière du malware avec son C2, visible dans les logs DNS sous forme d'un battement régulier.
DGA — Domain Generation Algorithm
🎲 Comment fonctionne un DGA
Le malware calcule des noms de domaine à partir d'une graine (seed) — souvent la date du jour. L'attaquant enregistre à l'avance 1-2 des milliers de domaines générés. Le malware essaie chaque domaine jusqu'à en trouver un actif.

Résultat forensique : des centaines de NXDOMAIN (domaine inexistant) suivis d'une connexion réussie = signature DGA très reconnaissable.
🔍 Détection DGA dans les logs
Indicateurs :
· Ratio NXDOMAIN > 50% pour un client
· Domaines à haute entropie (consonnes/voyelles inhabituelles)
· Même longueur de domaine en série
· Même TLD en série (.com, .net, .org alternant)

Outils : DGArchive (base de DGA connus) · dgaintel · scikit-learn (ML sur entropie)
# Exemples de domaines DGA réels (Conficker, Emotet)
tnhdlfspqv.com # NXDOMAIN
kwrxbmzgpa.net # NXDOMAIN
yvfmcqhtsj.org # NXDOMAIN
... # 300 essais...
abxkcmfght.com # → 185.x.x.x SUCCÈS = C2 actif

# Détecter dans Zeek — ratio NXDOMAIN par client
cat dns.log | zeek-cut id.orig_h rcode_name |
  awk '{count[$1"_"$2]++} END {for(k in count) print count[k], k}' |
  grep NXDOMAIN | sort -rn | head -20

# Calculer l'entropie d'un domaine (python)
python3 -c "import math; d='tnhdlfspqv'; e=-sum(d.count(c)/len(d)*math.log2(d.count(c)/len(d)) for c in set(d)); print(f'Entropie: {e:.2f}')"
DNS Beaconing — Détection des communications C2 périodiques
IndicateurTrafic DNS normalBeaconing C2
Intervalle Aléatoire selon l'utilisation Régulier : 30s, 60s, 5min, 15min — comme une horloge
Domaine cible Diversifié selon la navigation Unique ou très limité, souvent inconnu
Réponse IP IP stable (CDN, serveur fixe) IP changeante à chaque résolution (Fast Flux) ou NXDOMAIN alternant
TTL des réponses 300s–86400s selon le service TTL très bas (< 30s) — infrastructure éphémère
Heure d'activité Pendant les heures de bureau 24h/24 y compris nuit et week-end
Origine Plusieurs utilisateurs/processus Un seul processus ou une seule IP source
# Détecter beaconing — requêtes régulières vers même domaine
tshark -r capture.pcap -T fields -e frame.time_epoch -e dns.qry.name \
  -Y "dns.flags.response==0" |
  awk '{print $2, $1}' | sort | uniq -c

# Analyser les intervalles entre requêtes vers un domaine
cat dns.log | zeek-cut ts query | grep "evil.com" |
  awk 'prev{printf "%.0f\n", $1-prev} {prev=$1}' |
  sort | uniq -c | sort -rn

# Un pic à 60 secondes = beacon toutes les 60s
🎯 Jitter — Technique d'évasion anti-détection
Les beacons modernes (Cobalt Strike, Sliver) introduisent un jitter — une variation aléatoire de ±20-50% de l'intervalle — pour éviter la détection par des intervalles parfaitement réguliers. Un beacon configuré à 60s avec 30% de jitter sonnera entre 42s et 78s. La détection nécessite donc une analyse statistique (écart-type, distribution des intervalles) plutôt qu'une recherche d'intervalle fixe.

🔭 Passive DNS — Mémoire historique du système de noms
Le Passive DNS est une technique de collecte passive qui enregistre les réponses DNS observées sur le réseau mondial au fil du temps. Ces bases de données permettent de savoir quelle IP un domaine résolvait à une date précise, ou quels domaines ont pointé vers une IP donnée. C'est un outil d'investigation rétrospective indispensable — il permet de retracer l'infrastructure d'un attaquant même des années après l'incident.

🔍 Questions forensiques Passive DNS

  • Quand ce domaine a-t-il été enregistré ? (âge = signal de risque)
  • Vers quelle(s) IP ce domaine a-t-il résolu historiquement ?
  • Quels autres domaines partagent cette IP ? (infrastructure commune)
  • Ce domaine est-il classé malveillant sur VT, URLhaus, PhishTank ?
  • Le certificat TLS contient-il des anomalies (CN, organisation) ?

⚠️ Limites du Passive DNS

  • Ne couvre pas les requêtes DNS internes (réseau privé)
  • DoH/DoT → trafic chiffré invisible aux sondes Passive DNS
  • Domaines éphémères (quelques heures) peuvent ne pas être indexés
  • Résolutions sur IPv6 sous-représentées dans certaines bases
  • Données incomplètes selon la couverture géographique des sondes

🎓 Exam Tip — DNS Forensique

DNS = souvent seul protocole non filtré en sortie → vecteur privilégié exfiltration et C2

Exfiltration DNS = données Base64 dans sous-domaines · labels > 30 chars · types TXT/NULL/CNAME

DGA = centaines de NXDOMAIN suivis d'une connexion réussie · domaines à haute entropie

Beaconing = requêtes périodiques régulières · TTL très bas (< 30s) · actif 24h/24

Fast Flux = IP change à chaque résolution (TTL très bas) · résistance au blocage

Passive DNS = résolutions historiques · VirusTotal (gratuit) · DNSDB (payant, le plus complet)

Zeek dns.log = source principale · champs clés : ts, id.orig_h, query, qtype_name, answers, rcode_name

Sysmon EID 22 = DNSEvent → attribuer une requête DNS à un processus Windows précis

DoH/DoT = angle mort majeur → trafic DNS chiffré port 443 invisible aux logs DNS classiques
