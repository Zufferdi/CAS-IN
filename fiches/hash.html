# Qu'est-ce qu'un hash forensique ?
Un hash cryptographique est une empreinte numérique unique d'un fichier ou d'un disque : quelques octets qui identifient sans ambiguïté un contenu de plusieurs gigaoctets. Le même fichier donne toujours le même hash ; une différence d'un seul bit produit un hash radicalement différent (effet avalanche). C'est la pierre angulaire de l'authenticité d'une preuve numérique en Suisse (art. 192 CPP).
Algorithmes de hachage forensique
Les algorithmes diffèrent par leur longueur (résistance aux collisions) et leur statut (déprécié, standard, recommandé).

🇨🇭 Pratique suisse : X-Ways Forensics génère MD5 + SHA-1 + SHA-256 simultanément lors de l'acquisition. Le hash MD5 reste requis par certains tribunaux cantonaux pour la compatibilité avec les outils existants, mais ne doit jamais être utilisé seul comme preuve d'intégrité.
Rôle du hachage en forensique
✅ Authenticité de l'image

Le hash calculé juste après l'acquisition (hash A) doit être identique au hash recalculé avant analyse (hash B). A = B → l'image est intacte.

🔍 Identification de fichiers connus

Comparaison avec les bases NSRL (National Software Reference Library), HashKeeper, Project VIC. Permet de filtrer les fichiers système et identifier du contenu illicite connu.

🔗 Chaîne de possession

Chaque transfert de preuve doit être accompagné du hash. Si le hash change → altération détectée. Documenté dans le rapport d'acquisition.

⚠️ Limitations MD5 / SHA-1

MD5 : collisions connues depuis 2004 (Wang et al.). SHA-1 : collision pratique démontrée par Google (SHAttered, 2017). Ne pas utiliser seuls pour la recevabilité.

SSDEEP — Hachage par similarité (fuzzy hashing)
Contrairement à MD5/SHA qui donnent un hash radicalement différent au moindre bit modifié, SSDEEP varie graduellement avec le contenu.
Principe du fuzzy hashing

Deux fichiers similaires à 80 % auront des hashes SSDEEP similaires — impossible avec les hashes classiques. Utile pour détecter des variantes de malware, copies modifiées de documents, ou corréler des artefacts similaires.

🎯 Cas d'usage SSDEEP
  • Détecter des variantes d'un malware (même code, emballage différent)
  • Retrouver des copies modifiées d'un document
  • Corréler des artefacts similaires sur plusieurs systèmes
  • Outils : ssdeep CLI, X-Ways (fuzzy hash), Autopsy
📊 Score de similarité

Score 0–100 %. 0 = aucune similarité · 100 = identique.

Seuil pratique : ≥ 70 % → probable variante.
Attention aux faux positifs sur les petits fichiers (entropie faible).

Un disque est acquis avec MD5 seul. Lors du procès, la défense pointe les collisions MD5. La preuve est-elle invalidée ?Droit & hash · Niveau : moyen
En pratique : risque réel d'irrecevabilité. Les collisions MD5 sont démontrées depuis 2004 (Wang et al.) et SHA-1 depuis 2017 (Google SHAttered). Même si le MD5 de l'image reste inchangé, la défense peut argumenter qu'une collision est théoriquement possible. La pratique forensique recommande systématiquement MD5 + SHA-256 simultanément — MD5 pour la rétro-compatibilité des outils, SHA-256 pour la robustesse cryptographique. ISO/IEC 27037 exige la documentation de l'intégrité, ce qui sous-entend un algorithme non compromis.
Deux fichiers ont un SSDEEP de similarité 82 %. Que conclure ?Fuzzy hashing · Niveau : facile
Très probable variante (même famille de contenu). Au-dessus du seuil pratique de 70 %, les deux fichiers partagent la majorité de leur structure — cas typique : deux versions du même malware emballées différemment, deux copies modifiées du même document, ou deux exports CSV avec des modifications mineures. Vérifier néanmoins les faux positifs possibles sur des fichiers courts (entropie faible) ou des fichiers texte très répétitifs.
🎓 Exam Tip — Hash & Intégrité

Algorithmes : MD5 (128 bits, déprécié) · SHA-1 (160 bits, à éviter) · SHA-256 (standard) · SHA-512 (recommandé)

Collisions connues : MD5 (Wang 2004) · SHA-1 (Google SHAttered 2017) — ne jamais utiliser seul

SSDEEP : fuzzy hashing · score 0–100 % · seuil pratique ≥ 70 % = variante

Entropie de Shannon : 0 = prévisible · 1 = aléatoire · ≥ 0.95 sans magic bytes = probable chiffrement

Effet avalanche : 1 bit modifié → hash radicalement différent (≈ 50 % des bits changent)

Chaîne de custody : hash avant ET après chaque transfert · doit rester inchangé

Bases d'identification : NSRL · HashKeeper · Project VIC · NIST RDS

Cadre légal : ISO/IEC 27037 §8.3 · Art. 192 CPP (authenticité) · TF 1B_602/2020
