Windows Forensique — Guide opérationnel

Méthodologie 16 principes Artefacts & corrélation Valeur judiciaire

L'analyste Windows n'est pas un simple technicien — c'est un interprète de la mémoire du système. La majorité des enquêtes numériques impliquent Windows. Chaque interaction y laisse des traces persistantes, souvent invisibles pour l'utilisateur mais exploitables par l'analyste. La difficulté n'est pas de trouver des données, mais de les corréler en une chronologie défendable.

🪟 Windows Forensique — Reconstruire le comportement, pas chercher des fichiers
Windows est l'OS le plus analysé en forensique numérique : plus de 70% des postes professionnels et > 80% des systèmes attaqués. Sa complexité interne en fait un environnement riche en artefacts — Microsoft documente publiquement très peu d'entre eux, mais les chercheurs DFIR ont depuis 20 ans cartographié des centaines de sources qui enregistrent silencieusement l'activité utilisateur. Principe fondateur de SANS FOR500 : « Windows Forensics is not about finding files, it's about reconstructing behaviour. » L'OS enregistre passivement et automatiquement tout : (1) Les programmes lancés (Prefetch, Amcache, ShimCache, BAM, UserAssist, Jump Lists, Recent), (2) Les dossiers visités (ShellBags, MRU), (3) Les fichiers ouverts (LNK, RecentDocs, OpenSavePidlMRU), (4) Les USB branchées (USBSTOR, MountPoints2, setupapi), (5) Les connexions réseau (NetworkList, Event Logs), (6) Les authentifications (Security.evtx, Kerberos), (7) La persistance malware (Run keys, Services, Tasks, WMI). Chaque source a sa spécificité et ses limites — un bon analyste forensique croise toujours 3-5 sources pour valider une conclusion. Avec un identifiant utilisateur (SID) en colonne vertébrale (chaque utilisateur Windows a un SID unique global), l'analyste peut attribuer chaque action à un acteur précis. Le défi n'est plus la rareté des données, mais leur volume : un poste Windows actif génère des millions d'événements — d'où l'importance des outils de timeline (Plaso/log2timeline, EZ Tools, Hayabusa, Chainsaw) qui agrègent et corrèlent automatiquement.

⚖️ Les 4 exigences non-négociables
  • Copie forensique — jamais sur l'original

  • Reproductibilité — un autre expert doit pouvoir refaire

🎯 Principe cardinal : un artefact Windows isolé n'est jamais une preuve. La preuve naît de la corrélation.
② Nature de la preuve Windows

L'analyste doit raisonner en système, pas en élément isolé.

🌐 Diffuse

Répartie entre fichiers, registre, journaux, caches, espace non alloué, slack space.

♾️ Persistante

Certaines traces survivent aux suppressions — miniatures, entrées MFT, Shellbags.

🤖 Involontaire

Générée sans action consciente de l'utilisateur — le système enregistre par design.

🔀 Parfois contradictoire

Plusieurs artefacts peuvent diverger — c'est souvent un indice de manipulation.

④ Le Registre Windows — pilier de l'analyse

La mémoire interne du système.

🗝 Ce que contient le registre
  • Les profils utilisateurs (SID, comptes, mots de passe hashés)
  • Les programmes exécutés (UserAssist, MUICache)
  • Les périphériques connectés (USBSTOR)
  • Les préférences (ShellBags, MRU)
  • Des traces indirectes d'activité partout

Le registre est organisé en ruches (hives), stockées sous forme de fichiers physiques sur le disque.

👉 Ces fichiers existent physiquement et peuvent être analysés hors ligne (pas besoin de système vivant).

⑤ SID — Identifier l'utilisateur
🆔 Security Identifier

Windows n'identifie jamais un utilisateur par son nom, mais par un SID (Security Identifier) :

S-1-5-21-1234567890-987654321-111111111-1001
          └─────── machine / domaine ────────┘ └ RID
RID 500 = Administrator · 501 = Guest · 1001+ = utilisateurs
(le RID 1000 n'est jamais attribué par Windows — commence à 1001)

Le SID permet :

  • d'attribuer une action à un utilisateur précis
  • de relier fichiers, registre et corbeille entre eux
  • de résister aux changements de nom ou à la suppression de compte

Un analyste forensique travaille toujours avec les SID, jamais uniquement avec les noms affichés.

⑥ Prouver l'exécution d'un programme
🚨 La présence d'un programme sur le disque ne prouve PAS son utilisation. Il faut des artefacts d'exécution.
⚡ Prefetch

Prouve qu'un programme a été lancé. Donne une fréquence approximative (jusqu'à 8 timestamps) et les DLL chargées. Emplacement : C:\Windows\Prefetch\.

Outil : PECmd

👤 UserAssist

Clé registre NTUSER.DAT qui enregistre les programmes lancés depuis l'interface graphique (double-clic, menu Démarrer). Prouve l'usage par l'utilisateur, pas par le système.

⚠️ Les noms de programmes sont encodés en ROT13 — ne jamais oublier de décoder (CyberChef → recette ROT13, ou RegRipper le fait automatiquement).

Chemin : NTUSER.DAT\Software\Microsoft\Windows\CurrentVersion\Explorer\UserAssist

🧬 Amcache / ShimCache

Traces d'exécution et d'installation. Amcache.hve stocke le SHA-1 de chaque exécutable connu. ShimCache enregistre les programmes lancés pour compatibilité.

Outil : AmcacheParser

🎯 Utilité combinée

Ces artefacts sont centraux dans les enquêtes malware et intrusion. Un échantillon malveillant laisse des traces croisées : Prefetch → UserAssist → Amcache → $MFT = preuve robuste.

⏱ BAM / DAM — l'artefact Windows 10+ sous-estimé

Background Activity Moderator (et son pendant Desktop) est une fonction Windows qui régule les apps en arrière-plan. Bonus forensique : il garde des timestamps d'exécution précis par utilisateur (SID) — particulièrement utile quand Prefetch est désactivé.

SYSTEM\CurrentControlSet\Services\bam\State\UserSettings\<SID>\
SYSTEM\CurrentControlSet\Services\dam\State\UserSettings\<SID>\

Parseable par RECmd (Zimmerman) avec les packages de batch dédiés.

📆 Windows Timeline / Activities (Windows 10 1803–11)

Base SQLite ActivitiesCache.db située dans %LocalAppData%\ConnectedDevicesPlatform\<L.USER>\. Garde trace de toutes les activités (apps, documents, URLs) sur 7 à 30 jours.

Parseable directement en SQLite — voir fiche SQLite Forensique.

⑦ Fichiers consultés & documents manipulés

Windows conserve des traces d'accès, même après suppression.

🔗 Fichiers raccourcis (.lnk)

Créés automatiquement à l'ouverture d'un fichier. Contiennent le chemin cible complet, le numéro de série du volume source (clé USB), les MAC times. Localisation principale : %AppData%\Microsoft\Windows\Recent\.

📝 Listes MRU

Most Recently Used — clés registre qui mémorisent les derniers fichiers/dossiers utilisés par chaque application (Office, Paint, Notepad, éditeur d'URL…).

📌 Jump Lists

Listes de fichiers récents par application, visibles en clic droit sur la barre des tâches. Persistent au redémarrage. Chemin : %AppData%\Microsoft\Windows\Recent\AutomaticDestinations\.

🎯 Ensemble, ces artefacts démontrent : ① l'ouverture d'un fichier · ② son emplacement d'origine · ③ un contexte d'usage (application, date, répétitions).
⑧ La Corbeille Windows
♻️ Bien plus qu'un confort utilisateur

La corbeille Windows permet de déterminer :

  • qu'un fichier a existé
  • qu'il a été supprimé
  • par quel utilisateur (via le SID du sous-dossier)
  • à quel moment

Sur les versions modernes, chaque utilisateur a sa propre corbeille identifiée par son SID :

C:\$Recycle.Bin\S-1-5-21-...-1001\
  ├── $Ixxxxxx.ext  ← métadonnées (chemin original, taille, date)
  └── $Rxxxxxx.ext  ← contenu du fichier
⑨ Supports amovibles & périphériques USB
🔌 Ce que Windows retient

Windows conserve des traces détaillées des périphériques connectés : clés USB, disques externes, téléphones, cartes mémoire. Emplacements clés :

  • SYSTEM\CurrentControlSet\Enum\USBSTOR — numéro de série, VID/PID
  • SYSTEM\CurrentControlSet\Enum\USB — énumération USB générale
  • SYSTEM\MountedDevices — lettre de lecteur assignée (à croiser avec USBSTOR)
  • C:\Windows\INF\setupapi.dev.log (Vista+) · C:\Windows\setupapi.log (XP) — première connexion, datée
  • SOFTWARE\Microsoft\Windows Portable Devices\Devices — label du volume
🎯 Ces artefacts permettent de : prouver l'utilisation d'un support externe · établir des liens entre machines (même numéro de série sur plusieurs PC) · renforcer une chronologie d'exfiltration ou d'importation de données.
⑩ Images, vidéos & caches visuels
🖼 Thumbcache — la miniature qui survit

Même après suppression du fichier, la miniature peut subsister :

  • thumbcache_*.db (Windows Vista+) — localisation : %LocalAppData%\Microsoft\Windows\Explorer\
  • thumbs.db (Windows XP & certaines versions) — caché dans chaque dossier visualisé

Une image supprimée peut rester visible sous forme de miniature, parfois exploitable judiciairement (qualité réduite mais reconnaissable).

⑪ Journaux Windows (.evtx)
📋 Ce que les .evtx enregistrent
  • Connexions (Security.evtx — Event ID 4624/4625)
  • Démarrages & arrêts (System.evtx — 6005/6006/1074)
  • Erreurs système
  • Activités de services (7045 = installation de service)
  • Événements de sécurité (création de compte, changement de privilège)

Localisation : C:\Windows\System32\winevt\Logs\. Permettent de reconstruire une chronologie événementielle précise.

Outil dédié : EvtxECmd · voir aussi Logs Windows.

⑬ Timezone & temps UTC — vérifier AVANT toute timeline

C'est la première chose qu'un magistrat vérifie sur une chronologie.

🚨 Windows stocke les timestamps en UTC dans NTFS, mais les AFFICHE en heure locale. Chaque timestamp dans ton rapport doit être qualifié (UTC ou local+offset). Un décalage horaire non identifié peut invalider toute une chronologie.
🕰 Où trouver le fuseau horaire du système
SYSTEM\CurrentControlSet\Control\TimeZoneInformation

  TimeZoneKeyName   : "Romance Standard Time"
  Bias              : -60           // offset en minutes par rapport à UTC
  DaylightBias      : -60           // décalage heure d'été
  StandardBias      : 0

Procédure :

  1. Extraire le TimeZoneKeyName depuis SYSTEM
  2. Noter dans le rapport : « Système configuré en UTC+2 (Romance Standard Time) »
  3. Tous les timestamps présentés : soit en UTC explicitement, soit heure locale + offset
  4. Attention aux BIOS/UEFI qui peuvent stocker l'heure en local ≠ NTFS UTC
💡 Outils concernés : Timeline Explorer affiche en local par défaut — forcer l'UTC dans les exports CSV. X-Ways laisse choisir. Autopsy utilise UTC par défaut mais permet l'override.
⑭ ShellBags — navigation utilisateur
📁 Ce que prouvent les ShellBags
  • quels dossiers ont été ouverts via l'explorateur Windows
  • même si ces dossiers n'existent plus
  • même sur des clés USB débranchées

Ils permettent une reconstruction comportementale de l'utilisateur, particulièrement utile en audience pour réfuter l'argument « je ne savais pas que ce dossier existait ».

👉 Fiche dédiée : ShellBags

⑮ Méthodologie recommandée
1
Identifier les artefacts pertinents. Quelle hypothèse d'enquête ? Quels artefacts y répondent ?
2
Extraire sans modifier. Toujours sur copie forensique · write-blocker · hash MD5/SHA-256 avant/après.
3
Corréler entre sources. Registre + .evtx + $MFT + Prefetch = faisceau d'indices concordants.
4
Construire une chronologie. Timeline Explorer · log2timeline · Plaso · Timesketch.
5
Vérifier les incohérences. Timestomping sur $SI ? Journal effacé (Event 1102) ? Prefetch manquant ?
6
Documenter chaque étape. Commandes exactes · hashs · versions d'outils · captures d'écran.
⑯ Ce que la justice attend de l'analyste
⚖️ Les 4 questions du magistrat
  1. D'où vient l'information ? — source, emplacement, ruche, fichier
  2. Comment a-t-elle été obtenue ? — outil, commande, date
  3. Pourquoi est-elle fiable ? — hash, reproductibilité, doc technique
  4. Comment s'insère-t-elle dans le dossier ? — corrélation, chronologie
🚨 Règle d'or : si l'analyse ne peut pas être expliquée simplement, elle est juridiquement fragile. Le détail technique est un outil, pas une fin.
⑰ Conclusion opérationnelle

L'analyste forensique Windows n'est pas un simple technicien. Il est un interprète de la mémoire du système. Son rôle : préserver la preuve · reconstruire les faits · présenter une vérité technique claire, cohérente et défendable.

La forensique Windows ne révèle pas des fichiers. Elle révèle des comportements.

🧠 Testez-vous
Vous trouvez Prefetch + Amcache + UserAssist + ShimCache mentionnant le même malware. Tous diffèrent dans les dates. Que faire ?Cross-référence · Niveau : moyen
Chaque source enregistre un aspect différent de la vie du fichier — il est normal qu'elles diffèrent. Comprendre chacune : (1) Prefetch = jusqu'à 8 dernières exécutions effectives + compteur. Date la plus précise pour « quand le programme a effectivement tourné ». (2) Amcache = SHA-1 du fichier + chemin + dernière exécution + date d'installation. Idéal pour identification et présence. (3) UserAssist = uniquement si lancé via GUI (double-clic, menu Démarrer) — pas par script ou cmd. Encodé ROT13. (4) ShimCache (AppCompatCache) = preuve de présence sur le système, pas forcément exécution. Mis à jour au shutdown. Réconcilier les dates : (a) Si Prefetch montre une exécution mais UserAssist non → exécuté via cmd/script, pas via GUI (suspect ou normal selon contexte). (b) Si ShimCache montre la présence mais pas Prefetch → fichier présent mais jamais exécuté (ou Prefetch désactivé sur serveur, ou nettoyé). (c) Amcache antérieur à Prefetch → installation puis première exécution. (d) Différentes versions du fichier → comparer SHA-1 d'Amcache. Best practice timeline : utiliser Plaso/log2timeline pour fusionner toutes les sources dans une timeline unique, puis filtrer sur le fichier suspect. Ne jamais conclure sur une seule source — la cross-référence renforce l'admissibilité juridique.
L'OS Windows utilise des SID. Pourquoi est-ce critique en forensique et quelle est la structure ?Identification · Niveau : moyen
Le SID (Security Identifier) est l'identifiant unique global de chaque utilisateur, groupe ou compte service Windows. Critique parce que Windows référence partout le SID, pas le nom utilisateur. Renommer un compte ne change pas le SID. Structure : S-1-<Authority>-<SubAuthority1>-...-<RID>. Exemple : S-1-5-21-1234567890-987654321-1122334455-1001. Décomposition : S = Security identifier, 1 = revision, 5 = NT Authority, 21 = identifier authority, suivi de 3 nombres = identifiant unique de la machine ou du domaine, et terminé par le RID (Relative Identifier) qui identifie le compte spécifique. RID importants à connaître : 500 = Administrator local (toujours), 501 = Guest, 1000-1001+ = utilisateurs créés (le 1er user créé après installation = 1001, jamais 1000 — Microsoft saute 1000), 512 = Domain Admins, 513 = Domain Users, 519 = Enterprise Admins. Application forensique : (a) $Recycle.Bin\<SID>\ identifie qui a supprimé le fichier — chaque user a son sous-dossier dans la corbeille avec son SID. (b) NTUSER.DAT du profil utilisateur référencé par SID. (c) BAM/DAM = activité par SID. (d) Event Logs stockent le SID du compte concerné. Récupérer le mapping SID → nom : examiner SOFTWARE\Microsoft\Windows NT\CurrentVersion\ProfileList → liste tous les SID avec ProfileImagePath (chemin profil utilisateur, contient le nom). Outils : wmic useraccount get name,sid en live, ou RegRipper plugin profilelist. NB : un SID supprimé peut subsister dans certains artefacts (orphan SID) — utile pour reconstruire des comptes effacés.
Le suspect a fait un cipher /w: sur le disque. Que pouvez-vous encore récupérer ?Anti-forensique · Niveau : difficile
cipher /w:<volume> est l'outil natif Windows qui écrit des zéros + uns + données aléatoires sur l'espace libre (3 passes), rendant les fichiers supprimés non récupérables. Mais ce n'est pas une perte totale — beaucoup d'artefacts persistent car ils sont dans des fichiers actifs du système, pas dans l'espace libre. Restent intacts : (1) Tout le registre Windows — SAM, SYSTEM, SOFTWARE, NTUSER.DAT — donc USBSTOR, ShellBags, UserAssist, MRU, Run keys, etc. (2) Event Logs EVTX — Security, System, Application + canaux Sysmon/PowerShell. (3) Prefetch files (.pf) dans C:\Windows\Prefetch\. (4) Amcache.hve + ShimCache. (5) Fichiers .lnk dans Recent. (6) Jump Lists. (7) Thumbcache — miniatures persistent. (8) $LogFile, $UsnJrnl NTFS — historique des opérations fichier. (9) Volume Shadow Copies — snapshots automatiques. (10) Hibernation file hiberfil.sys — peut contenir l'état RAM lors de la dernière mise en veille. (11) Pagefile.sys — peut contenir des fragments de fichiers déjà overwritten. (12) RAM si machine encore allumée. Indicateurs anti-forensiques à documenter : (a) Prefetch de cipher.exe — preuve d'usage de l'outil, (b) Event 4688 avec ligne de commande cipher /w:, (c) Timeline : si grand vide d'activité fichier puis reprise → probable wipe entre les deux. Conclusion juridique : l'usage de cipher /w: peut être interprété comme destruction intentionnelle de preuves (art. 305 CP suisse, entrave à l'action pénale). Documenter méticuleusement.
🎓 Exam Tip — Windows Forensique (Guide opérationnel)

Principe : reconstituer le comportement, pas chercher des fichiers

Source d'attribution unique : SID (S-1-5-21-...-RID)

  • RID 500 = Admin · RID 1001+ = users (jamais 1000) · RID 512 = Domain Admins

━━ ① PREUVES D'EXÉCUTION ━━

• Prefetch (.pf) → 8 dernières exécutions + compteur (désactivé sur serveurs)

• Amcache.hve → SHA-1 + chemin + dates installation/exécution

• ShimCache (AppCompatCache) → présence (pas forcément exécution)

• UserAssist → GUI uniquement, encodé ROT13

• BAM/DAM → Windows 10+ par SID, timestamps précis

• Sysmon EID 1 / Security EID 4688 → process creation

━━ ② NAVIGATION GUI ━━

• ShellBags → dossiers visités via Explorer (USRCLASS.DAT + NTUSER.DAT)

• MRU par appli · TypedURLs · RecentApps

• ActivitiesCache.db → Windows Timeline 7–30 jours (Win10 1803+)

━━ ③ FICHIERS CONSULTÉS ━━

• .lnk Recent (avec Volume S/N de l'origine)

• Jump Lists par application

• Thumbcache → miniatures persistent même après suppression du fichier

• RecentDocs par extension

• $Recycle.Bin\<SID>\ → $I (métadonnées) + $R (contenu) · $I survit au vidage

━━ ④ USB / RÉSEAU ━━

• USBSTOR (SYSTEM) + setupapi.dev.log + MountPoints2 (NTUSER)

• NetworkList → SSIDs · 1re/dernière connexion

• Event 4624 type 3 (réseau) / 10 (RDP)

━━ ⑤ PERSISTANCE MALWARE (8 zones) ━━

1. Run / RunOnce (HKLM + HKCU)

2. Services (EID 7045 / 4697)

3. Scheduled Tasks (XML dans System32\Tasks\)

4. Startup Folder

5. AppInit_DLLs (DLL injection user32)

6. IFEO Hijacking (clé Debugger)

7. WMI Subscriptions (fileless)

8. Drivers (services kernel)
