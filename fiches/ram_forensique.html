Ordre de volatilité — RFC 3227
RFC 3227 — Ordre de volatilité obligatoire

Règle fondamentale : collecter du plus volatile au moins volatile. Ne jamais inverser cet ordre sous peine de détruire des preuves irremplaçables.

  • Registres CPU → Cache L1/L2 → RAM → État réseau → Processus → Disque → Sauvegardes
  • La RAM est perdue à l'extinction en quelques secondes
  • Un malware fileless n'existe que en RAM — invisible sur disque

Tableau de référence complet :

Outils d'acquisition RAM
WinPmem Windows
winpmem.exe memdump.raw
Outil open-source d'Rekall. Produit un dump brut (.raw) ou un AFF4. Fonctionne depuis Windows XP jusqu'à Windows 11. Recommandé par SANS.
DumpIt Windows
DumpIt.exe /output memdump.raw
Un seul exécutable, interface minimale. Écrit le dump dans le répertoire courant. Très utilisé en intervention d'urgence.
LiME Linux — kernel module
insmod lime.ko "path=/mnt/usb/mem.lime format=lime"
Linux Memory Extractor. Chargé comme module kernel. Format LiME ou raw. Peut exporter via réseau (path=tcp:4444). Indispensable sur Linux/Android.
osxpmem macOS
sudo osxpmem memdump.aff4
macOS impose des restrictions kernel. SIP doit être désactivé ou l'outil signé. Alternativement : Cellebrite UFED pour Mac saisi verrouillé.
Magnet RAM Capture Windows · Gratuit
MRC.exe
Interface graphique simple. Capture la RAM physique et le fichier de page. Format brut + compression optionnelle. Très utilisé par les forces de l'ordre.
Belkasoft RAM Capturer Windows
RamCapture64.exe
Capture même sur systèmes protégés (ELAM/Early Launch). Format .mem. Intégration directe avec Belkasoft Evidence Center.
Ce que la RAM contient — Artefacts clés
🔑 Clés de chiffrement

Clés BitLocker VMK (Volume Master Key), clés TrueCrypt/VeraCrypt, clés de session TLS, clés PGP — toutes présentes en RAM tant que la session est active.

🦠 Malwares fileless

Malwares qui ne s'écrivent jamais sur disque (PowerShell Empire, Cobalt Strike). Invisibles à l'analyse disque — RAM uniquement.

🌐 Connexions réseau

Toutes les connexions TCP/UDP actives avec IPs, ports et processus associés — même après que l'attaquant a fermé sa session.

👤 Sessions & credentials

Hashes NTLM, tickets Kerberos, mots de passe en clair (XP/Vista), tokens d'accès, secrets LSA — extractibles avec Mimikatz.

📋 Processus & DLLs

Processus masqués par rootkits (détection par comparaison PsList vs PsScan), DLLs injectées, handles ouverts.

📄 Données en transit

Contenu des pages web HTTPS, pièces jointes email avant chiffrement, texte de documents Word ouverts.

Edge cases d'acquisition
🖥️ Machines virtuelles — VMware/Hyper-V

Si la machine cible est une VM, privilégier le snapshot mémoire de l'hyperviseur plutôt qu'un agent in-guest :

  • VMware : .vmem (image RAM) + .vmsn (snapshot). Convertir avec vol.py -f machine.vmem.
  • Hyper-V : .bin + .vsv (savedstate). vol2bin pour convertir.
  • VirtualBox : .sav. Plus rare en pratique, conversion plus délicate.

Avantage : aucun outil installé sur la VM — pas d'altération de la chaîne de preuve.

🔒 Windows 11 — Secured-core PC / VBS

Windows 11 24H2+ avec Virtualization-Based Security (VBS) active isole certaines pages mémoire (Credential Guard, HVCI). Conséquence pour l'acquisition :

  • Pages protégées renvoient des zéros à la lecture standard.
  • WinPmem > 4.0 supporte un mode --vbs-bypass (signed driver requis).
  • LSA Isolation + Credential Guard : les hashes NTLM ne sont plus extractibles en RAM standard. Mimikatz inutile.

Workaround : si compte admin disponible, désactiver VBS via DG_Readiness avant capture (modifie l'état système — documenter).

⚙️ Acquisition à froid — Cold Boot Attack

Si la machine est éteinte mais a été récemment alimentée (< 30 sec), la RAM contient encore des résidus exploitables (Halderman et al. 2008) :

  • Spray de bombe de gaz refroidissant (-50°C) → préserve la RAM 5-10 min après extinction.
  • Boot sur USB minimal (msramdump, scraper.iso) → dump RAM avant zéroïsation BIOS.
  • Outils : volatility peut analyser un dump partiellement dégradé.

Limites : technique destructive sur le matériel. Réservé aux saisies critiques avec autorisation préalable.

🛡️ DMA via FireWire / Thunderbolt / PCILeech

Acquisition sans aucun logiciel sur la cible via accès DMA direct :

  • Inception (FireWire 1394) : encore valable sur machines anciennes Win XP/7.
  • PCILeech + boîtier ScreamerM2 / FPGA : Thunderbolt 3, expansion PCIe externe.
  • Bypass complet de l'OS : peut contourner BitLocker actif (clé en RAM).

Modernes (Windows 10+) : Kernel DMA Protection bloque par défaut. Détection : pop-up "New PCI device detected" si DMA en marche.

📱 Mobile — Android / iOS

RAM de smartphone : pratiquement inaccessible sans root/jailbreak. Solutions partielles :

  • Android rooté : LiME compilable comme module (rare).
  • iOS : checkm8 exploit (devices A11 et antérieurs) → mode DFU → acquisition RAM partielle.
  • Cellebrite UFED Premium ou GrayKey : commercial, support large mais cher (50k+ CHF).

Voir : iOS Forensique · Android Forensique.

🐧 Linux — choisir le mode kernel

Sur Linux, plusieurs approches selon le contexte :

  • LiME : module kernel, insmod lime.ko — option par défaut SANS.
  • AVML (Microsoft) : binaire userland, format LiME compatible. Plus simple à déployer.
  • /dev/mem ou /proc/kcore : seulement noyaux anciens, restrictif sur kernels récents (CONFIG_STRICT_DEVMEM).
  • fmem : module alternatif à LiME, version plus récente sur certaines distros.

Compatibilité kernel : LiME doit être compilé pour la version exacte du kernel cible. Vérifier uname -r avant.

Edge cases modernes — sécurité matérielle 2024-2026

Les évolutions de la sécurité plateforme depuis 2020 changent profondément l'acquisition RAM. Cinq mécanismes à connaître :

🔐 Secure Boot + Measured Boot

UEFI Secure Boot empêche le chargement de drivers non signés. Conséquence : winpmem et LiME non signés ne se chargent pas par défaut.

  • Solutions : utiliser une version signée Microsoft de l'outil (Magnet RAM Capture l'est).
  • Désactiver Secure Boot temporairement change la mesure TPM et invalide BitLocker auto-unlock — risque de perdre l'accès au disque si on ne sait pas la clé de récupération.
  • Alternative : driver signé WinPmem v4.x avec certificat Velociraptor.
🎲 KASLR — Kernel Address Space Layout Randomization

Le kernel est relogé aléatoirement à chaque boot (Windows 10+, Linux 4.12+, macOS).

  • L'analyse n'est pas bloquée — Volatility 3 trouve les structures via les signatures debug (PDB pour Windows, System.map pour Linux).
  • Symbolisation requise : sans accès au PDB Microsoft (ou cache local), Volatility ne peut pas parser le dump.
  • Dans un environnement isolé, vol.py windows.symbolserver --offline nécessite une banque locale.
🏰 VBS / Credential Guard / HVCI

Virtualization-Based Security (Windows 10/11) isole le LSASS dans une VM Hyper-V. Conséquences :

  • Hashes NTLM ne sont plus en RAM au sens classique — hashdump retourne du vide ou des artefacts incohérents.
  • Mimikatz traditionnel ne fonctionne plus (plus de DPAPI/wdigest).
  • Forensique : chercher dans Trustlet hvix64.exe et la mémoire VTL1, pas dans le LSASS classique.
  • Dans un dump : repérer la présence VBS via vol.py windows.driverirp + mention de hvix64.
🔒 BitLocker avec TPM 2.0 + PIN

Configuration durcie : déverrouillage exige TPM + PIN utilisateur (mode tpm-and-pin).

  • La VMK reste en RAM tant que la session est active : capturer avant arrêt.
  • Si la machine est éteinte : aucune extraction VMK possible — il faut le PIN ou la clé de récupération AAD/AD.
  • Cold boot attack théoriquement possible (RAM persiste < 1 min après extinction si refroidie au spray) mais difficile en pratique avec ECC RAM moderne.
  • Outil légal : Microsoft Recovery Key Backup dans Azure AD pour entreprises.
📦 Hyperviseur type-1 (VMware ESXi, Hyper-V, Proxmox)

VM cible tourne sur un hyperviseur — l'acquisition depuis l'invité est la méthode standard, mais on peut aussi capturer depuis l'hôte :

  • VMware ESXi : suspendre la VM (génère un fichier .vmem = dump RAM brut, utilisable directement par Volatility).
  • Hyper-V : Save-VM ou snapshot — fichier .vmrs + .bin à parser avec scripts dédiés.
  • Proxmox/QEMU : virsh dump --memory-only ou (qemu) pmemsave.
  • Avantages : pas besoin de modifier la VM (pas de driver à installer dans l'invité), bypass d'antivirus.
  • Limites : la VM voit potentiellement le snapshot (timer drift visible) — discrétion non garantie.
💾 SSD avec auto-encrypt (SED) + Opal 2.0

Self-Encrypting Drive : le SSD chiffre matériellement, transparent pour l'OS. La clé de chiffrement est dans le contrôleur, pas en RAM.

  • L'acquisition disque doit être faite avant que l'utilisateur ait verrouillé/redémarré, sinon le SSD se re-verrouille.
  • La RAM ne contient pas la clé SED (uniquement l'authent à l'allumage), donc dump RAM seul est insuffisant.
  • Stratégie : imager le disque en parallèle de la RAM avant tout reboot.
  • Outils SED : sedutil (open source, Opal 2.0).
Cas particulier — BitLocker & FileVault
⚠️ Procédure si chiffrement actif

BitLocker (Windows) : Si la session est déverrouillée, la VMK (Volume Master Key) est en RAM. Acquérir avec WinPmem avant toute extinction puis extraire avec python3 vol.py -f dump.raw bitlocker ou Elcomsoft Forensic Disk Decryptor. Ensuite monter le volume avec la VMK avant extinction.

FileVault 2 (macOS) : Si la session est ouverte, clé en RAM. osxpmem + Volafox pour extraction. Sinon → demander la clé de récupération iCloud au prestataire cloud (via MLAT si nécessaire).

LUKS (Linux) : Master key en RAM si volume monté. Extraction via vol.py linux.psaux + recherche de patterns clé dans dump LiME. cryptsetup-reencrypt sur clé extraite.

VeraCrypt : Master key en RAM si conteneur monté. Plus difficile à isoler — pas de plugin Volatility natif. Méthode : recherche manuelle de patterns AES key schedule dans la RAM.

Erreurs fréquentes en acquisition RAM
  • Lancer l'outil de capture depuis le disque cible : modifie l'état RAM avant capture. Toujours utiliser USB en lecture seule (write-blocker logiciel).
  • Capturer pendant un screensaver verrouillé : sur Windows 10+, certaines clés sont nettoyées au lock. Capturer si possible session active.
  • Oublier le pagefile.sys : contient des fragments mémoire paginés. À acquérir en plus du dump RAM (cf. Acquisition).
  • Compresser le dump pendant la capture : ralentit énormément, peut faire échouer la capture sur gros volumes RAM (32 GB+).
  • Capturer sur un disque presque plein : impossible. Vérifier l'espace libre > taille RAM × 1.2 avant lancement.
  • Ne pas hasher le dump immédiatement après capture : empêche de prouver l'intégrité du fichier en cas de contestation.
Intégrité du dump RAM

Contrairement au disque, un dump RAM ne peut pas être parfaitement identique à l'original — la RAM évolue pendant la capture (processus actifs continuent). C'est forensiquement acceptable et documenté. L'hash MD5/SHA-256 du fichier dump suffit à prouver que le fichier n'a pas été altéré après la capture.

Hash(dump_après_capture) == Hash(dump_à_l'analyse) → intégrité prouvée

Ordre opérationnel : 1) hash baseline du disque cible · 2) capture RAM · 3) hash dump · 4) capture pagefile.sys · 5) extinction si nécessaire.

Tu interviens sur un poste Windows 11 24H2 chiffré BitLocker. La session est ouverte. Tu dois capturer la RAM. Pourquoi est-il impératif d'agir avant tout reboot ou hibernation ?Acquisition RAM · Niveau : moyen
Trois raisons cumulatives : (1) VMK BitLocker en RAM uniquement — perdue au redémarrage ; (2) Windows 11 24H2 active VBS/HVCI par défaut — certaines pages devenant inaccessibles après un reboot avec policy renforcée ; (3) tout malware fileless ou processus injecté disparaît à l'extinction. Procédure : 1) capture RAM (WinPmem) 2) hash 3) capture pagefile 4) extraire VMK avec Volatility 5) si nécessaire, mounter le volume avec la VMK avant extinction. Hibernation écrit la RAM dans hiberfil.sys — peut être analysé après-coup mais pollue l'état. Sleep conserve la RAM mais une attaque DMA reste possible (à documenter).
Pourquoi capturer la RAM d'une VM via le snapshot hyperviseur (.vmem) plutôt qu'avec un agent installé dans la VM ?Forensique VM · Niveau : facile
Trois bénéfices forensiques majeurs : (1) aucune altération de la chaîne de preuve in-guest (pas de driver chargé, pas de fichier exécutable transféré) ; (2) capture instantanée de l'état complet de la RAM physique vue par la VM, sans risque de race condition ; (3) VMware/Hyper-V/VirtualBox supportent les exports de snapshot mémoire au format directement parseable par Volatility (.vmem, .bin). Le tout sans privilégier un dialogue avec le système compromis — l'attaquant ne peut pas résister à une capture qui se fait au niveau hyperviseur.
